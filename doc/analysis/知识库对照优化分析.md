## 〇、结论速览

### 0.1 一句话结论

> **Kquery 是一个"机制覆盖率很高、闭环程度不足"的 RAG 系统。** ~9 声称的能力几乎都能在代码里找到实现，但大量能力停留在"实现了、没接线"或"接线了、口径不对"的状态：真正的流式没有接通、语义缓存的隔离维度只做了一半、Agent 的工具选择在默认路径上仍由 if-else 决定、多副本基建（Redis 共享状态、有界队列）建成后零生产调用、检索质量至今没有评测集可以量化。

把它放在知识库的判据下，问题不是"不会写"，而是三类系统性偏差：

| 类型 | 定义 | 本项目实例 | 危害 |
|---|---|---|---|
| **A 类：已实现未接线** | 代码存在、测试通过，但生产路径没有调用方 | `core/tasks.py` 的 `BackgroundQueue`、`core/shared_state.py` 的 Redis 后端、`ToolRegistry.clear_cancel`、写工具审批的 `approved_tools` | 看代码以为有，扩容/上线后才发现没有；最容易被误判为"已完成" |
| **B 类：契约与实现矛盾** | 接口声明、注释承诺与实际行为不一致 | `VectorSearchTool` 声明 `top_k` 但忽略；`RetrievalFilters.current_version_only` 从未读取；`hybrid` 注释说重排失败降级、实际"成功返回空"不降级 | 调用方按契约使用会得到错误结果，且不报错 |
| **C 类：观测口径与业务不一致** | 指标/日志/预算的计量方式与实际链路不符 | 延迟直方图上限 10s 而 LLM 超时 60s；token 用"最后一次 usage × 调用次数"外推；日志强制 10 字段但 9 个无生产者 | 看板"一切正常"掩盖真实故障；成本与配额无法对账 |

### 1.1 知识库的八个横切判据

48 篇文档不必逐篇对应；把它们的判据压缩成八条，足以覆盖 Kquery 的全部优化面：

| # | 判据 | 来源篇目 | 一句话检验 |
|---|---|---|---|

对应知识库：`传统后端/31 FastAPI`、`传统后端/23 流式与异步`、`传统后端/12 实时通信`、`传统后端/05 性能诊断`、`大模型相关/01 LLM 输出可靠性`。

### 2.1 现状链路

以 `/ask` 同步路径为例，真实顺序如下（与模块 docstring 声称的"预处理→缓存"相反）：

| 阶段 | 位置 | 串行？ | 主要开销 |
|---|---|---|---|
| 1. 缓存键 + 语义查找 | `pipeline.py:953-955` | 是 | 1 次 embedding + O(2000×1024) 扫描 |
| 2. 输入侧 PII 探测 | `pipeline.py:575-584` | 是 | 正则 |
| 3. 意图识别 | `query/orchestrator.py:70-80` | 是 | 1 次 LLM（失败重试 1 次） |
| 4. 查询改写 | `query/orchestrator.py:91-104` | 是 | 1~3 次 LLM（fusion/stepback） |
| 5. 多跳拆解 | `query/orchestrator.py:112-124` | 是 | 1 次 LLM |
| 6. 检索（每条查询×每路） | `retrieval/hybrid.py:117-139` | 是 | 每条查询 1 次 embedding + 两路召回 |
| 7. 版本过滤 + RRF | `hybrid.py:150-174` | 是 | 内存排序 |
| 8. 重排 | `hybrid.py:176-194` | 是 | 1 次 rerank API |
| 9. ACL 后过滤 + 证据装配 | `pipeline.py:634,743` | 是 | 每候选 1 次文档查找 + ACL 判定 |
| 10. 生成 | `pipeline.py:750` | 是 | 完整生成（非流式） |
| 11. 幻觉自检（+可能重生成+二次校验） | `pipeline.py:761-789` | 是 | 1~3 次 LLM |
| 12. 输出侧敏感词 | `pipeline.py:820-831` | 是 | 正则 |
| 13. 切片重放 token | `pipeline.py:1040-1048` | 是 | 12 字符/片 |

一个中等问题的真实 LLM 调用次数：意图 1 + 改写 2 + 拆解 1 + 生成 1 + 自检 1 = **6 次**；若命中重生成则 8 次。这些调用全部串行，且在第一个 token 发给用户之前完成。

### 2.2 KQ-07：伪流式——TTFT 等于全链路耗时

**现状（A 级）**

- `pipeline.py:750` 使用 `self._llm.generate(...)`，不是 `stream`；线性路径从未消费流式输出。
- `ask_stream` 在拿到 `_final` 后才把最终答案按 12 字符切片 `yield`（`pipeline.py:1040-1048`）。
- 唯一调用 `LLM.stream` 的地方是 `agent/graph.py:627`，它同样把流拼成整串后再交给下游。

**知识库判据（J1）**

`传统后端/12` 给出的核心不等式是：**首字节时间 = 排队 + 首个可发送单元的产生时间**；流式的价值不是"总时长变短"，而是"把等待从 UI 上移走"。`大模型相关/01` 进一步指出：只要输出要经过"完整生成 → 校验 → 再发送"，流式就退化为分片传输，用户感知的仍是同步等待。

**后果**

- 用户点击提问后，页面在 3~10 秒内没有任何 token；前端只能显示"思考中"。
- 自检/重生成阶段额外增加 1~5 秒空白；如果自检失败降级，用户等待更久却得不到任何进度信号。
- `RetrievalTracePanel` 已有 `plan/tool_start` 等事件，但线性路径的进度事件（`crag_branch`、`refine`）在最终答案前才发出，无法缓解首字节。

**改法（两阶段流式）**

```text
阶段 A（< 1s）：先发 meta 事件
 event: accepted {trace_id}
 event: retrieval {queries, routes} ← 让前端立即渲染"正在检索"
阶段 B：检索/重排完成后先发证据
 event: evidence ...
 event: retrieval_stats ...
阶段 C：生成时直通
 for delta in llm.stream(prompt):
 event: token {content: delta}
阶段 D：生成后校验
 - 自检只下调 confidence，不改写已发出的 token（Agent 路径已是这个口径）
 - 若必须重生成，发 event: replace {reason}，前端整段替换并提示"已修正"
```

**验收**

- `curl -N /ask/stream` 的首个 `token`（或首个 `accepted`）出现在请求开始后 1.5s 内（Mock 模型）/ 3s 内（真实模型，检索命中）。
- 前端 `sse-client` 计时 `firstByteMs`，进 telemetry；P95 作为 SLO。
- 回归：`scripts/smoke_api.py` 的 `/ask/stream` 断言从"有 token 和 done"升级为"事件顺序 + 首字延迟上限"。

### 2.3 同步生成器把连接生命周期变成线程占用

**现状（A 级）**

- `/ask` 与 `/ask/stream` 都是 `def`（同步）端点（`api/ask.py:86,137`），FastAPI 会把它们丢到 AnyIO 线程池。
- `StreamingResponse` 的 body 是同步生成器（`api/ask.py:181-190`），生成器每 `yield` 一次都要占用一个线程池线程；在长回答期间，这个线程一直不释放。
- 没有 `request.is_disconnected` 检查，也没有 `finally` 取消；客户端断开后，要等到下一次 `yield` 抛 `GeneratorExit` 才释放，而两次 `yield` 之间可能隔着一次 30s 的 LLM 调用（`api/ask.py:156-179`）。

**知识库判据（J5）**

`传统后端/26`：并发连接数 `L = λW`。若平均一条 SSE 连接持续 20s，目标 50 QPS，则稳态需要 `50×20=1000` 个并发连接；而同步生成器意味着 **1000 个线程**。AnyIO 默认线程池上限 40，实际表现不是"慢"，而是"第 41 个请求排队到超时"。

**改法**

1. 端点改 `async def`，用 `asyncio.Queue` 桥接后台工作线程与 SSE 输出；
2. 或至少用 `iterate_in_threadpool` 显式包装生成器，并把每个连接的工作线程数限制为 1；
3. 在生成器内周期检查 `await request.is_disconnected`，断开即调用 `registry.cancel(run_id)` 并停止后续 LLM 调用；
4. 心跳：每 15s 发 `: ping\n\n`（SSE 注释行），避免网关 60s idle timeout 断流；
5. 连接数上限：超过阈值直接 503 + `Retry-After`，而不是无限排队。

**验收**

- 100 并发 SSE 连接下，进程线程数不超过 `固定工作线程数 + 常数`，而不是随连接线性增长。
- 客户端主动断开后 2s 内，后端日志出现 `cancelled`，且不再产生新的 LLM 调用。

### 2.4 预处理是 3~6 次串行 LLM，且失败也计费

**现状（A 级）**

- 意图、改写、拆解三步串行（`query/orchestrator.py:70-124`），每步独立调用模型。
- 失败降级只写 `analysis.degraded`，不中断（`orchestrator.py:77-80,99-103,121-124`），这是对的；但异常分支仍然 `llm_calls += 1`（`orchestrator.py:101`），会让成本估算偏高。
- `is_obvious_chitchat` 只在 Agent 路径接线（`api/ask.py:109`），线性路径的"你好"仍要付一次意图调用。
- 预算截断只改 `rewrites.used`，`analysis.sub_questions` 仍显示全部子问题（`orchestrator.py:119-137`），分析记录与实际检索不一致。

**知识库判据（J2/J7）**

`大模型相关/15` 的判据是：查询改写的收益必须用"改写后召回是否提升"证明；没有评测时，**增加改写器只是在增加成本与方差**。`大模型相关/05` 则指出，串行调用会线性推高 TTFT，且每一步都在放大 context rot 的风险。

**改法**

| 措施 | 预期收益 | 风险 |
|---|---|---|
| 闲聊先用零成本正则短路（把 Agent 路径的 `is_obvious_chitchat` 提到线性路径入口） | 省 1~6 次调用 | 正则误判；可用"短问句 + 问候词"双重条件 |
| 意图 + 拆解合并为一次结构化输出（同一 prompt 返回 `{needs_retrieval, sub_questions}`） | 省 1 次调用、少一次 JSON 解析 | 输出稳定性需评测 |
| 改写器按意图选择：只有"指代/省略"才走 fusion，事实型问题默认关闭 | 省 1~2 次调用 | 需评测集验证召回不降 |
| 改写与首轮检索并行：原 query 先检索，改写结果到达后补充召回 | TTFT 降低约一次改写耗时 | 需要合并两批结果、去重 |
| 失败不计费：只在成功返回时 `llm_calls += 1` | 成本口径准确 | 无 |

**验收**：同一评测集上，`recall@5` 不降的前提下，平均 LLM 调用次数从 6 降到 ≤4，P95 延迟下降 ≥25%。

### 2.5 同一请求里的重复计算

**现状（A 级）**

| 重复项 | 位置 | 次数 | 说明 |
|---|---|---|---|
| 问题向量 embedding | `pipeline.py:270,282` | 2 | 缓存查找与写入各算一次，可复用 |
| ACL 过滤 | `pipeline.py:634,425,497` | 2~3 | 后过滤、证据装配、被拒候选探测各一遍 |
| 文档查找 + ACL 判定 | `dependencies.py:51-58` | 每候选 1 次 | `fused_top_n=20` 即 20 次；无请求级缓存 |
| 父块回查 | `pipeline.py:442` | 每候选 1 次 | `docstore.get_parent` 无批量接口 |
| 文档名解析 | `pipeline.py:436,486` | 同文档 2 次 | 可先建 `doc_id → name` 映射 |
| 空结果权限探测 | `pipeline.py:332-349` | 1 次完整双路检索 + 重排 | 冷路径可接受，但 `rerank_query=""` 仍会调 rerank |

**知识库判据（J5）**

`传统后端/04` 的 N+1 判据：单次请求的存储往返次数应与结果条数无关；`传统后端/05` 的净收益公式要求"优化后的节省 > 优化本身的成本"。这里每一项都是低风险、零语义变化的纯节省。

**改法**：在 `RagPipeline` 内建请求级 `_RequestCache`（doc 元数据、visible 判定、父块、doc name），请求结束即丢弃；问题向量只算一次，传给 lookup 与 store；`_probe_denied_content` 传原 query 或跳过 rerank。

### 2.6 失败语义：HTTP 200 里装错误

**现状（A 级）**

- `/ask` 捕获 `LLMError` 后直接 `return error_envelope(...)`（`api/ask.py:127-128`），HTTP 状态仍是 **200**；兜底 `except Exception` 同样 200（`:131-133`）。
- 全局 `Exception` 处理器对同类未捕获异常返回 **500**（`main.py:656-661`），同一类故障两套传输语义。
- 任意 404 被映射成业务码 `DOCUMENT_NOT_FOUND(3002)`（`main.py:644-648`），URL 拼错也报"文档不存在"。
- `api/ask.py:132` 的 `logger.exception` 与全局 handler 的 `logger.exception` 可能对同一异常各打一次堆栈。

**知识库判据**

`传统后端/02`：错误契约要回答"谁重试、重试几次、对用户说什么"；HTTP 状态是给基础设施看的（网关、LB、告警），业务码是给应用看的。把 5xx 包在 200 里，会让所有基于状态码的 SLO/告警/重试策略失效。`传统后端/11` 补充：错误码一旦对外就是契约，404 不能混用"路由不存在"和"资源不存在"。

**改法**

1. `/ask` 的 `LLMError` 改为 `raise ApiError(exc.code, exc.message, http_status=502/504)`；超时 504、上游 5xx 502、配额 429。
2. 404 分层：路由未命中 → `1004 NOT_FOUND`；资源未命中 → `3xxx`。可在 `StarletteHTTPException` handler 里判断 `request.url.path` 是否匹配到路由。
3. 异常只在一个层记录堆栈：内层记录上下文（trace_id、stage），外层只负责信封。
4. SSE 路径保持 `event: error`，但 `code` 统一用 `int`，不要混用枚举对象（`api/ask.py:176` vs `:179`）。

### 2.7 超时预算链：单次 LLM 重试就能吃掉整个 Agent 预算

**现状（A 级）**

- `llm_timeout_s=60`、`llm_max_retries=3`（`config.py:235-236`）→ 单次调用最坏 60×4=240s（含首次）。
- `agent_deadline_ms=60000`（`config.py:120`）→ 整个 Agent 只有 60s。
- `agent_tool_timeout_s=30`（`config.py:108`）与整体 deadline 同量级。
- `validate_startup` 不校验这些交叉关系（`config.py:294-359`）。

**知识库判据（J5/J6）**

`传统后端/17`：Deadline 必须逐层递减——上游给 60s，下游每次调用必须拿到"剩余预算"，而不是各自 60s。`传统后端/02` 的重试放大公式 `1/(1-p)` 说明：在 p=0.3 的失败率下，3 次重试会把下游压力放大到 1.43 倍，而总延迟放大更多。

**改法**

```python
# 调用前计算剩余预算，而不是用固定 timeout
remaining = budget.remaining_ms
if remaining <= 0: raise BudgetExhausted
timeout = min(settings.llm_timeout_s, remaining / 1000)
# 重试次数由剩余预算决定，不固定 3 次
max_retries = min(settings.llm_max_retries, int(remaining // (timeout * 1000)))
```

启动期加交叉校验：`agent_deadline_ms ≥ agent_tool_timeout_s × 2` 且 `llm_timeout_s × (llm_max_retries+1) ≤ agent_deadline_ms`（或显式允许超时并告警）。

### 2.8 FastAPI 机制层的三个坑

| 坑 | 证据 | 后果 | 修法 |
|---|---|---|---|
| **每请求两次认证** | `/ask` 挂 `enforce_rate_limit`（`api/ask.py:85`），其内部调 `get_principal`（`dependencies.py:148`）；端点参数又 `Depends(get_principal)`（`api/ask.py:89`） | JWT 验签 2 次、目录加锁读 2 次、headers 复制 2 次 | 依赖缓存默认生效，但 `enforce_rate_limit` 是路由级依赖、`get_principal` 是参数级依赖，二者不在同一缓存树；改成 `enforce_rate_limit(principal=Depends(get_principal))` |
| **导入期建 app** | `app = create_app`（`main.py:785`），配置校验/日志/OTel 全在导入期 | 多 worker/`--preload` 每进程重复执行；`set_tracer_provider` 仅首次生效 | 把副作用移入 lifespan；`create_app` 只做装配 |
| **`/metrics` 匿名** | `main.py:763-769` 无 `Depends` | 熔断率、工具失败率、成本等运营指标对外可抓 | 独立内网端口，或加 `require_role("admin")` + 网络策略 |

## 三、检索质量、分块与评测（J2）

对应知识库：`大模型相关/02 RAG 与向量检索`、`大模型相关/14 文档解析`、`大模型相关/15 查询理解`、`传统后端/05 性能诊断`。

### 3.1 检索链路现状（正确的部分）

- 混合检索：BM25（jieba + Lucene 风格 IDF）+ 向量（COSINE），RRF `w/(k+rank+1)`，`k=60`（`retrieval/fusion.py:3,41`）——与知识库公式一致（多一个 +1 只是偏移，不改变排序）。
- 单路召回 20 → 融合 20 → 重排 4（`config.py:38-40`）——符合"每路 Top-N 20~50、精排后 Top-K 3~5"的推荐区间。
- 重排失败抛 `RerankError` 时降级为融合序（`hybrid.py:187-191`）——方向正确。
- 版本过滤在融合前统一做（`hybrid.py:150-164`）——比"各后端各自过滤"更一致。
- BM25 先过滤后排序（`bm25.py:128-142`）——避免不可见文档占名额。

这些设计本身没问题；问题在边界条件与缺失的度量。

### 3.2 KQ-13：版本过滤发生在召回之后，先占名额再丢弃

**现状（A 级）**

- `hybrid.py:150-164`：每条查询的每路先各取 `per_route_top_n=20`，再过滤历史版本块。
- `RetrievalFilters.current_version_only` 字段存在（`retrieval/filters.py:54`），但全仓无读取点。
- Milvus 的检索表达式只含 `tenant_id/doc_id`（`milvus_store.py:146-151`），不含版本条件。

**知识库判据（J4）**

`大模型相关/02`：过滤条件应在**候选生成阶段**生效，否则过滤率越高，有效召回越少；当一篇文章被 reparse 3 次、每版块数相近时，当前实现会让每路 20 条里最多只有 1/4 是当前版本，等效召回容量降到 5 条。

**改法**

1. 把版本条件下推到存储层：Milvus 增加 `version` 字段与 `version == current` 表达式；FAISS/BM25 在打分前按 `is_current_version` 过滤（BM25 已具备"先过滤"骨架，只需加条件）。
2. 若短期不能改 schema，至少把 `per_route_top_n` 按"当前版本占比"动态放大（例如 `20 / max(0.25, current_ratio)`），并在 `retrieval_stats` 里暴露 `version_filtered`。
3. 删除 `current_version_only` 死字段，或真正接上——不要保留"看起来能配"的开关。

**验收**：同一文档 reparse 3 次后，查询该文档的 `recall@5` 与首次入库时相差 ≤2pp。

### 3.3 KQ-14：ACL 后过滤仍会吃掉 top-k（Milvus/BM25）

**现状（A 级）**

- `filters.py:18-21` 注释声称"三个后端统一超额取数"，实际只有 FAISS 实现了 `OverfetchState` 迭代扩取（`vectorstore.py:122-156`）。
- Milvus 在 `filters` 存在时直接 `limit=top_k`（`milvus_store.py:146-158`）；当可见清单 >500 时，`to_milvus_expr` 放弃 `doc_id in [...]`（`filters.py:79-85`），只剩 tenant 粗过滤 → 不可见文档仍参与 top-k 竞争。
- BM25 没有扩取（`bm25.py:144-150`）。

**知识库判据（J3/J4）**

`传统后端/32`：ACL 必须"双过滤"——下推 + 后过滤；但下推降级时，后过滤会吃掉名额，必须用超额取数补偿。`大模型相关/02` 的召回链路也要求"过滤不减少有效候选数"。

**改法**

1. Milvus 在对 `visible_doc_ids` 降级时，按 `top_k × OVERFETCH_FACTOR` 取数，再在应用层过滤；因子从 4 起、按命中率自适应。
2. BM25 在可见率低时同样扩取（当前是"先过滤再排序"，若过滤后不足 top_n 应继续向更低分走，直到取满或耗尽）。
3. 暴露 `acl_pushdown_degraded` 与 `overfetch_rounds` 到 `retrieval_stats` 与 Prometheus。

**验收**：构造"1000 篇文档、当前用户可见 10 篇"的场景，`recall@5` 与"只有 10 篇文档"时相差 ≤5pp。

### 3.4 KQ-15：重排"成功但为空"被当成成功

**现状（A 级）**

- `hybrid.py:181-186`：只要 `_rerank` 不抛异常就 `reranked=True`，即使返回 `[]`。
- `rerank.py:53-54`：空候选直接返回 `[]`；`rerank.py:68-83` 只取 index+score，若上游返回空结果也会得到 `[]`。
- 注释（`hybrid.py:6-7`）承诺"重排失败降级为融合结果"，但"成功返回空"不触发降级 → 最终 `final=[]`，证据为空，用户得到拒答。

**改法**

```python
final = _rerank(...)
if not final:
 logger.warning("重排返回空，降级为融合序")
 final = fused[:config.top_k]
 reranked = False
 stats.rerank_degraded = "empty_result"
else:
 reranked = True
```

同时区分"接口失败"与"无相关结果"：前者降级，后者应触发 CRAG 的 incorrect 分支，而不是静默返回空。

### 3.5 KQ-16：上下文预算用字符估算，且硬截断分支不可达

**现状（A 级）**

- `context.py:20-27`：`CHARS_PER_TOKEN=2.0`，中文实际约 1.5 字符/token，英文约 4；同一预算下中英文的实际 token 数偏差可达 2 倍。
- `pipeline._settle_tokens` 用同一口径估算计费（`llm.py:46-52`），预算与账单都只能"大概齐"。
- ④ 硬截断（`context.py:126-153`）在 ③ 与 ③.5 之后不可能触发，是死分支；注释宣称"四段式"名不副实。
- MMR 用字符 4-gram Jaccard（`context.py:167-207`），不是 embedding 相似度；对中文短块尚可，对长表格块区分度低。

**知识库判据（J6）**

`大模型相关/05`：上下文预算必须按真实 token 计，否则会出现"预算 6000、实际 9000"的截断；`context rot` 说明超预算不是"多花点钱"，而是关键证据被挤掉。

**改法**

1. 引入真实 tokenizer（如 `tiktoken` 或 DashScope 的 token 计数接口），至少在生成前做一次精确计数；预算按模型分别配置。
2. `assemble_context` 返回 `tokens_estimated` 标记，前端与日志可见。
3. 删除不可达的 ④，或把它改成"单条超预算时的内容中段截断"（当前 ③.5 只保留开头，可能丢掉关键结论）。
4. MMR 改用 embedding 余弦（候选已有向量时零额外成本），或保留 Jaccard 但在 `mmr_lambda=1.0` 时不计算。

### 3.7 KQ-09：没有评测集，所有质量讨论都是猜测

**现状（A 级）**

- 全仓无 `recall@k`、`nDCG`、`MRR` 的计算代码；`scripts/` 只有接口冒烟与浏览器 E2E。
- 阈值分散：`ANSWER_THRESHOLD=0.6`（`reflector.py:20`）、`crag_correct_th=0.14` / `crag_incorrect_th=0.08`（`config.py:88-89`）、`HeuristicReflector.correct_th=0.14`（`reflector.py:109`）、`SEED_VECTOR_TH=0.5`（`graph/query.py:19`）、`parametric_fallback_score_threshold=0.6`（`config.py:100`）。
- 阈值顺序在 `CragRouter` 构造时校验（`validation/crag.py:57-60`），但**阈值本身没有评测依据**：0.14/0.08 来自一次混合语料实测（`config.py:82-89` 注释），没有评测集版本、没有召回/误拒曲线。
- README 声称"336 用例、覆盖率 85%"，但没有任何用例回答"检索变好了还是变坏了"。

**知识库判据（J2）**

`大模型相关/02` 的上线门禁：**任何检索参数改动必须绑定评测版本**；至少要有 `recall@k`（召回）与 `nDCG@k`（排序）两条曲线，否则"RRF k 从 60 调到 40"这类改动无法判断。`大模型相关/15` 进一步要求：查询改写的收益要用"改写前后同一金标集的召回差"证明，而不是看单个 case。

**改法（最小可行评测集）**

```text
data/eval/
 queries.jsonl # {qid, question, tenant, user, gold_doc_ids, gold_chunk_ids, answer_points}
 qrels.tsv # TREC 格式：qid 0 chunk_id relevance
 run_eval.py # 调 /knowledge/retrieval-probe 或直接调 HybridRetriever
```

- 规模：先 100 条（覆盖 5 类问题：事实型/多跳/表格/扫描件/无答案），3~5 人日可标注完。
- 指标：`recall@5`、`recall@10`、`nDCG@10`、`MRR`、`拒答准确率`、`平均 LLM 调用次数`、`P95 延迟`。
- 门禁：CI 或 nightly 跑；`recall@5` 回退 >2pp 直接失败。
- 阈值标定：用评测集的分数分布重新标 `crag_correct_th` / `ANSWER_THRESHOLD`，并在配置注释里写明"评测集版本 + 标定日期"。

**验收**：任何一个检索参数 PR 都能贴出"评测集 v1 上 recall@5 从 X 到 Y"的表格；没有这张表不允许合并。

## 四、语义缓存（J3/J4/J5）

对应知识库：`传统后端/19 缓存设计模式与数据一致性`、`传统后端/08 HTTP 缓存与条件请求`、`传统后端/30 请求合并与幂等复用`、`大模型相关/02`。

### 4.1 现状：键设计正确，命中路径只兑现了一半

缓存键由 `tenant + question + model_version + config_digest` 组成（`cache.py:21-39`），`config_digest` 又并入 `index_version`、`user`、`acl_version`、`crag` 开关（`pipeline.py:235-249`）。这部分设计是对的：

- 权限撤销会改 `acl_version` → 精确键失效；
- 重新入库会改 `index_version` → 精确键失效；
- 换模型会改 `model_version` → 精确键失效。

问题出在**近似命中**：`lookup` 先做精确键，未命中后遍历条目做余弦相似度（`cache.py:140-170`），此时只按 `tenant_id` 过滤（`:154`），不校验 `user / acl_version / index_version / config_digest`。也就是说：

```text
精确键：tenant + question + 模型 + 配置 + 用户 + ACL 版本 + 索引版本 ← 安全
近似键：tenant + 向量相似度 ≥ 0.95 ← 不安全
```

### 4.2 KQ-04：同租户跨用户串答案（P0）

**触发条件（A 级）**

1. 用户 A 与用户 B 同租户；
2. A 问"保修政策是什么"，B 问"保修条款有哪些"（余弦 ≥0.95）；
3. A 的答案写入缓存时，`payload` 已按 A 的 ACL 裁剪（`pipeline.py:970-973`）；B 的语义查询命中该条目，直接返回 A 的答案与证据。

**后果**

- 租户内越权：B 可能看到 A 才可见的文档片段（证据里带 `doc_id` 与内容）。
- 权限变更后脏命中：管理员撤销 A 的权限，`acl_version` 递增，但 B 的语义查询仍可能命中旧条目。
- 配置/模型变更后脏命中：改了 `top_k` 或换 embedding 模型，精确键变了，语义键没变。

**知识库判据（J3）**

`传统后端/19` 的核心判据：缓存键必须包含**所有影响结果的维度**；少一个维度就是"用旧结果回答新问题"，而且不会报错。`传统后端/32` 补充：多租户缓存的隔离维度是"主体 + 权限版本 + 数据版本"，缺一不可。

**改法（任选其一，推荐 B）**

| 方案 | 做法 | 成本 | 残留风险 |
|---|---|---|---|
| A. 语义命中只允许同用户 | `lookup` 增加 `user_id` 参数，`entry.user_id == user_id` 才参与 | 低 | 同用户权限变更仍需 `acl_version` |
| B. 缓存条目携带完整维度签名 | `CacheEntry` 存 `signature = hash(user, acl_version, index_version, config_digest, model)`；命中时签名必须完全相等 | 中 | 无 |
| C. 关闭语义命中 | `cache_sim_threshold=1.0` 或删 `lookup` 分支 | 低 | 失去改写命中收益 |

**验收**：新增测试 `test_semantic_cache_isolated_by_user`：A/B 同租户、问题余弦 0.99，B 不得命中 A 的条目；`test_semantic_cache_invalidated_by_acl`：`set_acl` 后旧条目不再命中。

### 4.3 KQ-17：O(2000×1024) 纯 Python 扫描 + 全局锁 + 无 single-flight

**现状（A 级）**

- 每次请求（包括 miss 之后）都做一次 `max_scan=2000` 的全量遍历，纯 Python 点积（`cache.py:150-166`），1024 维 → 单次约 200 万次乘加，且全程持 `threading.Lock`（`cache.py:80`）。
- 无空值缓存：无答案/拒答结果也走完整链路，热点问题并发 miss 会同时打下游。
- 无 single-flight：同一问题 10 个并发请求会触发 10 次完整检索+生成。
- `stats` 每次 O(n) 重建存活列表（`cache.py:172-181`）；`max_scan` 是"扫描上限"而不是"候选集"，条目超过 2000 后后面的条目永远不可能被语义命中。

**知识库判据（J5）**

`传统后端/30` 的 single-flight：相同键的并发请求应合并为一次真实计算，其余等待结果；`传统后端/19` 的缓存三大故障（穿透/击穿/雪崩）分别对应"空值缓存/互斥重建/过期抖动"。

**改法**

1. 语义索引：把条目向量放入 numpy 矩阵，批量点积 + `argpartition`，不要逐条 Python 循环；或直接复用 Milvus 的 `cache` 集合。
2. 锁外计算：`with lock` 只做条目快照复制，相似度计算在锁外。
3. single-flight：`dict[key, Future]`，首个请求计算、其余 `wait`；失败时广播异常。
4. 负缓存：拒答/空证据结果用短 TTL（如 60s）缓存，避免重复打上游。
5. 过期抖动：TTL 加 ±10% jitter，避免同一批条目同时过期。

### 4.4 缓存层的三个"小但值得修"的点

- **双份 embedding**：`pipeline.py:270` 与 `:282` 各算一次问题向量；合成一次传入 `lookup` 与 `store`。
- **私有属性取编码器**：`pipeline.py:255` 通过 `self._cache._embeddings` 读取编码器，破坏分层；应把 embedding 作为 `RagPipeline` 的显式依赖。
- **缓存命中路径跳过审计**：命中缓存时直接返回（`pipeline.py:956-963`），`log_request/log_retrieve/log_answer` 都不写；但审计要求"每次问答可追溯"，缓存命中也是问答。应在命中路径补一条 `rag.answer`（标注 `from_cache=true`），否则审计覆盖率会随命中率上升而下降。

### 5.1 决策权分布：图是 Agent 形状，决策仍是流水线

**现状（A 级）**

- 默认 `agent_mode="plan_execute"`（`config.py:146`）。
- `plan_execute` 的 `tool_node` 是确定性选择：扫描 `plan`，取第一个 `pending` 且依赖已完成的步骤（`agent/graph.py:182-193`）；工具名与参数来自 planner 一次性产出，运行期没有 LLM 参与。
- ReAct 的 `think_node` 已实现（`graph.py:459-482`），但只有 `agent_mode=="react"` 时才注入 `ReActThinker`（`runner.py:150-151`）；默认路径不会走。
- `reflect` 的 `replan` 结论在 ReAct 下被 `reflect_router` 一律送回 `think`（`graph.py:694-699`），等于白跑一次 reflect LLM。

**知识库判据（J7）**

`大模型相关/04`：工具选择的自主性有三个层次——① 规划期一次选择（plan-execute）、② 每步由模型选择（ReAct）、③ 模型可动态增删工具（MCP/A2A）。Kquery 目前是①，且①的工具选择提示词只给 `name + description`（`planner.py:75-77`），连参数 schema 与 `available` 都没给。`大模型相关/06` 指出：plan-execute 的典型失败是"计划漂移"——第一步失败后，后续步骤仍按原计划执行，不会换角度。

**改法（渐进式，不要直接全局切 ReAct）**

1. **先补 planner 的上下文**：把 `catalog` 的 `parameters`、`returns`、`danger`、`available` 全部拼进提示词；要求每步输出 `arguments`（JSON），而不是让 `arguments_from_step` 退化成 `{query: description}`（`tool_spec.py:141-150`）。
2. **按请求动态路由**：简单事实型问题走 plan_execute（1~2 步）；多跳/工具不确定的问题走 ReAct；由意图识别的 `sub_questions` 数量与首轮召回分数决定，而不是全局配置。
3. **修 ReAct 的 reflect 短路**：ReAct 下 reflect 只用于更新 `evidence_score` 与 confidence，不再产出 `next_action`；或直接把 reflect 与 think 合并为一次调用，省一次 LLM。
4. **保留 plan_execute 作为降级**：ReAct 解析失败 → `plan_fallback`（已有，`graph.py:423-425`），不要直接答错。

**验收**：在评测集上比较两种模式的 `工具调用准确率`、`平均迭代轮数`、`任务完成率`、`单次成本`；至少有一个场景 ReAct 胜出才默认开启。

### 5.2 KQ-18：三预算只覆盖了半条链路

**现状（A 级）**

- 预算三维：token/cost/deadline（`agent/budget.py:31-33`）。
- `tool_node` 每轮调用前检查 `budget.exhausted`（`graph.py:170`），但 `can_afford` 只在 verify 用了一次（`graph.py:510`）；`can_afford` 里的 `if not self.exhausted: pass`（`budget.py:73-76`）是死分支。
- **answer 阶段的真实 usage 只写 Prometheus 与 CostLedger（`runner.py:537-548`），不回填 `budget.tokens_used`**；预算只统计工具调用的估算值（`ESTIMATED_TOKENS_PER_TOOL_CALL=800`，`runner.py:48`）。
- deadline 不跨 resume：`resume` 新建 `AgentBudget` 并重置时钟（`runner.py:743-745`），`reset_clock` 定义但无调用点；用户反复 resume 可无限延长墙钟。
- deadline 触发后 consumer `break`，但 worker 线程仍在跑图、继续 `settle_tokens` 并向无人消费的队列写（`runner.py:296-304` vs `245-283`）；`budget` 对象跨线程共享且无锁。

**知识库判据（J7/J5）**

`大模型相关/10` 的 LLM10（无界消耗）要求：token、费用、墙钟三个维度都要在**每次模型调用前**检查，调用后按真实 usage 回填；否则"预算"只在最便宜的工具阶段生效，最贵的生成阶段反而漏计。`传统后端/24` 的 deadline 传播要求逐层递减，不能在 resume 时重置。

**改法**

```python
# 1) answer 前检查
if not budget.can_afford(estimated_answer_tokens):
 return degrade("budget_exhausted")

# 2) answer 后回填
usage = llm.last_usage
budget.settle_tokens(usage.total, usage.estimated)

# 3) deadline 持久化
state["budget"]["deadline_at"] = checkpoint_ts + deadline_ms
# resume 时按剩余时间恢复，已过期直接拒答

# 4) 早退后取消 worker
worker_thread.cancel_event.set # 工具/LLM 调用前检查
```

**验收**：构造一个"工具全空、生成很长"的问题，`budget.snapshot.tokens_used` 与 `CostLedger` 的差值 ≤5%；连续 resume 3 次后总墙钟不超过 `deadline_ms`。

### 5.4 KQ-22：长期记忆"记得住"但"用不好"

**现状（A 级）**

- 作用域只有 `tenant_id`（`memory.py:85`），没有 user/session 维度 → 同租户多用户互相污染。
- 只有两类写入：零召回查询 → `invalid_query`；拒答 → `missing_doc`（`memory.py:208-243`）。`KIND_CORRECTION` / `KIND_PREFERENCE` 常量存在但无写入点（`:49-52`）。
- `_append` 只追加，淘汰/`forget` 不回写 JSONL（`:106-114,138-152`）→ 文件无界增长；重启后被淘汰条目"复活"。
- `recall` 每次读取都 `hits += 1`（`:166-169`）→ 自我强化，注入过的条目永久优先，无衰减/TTL。
- `record_from_run` 把"0 召回查询"的查询串原文当 key 存（`:229`），与模块文档"不存用户原话"冲突。

**知识库判据**

`大模型相关/07`：记忆系统要有 ADD/UPDATE/DELETE/NOOP 四种操作、双时态（事件时间/记录时间）、三因子检索（相关性/新鲜度/重要性）、作用域隔离（user/session/tenant）。当前实现只有 ADD 与"按 hits 排序"，没有 UPDATE/DELETE，也没有时间衰减。

**改法（最小闭环）**

1. JSONL 改为"追加 + 定期 compact"：淘汰/forget 时写一条 tombstone，`compact` 重写文件；或直接换 SQLite。
2. `recall` 的 `hits` 更新移到"答案确实使用了该记忆"之后（需要 answer 节点反馈），而不是每次读取都加。
3. 增加 `scope` 字段（tenant/user/session），注入时先 user 后 tenant。
4. 写入 `KIND_CORRECTION`：HITL 的 `force_answer`/用户纠正可以作为高价值记忆来源。
5. 短问题原文存储改为"归一化键 + 哈希"，与模块承诺一致。

### 5.5 KQ-23：检查点与会话的无界增长

| 数据 | 现状 | 证据 | 风险 |

| `_locks` 字典 | 只在 delete 时移除 | `sessions.py:32-43,148-154` | 长生命周期进程内无界 |
| `SqliteSaver` 连接 | 单连接跨线程，`check_same_thread=False` | `checkpointer.py:61` | 全局锁串行，Agent 并发越高越慢 |

**改法**：提供 `prune(before_ts)` 并在 lifespan 定时任务/管理端点调用；`DELETE /sessions/{id}` 同步删对应 thread；`turns` 保留最近 N 轮（如 20）+ 摘要；`_locks` 用弱引用或 TTL 清理。

### 5.6 KQ-21：每请求一线程、每工具一池

**现状（A 级）**

- `AgentRunner.run` 每次 `spawn_thread(work)`（`runner.py:285`），无并发上限。
- 工具层每次调用新建 `ThreadPoolExecutor(max_workers=1)`（`tools.py:685`），超时后 `shutdown(wait=False, cancel_futures=True)`，但已在运行的线程无法中断（注释自认，`tools.py:670-674`）。
- deadline 早退后 worker 继续跑，线程泄漏。
- `core/tasks.py` 的 `BackgroundQueue`（有界、背压、优雅停机）零生产调用（全仓仅测试引用）。

**知识库判据（J5）**

`传统后端/20`：线程池的价值是"限制并发 + 复用"，不是"每次新建"；`传统后端/26`：到达率超过服务能力时必须有闸门，否则排队延迟无限增长；`传统后端/06`：队列要有界，满时拒绝而不是无限堆积。

**改法**

1. 建一个应用级 `ThreadPoolExecutor(max_workers=CPU×4)`，Agent run 提交到池；池满返回 503/429。
2. 工具调用复用同一个池，不再每次新建；用 `future.cancel` + 协作式取消标志。
3. 把 `BackgroundQueue` 接进 Agent 与图谱构建，获得背压与优雅停机；删掉"双套队列"。
4. 暴露 `agent_active_runs`、`agent_queue_depth`、`agent_rejected_total` 三个指标。

### 5.7 GraphRAG：KQ-06 与 KQ-41

**KQ-06（P0）：租户未下传**

- `GraphQueryService.search(question, tenant_id)` 接收 `tenant_id`，但 `self._store.neighbors(seed, depth=...)` 没传（`graph/query.py:71`）；SQLite 版 `neighbors` 默认 `tenant_id="default"`（`sqlite_store.py:253`）。
- `GraphBuilder` 是 lifespan 单例，固定 `tenant_id=settings.default_tenant_id`（`main.py:448`、`builder.py:48,82,97`）。
- `communities` 表主键是裸 `community_id`（`sqlite_store.py:62`），不同租户同编号会互相覆盖；`rebuild_communities` 先 `delete_doc(COMMUNITY_DOC_ID)` 再写入（`builder.py:116`）→ 一次重建清掉所有租户的社区。
- 社区检测用 `all_relations` 无租户过滤（`community.py:37,252`）→ 跨租户实体被合并。

**KQ-41（P1）：消歧索引重启失效 + 写放大**

- `EntityResolver.load` 只恢复 `_entities`/`_alias_map`，不重建 `_index`（`resolver.py:134-140`）→ 进程重启后向量消歧与向量种子召回失效，直到索引重新累积。
- 每次 `upsert_relation` 触发 2 次 `_refresh_degree`（`sqlite_store.py:148-149`），每次 1 SELECT + 1 count + 1 UPDATE → 一条关系约 6 条额外 SQL。
- `delete_doc_chunks` 全表 `SELECT * FROM relations` 并反序列化，再对每个实体查一次（`sqlite_store.py:161-197`）。
- BFS 边上限 50，超限静默截断，无 `truncated_from` 回传（`sqlite_store.py:260-283`）。

**改法**

1. `search` 把 `tenant_id` 传到 `neighbors`；`EntityResolver` 与向量索引按租户分区（`_k(tenant, name)` 或独立命名空间）。
2. `communities` 主键改 `(tenant_id, community_id)`；`rebuild_communities` 按租户删除/重建。
3. `load` 末尾重建 `_index`（从 `_entities` 的 vector 批量 add）。
4. `_refresh_degree` 合并为一次 `UPDATE ... SET degree = (SELECT COUNT ...)`；`delete_doc_chunks` 先在内存建 `entity→edges` 索引再删。
5. BFS 截断时返回 `truncated_from`，并在证据里标注"子图不完整"。

### 5.8 Agent 的评测口径

`大模型相关/11` 的三层评测是：end-to-end（任务完成）、process（工具选择/迭代轮数）、capability（单工具准确率）。Kquery 已有 process 指标的雏形（`agent_tool_calls_total`、`agent_iterations`、`agent_fuse_total`），但：

- `run` 与 `resume` 的 confidence/unvalidated 语义不同（`runner.py:474-489` vs `731-737`），无法横向比较。
- `retrieval_stats` 的 `fusion_ms/rerank_ms` 在 Agent 路径恒为 0（`runner.py:779-786`），前端会误读为"无融合/无精排耗时"。
- 熔断/降级/parametric 兜底三类终态无金标样本，`fuse_reason` 只进 state 与指标，不进可回放的评测量。

**建议**：在 §3.7 的评测集基础上加一列 `gold_tools`（该问题应调用哪些工具）与 `gold_answer_points`，先做 process 评测，再做 end-to-end。

## 六、安全、多租户与内容安全（J3）

对应知识库：`传统后端/07 身份权限`、`21 API 鉴权`、`22 中间件与安全架构`、`32 多租户与内容安全`、`大模型相关/10 Agent 安全护栏`。

### 6.1 KQ-03：认证档位"默认安全"的假象

**现状（A 级）**

- `auth_enabled=True` 默认，但 `build_auth_provider` 在没有 JWT、没有静态表时返回 `HeaderAuthProvider`（`security/auth.py:364-367`）；该 provider 完全信任 `X-User-Id / X-Tenant-Id / X-Roles / X-Groups`（`:52-64`）。
- `validate_startup` 只拦"没有任何凭证来源"（`config.py:322-326`），不拦"任何人都能通过"。
- `.env.example:37` 是 `AUTH_ENABLED=false`；README 的第一步就是 `cp .env.example .env`（`README.md:20`）。
- 开发档下 `_reconcile_with_directory` 有意跳过（`dependencies.py:86-91`），因此自报 `X-Roles: admin` 即可通过所有 `require_role("admin")` 端点。

**知识库判据（J3）**

`传统后端/07` 的越权四类中，"水平越权"与"垂直越权"都源于"主体身份来自可伪造输入"。头部透传只能作为**开发模式**，且必须在启动日志/探针里显式标红；生产环境应默认失败，而不是默认放行。

**改法**

1. `HeaderAuthProvider` 仅在 `KQUERY_DEV=1` 且监听 `127.0.0.1` 时可用；否则启动失败。
2. `validate_startup` 增加：`auth_enabled=false` 且 `cors_origins` 含非 localhost → 警告或失败；`auth_enabled=true` + Header 档 → 启动日志打 `WARNING: 开发认证档，任何人均可自报身份`。
3. `.env.example` 改为 `AUTH_ENABLED=true` + `AUTH_PASSWORD_ENABLED=true` + 必填 secret 注释；至少不能"复制即裸奔"。
4. `/healthz` 暴露 `auth_mode`（header/jwt/password），让运维一眼看到当前档位。

**验收**：默认 `.env.example` 启动后，不带凭证访问 `/admin/*` 必须 401；带 `X-Roles: admin` 也 401。开发模式需显式 `KQUERY_DEV=1`。

### 6.2 KQ-02：文档租户恒为 default

**现状（A 级）**

- `KnowledgeService.create_record` 固定 `tenant_id=settings.default_tenant_id`（`knowledge.py:203`），不接收调用者主体。
- 同步上传（`api/knowledge.py:38-48`）与任务上传（`services/ingest.py:291`）都走这条路径。
- `list_files`、`preview`、`probe`、`delete` 都不按主体租户过滤（`knowledge.py:126-135,505-515`、`api/knowledge.py:71-80,281-314`），只靠 router 级 `require_role("admin")`。

**后果**

- tenant-b 管理员上传的文档进入 default 租户：tenant-b 用户检索不到（功能坏），default 租户用户能看到（越权）。
- tenant-b 管理员可通过 `/knowledge/preview/{doc_id}` 读取 default 租户文档全文，通过 `DELETE` 删除它。
- `/knowledge/{doc_id}/probe` 用 `record.tenant_id` 而非主体租户（`api/knowledge.py:288-292`），等于替其他租户做检索探针。

**知识库判据（J3/J4）**

`传统后端/32`：租户隔离的第一条是"写入时写入主体租户，读取时校验资源租户"；`传统后端/07`：管理面也需要租户边界，"admin 不是跨租户超级用户"，跨租户操作应另立 `platform_admin`。

**改法**

1. `create_record(..., tenant_id: str)`，所有调用方传 `principal.tenant_id`。
2. 所有按 `doc_id` 取资源的端点统一加 `_assert_doc_tenant(principal, doc)`；跨租户返回 404（不要 403，避免存在性探测）。
3. `list_files` 按 `principal.tenant_id` 过滤；`probe` 用主体租户。
4. 引入 `platform_admin` 角色用于运维跨租户，且操作必须写审计。

### 6.3 ACL：判定树正确，系统块是后门

**现状（A 级）**

- 五步判定：租户 → deny → allow → public → 默认拒绝（`acl.py:81-100`），顺序正确。
- `acl_filter_of` 对 `doc_id.startswith("__")` 直接放行（`dependencies.py:52-53`）。系统块包括社区摘要 `__communities__`、图像 `__image__`、计算器 `__calculator__`、图谱 `__graph__`。
- 社区摘要由**全库块**生成（`graph/builder.py:114-118`），等于把 A 文档的内容以摘要形式暴露给同租户低权限用户。
- 图像描述同理：`/media/index` 把资产打成 `default_tenant_id`（`api/graph.py:249-252`）。

**知识库判据**

`传统后端/32` 的"双过滤"要求：系统块也要能追溯到来源文档集合，并按来源文档的 ACL 判定；不能因为 `doc_id` 是系统生成就无条件放行。`大模型相关/10` 的间接注入也强调：摘要/描述是"二次生成的内容"，其可见性不能高于来源。

**改法**

1. 系统块记录 `source_chunk_ids`/`source_doc_ids`；`acl_filter_of` 对系统块取来源文档的可见性交集（全部可见才可见）。
2. 社区摘要按租户重建，且只纳入该租户可见文档。
3. 图像描述记录来源文档，`/search/media` 与 `/assets/{name}` 都校验来源 ACL。
4. `__` 前缀白名单收敛为常量集合，不要用前缀判断。

### 6.4 KQ-24：审计"有制度、缺覆盖、弱防篡改"

**现状（A 级）**

- 三事件 + 管理动作：`rag.request`/`rag.retrieve`/`rag.answer`/`admin.action`（`audit.py:59-81`）。
- 哈希截断到 16 hex（64 bit）（`audit.py:22-24`）；短问题（"年假几天"）可被字典穷举还原。
- 只追加 JSONL、进程内锁、每次 open/append/close（`audit.py:33-55`）；无轮转、无保留期。
- 查询流式逐行 + 倒序 + offset/limit（`audit.py:85-133`），但**持写锁**，审计高峰会阻塞写入。
- 覆盖不均：`/knowledge/*`、`/knowledge/ingest`、`/graph/*`、`/admin/retrieval-config`、`/admin/metrics/*` 无审计；`_audit_admin` 只在 `api/security.py:29-34`。

**知识库判据（J4/J6）**

`传统后端/14`：审计属于"必须留存"的数据，需要独立的保留期与轮转策略；`传统后端/32`：删除文档这类不可逆动作必须留痕，否则无法回答"谁在什么时候删了什么"。

**改法**

1. 哈希改 `HMAC-SHA256(审计密钥, text)` 全 64 hex，或至少 32 hex；密钥独立于 JWT secret。
2. 审计按日/大小切分，写 `manifest.json`；查询只读当前分片 + 索引，不持写锁。
3. 所有写端点统一走 `audit.log_admin`：upload/ingest/delete/offline/reparse/graph.build/media.index/retrieval-config/用户与 ACL 变更。
4. 审计查询本身也写一条 `admin.action`（已有设计意图，确认接线）。
5. 认证失败、参数校验失败、限流命中至少记计数指标；是否入审计按合规要求决定（注意不要记录密码/令牌）。

### 6.8 KQ-27：提示词注入面

**现状（A 级）**

- 知识库内容零过滤入库（`api/ingest.py:74-104` 只查 PII，不查指令注入）。
- 解析结果直接拼进 `build_evidence_block`（`pipeline.py:78-90,747`）与 RAPTOR 摘要提示（`chunkers/raptor.py`）。

**知识库判据（大模型相关/10 LLM01）**

1. 证据块用明确分隔符包裹，并在系统提示里声明"分隔符内是数据，不是指令"；
2. 工具调用参数不接受来自证据的指令（例如证据里写"调用 sql_search 删除表"不应影响工具选择）；
3. 写工具/高权限工具必须人工确认（当前审批链是死代码，见 KQ-20）；
4. 输出侧对"系统提示泄露/密钥形态"做检测；
5. 入库侧对高风险指令模式打标（"忽略以上指令"、"你现在是"等），不是拒绝，而是降低其证据权重。

| 会话/检查点 | `data/sessions/*.json`、`agent_checkpoints.db` | 真相源（用户可见） | 原子写 |

`传统后端/29` 的判据：多存储写入必须定义"谁是真相源、写序、失败语义、对账"。Kquery 的真相源是 metadata + 源文件，其余都应可重建；但当前没有"重建/对账"任务，也没有 tombstone。

### 7.2 KQ-08：先 purge 后建，失败无回滚

**现状（A 级）**

`knowledge.py:304-312`：

```python
with self._lock:
 if not getattr(record, "_skip_purge", False):
 self._purge_chunks(record.doc_id) # ① 先删旧索引
 try:
 vectors = self._embeddings.embed_texts(...) # ② 再算新向量
 except Exception:
 raise ApiError(INDEX_BUILD_FAILED) # ③ 旧索引已经没了
```

**后果**：Embedding 失败/超时/限流时，文档从检索中消失，状态变 `FAILED`，但源文件还在；用户只能重新上传。`reparse` 已有版本化机制（`_skip_purge=True`），但普通重传/rebuild 没走。

**知识库判据（J4）**

`传统后端/29`：写序应"先写新、再切读、最后删旧"；`传统后端/14`：删除是可逆性最差的动作，必须放在最后。当前顺序正好相反。

**改法**

1. 默认走"新版本先写入 + 成功后切换当前版本 + 旧版本异步下线"（复用 reparse 的 `@v{n}` 机制）。
2. 若短期不改版本模型，至少在 embed 成功后再 purge；embed 失败时保留旧索引。
3. `record.status` 与 `index_version` 一起原子更新；失败时保留上一版 `index_version`。

### 7.3 删除的收尾动作缺失

**现状（A 级）**

`delete` 只做三件事：`_purge_chunks`（向量 + BM25 + DocStore）、删 metadata、删源文件（`knowledge.py:505-515`）。没有清理：

| 残留 | 位置 | 后果 |
|---|---|---|
| 图谱实体/关系 | `graph/store.py`，只有 `rebuild` 时 `delete_doc_chunks` | 已删文档内容仍可通过图检索/图谱页看到 |
| 图像索引 | `data/image-index.json` | `/search/media` 仍能命中 |
| 资产文件 | `data/assets/*` | `/assets/{name}` 仍可下载 |
| ACL 条目 | `data/acl.json` | 同名 doc_id 重新上传会继承旧权限（可能是 leak 或 deny） |
| 入库任务目录 | `data/ingest/<task_id>/` | 原件永久留存 |
| 检查点 | `agent_checkpoints.db` | 会话里仍含证据原文 |
| 审计 | 不需要删（合规要求保留） | — |

**知识库判据（J4）**

`传统后端/14` 的"删除流水线六阶段"：定位 → 标记 → 停止读取 → 删除派生 → 删除主数据 → 验证；顺序不可颠倒。当前只做了"删除主数据"。

**改法**：`delete` 编排为一个 `DeletionPlan`：

```python
plan = [
 ("acl", lambda: acl.remove(doc_id)),
 ("vector", lambda: store.delete_doc(doc_id)),
 ("bm25", lambda: bm25.delete_doc(doc_id)),
 ("docstore", lambda: docstore.delete_doc(doc_id)),
 ("graph", lambda: graph.delete_doc_chunks(doc_id)),
 ("images", lambda: image_index.remove_doc(doc_id)),
 ("assets", lambda: assets.remove_doc(doc_id)),
 ("task_dir", lambda: shutil.rmtree(task_dir, ignore_errors=True)),
 ("checkpoint",lambda: checkpointer.prune_threads_for(doc_id)),
 ("metadata", lambda: metadata.pop(doc_id)),
 ("source", lambda: source.unlink(missing_ok=True)),
]
```

每步失败记录并继续（除非是关键步骤），最后写一条 `admin.action` 审计 + 返回残留清单。

### 7.4 版本与 BM25 的不一致

- `_retire_version` 只对向量库调用 `delete_doc_versions`（`knowledge.py:480-487`）；BM25 仍持有历史版本块（靠 `hybrid` 的版本过滤兜住召回，但内存随 reparse 次数线性增长）。
- `vectorstore.py:219` 的 `renamed` 在第二次 reparse 后可能恒为 0，但日志仍报"改名 N 条"（`knowledge.py:489-492`）——失败语义不清晰。
- `apply_chunking` 的注释（`knowledge.py:443`）说"检索侧按 is_short/doc_id 过滤"，实际是版本过滤，注释已过期。

**改法**：BM25 的 `delete_doc_versions` 与向量库同步；`_retire_version` 返回结构化结果（renamed/removed/skipped），日志按实际值输出；更新注释。

### 7.5 KQ-34：JSON 全量重写与 O(n²) 写放大

| 文件 | 写入方式 | 频率 | 成本 |
|---|---|---|---|
| `metadata.json` | 全量 `write_text`（tmp+replace） | 每次入库/删除/状态变更 | O(文档数) |

**知识库判据（J5）**

`传统后端/25`：当单文件写入成本随数据量线性增长时，应换数据库或分片；`传统后端/10`：批处理的写放大要用"批量提交 + 水位线"控制。

**改法**：短期把 `docstore` 按 `doc_id` 分文件（`data/docstore/{doc_id}.json`），`tasks.json` 按日期分片；中期把 metadata/docstore/tasks/feedback 迁 SQLite（单表 + 索引），保留 JSON 作为导出格式。

### 7.7 KQ-35：幂等键缺失

**现状（A 级）**

- 全仓无 `Idempotency-Key`、无请求指纹去重。
- `POST /knowledge/ingest` 每次新建 `task_id`（`ingest.py:129`），重复点击产生两份任务与两份文档。
- `POST /knowledge/upload` 同名同内容会复用 `doc_id`（`knowledge.py:183-188`），但同名异内容会并存两份（`-{hash8}` 后缀），前端显示两条同名。
- `retry` 无条件再次入队（`ingest.py:377-401`），重复点 retry 会让同一任务多次执行。
- 反馈按 `ticket_id` 新建，不按 `trace_id + user` 去重（`feedback.py:60-72`）。

**知识库判据（J4）**

`传统后端/30`：内容寻址幂等键 = `hash(tenant, user, endpoint, canonical_body)`；重复请求应返回首次结果，而不是重新执行。对于上传，`(tenant, content_hash, filename)` 唯一约束是最自然的幂等键。

**改法**

1. 上传/入库：计算 `content_hash`，若 `(tenant, content_hash)` 已存在且状态 `INDEXED`，直接返回既有 `doc_id`/`task_id`（200 + `idempotent=true`）。
2. 支持 `Idempotency-Key` 头：存 `key → response` 24h，重复请求直接回放。
3. `retry` 在 `QUEUED/RUNNING` 时拒绝（409）。
4. 同批次同名文件 400。
5. 反馈按 `(trace_id, user_id)` 去重。

### 8.1 日志：结构对了，字段空了

**现状（A 级）**

- 单一 `StreamHandler(sys.stdout)`，每次 `setup_logging` 清空根 handler（`logging_setup.py:127-143`）；无文件 handler、无 `RotatingFileHandler`、无 `QueueHandler/QueueListener`。
- 文本格式 `%(asctime)s %(levelname)s %(name)s %(message)s`（`:142`）**没有 trace_id**；虽然 `ContextFilter` 注入了字段，但格式串没引用。
- JSON 形态强制 10 个字段（`:38-39`），但 `ContextFilter` 只注入 `trace_id`（`:93-101`）；`span_id/tenant_id/user_id/route/latency_ms` 没有平台级生产者，只有调用方手动 `extra`。
- `redact` 对 traceback 做正则替换（`:81`），会改写堆栈里的手机号/路径形态 token，排障时签名可能变化。
- 未处理 `uvicorn.access`，无访问日志；`request.state.started_ms` 设置了但从未读取（`main.py:669`）。

**知识库判据（J6）**

`传统后端/01`：结构化日志的价值在于"字段稳定 + 可聚合"；字段声明了但永远为空，比不声明更糟——看板会恒空且不报错。日志量三公式要求对 INFO 也要评估成本；异常链只记一次，且要保留原始堆栈。

**改法**

1. 在 `trace_middleware` 里把 `tenant_id/user_id/route/started_ms` 写入 `request.state`，并用 `logging.LoggerAdapter` 或 `contextvars` 注入到每条记录；或在 JSON formatter 里从 `request.state` 取（需要中间件把 state 挂到 contextvar）。
2. 文本格式加 `%(trace_id)s`，否则本地排障只能靠 grep 消息。
3. `uvicorn.access` 单独配置：JSON 化、采样、脱敏；至少把 `latency_ms` 填上。
4. 明确"只走 stdout + 外部采集"或"内置 RotatingFileHandler"，二选一写进 README；不要留下"看起来支持文件"的错觉。
5. 脱敏不要作用于 traceback 的源码行：只脱敏 `record.msg` 与明确的 `extra` 字段，保留 `exc_info` 原文（堆栈不落用户输入）。

### 8.2 指标：桶与业务超时不同量纲

**现状（A 级）**

- `rag_latency_seconds` 桶上限 10s（`metrics.py:32`），而 `llm_timeout_s=60`（`config.py:235`）、`agent_deadline_ms=60000`（`config.py:120`）→ 30~60s 的请求全部落进 `10.0` 桶，P95/P99 系统性低估。
- `rag_retrieval_top_score` 桶上限 0.1（`metrics.py:41`），而 CRAG 阈值 0.14/0.08（`config.py:88-89`）→ 合格分数全在最后一桶，分布不可读。
- `MetricsStore._top_queries` 无容量上限（`metrics.py:127-129`）；每请求一条 latency 常驻 24h（`:110,163`）。
- 只有 `pipeline` 与 `AgentRunner` 埋点；入库/管理/图谱端点无指标。
- 每个 app 实例独立 `CollectorRegistry`（`metrics.py:20`），多 worker/多副本下 `/metrics` 只反映被 scrape 的进程。

**知识库判据（J6）**

`传统后端/05`：直方图桶必须覆盖业务 SLO 的范围；`传统后端/26`：分位数样本量不足时 P99 无意义。把 60s 的超时塞进 10s 桶，等于主动放弃对长尾的观测。

**改法**

```python
buckets=(0.05, 0.1, 0.25, 0.5, 1, 2, 5, 10, 20, 30, 60, 120)
retrieval_buckets=(0.001, 0.005, 0.01, 0.02, 0.05, 0.1, 0.2, 0.5)
```

- `_top_queries` 改固定容量 LRU（如 500），latency 用 t-digest 或固定桶摘要，不要存原始列表。
- 增加 `http_requests_total{route,status}`、`http_request_duration_seconds{route}` 中间件指标；route 用**路由模板**（`/knowledge/{doc_id}`）而不是实际路径，避免基数爆炸。
- 多副本：要么用 `prometheus_client` 的 multiprocess mode，要么把 `/metrics` 聚合到独立 exporter；不要假装单进程指标能代表集群。

### 8.3 追踪：X-Trace-Id 被覆盖，W3C 没接

**现状（A 级）**

- `trace_middleware` 读取 `X-Trace-Id` 或自生成（`main.py:666`），但多数 API 端点用 `new_trace_id` 重新生成并 `set_trace_id`（`api/ingest.py:48`、`api/knowledge.py:43`、`api/admin.py:27`、`api/sessions.py:34`），丢弃入站 trace。
- 只 `trace.set_tracer_provider`（`otel.py:80`），无 FastAPI/httpx instrumentation、无 `propagate.set_global_textmap`、不解析 `traceparent`。
- `get_trace_id` 取不到时自动生成（`tracing.py:39-45`），会把"断链"伪装成"新请求"。

**知识库判据**

`运维体系` / `传统后端/01`：一个用户请求应只有一个 trace；跨服务要传播 W3C `traceparent`，而不是自定义头。断链时要显式标记，不要静默补一个 id。

**改法**：所有端点统一用 `get_trace_id`，只有后台任务/定时任务才 `new_trace_id`；接入 `opentelemetry-instrumentation-fastapi` 与 `httpx`；`get_trace_id` 在无 context 时返回空串并打 `warning`，由调用方决定是否新建。

### 8.4 探针：`/healthz` 串行、`/readyz` 只看 store

**现状（A 级）**

- `/healthz` 逐个同步 probe（`main.py:720-733`），无超时、无并发；任一慢依赖拖长整体，K8s probe timeout 会误判。
- `/readyz` 只判 `store is not None`（`:696-698`），不探 Milvus 连通性、LLM、Redis；空索引仍 200（这是有意的，注释已解释）。
- `/healthz` 返回 `str(exc)[:200]`（`:725-732`），可能泄露连接串/路径。
- `/metrics` 无鉴权（`:763`）。

**改法**：`/healthz` 用 `concurrent.futures` 并行 + 每项 1s 超时；错误只返回错误类型与 trace_id，不返回原文；`/readyz` 至少探 Milvus `has_collection` 与 Redis（若配置）；`/metrics` 独立端口或 admin 鉴权。

### 8.5 并发模型与容量估算

**现状（A 级）**

| 路径 | 执行模型 | 上限 | 证据 |
|---|---|---|---|
| `/ask` 同步 | AnyIO 线程池（默认 40） | 40 并发 | `api/ask.py:86` |
| `/ask/stream` | 每连接一个同步生成器 | 40（同一池） | `api/ask.py:137-190` |
| Agent run | 每请求一个新 daemon 线程 | 无上限 | `runner.py:285` |
| 工具调用 | 每次一个新 `ThreadPoolExecutor(1)` | 无上限 | `tools.py:685` |
| 入库 | 单 worker + 无界 `queue.Queue` | 1 并发 | `ingest.py:75-78` |
| 图谱构建 | 请求内同步执行 | 受线程池限制 | `api/graph.py:175-191` |
| 媒体索引 | 请求内同步循环 VL 调用 | 受线程池限制 | `api/graph.py:226-260` |

**用 Little's Law 算一遍**

设 `/ask` 平均延迟 `W=6s`、目标吞吐 `λ=20 QPS`，则稳态并发 `L=λW=120`。AnyIO 默认线程池 40，缺口 80 个请求全部排队；排队时间约 `(120-40)/40 × 6s ≈ 12s`，用户看到的是 18s。这不是"LLM 慢"，而是**线程池比业务并发小 3 倍**。

Agent 路径更糟：`L` 相同，但每请求额外占 1 个 Agent 线程 + 1 个工具池线程，且 deadline 60s 时 `L=λW` 可达 1200。

**改法**

1. 先压测得到真实 `λ` 与 `W`（用 `scripts/smoke_api.py` 扩展成 k6/locust 场景），再决定池大小；不要拍脑袋调到 200。
2. Agent 与工具统一到一个固定池，池满拒绝（503 + `Retry-After`），不要无限建线程。
3. SSE 走 async 路径，不占线程池；或单独一个 `ThreadPoolExecutor` 给流式，避免与普通请求争抢。
4. 入库改有界队列 + 多 worker（解析/OCR 可并行，索引写入串行）。

### 8.6 多副本失效矩阵

| 能力 | 当前实现 | 多副本后果 | 修法 |
|---|---|---|---|
| 令牌桶限流 | 进程内 dict（`ratelimit.py:25`） | 实际额度 ×N | Redis 令牌桶 |
| 滑动窗口配额 | 进程内 deque（`quota.py`） | 额度 ×N | Redis ZSET |
| 平台配额 | 进程内（`platform_quota.py`） | 统计不完整 | Redis + 定时汇总 |
| 语义缓存 | 进程内（`cache.py:79`） | 命中率 ÷N | Redis + 向量索引 |
| 指标 | 每进程 Registry | `/metrics` 只见一个副本 | multiprocess mode/exporter |
| 会话 | 本地 JSON + 进程内锁 | 同一会话被路由到不同副本时锁失效 | 共享存储 + 分布式锁 |
| 图谱 | 本地 SQLite + 全局锁 | 写冲突/读到旧图 | 单写副本或换服务端存储 |
| 检查点 | 本地 SQLite | 断点续跑/HITL 跨副本失效 | 共享 SQLite/Postgres |
| 检索配置 | 本地 JSON + 各进程晋升 | 生效时刻不一致 | leader 写或 Redis |
| 入库任务 | 进程内队列 | 各副本各跑一份，`tasks.json` 并发覆盖 | 真队列（RabbitMQ/Redis Stream） |

**知识库判据**：`传统后端/26` 的"无状态才能水平扩"；`传统后端/13` 的"配置热更新原子性"；`传统后端/06` 的"消费端幂等"。

**结论**：在补齐上述共享状态之前，**不要开多副本**；`--workers 1` 是当前唯一正确的部署方式（`backend/Dockerfile:67` 与代码语义自洽）。如果必须扩容，先做"读写分离"：把限流/配额/缓存/会话迁 Redis，指标走独立 exporter，入库改真队列。

### 8.7 KQ-32：队列与背压

- `core/tasks.py` 的 `BackgroundQueue` 设计完整（有界 200、背压、失败隔离、优雅停机、指标），但**生产零调用**（全仓仅测试 import）。
- `TaskManager` 用无界 `queue.Queue` + 单 daemon worker（`ingest.py:75-78`），`submit` 阻塞 `put`，无拒绝语义；`_save` 每次全量写 `tasks.json`（`:109-116`）。
- 优雅停机缺失：lifespan 收尾没有停 ingest worker（`main.py:582-598`），daemon 线程被直接掐断，可能留下半截任务/索引。

**改法**：把 `TaskManager` 改成 `BackgroundQueue(queue_size=200, workers=2)`；`submit` 返回 `False` 时 API 返回 503；lifespan 收尾 `shutdown(timeout=30)`；`tasks.json` 按任务分文件或迁 SQLite。

### 8.8 配置治理

**现状（A 级）**

- `Settings` 是 `BaseSettings` + `@lru_cache`（`config.py:14-20,378-380`），进程级只读；只能重启生效。
- 可热更新：检索配置（`config_store.py`）、配额策略、敏感词、ACL。不可热更新：模型名、超时、重试、上传上限、日志级别、OTel 开关、Agent 全部参数。
- 交叉约束缺失：`llm_timeout_s × (llm_max_retries+1)` 可以大于 `agent_deadline_ms`；`max_upload_mb` 可以为 0/负；`log_format` 任意字符串都落到 text 分支；`agent_mode` 任意值不校验。
- 凭证未统一 `SecretStr`：`auth_tokens_json`、`auth_users_json`、`redis_url`、`sql_dsn`、`web_search_api_key` 不在 `config_items` 的掩码清单里（`config.py:251-292`）。
- `RetrievalConfigStore` 的 pending 晋升在每个进程各自判断并写回同一文件（`config_store.py:81-90`），多副本会互相覆盖。

**知识库判据（J8）**

`传统后端/13`：配置、开关、密钥三分；启动快照 + fail-fast；热更新要原子；密钥要信封加密/租约轮换。`传统后端/11`：配置项也是契约，默认值是契约的一部分。

**改法**

1. `validate_startup` 增加交叉约束与枚举校验（见 §2.7）。
2. 所有密钥字段改 `SecretStr` 或至少进 `config_items(is_secret=True)`；`sql_dsn` 异常信息做 `_mask`。
3. 增加 `/admin/config` 只读视图（掩码），让运维能看到"当前生效值"，而不是只能猜。
4. 热更新白名单：`log_level`、`log_debug_sample_rate`、`retrieval_config`、`quota`、`sensitive_words`；其余明确"需重启"。
5. 多副本配置：`RetrievalConfigStore` 只允许 leader 写，或状态放 Redis；生效时间由服务端统一返回。

### 9.1 KQ-36：SSE 客户端的分帧与恢复

**现状（A 级）**

- 分帧用 `buffer.indexOf("\n\n")`（`sse-client.ts:178`），只识别 `event: ` 与 `data: ` 前缀（`:184-185`）。
- 多行 `data:` 每次覆盖，只保留最后一行（`:185`）——SSE 规范要求按行拼接；后端一旦返回多行 JSON，前端会静默丢内容。
- 不支持 `\r\n` 帧分隔、`:` 心跳注释行、`retry:` 字段、无空格 `data:`。
- 无自动重连/退避；`AbortError` 静默返回（`:196-197`），流结束无终止事件时报"连接中断"（`:200-202`）。
- `graph_path` 在白名单（`:85`）但 `dispatch` 无分支（`:146-169`），事件被静默丢弃。
- `onDone` 的类型断言比声明窄（`:165` vs `:46-64`），契约漂移。

**知识库判据**

`传统后端/12`：SSE 客户端必须处理"帧边界、心跳、断线重连、终止事件"四件事；`传统后端/11`：事件名与 payload 是契约，白名单与 dispatch 必须同源。

**改法**

```ts
// 1) 按规范解析
for (const line of rawEvent.split(/\r?\n/)) {
 if (line.startsWith(":")) continue; // 心跳
 if (line.startsWith("event:")) event = line.slice(6).trim;
 else if (line.startsWith("data:")) dataParts.push(line.slice(5).trimStart);
}
const data = dataParts.join("\n");

// 2) 终止后不再重连；非终止断流按指数退避重试（最多 3 次）
// 3) graph_path 补 handler 或从白名单删除
// 4) 类型从后端 OpenAPI/codegen 生成，禁止手写断言
```

### 9.3 KQ-37：聊天页的渲染与状态

**现状（A 级）**

- `messages.map` 全量渲染（`ChatPage.tsx:363-374`）；无虚拟化（依赖仅 react/react-dom/react-router）。
- 每 token 一次 `setMessages(prev.map(...))`（`:131-134`）；`MessageBubble` 未 `memo`（`components/MessageBubble.tsx:31`），`StreamText` 的 rAF 优化被父级全量重渲抵消。
- 滚动无条件贴底（`:65-68`），用户上滚阅读长答案时会被拽回底部。
- `retry` 不删除失败气泡（`:273-284`），重试后问答各多一份。
- 会话恢复只按 `turns` 重建问答对，`evidence: []`（`:294-303`）→ 历史引用变成死链。
- 全仓无 ErrorBoundary（`App.tsx` 仅 Provider + Routes），任一页面抛错整站白屏。
- 原文预览模态无焦点陷阱、无 Esc 关闭（`:384-409`）。

**知识库判据**

`传统后端/12` 的慢消费者/渲染成本；`部署/02` 的前端可观测。对聊天页，关键不是"渲染得多漂亮"，而是"流式期间不要把整棵树重渲"。

**改法**

1. 加全局 + 路由级 `ErrorBoundary`（重试/回首页），保留侧边栏。
2. `MessageBubble` 加 `memo`，流式内容用独立 store/`useSyncExternalStore` 订阅，只重渲当前气泡。
3. 长会话用 `react-window`/`virtuoso`（或现有 `WindowedList` 复用到消息列表）。
4. 滚动加"用户上滚则暂停贴底，回到底部再恢复"。
5. 重试前删除失败气泡，或标记为 `superseded`。
6. 会话恢复时拉取 `/ask/{trace}/evidence`（若不存在则补接口），至少保留 `trace_id` 可跳转原始记录。
7. 模态加 `role="dialog"` 之外的焦点陷阱与 Esc。

## 十一、优化路线图

### 11.1 分批原则

1. **先止血，再提质量**：安全/数据破坏类问题优先于性能与体验。

## 十三、并发能力与设计

> 本章只讨论并发、容量与过载治理，不涉及检索质量、Agent 能力、企业功能等其它方向。
> 与第二章至第十二章的缺陷修复不同，本章回答"要扛住更高并发，还缺哪些机制、怎么设计、如何验收"。

### 13.1 先拆清楚：RAG 的三种并发

混在一起谈"高并发"，就会得出"加线程/加副本"这种错误结论。RAG 系统里有三种资源完全不同的并发：

| 并发类型 | 占用资源 | 典型上限 | 本项目现状 | 正确解法 |
|---|---|---|---|---|
| **连接并发** | 文件描述符 + 内存（SSE 长连接） | 单机数千~数万 | 同步生成器，每连接占一个线程；AnyIO 默认池 40 | 异步生成器 + 心跳 + 断线取消 |
| **请求并发** | 上游 LLM/Embedding/Rerank 的 QPS 与并发配额 | 由供应商决定（常见几十） | 无准入控制，直接打上游 | 准入 + 有界队列 + 优先级 + 降级 |
| **计算并发** | CPU（解析、BM25、FAISS、JSON） | 核数 | 单 worker + 同步阻塞 | 分离池 + 批处理 + 异步化 |

**核心判断：RAG 服务扩容时，最先撞到的通常不是应用 CPU，而是上游配额与成本。** 因此并发设计的第一页应该是"上游预算表"，而不是"线程池大小"。

一个反直觉的推论：当上游配额是 50 次/s 时，把副本从 1 扩到 4 不会让吞吐变成 4 倍，只会让 429 变成 4 倍，并把成本打满。

### 13.2 目标架构

```text
 ┌─────────────────────────────────────────┐
 客户端 ──HTTP/SSE──▶ │ nginx / LB │
 │ limit_req（第一道闸）· HTTP/2 · 静态缓存 │
 └──────────────────┬──────────────────────┘
 │
 ┌─────────────────────────▼─────────────────────────┐
 │ API 副本 ×N（无状态，async） │
 │ 认证 → 租户配额(Redis) → 令牌桶(Redis) → 成本闸门 │
 │ 准入：优先级队列 + 有界信号量 │
 └───┬───────────────┬───────────────┬───────────────┘
 │ │ │
 ┌──────────▼──────┐ ┌──────▼───────┐ ┌─────▼────────────┐
 │ 交互请求池 │ │ 入库/批处理池 │ │ 图谱/后台池 │
 │ ask/stream │ │ ingest │ │ graph/build │
 └──────────┬──────┘ └──────┬───────┘ └─────┬────────────┘
 │ │ │
 ┌──────────▼───────────────▼───────────────▼────────────┐
 │ 上游隔离仓（每类独立信号量 + 熔断 + 超时） │
 │ LLM │ Embedding │ Rerank │ Milvus │ SQL │ Web │
 └──────────┬────────────────────────────────────────────┘
 │
 ┌────────────┼──────────────┬──────────────────┐
 ▼ ▼ ▼ ▼
 Redis 有界队列 Milvus 共享元数据/文件
 配额/限流/缓存 入库/后台任务 向量（HNSW） （多副本前置，另属数据平台改造）
 会话/取消标志 DLQ + 幂等
```

与当前架构的差别只有三处，但每一处都是"能不能扛住"的分水岭：

1. **状态外置**：限流、配额、缓存、会话从进程内移到 Redis；
2. **执行分离**：交互、入库、后台任务用不同池，互不抢占；
3. **上游隔离**：每类外部依赖独立信号量 + 熔断，慢的重排不能拖死快的向量检索。

> 多副本还要求元数据与上传文件共享（当前是本地 JSON/文件）。这属于数据平台改造，本章不展开；**在共享元数据完成前，保持单副本 + 异步化 + 背压，是唯一正确的并发路径。**

### 13.3 十二项并发能力

| 编号 | 能力 | 设计要点 | 验收 | 成本 |
|---|---|---|---|---|
| **F-C01** | 无状态多副本 | 状态外置：限流/配额/缓存/会话/取消标志走 Redis；API 不写本地文件；元数据/文件共享是前置条件 | 2 副本、120 QPS 下 429 比例与单副本一致；任一副本可服务任一请求 | L |
| **F-C02** | 全链路异步 | `httpx.AsyncClient`（连接池 + keep-alive + HTTP/2）；同步 SDK 改 `run_in_executor` 或直连 HTTP；重试改 `asyncio.sleep` | 100 并发下事件循环 lag P95 <50ms | L |
| **F-C03** | 有界执行器 + 背压 | 每类上游一个 `asyncio.Semaphore`；队列设 `maxsize`；满时 503 + `Retry-After`，不无限排队 | 压测中队列深度有上限、RSS 平稳、503 带 `Retry-After` | M |

### 13.4 容量模型：先算上游，再算副本

以一个可落地的目标为例：

```text
目标：峰值 30 QPS（交互问答），平均端到端 8s，P95 ≤ 15s
单次问答 LLM 调用：意图 1 + 改写 2 + 拆解 1 + 生成 1 + 自检 1 = 6 次
→ 上游 LLM 需求 = 30 × 6 = 180 次/s

若供应商账号配额只有 50 次/s：
 30 QPS 目标不可达（差 3.6 倍）
 可行方案：
 a) 把 6 次压到 3 次（闲聊短路 / 合并意图与拆解 / 关闭默认改写）→ 90 次/s，仍需排队
 b) 轻量步骤走更便宜的模型（意图/改写用 turbo，配额或成本独立）
 c) 缓存命中 30% → 有效 126 次/s
 d) 准入控制：超过 50 次/s 的请求排队或降级
```

再看连接与线程：

```text
30 QPS × 平均 8s = 240 个并发请求（Little's Law）
同步实现：240 个线程 × 1~2MB 栈 ≈ 240~480MB，且 AnyIO 默认池 40 → 200 个排队
异步实现：240 个协程 × 几十 KB ≈ 10~20MB
```

再看存储：

```text
Milvus FLAT：10 万块 × 1024 维 ≈ 1 亿次乘加/查询
30 QPS → 30 亿次/s，单机 CPU 不可能
→ 必须 HNSW（对数级）或分片；这是"高并发"真正的硬约束之一
```

**容量表模板**（建议写进 README）：

| 场景 | 单副本 QPS | 并发 | P95 | 上游调用/s | 成本/千次 | 备注 |
|---|---:|---:|---:|---:|---:|---|
| 缓存命中 | 500 | 50 | 50ms | 0 | ≈0 | 受 Redis/网络限制 |
| 简单事实问答 | 8 | 64 | 6s | 24 | ? | 3 次 LLM |
| 多跳问答 | 3 | 24 | 18s | 24 | ? | 8 次 LLM |
| 流式问答 | 10 | 80 | TTFT 2s | 30 | ? | 异步后连接不是瓶颈 |
| 批量入库 | 2 文档/min | 2 | — | OCR/Embedding 为主 | ? | 独立池 |

### 13.5 过载降级阶梯

高并发的最后一道防线是"有序降级"，而不是"全部 500"：

| 水位 | 动作 | 用户体验 |
|---|---|---|
| 正常 | 全功能 | — |
| 上游 P95 超阈值 | 关闭 HyDE/额外改写；减少 CRAG 轮次 | 略慢/略差，仍可用 |
| 队列深度 > 阈值 | 拒绝低优先级（入库/后台），交互保留 | 批量任务排队 |
| 上游错误率 > 50% | 熔断该上游；重排降级为 RRF；生成降级为模板/拒答 | 明确告知"降级模式" |
| 成本/配额耗尽 | 拒绝新请求或只服务缓存 | 429 + `Retry-After` |
| CPU/内存 > 90% | 只服务缓存与健康检查；触发告警 | 503，快速失败 |

**验收**：在 staging 注入"重排超时 + LLM 30% 失败 + 队列打满"，系统仍能在 2s 内返回可理解的降级结果，且指标能区分"正常/降级/拒绝"。

### 13.6 压测方案与验收

| 场景 | 方法 | 通过标准 |
|---|---|---|
| 流式连接 | 100/500/1000 条 SSE 并发，持续 10 分钟 | 线程数不随连接线性增长；RSS <500MB；断开 2s 内释放 |
| 问答吞吐 | 1→100 QPS 阶梯，每级 3 分钟 | P95 在容量表范围内；429 有 `Retry-After`；错误率 <2% |
| 慢上游 | 注入 rerank 5s 延迟 / LLM 30% 超时 | 向量检索不受影响；熔断打开；降级答案可读 |
| 队列背压 | 批量提交 1000 个入库任务 | 队列深度有上限；低优先级被拒；交互 P95 恶化 <20% |
| 优雅停机 | 压测中滚动重启 | 无半截任务/半截索引；SSE 收到终止事件 |
| 缓存抖动 | Redis 重启 | 自动退 L1；错误率上升但服务不中断 |

压测入口建议复用 `scripts/smoke_api.py` 的请求构造，新增 `scripts/load_test.py`（k6 或 locust），并把结果写入 `doc/analysis/并发容量基线.md`。

### 13.7 实施顺序

```text
（单副本，1~2 周）
 F-C02 全链路异步 → F-C09 SSE 异步化 → F-C03 有界执行器 → F-C10 压测基线
 目标：单副本在 100 并发下线程/内存可控，TTFT 与 P95 有基线

（共享状态，1~2 周）

 目标：上游故障可隔离，过载可降级，配额跨进程一致

（多副本，1~2 周）

 目标：2 副本容量接近线性，429 比例与单副本一致

```

### 13.8 并发反模式（明确不做）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 只调 `uvicorn --workers` | 六处进程内状态会分裂；上游配额不会变多 | 先状态外置 + 准入控制 |
| 每个请求新建线程/线程池 | 线程创建有成本，且无法限制总量 | 应用级固定池 + 信号量 |
| SSE 用同步生成器 | 连接生命周期 = 线程占用 | async generator + 队列桥接 |
| 无界队列 | 过载时内存无限增长，故障从"慢"变"崩" | 有界队列 + 503 + `Retry-After` |
| 用重试代替熔断 | 失败时放大下游压力（`1/(1-p)`） | 熔断 + 半开 + 降级 |
| 把 tenant 放进指标 label | 时间序列基数随租户线性膨胀 | 低基数 label + 日志维度 |
| 无上限 `asyncio.gather` | 瞬时打满上游配额 | 信号量 + 分批 |
| 用 `time.sleep` 轮询 | 阻塞线程/事件循环 | async sleep + 事件通知 |
| 在请求线程做 CPU 密集解析 | 单请求拖慢整个进程 | 后台池 + 队列 + 202 |
| 先扩副本再迁状态 | 数据错乱比性能不足更难查 | 状态外置是前置条件 |

## 附录 B：本文用到的公式与判据

### B.1 Little's Law 与容量

$$
L = \lambda \times W
$$

- $L$：系统内平均并发请求数；$\lambda$：到达率（QPS）；$W$：平均驻留时间（含排队）。
- 用途：反推线程池/连接池大小。若 $L=120$、池只有 40，则 $80$ 个请求在排队，排队时间约 $(L-C)/C \times W$。
- 反推吞吐上限：$\text{throughput}_{\max} = C / W$。

### B.2 M/M/1 与利用率

$$
W = \frac{1}{\mu - \lambda}, \quad \rho = \frac{\lambda}{\mu}
$$

- $\mu$：服务率；$\rho \to 1$ 时 $W$ 非线性爆炸。
- 用途：解释"为什么池调到刚好够用会抖"——要留 20%~30% 余量。

### B.3 RRF

$$
\text{RRF}(d) = \sum_{i=1}^{n} \frac{w_i}{k + \text{rank}_i(d)}
$$

- 本项目实现为 $k + \text{rank} + 1$（rank 从 0 起），与标准式的差别只是常数偏移，不改变排序。
- 性质：只用排名，不用分数，解决 BM25（0~∞）与余弦（-1~1）不可比的问题。

### B.4 BM25

$$
\text{score}(q,d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d)\,(k_1+1)}{f(t,d) + k_1\,(1 - b + b\,\frac{|d|}{\text{avgdl}})}
$$

- 本项目用 Lucene 风格恒正 IDF：$\ln\left(1 + \frac{N - n + 0.5}{n + 0.5}\right)$（`bm25.py:44-46`）。
- $k_1=1.5$ 控制词频饱和，$b=0.75$ 控制长度归一。

### B.5 重试放大

$$
\text{放大倍数} = \frac{1}{1-p}
$$

- $p$：单次失败率。$p=0.3$ 时放大 1.43 倍；若每层都重试 3 次，多层叠加会指数放大。
- 用途：解释为什么 `llm_max_retries=3` 与 60s 超时不能同时存在。

### B.6 缓存净收益

$$
\text{净收益} = H \times C_{\text{miss}} - (1-H) \times C_{\text{lookup}} - C_{\text{store}}
$$

- $H$：命中率；$C_{\text{miss}}$：未命中时的计算成本；$C_{\text{lookup}}$：查找成本。
- 本项目语义查找是 O(2000×1024) 纯 Python，$C_{\text{lookup}}$ 不低；命中率若 <20%，净收益可能为负。

### B.7 稳态容量

$$
V_{\text{稳态}} = \lambda \times R
$$

- $\lambda$：写入速率；$R$：保留期。没有 $R$ 就没有稳态，只有无限增长。
- 用途：审计/检查点/任务目录的容量预测。

### B.8 Token 成本

$$
\text{cost} = \frac{\text{prompt\_tokens} \times P_{\text{in}} + \text{completion\_tokens} \times P_{\text{out}}}{1000}
$$

- 本项目 `price_table` 按每千 token 配置（`config.py:123`）；未知模型记 0 并标 `priced=false`。
- 注意：用字符/2 估算会同时低估 prompt 与 completion，成本看板只能做趋势，不能做结算。

### B.9 Amdahl

$$
S_{\max} = \frac{1}{(1-f) + f/s}
$$

- $f$：可并行比例；$s$：并行加速比。用途：判断"把检索并行化"的收益上限——若检索只占端到端 20%，并行化最多省 20%。
