**但本设计的核心主张是**：

> **先收敛错误体系，再拆分模块。** 拆完再收敛，等于把同一个错误处理复制到多个新模块——这是「重构陷阱」里最常见的一种。

因此本设计的**前置依赖**是 `doc/design/03-错误体系与可观测性设计.md` §二（领域异常基类 + 裸异常收敛）。

## 一、现状的依赖结构

### 1.1 分层意图（项目已有）

```
app/api/          ← 端点层：解析请求、鉴权、组装信封
app/services/     ← 业务层：检索、生成、索引、图谱、Agent
app/core/         ← 基础设施：配置、信封、日志、指标、共享状态、限流
app/domain/       ← 领域模型：Pydantic schema
```

### 1.2 实际违规

| 违规 | 位置 | 影响 |
|---|---|---|
| `core` 依赖 `services` | `backend/app/core/*` 里的 `from app.services...` | 基础设施反向依赖业务 → 无法独立测试、无法复用 |
| `core` 依赖 `api` | `backend/app/core/*` 里的 `from app.api...` | 同上，更严重 |
| 顶层 `import app.`（模块级导入） | **30 处** | 循环依赖的温床：模块 A 顶层导入 B，B 顶层导入 A → 导入顺序决定谁拿到半成品模块 |
| `main.py` 承担全部装配 | 899 行 | 改一个依赖就要动 `main.py`；无法单测装配逻辑 |
| `pipeline.py` 承担全部阶段 | 1291 行 | 改检索就可能碰生成；无法单测阶段行为 |

### 1.3 循环依赖的具体位置

```
backend/app/services/vectorstore.py  ⟷  backend/app/services/milvus_store.py
```

`vectorstore.build_vector_store()` 要构造 `MilvusStore`，而 `MilvusStore` 又要 import `vectorstore` 的工具函数。现状靠「函数内 import」掩盖（这就是 `doc/plan/代码规范符合性审计与整改计划.md` 审计时说的「1 组循环依赖被 4 处无注释局部 import 掩盖」）。

## 二、A-12 · `main.py` 拆分

### 2.1 目标结构

```
backend/app/
├── bootstrap.py          # 新增：FastAPI 实例 + 路由注册 + 异常处理器 + 中间件
├── main.py               # 瘦身为：app = create_app()（约 30 行）
├── assembly/             # 新增：装配子模块（lifespan 的分块）
│   ├── __init__.py
│   ├── runtime.py        # 共享状态 / 隔离仓 / 限流器 / 缓存
│   ├── storage.py        # 向量库 / BM25 / DocStore / 索引版本
│   ├── knowledge.py      # KnowledgeService / KBService / ACL / 用户目录
│   ├── models.py         # LLM / Embedding / Rerank / OCR / ASR
│   ├── agent.py          # 工具注册 / 图谱 / 检查点 / 预算
│   └── hooks.py          # _post_index 钩子等跨域回调
└── ...
```

### 2.2 拆分原则

| 原则 | 说明 |
|---|---|
| **按「装配域」拆，不按「对象数」拆** | 每个子模块回答一个问题（"存储怎么装"、"模型怎么装"），而不是"把 50 个对象分成 5 堆" |
| **每个子模块导出一个 `install(app, settings) -> None`** | 统一签名，装配顺序由 `bootstrap.py` 显式编排 |
| **不引入框架** | 不用 DI 容器、不用装饰器注入；显式函数调用最易读 |
| **不改行为** | 拆分是**纯结构变更**，验收标准是「重构前后 `pytest` 全绿 + 端点数与信封不变」 |

### 2.3 拆分顺序（每步一个 PR）

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 抽 `app/api/**` 的路由注册到 `bootstrap.py` | 低 |
| 2 | 抽 4 个异常处理器 + CORS + trace 中间件到 `bootstrap.py` | 低 |
| 3 | 抽 `assembly/storage.py` | 低 |
| 4 | 抽 `assembly/models.py` | 低 |
| 5 | 抽 `assembly/knowledge.py` | 中 |
| 6 | 抽 `assembly/runtime.py` | 中 |
| 7 | 抽 `assembly/agent.py` + `assembly/hooks.py` | 中 |
| 8 | 抽 `lifespan` 到 `assembly/lifespan.py` | 中 |

**每步都要**：`pytest` 全绿 + `scripts/smoke_api.py` 通过 + 端点数不变（`app.openapi()` 端点集合 diff 为空）。

### 2.4 验收

- `main.py` < 200 行；`lifespan()` < 60 行；
- 无 3 层以上嵌套闭包；
- `app/bootstrap.py` 可被 `python -c "import app.bootstrap"` 独立导入（不触发 lifespan）。

## 三、A-13 / A-14 · 分层规则与机器校验

### 3.1 分层规则（写死进测试）

| 层 | 允许 import | 禁止 import |
|---|---|---|
| `app/core/**` | `app.core.*`、`app.domain.*`（纯模型） | **`app.services.*`、`app.api.*`** |
| `app/domain/**` | 标准库、pydantic | `app.*` 其它任何 |
| `app/services/**` | `app.core.*`、`app.domain.*`、同层其它 service | **`app.api.*`** |
| `app/api/**` | `app.core.*`、`app.domain.*`、`app.services.*` | —— |

### 3.2 允许的例外

| 例外 | 位置 | 原因 |
|---|---|---|
| **可选依赖** | `app/core/otel.py` | OpenTelemetry 是可选依赖，未安装时不能 import 失败 |
| **条件装配** | `app/core/*` 中仅在函数内 import 的 provider | 避免顶层硬依赖（如 `pymilvus` 未装时仍能启动） |
| **破环** | 显式标注 `# 破环` 的顶层 import | 循环依赖的**唯一**合法出口，且必须在 CI 里被计数（数量只减不增） |

### 3.3 A-13：AST 边界测试

**落点**：`backend/tests/unit/test_import_boundaries.py`

**做法**：

1. 用 `ast` 解析 `backend/app/**` 的所有 `.py`；
2. 收集每个文件的**模块级** import（`ast.Module.body` 里的 `Import` / `ImportFrom`）；
3. 按 §3.1 的表判定是否违规；
4. 对「函数内 import」只**统计不改判**（可选依赖本来就合法），但要求它们带注释说明原因；
5. 对带 `# 破环` 的顶层 import 计数，断言「数量 ≤ 当前基线」（防止新增破环）。

**为什么用 AST 而不是 grep**：grep 看不见「模块级 vs 函数内」的差别，也处理不了别名与条件导入。

### 3.4 A-14：30 处顶层 `import app.` 的逐个处置

每处顶层 `import app.X` 三选一：

| 处置 | 做法 | 适用 |
|---|---|---|
| **下沉到函数内** | 把 import 移到使用它的函数里 | 可选依赖、条件装配、破环 |
| **改相对导入** | 同包内用相对 import | 同层 service 之间 |
| **提取到共享层** | 把被依赖的公共部分下沉到 `core` 或 `domain` | 真正的底层依赖 |

**建议的提取清单**（把「底层依赖」真正搬到下面）：

| 目标 | 当前被谁依赖 | 搬到 |
|---|---|---|
| 错误码 / 信封构造 | 几乎所有层 | 已在 `app/core/envelope.py`（正确） |
| `Principal` | `services/security/*`、`api/*` | 已在 `app/services/security/auth.py`——但 `api` 层也依赖它，**应下沉到 `app/domain/principal.py`** |
| 配置项读取 | 所有层 | 已在 `app/core/config.py`（正确） |
| `ErrCode` 的判别逻辑 | 各处重复 | 抽 `app/core/envelope.py` 的 `kind_of(code)` |

### 3.5 验收

- `grep -rnE "^\s+(from|import)\s+app\." backend/app | grep -v "TYPE_CHECKING"` 的命中数 ≤ 当前基线且**只减不增**；
- `test_import_boundaries.py` 通过；
- `vectorstore ⟷ milvus_store` 的循环依赖消除（要么下沉公共部分，要么双方都用函数内 import + `# 破环` 注释）。

## 四、B0 X-27 · `pipeline.py` 的拆分

### 4.1 现状

`backend/app/services/pipeline.py` **1291 行**，承担：缓存、预处理、检索编排、CRAG、上下文组装、生成、自检、拒答判定、敏感词扫描、推荐追问、审计、single-flight。

### 4.2 目标：抽纯函数 → 抽阶段协作者

**第一步（纯函数，低风险）**：把无状态的转换逻辑抽出来，每个都是纯函数，可单测：

| 函数 | 现状位置 | 抽出后 |
|---|---|---|
| `build_prompt(question, evidence)` | `pipeline.py:64-89` | `app/services/generation/prompt.py` |
| `_to_evidence(hybrid_result)` | `pipeline.py:516` | `app/services/generation/evidence.py` |
| `assemble_context(...)` | `app/services/context.py`（已独立） | 保持 |
| 自检记录转换 `_to_self_check_record` | `pipeline.py` 内 | `app/services/validation/selfcheck.py` 的伴随函数 |

**第二步（阶段协作者，中风险）**：把有状态的阶段拆成协作者对象，各自持有自己的依赖：

```
app/services/pipeline/
├── __init__.py
├── core.py          # RagPipeline（编排：状态机 + 事件产出）
├── cache_stage.py   # 缓存查 / 存 / single-flight
├── retrieve_stage.py# 检索 + 后过滤 + 拒答探测
├── generate_stage.py# 生成 + 追问
├── guard_stage.py   # 自检 + 重生成 + 敏感词
└── types.py         # 阶段间数据结构
```

**边界原则**：协作者**不持有 pipeline 的可变状态**（如 `_context_dropped`），只通过参数与返回值通信。

### 4.3 X-28.8：`HybridRetriever._settings` 只写不读

`backend/app/services/retrieval/hybrid.py:79` 赋值后全文件无读取。拆分时应**顺手删除**，或在检索器真正需要配置时用它（例如按 `top_k` 自适应扩取）。
