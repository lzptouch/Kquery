# Kquery 值班 Runbook

> **这份文档是给「凌晨三点被叫醒的人」看的**：每一步都能照做，不需要先读完整个系统。
>
> 依据 Google SRE 的告警设计原则：
>
> 1. **告警症状而非原因**——「CPU 到 82%」没有处置价值，「错误率上升」才有；
> 2. **一个主要 SLO + 错误预算**——用**燃烧速率**而不是绝对阈值判断是否要叫醒人；
> 3. **事件分级 + 无责复盘**——分级决定「是否叫人」；复盘对事不对人。

## 通用流程（7 步）

```
① 接警 → ② 定级 → ③ 确认影响面 → ④ 定位 → ⑤ 处置 → ⑥ 回滚 → ⑦ 复盘
```

| 步骤 | 做什么 | 关键命令 / 入口 |
|---|---|---|
| ① 接警 | 读告警的 `summary` / `description`；翻到对应的处置卡 | 告警名 → `alerts/<连字符形式>.md` |
| ② 定级 | 按 `severity.md` 的分级表定 P 级；**P0/P1 立即叫人** | — |
| ③ 确认影响面 | 「用户看到什么」而不是「哪个组件 CPU 高」 | `curl -s localhost:8000/healthz \| jq` |
| ④ 定位 | 先看**症状类指标**（错误率 / 延迟 / 排队），再看依赖 | `curl -s localhost:8000/metrics` |
| ⑤ 处置 | 按处置卡的「处置动作」逐条执行 | 处置卡 |
| ⑥ 回滚 | **先回滚，再定位**——用户在等的是恢复，不是在等根因 | 处置卡的「回滚动作」 |
| ⑦ 复盘 | 无责复盘：对事不对人；产出一张「如果早知道该做什么」的卡 | `severity.md` 的升级路径 |

## 三条值班纪律

1. **回滚优先于定位**：用户感受到的是「不可用」，不是「根因未知」。
2. **不要用「加机器」代替「查原因」**：扩容能压住症状，但会掩盖真正的瓶颈
   （例：图写入成了瓶颈时，加机器只会让数据库更慢）。
3. **不确定就升级**：升级的成本是「多叫了一个人」，不升级的成本是「用户受影响 2 小时」。
