## 〇、摘要

- 指标双轨：Prometheus 文本经 `GET /metrics` 暴露（`main.py:874-880`），进程内 `MetricsStore` 支撑 `/admin/metrics/*` 五个 JSON 端点（`api/admin.py:25-64`）；两者互不依赖（`core/metrics.py:1-7`）。
- label 纪律：`rag_latency_seconds` 的 label 是 `path` 而非 `tenant`——租户是高基数维度，改由结构化日志承载（`core/metrics.py:24-34`）；指标侧绝不放 tenant / user / 请求原文。
- 日志已是结构化 JSON（生产形态），强制 10 个字段、PII 与凭证形态在日志层二次脱敏、DEBUG 按比例采样（`core/logging_setup.py:38-39`、`:26-34`、`:104-124`）。
- 追踪是「自研 16 位 trace_id + 可选 OTel」双层：HTTP 中间件入站复用 / 出站回写 `X-Trace-Id`（`main.py:770-783`）；OTel 默认关闭，启用后 span 自动携带自研 trace_id 做跳转（`core/otel.py:126-142`）。
- 探针四级分级：`/health` 静态、`/livez` 不查依赖、`/readyz` 只看 store 装配、`/healthz` 逐依赖报告（`main.py:785-872`）。
- 成本账本是进程内环形缓冲（上限 `MAX_RECORDS=5000`，`services/agent/cost.py:20`），`priced=False` 表示「价格表未覆盖 = 成本未知」而不是「免费」（`services/agent/cost.py:31`）。

## 一、四支柱总览

| 支柱 | 实现 | 代码位置 | 读取方式 |
|---|---|---|---|
| 日志 | 根 logger 单 handler 输出到 stdout；`text`（本地默认）/ `json`（生产）两种形态 | `core/logging_setup.py:127-147` | 容器 / 进程 stdout，由日志平台采集 |
| 指标 | `PromMetrics`（独立 `CollectorRegistry`，每 app 实例一份，测试可反复建 app）+ `MetricsStore`（分钟桶聚合） | `core/metrics.py:16-128`、`:141-391` | `GET /metrics`（Prometheus 抓取）；`GET /admin/metrics/{summary,timeseries,top-queries,agent,quality}`（JSON 看板） |
| 追踪 | contextvars 承载的自研 trace_id；可选 OTel（OTLP/HTTP 导出） | `core/tracing.py`、`core/otel.py` | 响应头 `X-Trace-Id`、日志 `trace_id` 字段、信封 `meta.trace_id`；OTel 开启后在 Jaeger/Tempo 查看 |
| 探针 | 4 个分级端点 + 指标端点，全部内建于 `create_app` | `main.py:785-880` | 见 §五 |

四条规则贯穿全部支柱：

1. **观测设施故障不得阻断业务**：指标采集异常被吞（`core/metrics.py:122-127`）、OTel 初始化失败降级 NoOp（`core/otel.py:85-87`）、日志取 trace 失败置空串（`core/logging_setup.py:99-100`）。
2. **原文不留存**：指标只存问题哈希（`core/metrics.py:271-280`），日志做 PII 脱敏（审计与敏感词下线后，已无其它环节再对原文做哈希化或掩码）。
3. **trace_id 一处生成、处处复用**：中间件生成 / 复用后写入 contextvar，下游（日志、信封、span attribute）全部读同一值。
4. **高基数维度只在日志，不进指标**：tenant / user 是日志字段，不是 Prometheus label。

### 2.2 label 纪律（为什么 label 是 `path` 不是 `tenant`）

`rag_latency_seconds` 的注释把这条写成反模式案例（`core/metrics.py:24-34`）：tenant 随客户数线性增长，作为 label 会让时间序列数量同步膨胀、最终打爆监控存储。因此：

- 指标侧只保留**有限枚举**的低基数 label（status / mode / tool / result / action / reason / stage / upstream）；
- 租户维度改由**结构化日志的 `tenant_id` 字段**承载，按租户的 P95 由日志后端聚合；
- 请求内容（问题原文）永远不做 label，也永远不进指标值。

### 2.3 隐私纪律：指标只存 `query_hash`

`MetricsStore._top_queries` 的键是 `sha256(question)[:16]` 而非原文（`core/metrics.py:271-280`）；返回字段名就叫 `query_hash`，防止调用方误以为还能拿到原文（`core/metrics.py:282-296`）。同一问题哈希一致，「哪些问题高频」仍可统计，但进程内聚合结构不再是第二份明文副本。

### 2.4 `MetricsStore` 业务指标（支撑 `/admin/metrics/*`）

## 三、结构化日志

### 3.1 字段表

`JsonFormatter` 输出一行一条 JSON（`core/logging_setup.py:54-82`），强制字段缺失时补空串而不是省略（字段时有时无会让下游看板时好时坏）：

| 字段 | 来源 |
|---|---|
| `ts` | 记录时间，UTC ISO8601 |
| `level` / `logger` / `msg` | LogRecord 标准字段（`msg` 已过 `redact`） |
| `trace_id` / `span_id` | 请求上下文（trace_id 由 `ContextFilter` 注入） |
| `tenant_id` / `user_id` / `route` / `latency_ms` | 调用方 `extra={...}` 附加 |
| 自定义字段 | `extra` 中的标量原样带出，字符串值再过一次 `redact`（`core/logging_setup.py:70-79`） |
| `exc` | 异常堆栈，整体脱敏后附入（`core/logging_setup.py:80-81`） |

### 3.2 PII 脱敏

`redact()` 内置 6 条正则：身份证 / 手机号 / 邮箱 / 银行卡 / `Bearer xxx` / `api_key=`、`token=`、`secret=`、`password=` 等凭证赋值形态（`core/logging_setup.py:26-34`、`:42-51`）。这组正则原与 `security/sensitive.py` 的 PII 正则同源但**刻意不复用同一对象**：日志脱敏要更激进（宁可多遮），答案掩码要考虑可读性，两者分别演化（`core/logging_setup.py:23-25`）。**敏感词功能下线后，答案侧已无掩码，这组正则只作用于日志**——脱敏放在日志层是因为堆栈与异常消息比答案更容易泄漏。

### 3.3 DEBUG 采样

`SamplingFilter` 只对 DEBUG 生效，INFO 及以上**全量**（线上排障靠它们）；用计数轮转而不是 random，行为可复现、测试不 flaky；`rate=0` 时仍至少放行第 1 条（`core/logging_setup.py:104-124`）。采样只在 JSON（生产）形态生效，本地 text 形态保留全量 DEBUG（`core/logging_setup.py:137-142`）。采样率默认见 README 关键数字表（`log_debug_sample_rate`）。

### 3.4 ContextFilter 注入 trace_id

`ContextFilter` 从 `core/tracing.py` 的 contextvar 读当前 trace_id 补到每条记录上（`core/logging_setup.py:85-101`）。没有这一步就得在每个 `logger.info` 手写 trace_id——现实中没人会坚持。取 trace 失败置空串，**日志不得因观测失败而丢**。

### 3.5 装配与噪声压制

`setup_logging()` 幂等（重复调用只更新 handler），默认 text 形态、生产显式 `LOG_FORMAT=json`（`core/logging_setup.py:127-143`）；`urllib3 / httpx / httpcore / asyncio / pymilvus` 五个第三方库压到 WARNING（`core/logging_setup.py:146-147`）。

## 四、追踪

### 4.1 `X-Trace-Id` 贯通

| 环节 | 行为 | 代码位置 |
|---|---|---|
| 入站 | 请求头带 `X-Trace-Id` 则复用（便于网关跨服务串联），否则新生成 | `main.py:770-775` |
| 生成 | `uuid4().hex[:16]`，16 位 hex 短号 | `core/tracing.py:23-24` |
| 承载 | contextvar，下游 `get_trace_id()` 读取；未设置时生成并写入，保证永远非空 | `core/tracing.py:20`、`:39-45` |
| 出站 | 响应头统一回写 `X-Trace-Id`（含 SSE 响应，中间件在 `call_next` 之后写头，流式同样生效） | `main.py:777-783` |
| 信封 | 错误 / 成功信封 `meta.trace_id` 同值（信封结构 → `03-接口与契约.md`） | `core/envelope.py:126-135` |
| 日志 | `ContextFilter` 自动注入（§3.4） | `core/logging_setup.py:85-101` |

### 4.2 OTel（可选，默认关闭）

- **默认关闭**：`otel_enabled` 默认关；未部署 collector 时开启只白占内存（`core/config.py:171-177`）。启用但未配 endpoint → warning 并明确降级 NoOp，杜绝「以为在上报其实没有」（`core/otel.py:43-47`）。
- **endpoint scheme 校验**：必须 `http(s)://` 前缀——`OTLPSpanExporter` 接受任意字符串、只在后台导出时静默失败，那是比明确降级更难排查的最坏情况（`core/otel.py:48-53`）。
- **依赖缺失静默降级**：OTel 包是可选依赖，ImportError → NoOp，绝不让「没有可观测后端」变成「服务起不来」（`core/otel.py:55-64`）。
- **采样**：`ParentBased(TraceIdRatioBased(ratio))`——上游已采样则跟随，独立请求按 `otel_sample_ratio` 控成本（`core/otel.py:72-79`）。
- **`span()` 无条件可用**：未启用时返回 `_NoOpSpan`，调用方不写 `if otel_enabled` 分支——埋点代码保持「无条件可读」（`core/otel.py:107-142`）。span 自动挂 `kquery.trace_id` 属性，实现「用户报的短号」→「Jaeger 链路」的跳转（`core/otel.py:132-141`）。
- **停机 flush**：`shutdown_otel` 在 lifespan 收尾 flush 缓冲的 span（`core/otel.py:145-157`）。

取舍说明：自研 16 位 trace_id 与 W3C 128 位 trace_id **不是同一个东西**，前端已在用短号、统一是破坏性变更，故保留双层并靠 span attribute 关联（`core/otel.py:18-24`）。

### 4.3 trace 断链修复：`spawn_thread` 携带 contextvars

`contextvars` 不随 `threading.Thread` 传播（Python 既定行为），直接开线程会让后台日志的 trace_id 变成新生成的另一个号，一次请求的日志被切成两段。`spawn_thread` 用 `contextvars.copy_context().run(...)` 把上下文快照带进新线程——必须 `copy_context()`（快照）而不是共享同一 context 对象，否则两个线程互相覆盖 trace_id。**所有后台线程都应经此函数创建**（`core/tracing.py:52-76`）。

## 五、探针分级

| 端点 | 语义 | 判据 | 失败表现 | 代码位置 |
|---|---|---|---|---|
| `GET /health` | 静态兼容探针 | 恒返回 `{"status": "up"}` | 进程死了才失败 | `main.py:785-787` |
| `GET /livez` | 存活探针 | **绝不查依赖**（依赖抖动会误杀 Pod），纯文本 `ok` | 同上 | `main.py:789-792` |
| `GET /readyz` | 就绪探针（接流量判据） | `store` 装配完成即 ready；**索引为空 ≠ 未就绪**（空索引单独标 `empty_index: true` 并打 WARNING） | store 为 None → 503 摘流不抛错 | `main.py:794-818` |
| `GET /healthz` | 完整依赖健康报告，不参与流量路由 | 逐依赖探针：vector_store / bm25_index / graph_store / shared_state / long_term_memory / parser_router / provider / auth / upstream，各带耗时与错误摘要（`platform_quota` 探针已随配额下线移除） | 任一 down → 503 `degraded`，`down` 数组列出失败依赖 | `main.py:820-872` |

三个刻意设计：

1. **readyz 不看索引是否为空**——全新部署索引本来就是 0，据此 503 会让 Service 永远没有 endpoints、没人能上传第一份文档（死锁）。真正该摘流的是「依赖不可达 / 集合没加载」（`main.py:796-802`）。
2. **healthz 把认证档位与共享状态后端暴露出来**：`auth` 探针返回 provider 类名（HeaderAuthProvider 是开发档，一眼可见），`shared_state` 探针返回当前后端快照（避免「以为在用 Redis 其实已降级」）（`main.py:845-855`）。
3. **upstream 水位进健康报告**：许可占用与熔断状态从隔离仓现采（`main.py:856-857`），与 §二的水位指标同源。

`GET /metrics` 与四个探针同属内建端点（`main.py:874-880`），定位是运营抓取、鉴权限流豁免（运营数据，不进用户响应）。

## 六、成本账本

### 6.1 `CostLedger` 结构与纪律

### 6.2 `priced` / `estimated` 双标记

- 价格表来自配置 `agent_price_per_1k_json`（每千 token 单价、按模型名，`core/config.py:127-129`）；**显式配置而非内置**——内置价格会过期，过期价格比没有价格更危险（`services/agent/budget.py:17-18`、`:110-113`）。
- 模型不在价格表 → 成本记 0 且 `priced=False`：宁可显示「未知」也不给错误数字做预算依据；聚合时任一条未定价则总额 `priced=False`，明确告知不可信（`services/agent/cost.py:31`、`:90-91`、`:124`）。
- 工具调用等无真实用量回传的环节按固定估算 token 入账；真实 LLM 用量但为估算值时同样降级 `priced=False`（`services/agent/runner.py:349-357`、`:560-566`）。
