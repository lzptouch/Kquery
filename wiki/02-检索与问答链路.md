# 02 检索与问答链路

本篇按数据流向讲三件事：**文档怎么进库 → 问题怎么被检索 → 答案怎么被生成与约束**。

## 1. 入库链路

```
上传 → 解析(parsers) → 分块(chunkers) → 向量化 → 写入 Milvus/FAISS + BM25 倒排 → 任务状态回写
```

### 1.1 解析

`services/parsers/` 按扩展名分派，覆盖文本、PDF、Word、PPT、Excel、Markdown、HTML、图片（OCR）等格式。解析统一产出"文本 + 结构信息（页码/工作表/幻灯片号）"，后者用于把引用定位回原文位置。

新增格式只需在解析器注册表里加一项，并补 `tests/format/` 的通用解析契约用例。

### 1.2 分块

分块策略由 `core/chunk_policies.py` 决定，按文档类型选择：正文类按段落/标题层级切，表格类保留行列结构，代码类按语法块切。块与块之间保留标题路径，检索命中后能还原上下文。

### 1.3 向量化与索引

- 向量后端优先 Milvus；不可用时回退 FAISS 本地索引（单机演示与 CI 走这条）。
- BM25 倒排索引与向量库**同步增删**，启动时从向量库元数据重建，避免两路数据漂移。
- 每个分块带 `doc_id + version`，检索时会按版本过滤，旧版本分块不参与召回。

### 1.4 入库任务

入库是异步任务：接口返回任务标识，进度与失败原因通过任务查询接口读取。解析失败会记录到失败的 stage，便于定位是"文件损坏"还是"格式不支持"。

## 2. 检索链路

```
查询理解 → 多路召回(BM25 / 向量) → RRF 融合 → 重排 → 过滤 → Top-K
```

### 2.1 查询理解

`services/query/` 做三件事：

| 模块 | 作用 |
| --- | --- |
| `intent.py` | 判断问题类型（事实型 / 比较型 / 多跳型 / 寒暄），决定是否走检索与深度 |
| `expanders.py` | 查询改写：补全指代、扩展同义表述，提升短查询召回 |
| `decomposer.py` | 多跳问题分解为子问题，每个子问题独立召回后再合并 |

**改写结果与用户原话一起进检索**：每条查询分别做双路召回，全部结果进同一个融合池。重排时以**用户原话**为基准，避免改写引入的语义漂移影响最终排序。

### 2.2 双路召回与 RRF

- BM25（jieba 分词，`k1=1.5`、`b=0.75`）取前 20，零分文档直接丢弃——否则会污染排名计算。
- 向量召回取前 20。
- 两路分数**不可直接比较**（BM25 无界、余弦有界），因此只传排名进 RRF：

  \[ \text{score}(d) = \sum_i \frac{w_i}{k + \text{rank}_i + 1} \]

  默认 \(k=60\)（论文默认值），路权重由检索配置给出（`bm25_weight` / `vector_weight`）。

RRF 是唯一允许跨路比较的位置。所有召回条数、融合候选数、\(k\) 值都可在运行时配置里改（`/admin/retrieval-config`），改完下一个请求即生效，不需要重启。

### 2.3 重排与降级

融合后的候选交给重排模型精排取 Top-K。两种降级：

- **重排不可用**（超时 / 未配置）：跳过重排直接用融合分，响应里 `reranked=false` 显式标记，调用方据此判断结果质量。
- **候选命中注入风险**：不排除，只降权（乘一个惩罚系数）。排除会变成攻击者的工具——在文档里写一句"忽略以上指令"就能让这段内容从检索里消失，这比让它排低更危险。

### 2.4 过滤

`retrieval/filters.py` 处理标量过滤：文档范围、标签、时间窗、版本。过滤在召回阶段下推，避免"先取 100 条再丢掉 95 条"。

## 3. 生成链路

`services/generation/` 是一条 stage 化流水线，`core.py` 只负责调度与传参：

```
cache → preprocess → retrieve → (CRAG 多轮) → evidence → generate → guard
```

| 阶段 | 职责 |
| --- | --- |
| cache | 语义缓存命中检查，命中直接返回并标记 cache 类型 |
| preprocess | 问题规范化、会话上下文注入 |
| retrieve | 调混合检索，收集 candidates 与耗时 |
| CRAG | 检索结果自评：证据不足则改写查询再召回，最多 N 轮 |
| evidence | 证据装配：去重、按相关度与篇幅裁剪、编引用编号 |
| generate | 提示词组装 + 流式生成（`generate_stage.py`） |
| guard | 护栏：敏感信息、越权内容、格式约束（`guard_stage.py`） |

**引用可追溯**：`evidence.py` 在装配证据时给每个分块分配编号，生成阶段要求模型用编号标注结论来源；`validation/` 再校验编号是否真实存在、内容是否支持结论。无依据的断言会被降级或标注为"推测"。

**客户端断开即中止**：每个阶段开始前检查取消信号，已断开的连接不再继续调用 LLM 和检索，指标里记为 `cancel_stage`。

## 4. Agentic 与图谱

### 4.1 Agent 状态机

`services/agent/` 基于 LangGraph，状态包含 Plan / Tool / Reflect / Replan / Answer：

- **Plan**：把问题拆成可执行步骤。
- **Tool**：调用工具（检索、计算等），工具入参结构化，`top_k` 这类参数会真正透传到检索。
- **Reflect**：评估当前证据是否足够，不足则 Replan。
- **Answer**：汇总证据生成最终答案。

会话状态用 SQLite checkpoint 持久化，刷新页面后可恢复执行轨迹。

### 4.2 图谱

`services/graph/` 从分块中抽取实体与关系，提供实体检索与关系扩展，用于"跨文档找关联"的问题；图谱检索结果与向量检索结果走同一套融合与重排。

## 5. SSE 事件协议

流式问答使用 Server-Sent Events。事件顺序与语义：

| 事件 | 内容 |
| --- | --- |
| `evidence` | 检索证据（分块编号、来源文件、片段），可能在生成前多次下发 |
| `answer` | 增量答案片段（token 流） |
| `done` | 结束：耗时、阶段耗时、缓存命中、重排是否生效等元信息 |
| `error` | 错误码 + 可读消息 |

完整字段以 `GET /openapi.json` 与实际响应为准；客户端实现应**忽略未知事件**，以便服务端后续扩展。

## 6. 调效果时先看哪里

| 现象 | 先查 |
| --- | --- |
| 召回不到文档 | 分块策略是否把关键信息切碎；BM25 分词；向量是否入库成功 |
| 召回但排序差 | RRF 权重、召回条数、重排是否生效（`reranked` 字段） |
| 答非所问 | 查询改写是否漂移；CRAG 轮数；提示词证据篇幅 |
| 有答案但没引用 | 证据装配编号；`validation` 的引用校验结果 |
| 偶发超时 | deadline 配置、provider 主备切换、重排超时 |

改完任何检索参数，用 [05 测试与评测](./05-测试与评测.md) 的评测集跑一遍基线对比，不要凭单条 case 判断。
