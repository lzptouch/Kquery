## 〇、摘要

1. **依赖方向是单向的三层**：`api/` → `services/` → `core/` 与 `domain/`；`services/` 内部按领域切成 9 个子包 + 16 个根级服务文件，`core/` 是横切设施，`domain/` 只放 Pydantic 模型、不含行为。
2. **启动装配集中在 `lifespan` 的一段连续代码**（`backend/app/main.py:184-692`），按「外部依赖 → 核心服务 → 状态注册 → 护栏 → Agent → 共享状态」六阶段推进；只有向量索引损坏、Milvus 不可用、配置校验未过、认证无人可通过、JWT 密钥过短、引导口令不合规这6 类是 **fail-fast**，其余一律降级不阻断。
3. **中间件实际顺序不是注册顺序**：Starlette 的 `add_middleware` 用 `insert(0)`，后注册的在外层，因此实际链路是 `ServerErrorMiddleware → trace_middleware → CORSMiddleware → ExceptionMiddleware → Router`（`backend/app/main.py:709-715` 先加 CORS，`backend/app/main.py:770-783` 后加 trace）。
4. **没有全局 body 大小限制**：上传体积约束是**按端点各自实现**的（`backend/app/api/upload_util.py:40-57`、`backend/app/api/speech.py:194-210`、`backend/app/services/quickask.py:162-165`），新增端点若忘记实现即等于无限制。
5. **关闭序列不完整**：`backend/app/main.py:682-705` 关了执行器、线程池、任务队列、checkpointer、OTel、向量库与图存储，但**未关闭 Redis 连接与 `AnalysisStore`**，存在待写缓冲丢失的窗口（审计下线后已无此问题）。
6. **存在一处真实的装配不一致**：`SharedState` 在 `backend/app/main.py:244-245` 与 `backend/app/main.py:635-636` 被实例化两次，第二次覆盖 `app.state.shared_state`，而第一份仍被 cache / limiter 持有——探针报告的后端与实际使用者可能不是同一份状态。

## 一、分层与依赖

### 1.1 依赖方向

```
api/  ──►  services/  ──►  core/
 │            │              │
```

| 层 | 目录 | 允许依赖 | 禁止依赖 | 说明 |
|---|---|---|---|---|
| 路由层 | `backend/app/api/` | `services/`、`core/`、`domain/`、`dependencies.py` | 不得直接 new业务对象；不得绕过 `dependencies.py` 取 `app.state` | 13 个 router + 共享工具 `upload_util.py`；认证与限流统一从 `dependencies.py` 出口取（`backend/app/dependencies.py:1-7`） |

## 三、请求生命周期

### 3.1 中间件实际顺序

| 序 | 组件 | 说明 | 位置 |
|---|---|---|---|
| 1 | `ServerErrorMiddleware` | Starlette 内置最外层，负责未捕获异常兜底 | 框架内置 |
| 2 | `trace_middleware` | 生成 / 复用 `trace_id`，写入 `request.state`，回写 `X-Trace-Id` 响应头 | `backend/app/main.py:770-783` |
| 3 | `CORSMiddleware` | 允许来源、方法、请求头全部放开（来源按 `cors_origins` 配置） | `backend/app/main.py:709-715` |
| 4 | `ExceptionMiddleware` | Starlette 内置，负责路由抛出的 `HTTPException` | 框架内置 |
| 5 | Router | 具体端点 | `backend/app/main.py:883-895` |

> **为什么 trace 在 CORS 之外**：Starlette 的 `add_middleware` 内部是 `user_middleware.insert(0, ...)`，**后注册的在更外层**。本项目先注册 CORS（`:699`）、后用 `@app.middleware("http")` 注册 trace（`:760`），所以 trace 实际更靠外——这正是「trace_id 必须覆盖 CORS 预检与错误响应」的意图。**这是一个依赖框架语义的隐式约定**：若有人把 CORS 注册挪到 trace 之后，链路顺序会静默反转。

### 3.2 鉴权 → 限流 → 端点 → 异常映射 → 信封

| 序 | 环节 | 机制 | 失败表现 | 位置 |
|---|---|---|---|---|
| 1 | 认证 | `Depends(get_principal)`；Bearer 令牌或请求头；令牌再与用户目录复核（启用状态 / 角色即时生效） | 401（1101），文案不区分「账号不存在」与「口令错」 | `backend/app/dependencies.py:114-153` |

### 3.3 body 大小限制：无全局约束，按端点实现

| 端点 | 约束实现 | 超限表现 | 位置 |
|---|---|---|---|
| 知识库 / 入库上传 | 流式分块落盘，边写边计数，超限即删除半成品 | 413 `FILE_TOO_LARGE` | `backend/app/api/upload_util.py:40-57` |
| 语音转写 | 先按 multipart 解析出的长度预拒，再读全量后二次校验 | 400 `FILE_TOO_LARGE` | `backend/app/api/speech.py:194-210` |

> **缺口**：FastAPI / Starlette 层**没有**全局 `Content-Length` 或请求体上限中间件。任何**新增**的上传类端点若不显式调用 `stream_to_disk` 或自行校验，就等于**没有任何体积保护**——这是结构性风险，不是当前某个端点的 bug。
