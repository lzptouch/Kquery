## 一、阻塞项（不处理不要上线）

### 1.1 认证处于关闭状态，任何身份都可由请求头伪造 🔴

**现状**：`backend/.env:34` 显式设了 `AUTH_ENABLED=false`。

```
backend/.env:34:  AUTH_ENABLED=false
backend/.env:35:  AUTH_TOKENS_JSON=（空）
```

当 `auth_enabled=false` 时，`build_auth_provider()` 返回 `HeaderAuthProvider`
（`app/services/security/auth.py:291`），其 `authenticate()` 直接采信请求头
（`app/services/security/auth.py:58-64`）：

```python
user_id=headers.get("x-user-id", "anon"),
tenant_id=headers.get("x-tenant-id", "default"),
roles=[r.strip() for r in headers.get("x-roles", "").split(",") if r.strip()],
```

**它自己的 docstring 已写明**（`auth.py:53-55`）：
> 仅供开发与演示——不验证任何凭证，生产必须换标准令牌提供者。

**影响**：任何人加一行 `X-Roles: admin` 即可通过全部 30 个 `/admin/*` 端点与
所有 `require_role("admin")` 门禁。TASK-160 做的端点鉴权本身是有效的，但在这种
模式下等于**没有任何门槛**。同时租户隔离也失效——`X-Tenant-Id` 可随意指定。

> ⚠️ **一个容易误判的细节**（实测）：**不带任何请求头**访问管理端点会返回 **403**，
> 看起来"鉴权是生效的"。但那只是因为 `HeaderAuthProvider` 在缺少 `X-Roles` 时
> 把角色解析为空列表，属于**巧合**而非防护——攻击者只需自己声明 `X-Roles: admin`。
> 因此**不要**用"匿名访问被拒绝"来验证认证是否真的开了；必须用下面的
> 「自报 admin」用例。

**注意**：`app/core/config.py:189` 的**代码默认值是 `True`**，且启动期校验
（`config.py:305-308`）在 `auth_enabled=true` 且无凭证时**拒绝启动**。
也就是说代码侧是"安全的默认"，是 `.env` 把它覆盖成了关闭——
**这是配置问题，不是代码缺陷**。

**处理方式**（三选一）：

| 方案 | 配置 | 适用 |
| --- | --- | --- |
| JWT（推荐） | `AUTH_ENABLED=true` + `AUTH_JWT_ENABLED=true` + `AUTH_JWT_SECRET`（校验要求 ≥16 字符，启动期硬校验；建议直接用 32 字节随机串，`config.py:309-310`） | 生产，接统一认证中心 |
| 静态凭证表 | `AUTH_ENABLED=true` + `AUTH_TOKENS_JSON={...}` | 内部演示，短期可用 |
| 维持关闭 | 保持现状 | **仅限本机开发**，必须确保不可从外部网络访问 |

⚠️ **静态凭证表方案也有前提**：`AUTH_TOKENS_JSON` 里的 token 是**长期有效**的
明文凭证（`StaticTokenAuthProvider` 只查表、不校验有效期，`auth.py:74-88`），
且该配置项会进入进程环境。仅适合短期内部演示，且必须配合密钥管理注入，
不要写进 `.env` 提交或镜像层。

**验证方式**（下面是在当前关闭状态下的**实测输出**）：

```bash
# ① 匿名访问 → 403（注意：这是"角色为空"造成的，不代表认证生效）
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8100/admin/costs
#   实测：403

# ② 自报管理员 → 200（← 这才是真正的绕过，认证开启后应变为 401）
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8100/admin/costs \
  -H "X-User-Id: attacker" -H "X-Roles: admin"
#   实测：200

# ③ 自报任意租户 → 200（租户隔离同样失效，可读到他人审计）
curl -s -o /dev/null -w "%{http_code}\n" \
  "http://localhost:8100/admin/audit?range_s=60" \
  -H "X-Tenant-Id: some-other-tenant" -H "X-Roles: admin"
#   实测：200
```

认证正确开启后，① 应为 **401**（无凭证），② 应为 **401**（凭证无效），
③ 应为 **403**（凭证有效但无权限，且租户锁定为凭证内声明的值）。

### 1.2 `.env.example` 同样带 `AUTH_ENABLED=false` 🔴

新环境按 `cp backend/.env.example backend/.env` 的标准做法部署时，
**会直接继承"认证关闭"**，而注释只写了「仅本地演示」，容易被忽略：

```
backend/.env.example:
# 认证（静态凭证表，仅本地演示；生产应接统一认证中心，本系统只校验不签发）
AUTH_ENABLED=false
```

**建议**：把示例文件里的默认值改为 `true`（与代码默认一致），
或在文件顶部加显著警示。让"忘记改"的结果是**启动失败**（可发现），
而不是**静默裸奔**（不可发现）——这正是 `config.py` 启动校验的设计意图。

**注**：`docker compose` 通过 `env_file: ./backend/.env`（`docker-compose.yml:64-65`）
注入，因此**容器部署同样受影响**，不只是本机直跑。

### 2.2 运行期产物已提交进 git，需要清理 🟡

实测确认这两个目录**已被 git 跟踪**，且**都不在 `.gitignore` 里**：

| 路径 | 大小 | 内容 | 问题 |
| --- | --- | --- | --- |
| `deploy/milvus/volumes/` | **146 MB** | etcd 的 `member/wal/*.wal`、`member/snap/db`，以及 Milvus 数据 | 这是**数据库的活跃文件**（预写日志 + 快照），不是普通附件。提交它们意味着每次起停容器都产生 diff，且 WAL 与本地实际状态不一致时极易误导 |
| `.playwright-cli/*.yml` | 344 KB / 24 个文件 | Playwright 页面的时间戳快照（`page-2026-10-03T01-08-12-485Z.yml` 等） | 一次性调试产物，无复用价值 |

**影响**：仓库噪声持续增长（每次本地起一次 compose 就可能多出改动），
`git status` 失去参考价值；更重要的是把数据库内部文件当成源码管理，
一旦有人误用历史版本覆盖，会造成数据损坏。

> 顺带确认过：这个问题**只影响仓库卫生，不影响构建**。
> `docker-compose.yml` 的构建上下文是 `./backend` 与 `./frontend`（`:60,86,126`），
> 不包含仓库根目录，因此那 146 MB 不会被 `docker build` 打进镜像上下文。
> （根目录也没有 `.dockerignore`；上面这条结论是针对现状的核实结果，
> 若将来把构建上下文改成 `.`，就需要补 `.dockerignore`。）

**处理建议**（属**破坏性操作**，需确认后再做）：

```bash
# 1) 先加入 .gitignore，避免清理后又被加回来
echo "deploy/milvus/volumes/" >> .gitignore
echo ".playwright-cli/"       >> .gitignore

# 2) 从索引移除但保留本地文件（--cached 不会删磁盘数据，相对安全）
git rm -r --cached deploy/milvus/volumes .playwright-cli
git commit -m "chore: 停止跟踪运行期产物（Milvus 数据卷与 Playwright 快照）"
```

⚠️ 第 2 步只影响 git 索引，**不会删除磁盘上的 Milvus 数据**。
若确认不再需要这些本地数据（例如打算重建索引），也可直接删目录——
**这一步需要你明确确认**，故本清单不代为执行。

## 五、复现"当前全绿"状态的命令

改造后已验证：**673 单测 + 69 接口 + 43 + 35 浏览器点击全部通过**，覆盖率 85%。

```bash
# 单元与集成（Mock 模型，不需要任何外部服务）
cd backend && uv run pytest -p no:cacheprovider --cov=app --cov-report=term

# 以下三项需要后端 + 前端都在跑：
#   后端：cd backend && uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
#   前端：cd frontend && KQUERY_API_TARGET=http://127.0.0.1:8000 npm run dev
cd ../ && python3 scripts/smoke_api.py --base http://127.0.0.1:8000 --report-timeout 600
python3 scripts/e2e_browser.py --base http://127.0.0.1:5173 --sample <任一 md 文件>
python3 scripts/e2e_new_features.py --base http://127.0.0.1:5173
```

**三个会浪费半天的环境坑**（都已踩过，详见下方）：

1. **前端必须显式指定 `KQUERY_API_TARGET=http://127.0.0.1:8000`**。
   本机若已有其它服务监听 `0.0.0.0:8000` / `[::]:8000`，而 vite 默认 target 是
   `localhost:8000`——Windows 下 `localhost` 优先解析到 `::1`，
   于是**代理会把请求转发到别人的服务**。症状极具迷惑性：页面能开、部分接口有响应，
   但数据是错的。
2. **vite 代理列表必须与 `frontend/nginx.conf` 的 location 一致**。
   曾漏 `/readyz` `/livez` `/healthz`：开发环境下这些请求会回落到 SPA 的
   `index.html`，返回 **200 + HTML**，"看起来通了"但永远拿不到探针数据。
3. **前端所有出站请求都要注入身份**（TASK-160 后 `/admin/*` 需要 admin 角色）。
   统一入口是 `frontend/src/lib/auth.ts` 的 `authHeaders()` / `withAuth()`；
   `request()`、XHR 上传、`askStream` 以及任何**裸 `fetch()`** 都要接上——
   漏一处就表现为"某个页面单独 403"。
   身份存 localStorage（`kquery.user_id` / `tenant_id` / `roles` / `token`），
   其中**空串表示"显式无角色"**（不可用 `||` 兜底成 admin，否则非管理员的
   越权路径无法测试）。

## 六、本清单未覆盖的范围

- **容量与压测**：未做。向量库规模、并发上限、队列背压阈值（`report_queue_size=100`）
  都是按经验设的默认值，未经实测标定。
- **安全渗透**：只做了越权与身份伪造方向的检查，未做注入、SSRF、依赖漏洞扫描。
  注意 `http_request` 与 `python_sandbox` 两个高危工具**刻意未实现**，
  若要新增需单独评估。
- **数据备份与恢复**：审计日志、会话、图谱存储的备份策略未定义。
- **上游依赖的 SLA**：千问平台（DashScope）的限流与配额（`platform_quota_per_day=0`
  当前为"只统计不拦截"）未与业务容量对齐。
