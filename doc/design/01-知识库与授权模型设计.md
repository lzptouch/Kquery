## 〇、问题陈述

KB 能力（2026-10-27 落地）本身**没有引入安全缺陷**，但引入了 4 条限制。它们的共同根因是：

> **KB 授权被设计成文档 ACL 的「简化版」，而文档 ACL 已有的表达式语法（`role:` / `group:`）没有同步过来。**

于是两个权限体系**不对称**：管理员能对文档写「`role:admin` 可见」，却只能对知识库逐个用户勾选。这不是功能缺失，而是**模型不一致**。

## 一、现状（带行号）

### 1.1 KB 授权判定树

```
① KB 不存在 → 拒绝                    backend/app/services/security/kb.py:111-112
② 租户不匹配 → 拒绝（默认库除外）      kb.py:116-117
③ 命中授权名单（user_id 精确匹配）→ 放行  kb.py:119-121
④ 库公开（is_public）→ 放行            kb.py:123-124
⑤ 默认拒绝                            kb.py:126
```

### 1.2 文档 ACL 判定树（对照）

```
backend/app/services/security/acl.py:81-100 —— 五步，同样 deny 优先，
但支持 `user:` / `role:` / `group:` 三类主体表达式
```

**差异点**：`kb.py:119-121` 的第 ③ 步只做 `user_id` 精确匹配，**没有表达式求值**。

### 1.3 授权存储

| 文件 | 内容 | 位置 |
|---|---|---|
| `data/knowledge_bases.json` | KB 实体数组（`KnowledgeBase`，`backend/app/domain/schemas.py:42-55`） | `backend/app/services/security/kb.py:57-88` |
| `data/kb_grants.json` | `kb_id → [授权条目]`；条目只有 `user_id` | `kb.py:48`（`self._grants`）、`:239-275`（`set_grants`） |
| `data/users.json` | 用户目录（含 `roles` / `groups`） | `backend/app/services/security/auth.py` |

### 1.4 KB 判定的落点

KB 判定被**合并进 `acl_filter_of` 的同一个闭包**（安全关键，不可拆）：

```
backend/app/dependencies.py:92-111
  ├─ 93-94   `__` 前缀豁免（系统内置块）
  ├─ 95-96   `quick_` 前缀豁免（快问临时文档）
  ├─ 97-98   请求级记忆化（同一文档只查一次）
  ├─ 99-103  无主文档 → 拒绝
  ├─ 104     文档 ACL 五步判定（先）
  ├─ 106-107 KB 判定（后；`acl_enabled=false` 时整段跳过）
  └─ 108-111 记忆化落盘并返回
```

## 二、K1 · 授权粒度从「用户」升到「表达式」

### 2.1 目标态

`PUT /admin/kb/{kb_id}/grants` 接受**与文档 ACL 同构**的主体表达式：

```json
{
  "grants": [
    {"subject": "user:bob",      "effect": "allow"},
    {"subject": "role:admin",    "effect": "allow"},
    {"subject": "group:finance", "effect": "allow"}
  ]
}
```

### 2.2 数据模型变更

`backend/app/domain/schemas.py:58-64` 的 `KbGrant` 从「只存 `user_id`」扩为「主体 + 效果」：

```python
class KbGrant(BaseModel):
    kb_id: str
    subject: str                 # "user:bob" | "role:admin" | "group:finance"
    effect: str = "allow"        # allow | deny（预留 deny）
    granted_by: str = ""
    granted_at: str = ""
```

**迁移**：`kb_grants.json` 的旧格式（`{kb_id: [{user_id, granted_by, granted_at}]}`）在加载时自动升级为 `subject="user:<user_id>"`。迁移必须**幂等**且**失败即拒绝启动**（与全局「损坏即拒绝启动」纪律一致，见 `doc/analysis/09-数据模型与存储.md`）。

### 2.3 求值器复用

**不要**在 `kb.py` 里另写一套表达式解析——直接复用文档 ACL 的求值逻辑。落点：

```
backend/app/services/security/acl.py  —— 抽出 subject → 是否满足 的纯函数
backend/app/services/security/kb.py:107-135  —— 判定树第 ③ 步改为调用该纯函数
```

### 2.4 验收

- `PUT /admin/kb/{id}/grants` 传 `role:admin` 后，**目录中 `roles` 含 `admin` 的所有用户**都能看见该库文档；
- 传 `group:finance` 后同理；
- 表达式非法（`"bob"` 无前缀 / `""`）→ 400 + 明确文案；
- 旧格式 `kb_grants.json` 启动后自动升级，文件内容改变且可重复启动（幂等）。

## 三、K2 · 空结果探测从 tenant 级改为 KB 级

### 3.1 现状问题

`backend/app/services/pipeline.py:406-423` 的 `_probe_denied_content` 用**不带允许清单**的 `RetrievalFilters` 探测：

```python
probe = RetrievalFilters(tenant_id=tenant_id)  # 不带允许清单 = 不过滤
```

后果：探测会命中**其它知识库**的内容。于是「无内容」与「无权限」两种拒答原因**无法区分**——一个只对库 A 有权限的用户问库 B 的内容，系统可能判成「无内容」而不是「无权限」。

泄露面有限（只返回布尔、不外带内容），但**区分力**丢失。

### 3.2 目标态

探测应带**该 KB 的允许清单**。但当前 pipeline 在**检索时才知道要查哪个 KB**（`doc_id` 可能为空 = 全库），所以要分两种情况：

| 场景 | 探测策略 |
|---|---|
| `doc_id` 明确（单文档 / 快问） | 用该文档所属 KB 的允许清单探测 |
| `doc_id` 为空（全库检索） | 用**租户内所有可见 KB** 的并集清单探测 |

### 3.3 实现要点

- 允许清单的来源已经是现成的：`acl_filter_of` 闭包内的 `check(doc_id)`（`backend/app/dependencies.py:92-111`）返回布尔；而 `backend/app/services/retrieval/filters.py` 的 `visible_doc_ids` 能给出清单。
- 实现上需要给 `_probe_denied_content` **传入一个可见性判定函数**（而不是只传 `filters`），由它决定「有没有可见但未召回的内容」。
- **保持只回传布尔**——不要为了「更精确」而把命中内容带回响应，那会把探测变成泄露通道（当前 docstring 的判断是对的，应保留）。

### 3.4 验收

- 构造用例：用户对库 A 有权限、对库 B 无权限；查询命中库 B 的内容 → 拒答原因应为 **`permission_denied`**（不是 `no_content`）；
- 构造用例：用户对所有库都有权限，查询库 A 中不存在的内容 → 拒答原因应为 **`no_content`**；
- 两种 reason 在 SSE `refused` 事件中可区分。

## 四、K3 · `kb_enabled` 与 `acl_enabled` 解耦

### 4.1 现状

`backend/app/dependencies.py:82-83`：

```python
if not acl_enabled:
    return None      # ← KB 判定整段被跳过
```

于是 `acl_enabled=false` ⇒ `kb_enabled` 无论开关都**无效**。

### 4.2 目标态

把两个开关的语义分开：

| 场景 | `acl_enabled` | `kb_enabled` | 期望行为 |
|---|---|---|---|
| 默认（全开） | true | true | 文档 ACL ∩ KB 授权 |
| 只开 KB | false | true | **仅 KB 授权**（KB 不可见 ⇒ 不可见） |
| 只开 ACL | true | false | 仅文档 ACL |
| 全关 | false | false | 无过滤（仅租户隔离） |

### 4.3 实现要点

`acl_filter_of` 的短路顺序需要重排：**先判 KB（若开启）→ 再判文档 ACL（若开启）→ 都通过才可见**。当前顺序是「文档 ACL → KB」，解耦后需要保证：

- `acl_enabled=false` 时，KB 判定**仍在闭包内执行**；
- `__` / `quick_` 前缀豁免**对两者都生效**（否则关掉 ACL 后系统块会被 KB 拦住）。

### 4.4 风险

这是**安全关键**改动——顺序错了会越权。必须配套：

- `backend/tests/unit/test_kb_filters.py` 扩展出 4 种开关组合的矩阵用例；
- `backend/tests/integration/test_kb_grants.py` 补跨开关组合的越权用例；
- 落地时**先写测试再改实现**（现有 `doc/plan/知识库实体与授权-分析与实施计划.md` §12.3 的六条不变式必须全部重读）。

### 4.5 验收

- 四种开关组合各有测试覆盖；
- `acl_enabled=false` + `kb_enabled=true` 时，未授权 KB 的文档**检索不到**（用 `acl_filtered` 计数或直接断言证据为空）。

## 五、K4 · 批量移库时显式处理授权

### 5.1 现状

`backend/app/api/kb.py:214-242` 的 `PUT /admin/kb/{kb_id}/documents` 与 `backend/app/services/knowledge.py:155-164` 的 `move_to_kb` **只改归属字段**：

```python
record.knowledge_base_id = knowledge_base_id or "default"
self._save_metadata()
```

文档 ACL 挂 `doc_id`，天然跟随；但 **KB 级授权名单不跟随**——原库的授权人对新库可能没有权限，文档的可见性会静默改变。

### 5.2 目标态

移库接口**显式返回授权影响**，并提供可选的「同步迁移授权」：

```json
{
  "moved": ["doc1", "doc2"],
  "skipped": [{"doc_id": "doc3", "reason": "已是目标库"}],
  "authorization_impact": {
    "granted_before": ["alice", "bob"],     // 原库授权人
    "granted_after":  [],                    // 新库授权人（交集）
    "lost_access":   ["alice", "bob"]        // 移库后失去可见性的人
  }
}
```

可选参数 `"migrate_grants": true` → 把原库的授权名单**并入**新库（union），避免「移库即失权」。

### 5.3 验收

- 移库后响应含 `authorization_impact`，`lost_access` 非空时前端弹出确认；
- `"migrate_grants": true` 时新库授权名单含原库名单；
- 移库**不触发**向量重建（索引不动），`index_version` 不变（除授权写操作外）。

## 六、K5 · 保留错误码裁决（与 `03-错误体系与可观测性设计.md` §四 联动）

KB 能力新增的 4 个 39xx 码（`KB_NOT_FOUND` / `KB_DUPLICATED` / `KB_NOT_EMPTY` / `KB_GRANT_INVALID`）**全部已接线**；但更早的 13 个保留码仍是枚举死位。裁决规则见 `03` §四。KB 侧需要参与的一条：

- `KB_NOT_FOUND`（3901）在 `kb.py` 内部被转成 1201「无权限或不存在」防探测——**这个码对外不可见**，是否保留？建议：**保留但明确标注为内部码**（不占用对外映射表），或在 `api/kb.py` 的存在性校验失败处直接抛 1201 并从枚举移除 3901。
