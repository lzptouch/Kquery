## 〇、摘要

1. **认证分四档，由 `build_auth_provider` 单一入口装配**：JWT（含账号密码自签发）> 静态凭证表 > 头部透传；`auth_enabled=true` 但无任何凭证来源时**拒绝启动**（`app/services/security/auth.py:338-367`、`app/core/config.py:413-417`）。
2. **JWT 刻意自实现且不引第三方库**：显式拒绝 `alg != HS256`（防 alg=none 与算法混淆），校验 exp/nbf/iss/aud/sub 五项声明，密钥 <16 字符直接报错（`app/services/security/auth.py:91-195`，alg 拒绝在 `:160-165`）。
3. **ACL 是五步短路判定树，顺序不可调换**：租户闸门 → deny 优先 → allow → 租户内公开 → 默认拒绝；ACL 全局版本进缓存键，权限撤销后旧缓存自然失效（`app/services/security/acl.py:81-100`、`:139-142`）。
4. **敏感词与 PII 检测已下线**：内置 PII 正则与租户词表能力整体移除，入库不再做 PII 硬拦、输出不再掩码（见「六」下线说明）。合规兜底仍由结构化日志的 PII 脱敏承担（`app/core/logging_setup.py:23`）。
5. **审计日志已下线**：不再落任何审计事件，管理动作也不再留痕（见「七」下线说明）。请求级 trace_id 与结构化日志仍可支撑排障。
6. **最大部署风险是 HeaderAuthProvider**：它不验证任何凭证，`X-Roles: admin` 自报即越权，仅应在 `auth_enabled=false` 的开发/测试档出现（`app/services/security/auth.py:52-64`，见「十一」缺口 1）。

## 一、安全模型总览

Kquery 的安全边界按**五层防线**组织，每层有独立代码位置，任一层的放行都以"上一层已通过"为前提（原七层中的输出侧扫描与审计两层已随敏感词/审计功能下线，见「六」「七」「八」）：

| # | 防线 | 机制 | 代码位置 |
|---|---|---|---|
| 1 | 身份 | `get_principal` 统一认证出口：Bearer 令牌或头部透传 → `Principal`；令牌档下再与用户目录对账（停用/降权即时生效） | `app/dependencies.py:114-168` |
| 2 | 租户 | `tenant_id` 是一切过滤的第一道闸门；限流按**认证结果**的租户分桶而非请求头 | `app/services/security/acl.py:85-86`、`app/dependencies.py:171-206` |
| 3 | 文档 ACL | 五步判定树（见「五」）；`acl_filter_of` 收口为共享过滤函数，无主文档一律拒绝 | `app/services/security/acl.py:81-100`、`app/dependencies.py:71-111` |
| 4 | 知识库授权 | KB 粒度判定（见「五 · 5.4」）：管理员按用户授予知识库可用权；判定合并进 `acl_filter_of` 同一闭包，与文档 ACL **叠加取交集** | `app/services/security/kb.py:107-135`、`app/dependencies.py:71-111` |
| 5 | 检索下推 | 可见文档 ID 集合下推向量库/关键词检索，不可见文档不参与 top-k 竞争；超过 5000 文档退回后过滤 | `app/services/security/acl.py:107-119`，检索侧细节 → `05-检索链路.md` |

两点贯穿性设计：

- **身份以认证主体为准，不以请求头为准**。ACL、KB 授权、限流全部消费 `request.state.principal`（`app/dependencies.py:163-165`）。
- **默认拒绝是全域基调**：ACL 默认拒绝（`acl.py:99-100`）、知识库默认拒绝（`kb.py:126`）、无主文档拒绝（`dependencies.py:99-103`）、无凭证来源拒绝启动（`config.py:407-411`）、认证失败统一 401（`dependencies.py:125-126`）。

## 二、认证四档

### 2.1 四档总览

| 档位 | Provider | 启用条件 | 凭证验证强度 | 定位 |
|---|---|---|---|---|
| 标准令牌 | `JwtAuthProvider` | `auth_enabled=true` + `auth_jwt_enabled=true` | HS256 验签 + 五声明校验 | 企业生产（外部 IdP 签发，本系统只验签） |
| 账号密码 | `JwtAuthProvider`（复用，登录端点自签发） | `auth_enabled=true` + `auth_password_enabled=true` | 同上（签发与验签同一把密钥） | 无 IdP 的正式部署 |
| 静态凭证表 | `StaticTokenAuthProvider` | `auth_enabled=true` + 仅配 `auth_tokens_json` | 查表比对 token | 开发/内部演示，严禁生产 |
| 头部透传 | `HeaderAuthProvider` | `auth_enabled=false` | **不验证任何凭证** | 开发/测试兼容档 |

装配优先级与"账号密码与外部 IdP 共用同一 Provider"的取舍说明见 `app/services/security/auth.py:338-367`：两者产出的都是 HS256 令牌，验签路径完全相同；拆成两个 Provider 只会多出"有 token 验签、无 token 怎么办"的分支歧义，且不回落身份头（回落等于给未认证请求开后门）。

### 2.2 `JwtAuthProvider`（`app/services/security/auth.py:91-195`）

- **刻意不引第三方 JWT 库**（`:92-97`）：验签只需 HMAC-SHA256 + base64url，自实现可以把"接受哪些算法、校验哪些声明"写在代码里而不是藏进依赖。
- **显式拒绝 `alg != HS256`**（`:160-165`）：alg=none 与 RS256/HMAC 算法混淆都必须拒绝，否则签名校验形同虚设。
- **声明校验五项**（`:170-182`）：`exp`（含 leeway）、`nbf`、`iss`（配置了才校验）、`aud`（同前）、`sub`（缺失即 401）。
- **密钥下限**：构造时 `len(secret) < 16` 直接抛错（`:99-103`）；启动校验再拦一次并建议 ≥32 字节随机串（`app/core/config.py:418-420`）。
- **签名比较用 `hmac.compare_digest`**（`:119-121`），防时序侧信道。
- `encode` 与 `decode` 严格成对（`:123-146`）：签发的每条声明都是 decode 会回头校验的，少一条就会出现"签发成功、下一请求立刻 401"。

### 2.3 `HeaderAuthProvider`（`app/services/security/auth.py:52-64`）

头部透传档：`X-User-Id` / `X-Tenant-Id` / `X-Roles` / `X-Groups` 四个头直接拼成 `Principal`，缺省 `anon` / `default`。**它不验证任何凭证**——客户端自报 `X-Roles: admin` 即获得管理员身份，全部 `/admin/*` 端点洞开。它只在 `auth_enabled=false` 时生效（`auth.py:367`），该开关是"显式承认开发/测试模式"的语义；测试基座也固定使用此档。**部署风险登记为缺口 1（见「十一」）**。

### 2.4 `StaticTokenAuthProvider`（`app/services/security/auth.py:67-88`）

`auth_tokens_json` 配置的 token → 身份映射表：缺 token、token 不在表内、账号 `enabled=false` 三种情况分别 401。文件头注释与 `build_auth_provider` 的告警（`:365`）都标注"仅限开发/演示，生产请启用 `auth_jwt_enabled`"。

### 2.5 账号密码登录（第四档）

复用 `JwtAuthProvider`：登录成功由 `encode()` 自签发 HS256 令牌，与外部 IdP 档**同一种令牌**，前端处理一致、后端无第二条验签分支（`app/api/auth.py:10-14`、`:114-130`）。要点：

- **静态 token 表被忽略**：`auth_password_enabled=true` 时若同时配了 `auth_tokens_json`，启动日志明确告警"静态凭证表被忽略"（`app/services/security/auth.py:356-358`）。
- **半开半关组合显式拦截**：`auth_password_enabled=true` 但 `auth_enabled=false` 时 provider 是没有 `encode` 的 HeaderAuthProvider，登录端点直接 403"账号密码登录未启用"，而不是签出一个验不过的令牌（`app/api/auth.py:62-82`、`:116-121`）。
- 登录端点不挂任何角色门禁（先有 admin 才能登录 = 死锁），`/auth/login`、`/auth/register` 公开，`/auth/me` 只需已认证（`app/api/auth.py:1-8`）。
- 登录限流用**独立的** TokenBucketLimiter（键 `login:{username}`），不与租户问答配额共用计数器（`app/api/auth.py:39-42`、`:85-96`）。
- 自助注册角色写死 `sales`（最小能力集），请求体里的 `roles` 一律丢弃——否则任何人都能注册成 admin（`app/api/auth.py:44-46`、`:218-228`）。
- 令牌有效期由 `auth_session_ttl_s` 控制，下限 60 秒（`app/api/auth.py:110-111`）。

### 2.6 启用组合与启动校验

| `auth_enabled` | `auth_jwt_enabled` | `auth_password_enabled` | `auth_tokens_json` | 实际行为 |
|---|---|---|---|---|
| false | 任意 | 任意 | 任意 | HeaderAuthProvider（开发档，不验凭证） |
| true | true | 任意 | 任意 | JwtAuthProvider（标准令牌） |
| true | false | true | 任意 | JwtAuthProvider（账号密码自签发；静态表忽略并告警） |
| true | false | false | 非空 | StaticTokenAuthProvider（告警：仅限开发/演示） |
| true | false | false | 空 | **拒绝启动**（`app/core/config.py:413-417`） |
| true | true 或 password | — | — 且 secret <16 字符 | **拒绝启动**（`app/core/config.py:418-420`） |
| password=true | — | — | — 且 `auth_session_ttl_s` ≤0 | **拒绝启动**（`app/core/config.py:421-422`） |

启动校验的取向写在 `validate_startup` docstring：缺项宁可在 boot 时崩，也不要运行期才暴露（`app/core/config.py:378-383`）。

### 2.7 令牌档下的目录对账（停用/降权即时生效）

`get_principal` 认证通过后，只要请求带 Bearer 头，就回查用户目录：账号已从目录消失 → 401；`enabled=false` → 401；`roles`/`groups` **以目录为准覆盖令牌里的签发值**（`app/dependencies.py:134-153`）。取舍说明写在 docstring：令牌里烧的是签发时的角色与启用状态，不复核的话管理员停用某人后，对方旧令牌仍能用到过期。头部透传档刻意**不**对账（避免搅乱测试语义，`dependencies.py:142-146`）。

## 三、用户目录与角色模型

### 3.1 `Principal`：身份集合的载体（`app/services/security/auth.py:24-45`）

| 要素 | 说明 |
|---|---|
| `user_id` | 主键；登录名**就是** user_id，刻意不引入独立 username 字段（`:254-263`） |
| `tenant_id` | 一切过滤的第一道闸门 |
| `roles` / `groups` | 角色与群组列表 |
| `enabled` | 启用状态（目录对账的依据之一） |
| `identities`（属性） | 身份集合：`user:<id>` + `role:<r>`… + `group:<g>`… 三类表达式取并集——**ACL 匹配的是身份集合，不是用户名字符串**（`:34-41`） |
| `is_admin`（属性） | `"admin" in roles`（`:43-45`） |

### 3.2 `UserDirectory`：落盘的用户目录（`app/services/security/auth.py:198-335`）

- **持久化**：`data/users.json`，写盘走临时文件 + 原子替换（`:235-239`）；文件损坏**拒绝以脏数据启动**（`:225-227`）。
- **内置账号**：`DEFAULT_USERS` 四条（admin / zhangsan / lisi / wangwu，分属 default 与 tenant-b 两租户），仅在文件不存在且无初始种子时写入（`:205-210`、`:228-233`）；`auth_users_json` 只是首次启动的种子，此后真相源是落盘文件。
- **`set_password` 不隐式建号**（`:277-285`）：账号必须已存在，否则"给 zhangsan 设密码"会意外产生新账号。
- **`upsert` 主键保护**：`user_id` / `tenant_id` 不允许被 patch 改掉（`:287-303`）。
- **`identities_to_users`**（`:322-335`）：把身份表达式集合展开为具体用户——ACL 变更的"影响人数预览"靠它**真实反查**用户目录，管理员不凭角色名猜影响面；`matches`（`:305-320`）供表达式存在性判断，两者都只统计 `enabled` 账号。
- **API 边界脱敏**：`password_hash` 绝不离开后端——`_USER_SECRET_FIELDS` 在 `GET /admin/users` 与 `PUT /admin/users/{id}` 的响应里剥掉它（`app/api/security.py:39-49`）。理由写在注释里：哈希一旦落进浏览器，离线爆破成本远低于直接猜口令。

### 3.3 角色 × 能力矩阵（`app/api/security.py:327-397`）

`ROLE_CAPABILITIES` 声明四种角色（admin 全量 / hr / finance / sales 最小集），未分配角色的账号只有"提问 + 看自己数据"。`GET /admin/users/permission-matrix` 由**后端**输出矩阵并回带每个角色的真实用户数——角色与能力是策略声明，写在前端等于让界面自定义权限；对着零成员角色做授权决策本身也是错的（`:350-356`）。注意它是**展示层声明**，真正的强制在各端点的 `require_role("admin")` 与文档 ACL（见「十一」缺口 7 的口径说明）。

### 3.4 前端守卫（`frontend/src/features/auth/guards.tsx`）

- `RequireAuth`（`:23-29`）：未登录跳登录页。
- `RequireAdmin`（`:32-48`）：**不跳转**，渲染"无权访问"页——非管理员不该被弹来弹去，也不该从跳转行为推断出管理页存在。
- `RedirectIfAuthenticated`（`:51-56`）：已登录不再看到登录框。
- 管理区路由与后端 `require_role("admin")` 逐个 router 对应（`frontend/src/app/routes.tsx:67-83`）；前端守卫只是体验层，强制永远在后端。

## 四、口令

实现：`app/services/security/password.py`（零第三方依赖，只用标准库 `hashlib.pbkdf2_hmac`）。

| 决策 | 现状 | 位置 |
|---|---|---|
| 算法 | PBKDF2-HMAC-SHA256 | `password.py:30-33` |
| 迭代轮数 | 600 000（OWASP 2023 对 PBKDF2-HMAC-SHA256 的建议下限；轮数只增不减） | `password.py:32-33` |
| 盐 | 16 字节随机盐（`secrets.token_bytes`），相同口令每次哈希不同 | `password.py:31`、`:43-47` |
| 存储格式 | 自描述单行：`pbkdf2_sha256$<iterations>$<salt_b64>$<hash_b64>` | `password.py:16-21`、`:43-47` |
| 强度规范 | 只有两条：≥8 位 + 同时含字母和数字 | `password.py:35-36`、`:77-85` |
| 常量时间比较 | `hmac.compare_digest` | `password.py:73-74` |

**为什么不用 bcrypt/argon2（取舍说明）**：`auth.py` 已确立"安全关键逻辑自己写，把接受哪些参数、拒绝哪些输入留在代码里而不是藏进依赖"的约束，口令模块沿用同一取向；PBKDF2 是 NIST 认可的口令派生函数，轮数显式可见可调，出问题时能定位到"轮数不够"而不是"库的默认值变了"（`password.py:1-14`）。

**自描述格式的价值**：轮数写在每条记录里，`verify_password` 读记录自带的轮数而非当前常量（`:68-73`），因此调高轮数后旧口令仍可校验；`needs_rehash`（`:88-98`）供登录成功后**顺带升密**，不打扰用户。

**防账号枚举三连**：

1. 登录失败对"账号不存在 / 口令错误 / 账号已停用"返回**完全相同**的错误码、文案与 HTTP 状态（`app/api/auth.py:18-21`、`:48-49`、`:133-135`、`:161-171`）；`verify_password` 对"未设口令"与"口令错"也一律返回 False（`password.py:50-56`）。
2. `burn()`（`password.py:101-107`）：对不存在的账号也执行一次等价强度的派生运算——没有这一步，"账号不存在"会因少一次 PBKDF2 而快几十倍，时序差即可枚举账号。调用点在 `app/api/auth.py:163-166`。
3. 登录限流按登录名分桶（挡脚本不挡手滑，`app/api/auth.py:149-159`）。

代价也写在代码里：停用账号的用户看到的是"用户名或密码不正确"而非"账号已停用"——这个代价换来不可枚举（`app/api/auth.py:20-21`）。

## 五、ACL 五步判定树

实现：`app/services/security/acl.py:81-100`。**顺序是短路语义，不可调换**：

```
① 租户不匹配 → 拒绝（跨租户一律不可见）              acl.py:85-86
② 命中 deny（身份集合 ∩ deny 非空）→ 拒绝           acl.py:88-90   deny 优先于 allow：角色授权救不回被拉黑者
③ 命中 allow（身份集合 ∩ allow 非空）→ 放行         acl.py:92-94   user:/role:/group: 三类粒度并集
④ 租户内公开 → 放行                                acl.py:96-98   ACL 覆盖字段优先，回落文档默认 acl_public
⑤ 默认拒绝                                        acl.py:99-100
```

② 必须在 ③ 之前：同一身份同时在 allow 与 deny 中时，deny 胜出。④ 不会削弱 ①：跨租户在第 ① 步已拦截，"公开"只在租户内生效。

### 5.1 判定树之外的四组配套机制

- **检索后过滤与下推**：`filter_docs` 逐条判定并只回报被过滤数量（`acl.py:102-105`）；`visible_doc_ids`（`:107-119`）把可见文档集合下推给检索层，让不可见文档**不参与 top-k 竞争**——**文档数 >5000 时返回 None**，退回 tenant 粗过滤 + 应用层后过滤（Milvus 表达式超长会降级，枚举本身也变贵）。下推与空结果只读探测的链路细节 → `05-检索链路.md`。
- **变更影响反查与风险分级**：`set_acl` 返回 before/after + impact + risk（`:144-162`）。impact 由 `identities_to_users` 真实反查目录的启用账号（`:164-191`）；风险分级（`:193-202`）：**移除 deny 条目或改为公开 → critical；扩大 allow → high；其余 → low**——前端据此做二次确认。
- **ACL 全局版本进缓存键**（`:68-70`、`:139-142`）：任何 ACL 写操作递增 `_version`，缓存键携带该版本——否则权限撤销后旧缓存仍命中（缓存命中路径跳过检索与 ACL 过滤）。缓存键的完整维度 → `05-检索链路.md`。
- **删除联动**：文档删除时 `ACLService.remove` 清掉该文档条目（`:126-137`）——同名 doc_id 重新上传不应继承旧权限（旧 allow 可能越权、旧 deny 可能误伤）。删除编排整体 → `09-数据模型与存储.md` §四。

### 5.2 存储纪律

`acl.json` 损坏**拒绝启动**——权限数据损坏比"没有权限数据"严重得多，不能以空 ACL 对外服务（`acl.py:71-77`）；写盘一律临时文件 + 原子替换，因为启动校验是"损坏即拒绝"，半截文件等于把整个服务打挂（`:214-220`）。

### 5.3 ACL 过滤的统一出口

`acl_filter_of`（`app/dependencies.py:71-111`）把"按文档收口权限"提取为共享依赖：`__` 前缀的系统块（社区摘要/图像索引）放行、`quick_` 前缀的快问临时文档放行（归属另行校验）、无主文档拒绝；同一请求内同一文档只查一次（请求级记忆化）。线性链路、Agent 工具层、图谱/图像证据都经此同一实现，语义不会分叉。

### 5.4 知识库授权（KB 粒度）

实现：`app/services/security/kb.py`。知识库是**文档的上位容器**，`DocumentRecord.knowledge_base_id` 指向所属 KB（`app/domain/schemas.py:39`）。管理员按**用户粒度**授权某个知识库（`user_id` 粒度，角色粒度未实现），未授权用户检索不到该库任何文档。

判定树（与 ACL 五步同构，顺序短路）：

```
① KB 不存在 → 拒绝                                    kb.py:111-112   防探测：不抛异常
② 租户不匹配 → 拒绝（默认库除外，见下）              kb.py:116-117
③ 命中授权名单（user_id 精确匹配）→ 放行              kb.py:119-121
④ 库公开（is_public）→ 放行                          kb.py:123-124
⑤ 默认拒绝                                           kb.py:126
```

**与文档 ACL 的关系**：两道闸门**叠加取交集**——KB 管「能不能进这个门」，文档 ACL 管「进门后能不能看这个柜」。判定顺序上文档 ACL 在前（`dependencies.py:104-108`），ACL 拒绝的文档不再查 KB；**deny 优先的语义不变**，KB 授权救不回被文档 ACL 拉黑者。

**必须落在兜底闭包内**：检索链路有两条独立过滤路径——下推（`pipeline.py:171-190` 的 provider，可降级）与后过滤（`pipeline.py:450-467` 的 `_visible_candidates`，无条件生效）。KB 判定合并进 `acl_filter_of` 的 `check(doc_id)` 闭包（`dependencies.py:81-109`），因为 provider 降级时（文档数 >5000 或枚举异常）后过滤是唯一闸门；而文档 ACL 默认公开（`acl_public=True`），对多数文档恒放行，KB 若不在闭包内就是**确定越权**。`__`（系统内置块）与 `quick_`（快问临时文档）前缀豁免在 KB 判定之前（`dependencies.py:93-96`），快问因此不受 KB 约束。

**默认知识库**：`kb_id="default"`，`is_public=True`，承接全部存量文档（首次启动自动创建，`kb.py:75-90`；存量文档的 `knowledge_base_id` 空值在加载时回填，`services/knowledge.py:117-125`）。默认库对各租户公开且**禁止删除**（`kb.py:221-222`）——它是存量文档的锚点。

**授权写入是全量覆盖**：`PUT /admin/kb/{kb_id}/grants` 提交目标用户全集，返回 `impact`（新增/减少人数）与 `risk`（扩权 high / 缩权 low），字段名与文档 ACL 的 `set_acl` 同构，前端结果回显区零改动复用（`kb.py:239-270`）。授权目标必须是目录中真实存在且启用的用户，否则 3904 拒绝（把权限挂在空气上会让事后排查极难）。

**版本进缓存键**：任何 KB / 授权写操作递增 `_version`——创建 `kb.py:188`、改名 / 改可见性 `:212`、删除 `:234`、授权写入 `:260`（初值 `kb.py:52`），与 ACL 版本复合后进缓存签名（`main.py:417`）——缓存命中路径跳过检索与全部过滤，撤权若不使版本变化，同用户旧答案仍会被命中。

**已知限制**：`_probe_denied_content` 的空结果探测用不带允许清单的 tenant 级 filters（`pipeline.py:406-423`），会命中其它 KB 的内容；因只返回布尔、不外带内容，泄露面有限，但「有权看但内容真没有」与「无权限」的区分力会被削弱。

## 九、工具治理

实现：`app/services/agent/tools.py`。Agent 工具层的治理与主线 ACL 同语义、不同执行点：

- **ACL 在注册表层统一执行**（`:601-619` + `:664-673`）：`run_with_timeout` 返回前对所有工具的结果统一过 `_apply_acl`——此前只在图编排里对 vector_search 做，图谱/图像/SQL 结果可绕过。放行规则：无 `doc_id`（calculator / sql_search / web_search 等非知识库来源）与 `__` 前缀系统块放行；其余交 `acl_filter` 判定（deny 优先在 `acl.check` 内）。全部被滤光时回结构化错误"结果均无访问权限"。

- **入参 Schema 校验**（`:679-687`）：校验失败返回**错误文案**回传给 LLM 自我修正，而不是让整步失败——"参数写错"是模型最能自愈的一类错误。

- **单步超时**（`:689-704`）：固定线程池 + future 超时；Python 线程无强制中断能力，已运行的工具线程仍会跑完（边界写在注释里）。
- **条件注册**：`sql_dsn` 为空则不注册 sql_search，web_search 同理（`app/core/config.py:229-237`；注册编排见 `app/main.py:465-536`）——工具目录与熔断状态经 `GET /admin/tools` 暴露（`app/api/security.py:295-314`）。
