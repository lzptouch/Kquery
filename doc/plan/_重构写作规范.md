## 三、写作规范 N1~N10（强制）

| # | 规范 | 落地做法 |
|---|---|---|
| N1 | 事实标注 | 关键结论带 `文件:行号`（相对 `backend/` 或 `frontend/` 的路径）。**禁止**写绝对路径（`C:\`、`/Users/`） |
| N2 | 基线戳 | 文首有「代码基线」字段，值为「见 README 关键数字表」。**不要**自己钉 git SHA（只有 README 钉） |
| N3 | 现状 vs 计划 | 只写**已落地**的现状。设计意图、未实施的改进一律不写；确需说明"为什么这样设计"时，写成"取舍说明"并明确标注为取舍而非计划 |
| N4 | 失效标记 | 报告中心 / 评测平台 / 8xxx 错误码段 / 阶段 8~10 叙事**一律不写**（唯一例外：`14-差距与演进.md` 的「已下线留档」小节）。不写"⚠️ 已失效"横幅 |
| N5 | 未接线必须点名 | 「代码存在但生产路径无调用点」「默认关闭」「有机制无度量」必须显式标注 |
| N6 | 口径单一 | 跨篇复用的数字（端点数、用例数、参数默认值、端口）**不写具体值**，写「见 README 关键数字表」；只有本篇独有的细节才写数字 |
| N7 | 无死链 | 文档互链用 `→ NN-xxx.md` 形式，指向的文件必须存在。**禁止**引用 `doc/series`（已删除） |
| N8 | 篇幅上限 | 单篇 ≤ 45 KB |
| N9 | 表格优先 | 端点、配置、模型、指标、状态一律用表格 |
| N10 | 维护触发 | 文末必须有「维护触发」章节，列出触发更新的代码文件 |

> **v1.1 校准**：N8 的 45 KB 上限已被「分析文档体系重构」计划 v1.2 校准为 **70 KB**（实测最大篇 `04-问答链路.md` 66 KB）。**现行上限以 `doc/analysis/README.md` §五 N8 为准。**

## 四、能力状态判定标准（唯一标准，不得自创）

| 状态 | 判据 | 示例 |
|---|---|---|
| ✅ 可用 | ① 有生产调用点（非仅测试）② 走默认配置即可工作 ③ 有覆盖主路径的测试 —— **三条全满足** | 混合检索 |
| ⚠️ 有条件可用 | 满足 ①③ 但**默认关闭**（需改配置） / **有机制无度量** / **已知缺口内** —— **满足其一即降级** | ReAct（默认 `plan_execute`）、HITL（默认 `False`）、检索质量（无金标集） |
| ⛔ 不可用 | 无生产调用点，或依赖外部系统未配置且无降级 | SQL 工具（`sql_dsn` 空则不注册） |
| 🚫 已下线 | 代码已删除 | 报告中心、评测平台 |

**三条硬规则**：① "有代码"≠"可用"（只被测试调用的最高 ⚠️）；② 默认关闭一律 ⚠️；③ "有机制无度量"一律 ⚠️。
