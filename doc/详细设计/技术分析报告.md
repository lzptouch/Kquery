## 4. 架构分析

### 4.1 当前架构

系统采用 **7层架构**，从L1到L7依次为：

```
L7 数据持久层      ┌──────────┬──────────┬──────────┐
                   │ SQLite   │  Milvus  │  Neo4j   │
                   │ 业务数据  │ 向量知识库│ 图数据库  │
                   └──────────┴──────────┴──────────┘
                             ↑
L6 连接集成层      ┌──────────┬──────────┬──────────┐
                   │ CRM API  │ 订单系统  │  AI服务  │
                   │ 适配器    │ 对接SDK   │  通义千问 │
                   └──────────┴──────────┴──────────┘
                             ↑
L5 核心决策层      ┌──────────┬──────────┬──────────┐
                   │ Agent    │ 工作流    │ 规则引擎  │
                   │ 调度算法  │ DAG引擎   │          │
                   └──────────┴──────────┴──────────┘
                             ↑
L4 业务服务层      ┌──────────┬──────────┬──────────┐
                   │ RAG引擎   │ 知识图谱  │ 意图识别  │
                   │ 检索/问答  │ 实体/关系  │ 话术模板  │
                   └──────────┴──────────┴──────────┘
                             ↑
L3 会话管理层      ┌──────────┬──────────┬──────────┐
                   │ Redis    │ 对话    │ Session  │
                   │ 分布式缓存 │ 状态机   │ 管理器    │
                   └──────────┴──────────┴──────────┘
                             ↑
L2 API网关层       ┌──────────┬──────────┬──────────┐
                   │ FastAPI  │ JWT鉴权   │ 限流     │
                   │ 路由分发  │ RBAC权限  │ 审计日志  │
                   └──────────┴──────────┴──────────┘
                             ↑
L1 多端交互层      ┌──────────┬──────────┬──────────┐
                   │ Web前端   │ 语音转文字│ 微信/APP  │
                   │ React/Vite│ SDK      │ 交互组件  │
                   └──────────┴──────────┴──────────┘
```

### 4.2 架构优点

1. **7层清晰分层**：L1多端交互层 → L2 API网关层 → L3会话管理层 → L4业务服务层 → L5核心决策层 → L6连接集成层 → L7数据持久层
2. **端到端销售场景覆盖**：从多端客户接入（L1）到外部系统集成（L6），全链路支持智能销售场景
3. **决策与执行分离**：L5核心决策层专注决策逻辑，L4业务服务层专注业务执行，职责清晰
4. **会话管理独立成层**：L3确保多轮对话的上下文管理和状态一致性
5. **模块化设计**：文件加载器采用插件体系，易于扩展
6. **异步处理**：全面采用async/await，适合IO密集型操作
7. **配置集中**：config.py统一管理，支持环境变量

### 4.3 架构问题

| 问题 | 严重程度 | 影响 |
|------|----------|------|
| **多模态服务耦合** | 高 | 代码难以维护，无法切换服务提供商 |
| **无服务抽象层** | 高 | 违反开闭原则，扩展性差 |
| **无消息队列** | 高 | 大文件处理阻塞请求，无法后台处理 |
| **无统一异常处理** | 中 | 错误处理不一致，用户体验差 |
| **无中间件体系** | 中 | 认证、限流、日志等散落在各处 |
| **无图谱层** | 高 | 无法进行实体关联和知识推理 |
| **无多租户支持** | 中 | 无法支持多客户隔离 |

## 6. 性能分析

### 6.1 性能瓶颈

| 瓶颈点 | 影响 | 严重程度 |
|--------|------|----------|
| **大文件处理阻塞** | 用户等待时间长 | 高 |
| **并发控制简单** | 无法充分利用资源 | 中 |
| **缓存策略单一** | 命中率低 | 中 |
| **无查询批处理** | 批量查询效率低 | 中 |
| **无连接池优化** | 数据库连接开销大 | 低 |

### 6.2 缓存现状

**当前缓存使用**：
- Redis：仅用于向量检索结果缓存
- 无内存缓存（如lru_cache）
- 无缓存预热机制
- 无缓存失效策略

**缓存命中率估算**：
- 预计<40%，主要原因是：
  - 查询多样化，重复度低
  - 缓存粒度过粗
  - 无缓存预热

### 6.3 并发控制

**当前并发控制**：
```python
BATCH_MAX_CONCURRENCY = 3  # 固定并发数
EMBEDDING_MAX_CONCURRENCY = 5
```

**问题**：
- 并发数固定，无法根据系统负载动态调整
- 无资源限流（CPU/内存）
- 无任务优先级队列

### 6.4 数据库性能

**Milvus性能**：
- 索引：IVF_FLAT（适合小规模，不适合大规模）
- 无查询批处理
- 连接池未优化

**建议优化**：
- 使用HNSW索引（适合大规模）
- 实现查询批处理
- 优化连接池配置

## 12. 竞品对标分析：KQuery vs 腾讯 ima

> 本章整合自 `doc/KQuery-vs-ima/`，基于对本项目代码事实的核查，与腾讯 ima（AI 知识库工作台）的能力边界进行对比，识别差距并给出优先级与风险规避建议。调研时间：2026-07-19。

### 12.1 KQuery 现状梳理（基于代码事实）

**已具备的底座能力（强项）**

- **GraphRAG 混合检索**：向量语义检索（Milvus）+ 知识图谱扩展（Neo4j），支持 HyDE、双路融合与时间衰减排序。
  - `ResultFusionEngine`（`graphrag_engine.py`）：向量召回 + 知识图谱召回加权融合，默认 `vector_weight=0.6 / graph_weight=0.4`，并按问题类型动态调整。
  - `RRFusionEngine`（`retriever.py`，`rrf_k=60`）：向量召回 + BM25 关键词召回的 Reciprocal Rank Fusion。
  - 时间衰减排序 `TimeDecayScorer`、重排序 `RerankerService`（Qwen3-Reranker-8B via API，失败时回退本地打分）。
  - BM25 为基于 `rank_bm25` 库 + jieba 中文分词的**真实实现**，非简化 TF-IDF。
- **知识图谱**：自动实体/关系抽取、PageRank、Louvain / Label Propagation / Leiden 社区发现；前端 `KnowledgeGraph.tsx` 使用 `react-force-graph-2d` 力导向渲染（cytoscape、@antv/g6 为已声明依赖但非主渲染器）。
- **文档解析**：10 种解析器（PDF、Word、Excel、PPT、HTML、MD、TXT、JSON、XML、图片-OCR/VL），覆盖约 28 种扩展名，`LazyLoaderRegistry` 按需加载。支持多模态图片理解。
- **Agent 问答**：`LangGraph create_react_agent` 骨架已搭建（但运行时 RAG 模式直调 `GraphRAGEngine.generate_answer()`、通用模式直调 `LLM.ainvoke()`）；已定义 `rag_search`、`process_document` 工具并注册于 `TOOLS_REGISTRY`；支持 SSE 流式。
- **企业级基础设施**：JWT 认证 + 输入安全验证、L1+L2 多级缓存、Redis 滑动窗口限流、结构化审计日志、Celery 异步任务、健康检查、Prometheus 指标。

**曾经"临门一脚"、现已落地的能力（v3.0 更新）**

- **多模型切换**：已在 `llm_client.py` 三通道之上暴露为 `app/api/llm_router.py`（`/api/v1/models`、`/api/v1/chat`），前端具备模型切换能力。
- **多租户**：`app/core/tenant.py` 提供 `TenantContext/TenantService` 抽象；共享知识库通过 `kb_id` + 集合前缀实现资源隔离（`services/knowledge_base_service.py`）。
- **集成模块**：CRM 适配器、订单 SDK、企业微信集成仍为 `services/integration/` 层脚手架（未暴露为公开 API）。
- **插件系统**：`app/plugins/` 提供插件框架与注册表（`registry.py`）。
- **Celery 异步任务**：核心文档/图谱任务已实现，部分维护类任务由 Beat 触发。

**曾经的短板（对标 ima），现已全部实现（v3.0）**

- ✅ 「写」的能力：AI 写作笔记（`notes_router.py`）；✅ 思维导图（`mindmap_router.py`）；✅ 统一模型路由（`llm_router.py`）；✅ 联网搜索（`web_search_router.py`）；✅ 语音 ASR/TTS（`speech_router.py` + `services/speech/`）；✅ 长期记忆（`memory_router.py` + `long_term_memory_service.py`）；✅ 任务式 Agent（`tasks_router.py` + `task_service.py`）；✅ 协作生态：共享知识库（`knowledge_base_router.py`）与 Skills（`skills_router.py`）。

### 12.4 拓展能力风险与注意事项

#### 12.4.1 通用工程风险

- **用户认证与权限**：`api/auth_router.py` 已提供 register/login/refresh/me 四端点，`get_current_user` 依赖已用于知识库、Skills 等写接口；检索/图谱只读接口当前默认开放（便于本地开发）。共享知识库通过 `require_kb_role` 做成员级鉴权。后续可在生产环境将只读接口纳入统一登录校验。
- **Celery 与部署脱节**：任务已定义但 `docker-compose.yml` 未启动 Worker，需新增 `kquery-worker` 服务，并将任务拆分到 `app/tasks/`。
- **数据库能力不足**：默认 SQLite 在并发写入/多实例/审计上有短板，M2 结束前引入 PostgreSQL，用户/KB/成员/任务/Skill 必须进 RDBMS。
- **配置与 Feature Flag**：每个新能力在 `settings.py` 增加 `*_enabled` 开关，`GET /api/v1/config` 暴露给前端，默认关闭以支持灰度。

#### 12.4.2 分阶段风险

- **P0-1 多模型**：Provider 解析失败可能导致 Agent 全线不可用 → 保留默认 provider 兼容并降级到 `call_openai_chat()`。
- **P0-2 写作笔记**：AI 生成幻觉污染知识库 → 标注「AI 草稿」，入库区分 `source_type` 并降低草稿权重。
- **P0-3 思维导图**：图谱成环导致无限递归 → BFS 限制最大深度、已访问节点不重复、关系去重。
- **P0-4 联网搜索**：成本失控与内容质量 → `query_classifier` 判定 + 接口限流 + 结果缓存 1–5 分钟 + 内容长度/敏感词过滤。
- **P1-1 语音**：格式多、噪声大、隐私敏感 → 限制录音时长与大小、`pydub` 统一转码、语音文件 24 小时清理、HTTPS。
- **P1-2 长期记忆**：错误事实累积 → 记忆管理页可查/删/改、置信度阈值、冲突以最新或用户确认为准、脱敏存储。
- **P1-3 任务式 Agent**：工具越权/循环调用 → `validate_input()` 限制参数范围、步数与超时上限、高危工具二次确认、审计日志。
- **P2-1 共享知识库**：物理集合名暴露 → `kb_id`(UUID) 隔离 + `require_kb_role` 校验 + 邀请码过期可撤销。
- **P2-2 Skills**：自定义系统提示词注入 → 敏感词/指令注入检测、默认只读工具、内置 Skill 审核、MCP 工具白名单。
- **平台化成本失控**：能力叠加使单请求 token 呈指数增长 → 统一成本中心记录 model/token/耗时/来源，设置预算上限，非核心流程用轻量模型或异步批处理。

#### 12.4.3 风险总览矩阵

| 风险 | 阶段 | 严重度 | 概率 | 主要规避手段 |
|------|------|------|------|------|
| 用户认证与权限 | 通用 | 中 | 中 | 生产环境对只读接口补登录校验、权限依赖全覆盖 |
| Celery Worker 未部署 | 通用 | 高 | 高 | 增加 docker-compose 服务 |
| 数据库能力不足 | 通用 | 中 | 中 | 生产切换 PostgreSQL |
| 多模型切换致 Agent 不可用 | P0 | 中 | 中 | 保留默认 Provider 兼容降级 |
| 联网搜索成本失控 | P0 | 高 | 中 | 查询分类 + 限流 + 缓存 |
| 语音文件泄露/磁盘占满 | P1 | 中 | 中 | 大小限制 + 自动清理 + HTTPS |
| 长期记忆错误累积 | P1 | 中 | 中 | 用户管理 + 置信度 + 冲突解决 |
| 任务 Agent 安全越界 | P1 | 高 | 中 | 参数校验 + 步数限制 + 审计 |
| 共享知识库越权访问 | P2 | 高 | 中 | kb_id 隔离 + RBAC + 邀请码过期 |
| 自定义 Skill 提示注入 | P2 | 中 | 中 | 敏感词过滤 + 工具白名单 + 审核 |
| 成本指数增长 | P2 | 高 | 中 | 成本中心 + 预算上限 + 异步批处理 |
