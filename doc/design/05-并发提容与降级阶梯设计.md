## 一、C-01 ~ C-03 · 压测基线

### 1.1 C-01：多租户压测编排

**问题**：`scripts/load_test.py` 只有 `--password` 单账号（`:185,231`），受单租户 60/min 限流约束，**聚合吞吐无法区分「系统上限」与「限流上限」**。

**目标**：支持 `--users` 多账号。

```
python scripts/load_test.py \
  --api http://localhost:8100 \
  --users admin:Admin12345,bob:Bob12345,carol:Carol12345 \
  --rps 50 --duration 60
```

实现要点：

1. 逐个 `POST /auth/login` 换取 token，**token 池按用户轮转**；
2. 每个请求随机取一个 token（保证多个租户的配额都被消耗，而不是打满一个）；
3. 报告里**按用户分组**统计 QPS 与错误码（区分「429 限流」与「5xx 故障」）；
4. 账号不存在时**明确报错并提示创建命令**，不要静默跳过。

**验收**：三账号压测时，`/auth/login` 返回 3 个不同 `sub` 的 token；报告中能看出每个账号的请求数与 429 分布。

### 1.2 C-02：基线数据落盘

**问题**：压测结果只在终端，**没有留档**，导致「§四 验收指标」里的 11 个数字全部无据可依。

**目标**：新建 **`doc/analysis/并发容量基线.md`（待建，见 C-02）**，或在 `doc/analysis/11-并发与容量.md` 增设「压测实测」小节，每次压测**追加**一行：

| 日期 | 镜像 tag | 场景 | 并发 | 吞吐 | P50 | P95 | 429 | 5xx | 备注 |
|---|---|---|---:|---:|---:|---:|---:|---:|---|
| 2026-10-30 | `0363f12` | `/ask` mock | 32 | — | — | — | — | — | 批次 1 后首测 |

**关键纪律**：**追加不覆盖**。趋势比单点重要。

**验收**：`scripts/load_test.py` 支持 `--out-markdown <路径>`，直接产出上表的 Markdown 行。

### 1.3 C-03：旧数字重测

**问题**：`doc/plan/单体内并发能力提升-分析与实施计划.md` §1.1 的实测（454 QPS / 511 QPS / TTFT 7.6s）是 **2026-10-19、批次 1 落地前**的口径。批次 1 改变了线程模型，旧数字**不再代表当前系统**。

**验收**：基线表里有两组数据并标明口径。

## 二、C-04 ~ C-06 · 线程模型剩余项

### 2.1 C-04：客户端断开主动取消

**问题**：`request.is_disconnected` **全仓 0 命中**。客户端关掉 SSE 连接后，服务端仍跑完整条管线，占着一个执行器线程直到自然结束。

**目标**：`/ask/stream` 的生成器循环里检测断开：

```python
async for event, payload in executor.stream_events(factory, cancel):
    if await request.is_disconnected():
        cancel.set()                 # 管线在阶段边界检查并停止
        registry.cancel(run_id)
        break
```

**注意**：`executor.stream_events`（`backend/app/services/pipeline_executor.py:151-189`）已经接受一个 `cancel` 事件（`threading.Event`），管线侧已有阶段边界检查机制——**缺的只是「谁来 set 这个事件」**。

**验收**：打开一条 SSE 后立即关闭浏览器，服务端日志显示该 run 在 ≤2s 内进入取消态；线程数不增长。

### 2.2 C-05：指标延迟采样

**现状**：`backend/app/core/metrics.py` 无采样逻辑。

**评估**：Prometheus `Histogram` 在客户端侧按 bucket 聚合，**不驻留原始样本列表**，内存风险低。原计划设想的「每 10 个请求留 1 个」采样策略**收益有限、可能丢失长尾信息**。

**结论**：**降级为「有条件做」**——只有在压测证明 Histogram 的 `_metrics` 字典（label 组合数）膨胀时才需要采样。若需要，正确做法是限制 label 基数，而不是采样。

### 2.3 C-06：`api-client.ts` 的 429/503 倒计时

**问题**：`frontend/src/lib/sse-client.ts:122-126` 处理了 429/503，但 `frontend/src/lib/api-client.ts` 只处理 401（`:57,80`）。管理面写操作（入库、移库、改权限）遇背压时，用户看到的是「请求失败（HTTP 503）」。

**目标**：抽出同源 helper：

```ts
// frontend/src/lib/api-client.ts
export function readRetryAfter(resp: Response, fallback = 5): number {
  const raw = resp.headers.get("Retry-After")
  const n = Number(raw)
  return Number.isFinite(n) && n > 0 ? n : fallback
}
```

在通用错误分支里：对 429 / 503 产出 `{ code, message, retryAfterSeconds }`，**不触发登出、不跳全局错误页**；由调用方展示倒计时。

**验收**：单测断言 503 响应 → 信封带 `retryAfterSeconds`；`onUnauthorized` 未被调用。

## 三、C-07 ~ C-09 · 上游与检索观测

### 3.1 C-07：`upstream_saturation{upstream}` gauge

**问题**：隔离仓（`backend/app/services/upstream.py`）只暴露熔断状态，**没有许可占用率**。批次 4 的降级阶梯与容量调参都依赖「上游许可是否打满」。

**目标**：

```
backend/app/services/upstream.py
  class Bulkhead:
      self._in_use = 0            # 当前占用许可数
      def stats(self) -> dict:    # 已有出口
          return {..., "in_use": self._in_use, "permits": self._permits,
                  "saturation": self._in_use / max(1, self._permits)}
```

```
backend/app/core/metrics.py
  self.upstream_saturation = Gauge(
      "kquery_upstream_saturation", "上游许可占用率（0~1）", ["upstream"], registry=self.registry
  )
```

**关键约束**：`stats()` 会被 `/healthz` 探针调用（`backend/app/main.py` 的 `probe("upstream", bulkheads_stats)`），所以**必须是 O(1) 且无锁**。

**验收**：`/metrics` 暴露该 gauge；压测时它随并发上升，并在限流处逼近 1。

### 3.2 C-08：图 / 检查点锁等待指标

**问题**：`backend/app/services/graph/sqlite_store.py` 的单连接 + 全局锁在 Agent 并发 >16 时可能成为瓶颈，但**没有任何指标能证明**。

**目标**：

```
backend/app/services/graph/sqlite_store.py
  # 锁获取处
  t0 = time.perf_counter()
  with self._lock:
      wait = time.perf_counter() - t0
      self._lock_wait.observe(wait)
```

```
backend/app/core/metrics.py
  self.graph_lock_wait = Histogram(
      "kquery_graph_lock_wait_seconds", "图存储全局锁等待时长", ["store"], registry=self.registry
  )
```

**判定阈值**：Agent 并发 16 与 32 两档压测，若锁等待 P95 超过锁持有 P95 的 1/3，判定图写入成为瓶颈 → 触发 C-09。

### 3.3 C-09：图写入后台化

**现状**：`backend/app/services/graph/builder.py` 与 `backend/app/services/agent/graph.py` 都**没有** queue / Thread / 后台关键词——图构建仍在请求或入库线程内**同步执行**。

**目标**（**条件项，依赖 C-08 的数据**）：

1. 图构建改走**独立单线程队列**（复用批次 1 的执行器模式：`ThreadPoolExecutor(max_workers=1)` + 有界队列 + 满时降级）；
2. 索引写入仍由 `KnowledgeService._lock` 串行保护，**语义不变**；
3. 队列满时：入库链路**跳过图构建**（记日志 + 指标），**不阻塞主链路**；
4. 读路径（`graph_search` 工具、图谱查询端点）**完全不受影响**。

**验收**：压测（Agent 并发 16 / 32）下，图查询端点延迟不随图写入量上升。

## 四、C-10 ~ C-12 · 降级阶梯完整化

### 4.1 现状

`backend/app/services/pipeline.py:347-364` 的 `_degrade_level()`：

```python
if not getattr(self._settings, "degrade_ladder_enabled", False):
    return 0
...
if bulkhead("rerank").stats().get("state") == "open":   # ← 唯一判据
```

即：**只实现了「熔断打开 → CRAG 轮次收缩为 1」这一级**，且**默认关闭**。

| 计划中的水位 | 计划动作 | 现状 |
|---|---|---|
| 上游 P95 > 阈值 | 关 HyDE / 额外改写；CRAG 轮次 2→1 | ❌ 判据不存在（`config.py:271` 的 `degrade_upstream_slow_ms` **无消费点**） |
| 队列深度 > 阈值 | 拒低优先级（入库 / 图谱），交互保留 | ❌ `queue_depth` 指标已有（`core/metrics.py:103`）但**不参与任何决策** |
| 熔断打开 | 重排降级 RRF；生成降级模板 / 拒答 | ⚠️ CRAG 轮次收缩 ✅；生成降级模板 ❌ |

### 4.2 C-10：上游 P95 判据

**目标**：`Bulkhead` 维护一个滚动窗口的调用耗时（复用已有的熔断统计结构），暴露 `p95_ms`；`_degrade_level()` 增加一级：

```python
p95 = bulkhead("llm").stats().get("p95_ms", 0)
if p95 > self._settings.degrade_upstream_slow_ms:
    level = max(level, 1)
```

**注意**：`degrade_upstream_slow_ms` 默认 **2000ms**（`backend/app/core/config.py:271`），而正常单次 LLM 调用可能就 3~8s——**默认阈值偏小，开了就会一直降级**。落地时必须重新标定（建议按实测 P95 的 2 倍设定，并写进配置注释）。

### 4.3 C-11：队列深度参与拒绝决策

**问题**：`queue_depth` 只被暴露、不被消费。管线排队 200 满时直接 503（`backend/app/services/pipeline_executor.py:221-230`），**低优先级的入库 / 图谱与交互式问答争抢同一批线程**。

**目标**：引入**流量优先级**。

| 优先级 | 端点 | 深度超阈值时的行为 |
|---|---|---|
| 高（交互） | `/ask`、`/ask/stream` | 继续接纳 |
| 低（后台） | `/knowledge/ingest`、`/graph/build`、`/knowledge/rebuild` | **拒绝并返回 503 + `Retry-After`**，附明确文案 |

实现落点：

- `backend/app/services/pipeline_executor.py`：增加 `priority` 参数或分开的两个有界队列（**推荐分队列**：语义更清晰，指标可分开看）；
- `backend/app/core/metrics.py`：`queue_depth` 增 `priority` 标签（注意基数只有 2，可控）；
- `shed_total{reason}` 的 `reason` 增取值 `low_priority`（当前已有该指标，`core/metrics.py:113`）。

**验收**：队列深度 > 阈值时，`/ask` 仍返回 200，`/knowledge/ingest` 返回 503 且 `shed_total{reason="low_priority"}` 递增。

### 4.4 C-12：生成降级模板

**问题**：熔断打开时若 LLM 也不可用，现在只能走 `5001` 异常或拒答，没有「可读的降级结果」。

**目标**：在 `_core_events` 的生成阶段，捕获上游不可用 → 产出一段**固定的降级文本**（不是模板变量填充，而是预设文案），并把 `verdict` 标为 `refused`、`refusal_reason` 标为 `upstream_unavailable`。

**注意**：`refusal_reason` 的取值集合当前是 `no_content` / `insufficient_evidence` / `permission_denied`（`backend/app/domain/schemas.py:381`）——新增取值要同步改 `doc/analysis/03-接口与契约.md` 与 `doc/analysis/08-安全与治理.md`。

**验收**：故障注入（断开 LLM）时，`/ask` 返回 HTTP 200 + `verdict="refused"` + 可读文案，**不返回 5xx**。

### 4.5 降级阶梯的开关策略

`degrade_ladder_enabled` 当前默认 **False**。建议：

- **保留默认关闭**，直到 C-10 的阈值被标定（否则会误降级）；
- 灰度方式：先在**压测环境**开，验证降级行为符合预期，再考虑默认开；
- 开关应**记录实际生效的降级级别**（指标 `kquery_degrade_level`），便于观测。

## 五、C-13 · 真流式（TTFT）专项

### 5.1 为什么被移出原计划

`doc/plan/单体内并发能力提升-分析与实施计划.md` §三「移出本计划」列了两条**语义冲突**：

1. **输出侧安全**：`backend/app/services/pipeline.py:930-941` 要求拿到完整答案再扫描（`scan(answer)` 后才决定 refuse / mask）。边生成边发会让敏感词跨 chunk 漏检，必须引入「holdback 窗口 + 增量扫描」——等于重做护栏。
2. **自检与重生成**：`backend/app/services/pipeline.py:866-899` 可能整段重写答案。先发 token 再重写会造成「用户看到的内容和最终记录不一致」。

### 5.2 现状确认

```
backend/app/services/pipeline.py:1203,1252
    yield "token", {"content": text[i : i + step]}
```

即：**整段生成完成后，按 12 字符切片重放**。TTFT = 全链路耗时（与 `doc/analysis/14-差距与演进.md` KQ-07 一致）。

### 5.3 目标态设计

```
┌─ 生成 ─────────────────────────────────────────────────┐
│  LLM 流式输出 chunk                                     │
│      ↓                                                 │
│  ┌─ holdback 窗口（保留最后 N 个字符不外发）─────────┐  │
│  │  窗口内做增量敏感词扫描 + 跨 chunk 词边界检查     │  │
│  └───────────────────────────────────────────────────┘  │
│      ↓ 安全字符 → 立即 yield token                       │
│      ↓ 命中敏感词 → 停止外发，转 refuse                 │
└─────────────────────────────────────────────────────────┘
```

#### 5.3.1 决策一：自检是否允许重生成

**必须先决策**，这是所有设计的前提：

| 方案 | 语义 | 代价 |
|---|---|---|
| **A. 真流式 + 禁重生成** | 首次生成的 token 直接外发；自检只下调 `confidence`，**不重写** | 答案质量下降（有据声明可能残留）；但语义最简单、最一致 |
| **B. 真流式 + holdback 到自检后** | 生成完 → 自检 → 若需重写则**撤回已发 token** | 需要「撤回」协议（前端要支持替换已渲染内容），复杂度高 |
| **C. 保持伪流式** | 不改 | TTFT 仍是全链路耗时 |

**建议**：**A**。理由——自检的价值主要在「不给无据声明」，而**证据在进上下文前已被过滤**（`pipeline.py` 的证据筛选），所以自检重写的触发率本就低；用「不重写」换 TTFT 是划算的。**但必须同时把「置信度下调」明确呈现给用户**（`confidence` 事件已有）。

#### 5.3.2 决策二：holdback 窗口长度

敏感词扫描需要**跨 chunk 的词边界**（如「内部」被切成两半）。窗口长度必须 ≥ **最长敏感词长度 + 1**（中文按字符，英文按字节）。

当前词表最长词是多少？→ 由 `backend/app/services/security/sensitive.py` 的词表决定。**设计要求**：holdback 长度取 `max(最长词长度) + 1`，并作为**动态计算**而非硬编码。

#### 5.3.3 决策三：Agent 路径的 token 缓冲

Agent 路径（`backend/app/services/agent/runner.py`）也是「缓冲后按终稿重放」。若 Agent 也改真流式，需要处理「工具调用前的思考 token」与「最终答案 token」的区分——**建议 Agent 路径本期不改**（工具调用会产生多次中间输出，真流式语义更复杂）。

### 5.4 分阶段落地

| 阶段 | 内容 | 风险 |
|---|---|---|
| 1 | **只做 holdback 的增量扫描器**（不发 token），验证「跨 chunk 词边界不漏检」 | 低 |
| 2 | 线性路径改真流式（方案 A），前端 `sse-client.ts` 消费真 token | 中 |
| 3 | 压测验证 TTFT 改善，并确认输出侧扫描无漏检 | 中 |

### 5.5 验收

- TTFT（首 token 时间）< 全链路耗时的 50%；
- 敏感词跨 chunk 命中仍能被检出（构造「内部|审计」被切成两半的用例）；
- 自检触发重写时**不发生**（方案 A）或前端能正确替换（方案 B）；
- 前端 `sse-client.ts` 的事件白名单不变（`token` 事件已在白名单内，见 `frontend/src/lib/sse-client.ts:81-92`）。
