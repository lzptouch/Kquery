> **这份表是趋势，不是单点。** 单点会被环境噪声支配（机器负载、邻居进程、
> 磁盘缓存冷热），只有连续几行的**同口径**数据才能支撑容量结论。


## 为什么 v2 还是空的

`C-03` 的目标是「批次 1 之后重跑全部场景产出 v2 基线」。本轮**没有**填数字，
原因是诚实的：压测需要**一个跑起来的真实后端**（含真实模型与索引），
而本机是 mock 模型 + faiss 的**开发环境**——

- mock 模型的响应时间与真实模型差一个数量级，**吞吐数字不可外推**；
- 开发机有其它负载，与生产不同源；
- 在这种环境跑出来的数字会被当成「容量基线」，比没有基线**更危险**。

所以：**基线表留好口径与产出脚本（已完成），数字等在目标环境跑出来再追加**。

## 判读纪律

1. **同口径才可比**：镜像 tag 变了、线程模型改了、索引后端换了 → 旧行不再可比；
   此时**另起一段**（用「批次 1 前 / v2」这样的分段标题），不要混在一张表里比。
2. **429 / 503 是设计内的背压**，不是故障：只要 5xx（不含 503）为 0 就是健康的。
3. **一次压测不构成结论**：至少三次取中位数，并把机器负载写进备注。
4. **基线变更要显式**：改了 `pipeline_workers` / 许可数 / 队列上限之后，
   旧基线作废并在备注里写明原因——否则下次看到「吞吐下降」会误判成回归。

## 指标标签基数（`C-05`）

压测表只回答「扛得住多少」，回答不了「**扛久了指标会不会把内存吃穿**」——那是基数问题。
`C-05` 的判据**不是**「序列数 < N」：基数事故的成因是「**label 取值由请求方决定**」，
与请求量无关；用请求量或固定阈值做门禁，必然随业务增长误报（新端点、新状态码都会顶到阈值）。

因此本节的判据是两条**可证伪的性质**：

| # | 性质 | 判据 | 违反时的表现 |
|---|---|---|---|
| 1 | **不随请求量增长** | 同样形状的流量打 5 倍后，`{指标名: label 组合}` 集合**完全不变** | 每条请求新建时间序列（`/wp-login.php`、随机 UUID 路径） |
| 2 | **取值有界** | `route` ∈ 路由模板集合 ∪ `{<unmatched>}`；任何 label 不得出现 `tenant` / `user` / `doc_id` / `query` / `trace_id` / `path` | 业务主键被写进 label |

两处执行点（同一判据，不同环境）：

- **进程内（CI 闭环）**：`tests/integration/test_metrics_cardinality.py`——5 例，含「形状 ×5 序列集合不变」
  与「`route` 取值上界 = `app.routes` 数量 + 1」。不需要压测环境就能判，因此**每次 CI 都跑**。
- **压测实例（真机）**：`scripts/metrics_cardinality.py --base-url ... --rounds 5 --per-round 20`
  ——每轮用 uuid 生成**全新路径**打进去，退出码 1 表示膨胀；`--snapshot-only` 只出当前基数排行（Top N）。
  真机数字**尚未留档**（需目标环境跑一轮，与上表同样的理由：开发机数字不可外推）。

**已修的缺陷（这条判据一写就红）**：未匹配路由（404 / 扫描器）的 `route` label 曾回退到
`request.url.path`，等于**把标签取值交给任意请求方**——`/wp-login.php`、随机 UUID 每次都新建一条时间序列。
现已统一收敛到 `<unmatched>`；**日志**仍保留原始路径（可检索），只有**指标**必须低基数。
口径实现在 `backend/app/bootstrap.py` 的 HTTP 指标中间件，两处（`http_requests_total` / `http_latency_seconds`）同源。
