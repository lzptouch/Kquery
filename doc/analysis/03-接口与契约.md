## 〇、摘要

1. **端点由 10 个 router 组成（69 个端点 = 业务 9 个 router 共 64 + probes 5）**（语音下线后从 11 个 / 72 个减少）：`auth` / `security` / `kb` 三个 router 已随认证授权下线删除（2026-11-12），**鉴权分三档的说法同时失效**——现在请求身份是**固定值**（`tenant=default`、`user=local`），访问边界改由部署层承担。router 注册顺序与 prefix 见 `backend/app/bootstrap.py:274-285`（`A-12` 拆分后探针也从 `main.py` 移出，见 `api/probes.py`）；逐端点清单见 §一。
2. **统一信封只覆盖非流式 JSON 端点**：`status/data/error/meta` 四字段定义在 `backend/app/core/envelope.py:194-208`（`ErrorBody` 194-196 / `Meta` 199-201 / `Envelope` 204-208）；SSE 端点、CSV 导出、图像资源、5 个运维探针**不走信封**（§三列出全部例外）。
3. **`warn` 三态实际只在 `/ask` 一处产生**：`warn_envelope` 的唯一生产调用点是 `backend/app/api/ask.py:174`（经 `_envelope_for` `:155` 与 `_degraded_warning` `:135`），其余 64 个 API 端点只用 `ok_envelope` / `error_envelope`（§三）。
4. **错误码 53 个、7 个区段**：`backend/app/core/envelope.py:12-111`（1xxx `:23` / 2xxx `:29` / 3xxx `:38` / 31xx~38xx `:44` / 4xxx `:59` / 5xxx `:87` / 6xxx `:110`）；**39xx 知识库段已随该能力删除**；`6201 QUOTA_EXCEEDED` 已随配额下线移除，6xxx 段现只剩 `6101 RATE_LIMITED`。降级码集合（4401/4402/4501/4601/4701/4801/4901/4902）定义在 `backend/app/core/envelope.py:113-129`，`is_degraded_code` **已有生产调用点**（`backend/app/api/ask.py:164`，warn 信封路径用它做「非降级码不得走 warn」的校验）。另有 `kind_of(code)`（码段 → 6 类类别，`:149`）供错误指标的 `kind` 标签使用，以及 `RETAINED_CODES`（有意保留但无抛出点的码 + 保留理由，`:166-180`）。**死位已清零**：每个码要么有生产引用，要么登记了保留理由（守卫：`tests/unit/test_error_code_liveness.py`）。
5. **SSE 是跨端契约，不是后端内部实现**：前端在 `frontend/src/lib/sse-client.ts:89-99` 用白名单登记事件名，白名单外的事件在 `frontend/src/lib/sse-client.ts:166` **静默丢弃**（无报错、无日志）。后端新增事件必须同步前端白名单（§五）。
6. **后端已发出但前端白名单未登记的事件有 3 个**：`thought`（`services/agent/graph.py:566`）、`verify`（`:621`/`:624`/`:639`）、`hitl_resolved`（`:296`/`:318`/`:704`/`:717`）；`awaiting_human` **已登记且已接线**（白名单 `sse-client.ts:94`，后端 `services/agent/runner.py:434`/`:960`）——前三个的表现是"后端有发、前端没反应"，且无处可查（§五、§八）。`input_pii_detected` 已随敏感词功能下线移除；`graph_path` 白名单登记位也已移除（后端从无产出点）。
9. **请求体上限没有全局设置**，只有三处端点级实现，超限一律 `FILE_TOO_LARGE`（2004）；超时分四层，各自有独立上限（§七）。

## 三、统一信封

### 3.1 结构

`backend/app/core/envelope.py:194-208`（`ErrorBody` 194-196、`Meta` 199-201、`Envelope` 204-208）：

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `status` | `str` | 是 | 三态：`ok` / `warn` / `error` |
| `data` | `Any` | 否（默认 `null`） | 业务数据；`error` 信封下为 `null` |
| `error` | `{code:int, message:str}` \| `null` | 否 | 仅 `warn` / `error` 非空；`code=0` 表示"有告警但无固定码" |
| `meta` | `{trace_id:str, elapsed_ms:int}` | 是 | 追踪号与耗时；由 `Meta`（`core/envelope.py:199-201`）定义 |

三个构造器：`ok_envelope`（`core/envelope.py:211-212`）、`warn_envelope`（`:215-232`）、`error_envelope`（`:235-240`）。

### 3.2 三态语义

| 状态 | 构造器 | 语义 | 前端处置 | 生产调用点 |
|---|---|---|---|---|
| `ok` | `ok_envelope` | 完全成功 | 正常渲染 |全部非流式端点 |
| `warn` | `warn_envelope` | **部分成功 + 部分告警**：结果可用，但有降级事实需要让用户知道 | 正常渲染并附加提示 | **仅 `api/ask.py:174`**（经 `_envelope_for` `:155` / `_degraded_warning` `:135`） |
| `error` | `error_envelope` | 失败 | 展示 `error.message` | 全局异常处理器（`bootstrap.py:98-99` / `:115-116` / `:131` / `:156-158` / `:190-191`） |

`warn` 的两条纪律（`core/envelope.py:215-232` 的 `warn_envelope` 实现与注释）：①永远不用它表达失败；② `code` 传降级类错误码，为 0 表示软提示。

**实际覆盖面**：`warn_envelope` 在生产代码中的唯一调用点是 `api/ask.py:174`。`/ask/stream`、`/quickask/ask`、`/ask/runs/*/resume` 三条 SSE 路径**不产 warn 信封**——降级信息只能靠 SSE 的 `confidence` / `crag_branch` 事件携带。这是一条**跨路径不一致**：同一份降级事实，聚合路径用 `warn` 表达、流式路径用事件字段表达。

### 3.3 `ApiError`

`backend/app/core/envelope.py:243-257`：

| 属性 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `code` | `ErrCode` | 必填 | 业务错误码；全局处理器据此选文案区段 |
| `message` | `str` | 必填 | 用户可读文案（**不直接回显上游原文**，见 `services/openai_compat.py` 的错误包装） |
| `http_status` | `int` | `400` | HTTP 状态码；不是400 的必须显式传 |
| `retry_after` | `int \| None` | `None` | 限流时携带秒数；全局处理器写入 `Retry-After` 响应头（`bootstrap.py:122-123`） |

`ApiError` 是**业务失败**的唯一通道：抛 `ApiError` → `bootstrap.py:115-130` 的异常处理器 → 统一信封 + 对应 HTTP 状态码。

### 3.4 不走信封的端点（例外清单）

| 端点 | 响应形态 | 理由 |
|---|---|---|
| `POST /ask/stream`、`POST /quickask/ask`、`POST /ask/runs/{run_id}/resume` | SSE `text/event-stream` | 流式协议，`X-Trace-Id` 放在响应头 |
| `GET /assets/{name}` | 文件流 | 资源服务 |
| `GET /health`、`/livez`、`/readyz`、`/healthz`、`/metrics` | JSON / `text/plain` | 运维探针，不与前端契约耦合 |

### 6.1 `X-Trace-Id`

| 环节 | 位置 | 行为 |
|---|---|---|
| 入站 | `bootstrap.py:213` | 复用请求头带来的 `X-Trace-Id`（去空白后）；为空则 `new_trace_id()` 生成 |
| 上下文 | `bootstrap.py:213-221` | 写入 contextvar（`set_trace_id`）并挂到 `request.state.trace_id` / `Principal` |
| 出站回写 | `bootstrap.py:247` | 响应头回写同一个 `X-Trace-Id` |
| SSE 响应头 | `api/ask.py:252`、`api/quickask.py:131` | 同样回写 |
| 信封内 | `core/envelope.py:126-128` | `meta.trace_id` |
| 错误信封 | `bootstrap.py:91-199`（五档异常处理器统一取请求期 trace_id） | 复用请求入口的 trace_id——用户从前端复制的追踪号必须能反查到本次请求日志 |

### 6.2 身份（**已下线**，2026-11-12）

原「身份头与令牌」记录的是已删除的机制：前端从 `localStorage` 取身份、按
`Authorization: Bearer` 发送、并区分"未设置"与"显式空串"。

现在：

| 项 | 现状 |
|---|---|
| 身份来源 | **无凭证**。`Principal` 是固定常量（`backend/app/core/identity.py`） |
| 前端发送 | `frontend/src/lib/api-client.ts` 直接 `fetch(path, init)`，**不注入任何身份头** |
| 请求头中的 `X-User-Id` / `X-Tenant-Id` / `X-Roles` | **一律被忽略**（中间件按固定身份挂载 `request.state.principal`） |
| `localStorage` 中的身份键 | 已删除（`frontend/src/lib/auth.ts` 随之删除） |

### 6.3 前端发送口径

`frontend/src/lib/api-client.ts` 的 `request()` 直接透传调用方的 `init`：

- 不注入身份头；
- 不再对 401 触发"清会话 + 跳登录"（后端不再返回 401，唯一例外是 `/metrics`）；
- 非 JSON 响应（网关 502 等）返回统一信封形态的错误体，而不是崩在 `JSON.parse`。

SSE 路径同理：`frontend/src/lib/sse-client.ts` 只发 `Content-Type`，不做身份处理；
429 / 503 仍走"稍后重试 + Retry-After 倒计时"的既有处置。

### 6.4 401 / 403 的前端处置（**已下线**）

原口径：401 触发全局登出，403 展示"无权限"页。认证与授权下线后**两个状态码在应用端点
上都不会出现**（`/metrics` 除外），因此前端的 401/403 分支随之删除：

| 状态码 | 现状 |
|---|---|
| 401 | 仅 `/metrics`（缺 `X-Metrics-Token`）可能出现；前端不消费该端点 |
| 403 | 应用端点不再返回 |

## 七、请求体上限与超时约定

### 7.1 请求体上限：无全局设置，三处端点级实现

应用层**没有**任何全局 body 大小限制（FastAPI/Starlette 未设相关中间件）。实际约束来自三处端点级实现 + 网关：

| # | 位置 | 覆盖端点 | 做法 | 失败码 |
|---|---|---|---|---|
| 1 | `api/upload_util.py:40-57` `stream_to_disk` | `POST /knowledge/upload`（`api/knowledge.py:73`）、`POST /knowledge/ingest`（`api/ingest.py:92`） | **边写边计数**，1MB 分块，超限立即中断并删除半成品——不把整文件读进内存 | 2004 `FILE_TOO_LARGE`（HTTP 400） |
| 2 | `services/quickask.py:193-197`、`:220-225` | `POST /quickask/upload` | 文件**整体读入内存后**校验字节数与解析段数 | 2004 `FILE_TOO_LARGE` |

> 两处口径不一致：① 流式落盘 vs 内存读全量；② HTTP 413（网关层拒绝）被映射为同一个 2004（`main.py:744`），前端无法区分"应用层拒的"与"网关拒的"。
> 网关侧另有独立的上传大小限制（`deploy/nginx/nginx.conf` 与 `frontend/nginx.conf`），与本层并存——具体值见 README 关键数字表。

### 7.2 超时约定（四层，各自独立）

| 层 | 位置 | 语义 | 超限表现 |
|---|---|---|---|
| 管线在飞 / 排队 | `services/pipeline_executor.py:58`（同步 `acquire`）、`:88`（异步 `acquire_async`）、`:118`/`:128`（`run` / `run_async`） |申请执行槽位；排队已满**立即返回 False**（不阻塞） | 抛 `OverloadedError` → 503 + `Retry-After: 5`（`:221-230`） |
