# 第一部分 · 项目部署（Q1–Q100）

## 一、部署形态与拓扑

### Q1. 这个项目有哪几种运行形态？为什么要保留四种？

**回答：** 四种，对应四类使用场景：

1. **Docker Compose 全栈**（`deploy/docker/docker-compose.yml`）：单机一键起 etcd / milvus / redis / backend / frontend，外加一次性 `init`。用于验收、演示、集成测试。
2. **本机直跑后端**（`uv run --project backend uvicorn app.main:app --reload`）：开发调试，数据落本地 `data/`。
3. **本机直跑前端**（`npm run dev`）：Vite 代理到 `KQUERY_API_TARGET`。
4. **K8s**（`deploy/k8s/base` + overlays + canary）：生产与多副本。

只留一种的问题是没有哪种形态能同时满足"改一行就要看效果"和"滚动发布不断流"。取舍是按生命周期分层：开发要快、CI 要可复现、生产要可编排。四套共享同一份镜像与同一份配置真相源，差异只在编排层——这样"本地能跑、线上能跑"不靠运气。

补一句加分项：所有部署资产收敛在 `deploy/`，仓库根没有第二份 compose 或 Dockerfile，避免"改了一份忘另一份"。

### Q2. Compose 里六个服务的依赖是怎么设计的？哪一步最容易踩坑？

**回答：** 依赖链是 `etcd → milvus → backend ← redis`，以及 `frontend → backend(healthy)`：

- `redis` 配 `healthcheck: redis-cli ping`，backend 用 `depends_on: service_healthy`；
- backend 依赖 milvus 与 redis，但自己不挂 compose 级 healthcheck，靠镜像 `HEALTHCHECK` 打 `/healthz`；
- frontend 依赖 `backend: service_healthy`，不会在向量库未就绪时抢跑；
- `init` 与后端同镜像、`restart: "no"`，只建集合/建别名/初始化目录。

两个坑。第一，**把 `depends_on` 当"等待就绪"**：裸 `depends_on` 只保证启动顺序，Milvus 的 gRPC 端口起来到可服务仍有窗口，必须用 healthcheck。第二，**数据卷**：`docker compose down -v` 会连 `backend_data` 一起删，向量索引、元数据、图谱都在里面，升级只能用 `up -d --build`。

### Q3. `init` 为什么做成一次性容器，而不是塞进 backend 启动流程？

**回答：** 因为它是**幂等的一次性迁移**，不该每次启动都跑：

- 塞进启动会变成"每个副本每次启动都建集合"：多副本并发建集合要么报 already exists，要么在 Milvus 侧竞争锁；
- 启动流程做重活会拉长冷启动，直接顶到 `startupProbe` 的 150s 预算；
- 失败语义不同：init 失败应让部署**显式失败**（`restart: "no"` 便于看日志），而不是让后端反复重启掩盖问题。

K8s 上换成 `CronJob`（`0 3 * * *`、`concurrencyPolicy: Forbid`、命令 `python -m app.cli.init_index`），每天跑一次纠正"集合/别名漂移"，同时禁止并发。代价是它必须真幂等——`already exists` 要吞掉、别名指向可重复执行，否则每天报一次红。

### Q4. 为什么镜像构建的上下文必须是仓库根，而不是 `backend/`？

**回答：** 因为 Dockerfile 的 `COPY` 路径带 `backend/` 前缀：

```dockerfile
COPY backend/pyproject.toml backend/uv.lock ./
COPY --chown=kquery:kquery backend/app ./app
```

在根执行 `docker build -f deploy/docker/backend.Dockerfile .` 才能解析；`cd backend && docker build .` 时上下文里没有 `backend/` 这一层，`COPY` 直接失败。

用根还有结构性好处：前后端镜像共用一份 `.dockerignore`，且与 compose 的 `build.context` 一致，不会出现"compose 能构建、手动构建失败"的双口径。CI 也从根构建，保证"本地怎么构建、CI 就怎么构建"。

代价是上下文变大，必须靠 `.dockerignore` 排除 `data/`、`node_modules/`、`.venv/`，否则每次构建都在传几个 G。

### Q5. 前后端为什么放在同一个 host 的两个路径下，而不是两个域名？

**回答：** 因为前端调用的是**相对路径**（`/ask`、`/knowledge`、`/admin`），同 host 下由 nginx 按根前缀分流：

- ingress 只有一条 `path: /` → `kquery-frontend`；
- 前端容器内的 nginx 再把 `/ask|/knowledge|/admin|...` 这些前缀 `proxy_pass` 到后端；
- 其余路径 `try_files` 回 `index.html`（SPA 兜底）。

两个域名的代价是 **CORS 与 Cookie**：跨域要配 `allow_origins`/`allow_credentials`，SSE 还要处理预检与凭据，出错面比同源大得多。同源之后前端一个 `fetch("/ask")` 就够，开发环境用 Vite 代理模拟同样的前缀结构。

代价是所有流量都过前端 nginx 一跳，前端 pod 成了静态资源与 API 的共同入口，所以它也必须配探针与副本，不能当"纯静态目录"对待。

### Q6. Milvus 为什么单独放一份 compose？

**回答：** `deploy/milvus/docker-compose.yml` 是**基础设施的独立生命期**：

- 向量库**有状态**，升级/重建节奏与应用不同，混在一个 compose 里会导致"改后端镜像顺手把 Milvus 重启了"；
- 集成测试只需要 etcd + Milvus，不需要前端与后端，独立 compose 可直接复用；
- 卷归属清晰：Milvus 数据卷不该跟应用数据卷绑在同一个 `down -v` 里。

主 compose 仍编排了 milvus（为了"一键起全栈"），但引用同一套镜像与配置，不是第二份实现。真正的生产 K8s 清单**不含** Milvus——`deploy/k8s/README.md` 明确"不编排有状态服务"，Milvus 由外部托管或独立集群提供，通过 `KQUERY_MILVUS_URI` 接入。

### Q7. 单机 Compose 与 K8s 部署的本质差别？哪些东西不能照搬？

**回答：** 三个本质差别：

1. **副本与状态**：compose 单实例 + 本地卷；K8s 2 副本 + PVC。而 PVC 默认 `ReadWriteOnce`，两个 Pod 抢同一个卷会有一个挂不上——所以后端虽然 2 副本，`data/` 仍是单卷；多副本真正共享的是 Redis（限流/缓存/幂等/会话），不是数据目录。
2. **流量入口**：compose 靠宿主端口映射（8100/8090），K8s 没有这一层，容器端口必须与镜像真实监听端口一致（8000）。清单注释专门记过这个坑：`containerPort` 曾写成 8100，三个探针全打不通、Pod 永远 NotReady。
3. **健康语义**：compose 的 healthcheck 只决定依赖顺序；K8s 三种探针决定"是否重启""是否接流量"，混用会把依赖抖动放大成重启风暴。

不能照搬的还有停止方式：compose `stop` 是 SIGTERM 后等 10s，K8s 是 `preStop` + `terminationGracePeriodSeconds: 70`，SSE 长连接必须靠后者排空。

## 二、镜像与构建

### Q8. 后端镜像两阶段构建各做了什么？为什么运行阶段还要装 curl？

**回答：** 两阶段（`deploy/docker/backend.Dockerfile`）：

- **builder**：装 `build-essential` + `curl`，拷 `pyproject.toml`/`uv.lock`，`uv sync --frozen --no-dev --no-install-project` 把依赖装进 `/opt/venv`；
- **runtime**：只拷 `/opt/venv` 与 `backend/app`，装 `curl`，建非 root 用户，`VOLUME /data`，`EXPOSE 8000`，`CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]`。

运行阶段装 curl 的唯一原因是 `HEALTHCHECK` 要发 HTTP 请求（`curl -fsS http://127.0.0.1:8000/healthz`）；`python:slim` 自带没有 curl。这是一个有意识的取舍：多约 1MB 镜像体积，换来 Docker 与 Compose 层面能直接看到 healthy/unhealthy，而不用写一段 Python 探针脚本。

### Q9. `uv sync --frozen` 里的 `--frozen` 是什么意思？去掉会怎样？

**回答：** `--frozen` 表示**只按 `uv.lock` 原样安装，不重新解析依赖、不更新 lock**；如果 lock 缺失或与 `pyproject.toml` 不一致，直接失败。

去掉它的后果是"构建不可复现"：每次 `docker build` 都可能因为 PyPI 上的新版本重新求解，今天构建出 `numpy 2.3.1`，明天构建出 `2.4.0`，而镜像 tag 没变。线上排障时最怕这种"同名不同物"——本地复现不出来，因为本地有 lock。

这也是为什么 `uv.lock` 必须进镜像上下文（`COPY backend/pyproject.toml backend/uv.lock ./`）：**lock 是构建输入的一部分，不是开发机的私人物品**。CI 会额外跑 `uv lock --check`，把"改了 pyproject 忘了更新 lock"在提交阶段拦住。

### Q10. `UV_PROJECT_ENVIRONMENT` 这个环境变量为什么必须设？

**回答：** 因为 `uv` 默认把虚拟环境建在**项目根目录**的 `.venv/`，而本项目的构建上下文是仓库根、项目在 `backend/`。不设的话会出现两种错位：

1. builder 阶段装到了 `/src/.venv`（或 `backend/.venv`），runtime 阶段 `COPY --from=builder /opt/venv /opt/venv` 拷的是空目录，镜像起来直接 `ModuleNotFoundError`；
2. 即使路径凑巧对上，`.dockerignore` 里排除 `.venv/` 也会让 COPY 失败。

所以显式 `ENV UV_PROJECT_ENVIRONMENT=/opt/venv`，让"装到哪里"和"拷哪里"是同一个常量。这是典型的两阶段构建陷阱：**依赖管理工具的项目根假设，与 Docker 的分层假设不一致**，必须用显式路径对齐。

### Q11. Dockerfile 里为什么故意不写 `# syntax=docker/dockerfile:1`？

**回答：** 那行指令会让 Docker 去拉 `docker/dockerfile:1` 这个**外部的 frontend 镜像**来解析 Dockerfile，用于启用 heredoc、`COPY --link`、mount cache 等新语法。

本项目的约束是**企业内网 / 受限网络能构建**：拉不到 Docker Hub 的环境（本项目所在机器就是 Docker Hub 不通、需走镜像源）会因为解析器镜像拉取失败而**整个构建报错**，且报错信息指向 syntax 行，很容易被误判成"基础镜像不存在"。

而现有 Dockerfile 只用了最基础的 `FROM/COPY/RUN/ENV/USER/EXPOSE/HEALTHCHECK/CMD`，不需要新 frontend。所以选择"不写"，把构建的外部依赖降到只剩 `python:3.12-slim` 一个。取舍是失去 `RUN --mount=type=cache` 的 pip/uv 缓存加速——但本项目 uv 下载本来就快，收益不抵风险。

### Q12. `--no-install-project` 的作用是什么？

**回答：** 它告诉 uv：**只装第三方依赖，不要装项目自身**（不执行 `pip install .`）。

原因是分层顺序：`COPY backend/pyproject.toml backend/uv.lock ./` 之后立刻 `uv sync`，此时 `backend/app` 还没拷进来，项目源码不存在，装自身必然失败。省略这个参数，要么构建报错，要么 uv 生成一个空的 `*.egg-info` 占位，后续 `COPY app ./app` 覆盖源码但元数据仍指向不存在的路径——启动时报 `ImportError` 且很难看出根因。

代价是本项目在镜像里**不是"已安装的包"**，只能靠 `WORKDIR /app` + `app` 目录在 `sys.path` 里工作。所以 `CMD` 必须写 `uvicorn app.main:app` 而不是 `python -m kquery`。这也解释了为什么容器里跑 `python -m app.cli.init_index` 能工作——`app` 是个普通目录，不是安装包。

### Q13. 容器为什么必须非 root？`VOLUME /data` 又带来什么权限问题？

**回答：** 非 root 是为了把"容器逃逸"的收益压到最低：镜像里 `useradd --uid 1001 kquery`，所有 `COPY` 用 `--chown=kquery:kquery`，`USER kquery` 后进程只有普通权限，写不了系统目录。

`VOLUME /data` 与挂载卷带来两处真实麻烦：

1. **属主**：宿主目录或 PVC 挂进来时属主可能是 root，非 root 进程写不了。所以启动脚本只做"检查 + 明确报错"，而不是尝试 `chown`（容器内没有权限改别人属主）。K8s 侧靠 `securityContext.fsGroup` 把卷的组改成 `10001` 并给组读写。
2. **清单与镜像的 uid 不一致**：镜像建的是 `1001`，而 `backend-deployment.yaml` 写的是 `runAsUser: 10001`。`runAsNonRoot: true` 会校验"不是 root"通过，但文件属主仍是 `1001`，`10001` 只能靠 `fsGroup` 拿到组权限。这是清单层的遗留不一致，正确做法是两边统一成一个 uid（或干脆用 `fsGroupChangePolicy: OnRootMismatch`）。面试时把它当"清单必须与镜像对齐"的反例讲，比背概念有说服力。

### Q14. `HEALTHCHECK` 为什么打 `/healthz` 而不是 `/readyz`？

**回答：** 因为两者的**后果**不同：

- `/readyz` 是"要不要接流量"，它会在**索引为空、共享状态退化为 local、装配缺失**时返回 503。把它接给 Docker 的 `HEALTHCHECK`，会出现"容器明明能服务静态与写请求，只因为索引还没建就被标 unhealthy"，进而被编排层重启——越重启越建不完。
- `/healthz` 是"依赖是否可达"：8 项依赖各 1s 超时（Milvus/Redis/元数据/图库/资产/BM25/嵌入/重排），任何一项不通就红。它回答的是"这容器还活着吗"，与"该不该给它流量"解耦。

所以 `HEALTHCHECK --interval=30s --timeout=5s --start-period=40s --retries=3` 打 `/healthz`；K8s 里 liveness 打 `/livez`（**不查依赖**，避免依赖抖动引发重启风暴），readiness 打 `/readyz`。三种探针三种语义，任何两个混用都会产生"自愈变自伤"。

### Q15. `.dockerignore` 为什么必须排除 `data/`？镜像里为什么不装 OCR 依赖？

**回答：** 排除 `data/` 有两个原因：① 构建上下文里带着向量索引、上传文件、SQLite 库，几个 G 起步，每层都进构建缓存；② 一旦误 `COPY` 进去，镜像会包含**真实业务数据**，推到 registry 就是数据泄露。

镜像不装 OCR 系统依赖（tesseract/poppler 等）是体积与通用性的取舍：后端主镜像要覆盖 90% 的场景（Markdown/文本/Office），装全套 OCR 工具会多几百 MB，而多数部署用不到扫描件。真需要 OCR 时的正确做法是**派生镜像**：

```dockerfile
FROM kquery/backend:latest
USER root
RUN apt-get update && apt-get install -y --no-install-recommends tesseract-ocr poppler-utils
USER kquery
```

代价是"默认镜像遇到扫描 PDF 会降级"：`PdfParser` 的按页 OCR 路径会因缺少工具而失败，日志里能看出是工具缺失。这一点必须在部署文档里写清，否则会被当成解析 bug。

## 三、K8s 编排

### Q16. Deployment 为什么是 `maxSurge: 1` + `maxUnavailable: 0`？

**回答：** 因为这是**读多写少、且允许短暂多占资源**的服务：

- `maxUnavailable: 0` 保证滚动期间**可用副本数不低于期望值**，任何时刻都有 2 个 Ready pod 在接流量；
- `maxSurge: 1` 允许临时多起 1 个，先拉起新的、Ready 之后再杀旧的。

代价是发布瞬间需要 3 个 pod 的资源配额。如果集群资源紧张，`maxSurge: 1` 会卡在 Pending，发布表现为"卡住但不断流"——这比"快速发布但掉一半容量"更符合在线问答的诉求。

反面选择是 `maxSurge: 0` + `maxUnavailable: 1`：省资源、发布快，但滚动窗口内只有 1 个副本扛流量，而单副本的并发上限是 32 个在飞请求（见 Q54），高峰期必然 503。所以这个组合在"可用性优先"的配置里是被明确排除的。

### Q17. `terminationGracePeriodSeconds: 70` 与 `preStop sleep 10` 是什么关系？

**回答：** 两者是一套"先摘流量、再排空"的组合：

- `preStop: sleep 10` 让容器在被 SIGTERM 之前先**继续服务 10 秒**。目的是等 kube-proxy / ingress 把该 Pod 从 Endpoints 摘掉——摘除是异步的，如果进程一收到 SIGTERM 就退出，会有几秒的"流量还在打、后端已死"的 502 窗口。
- `terminationGracePeriodSeconds: 70` 是**总预算**：10s preStop + 最多 60s 给进程优雅退出。K8s 默认 30s，对 SSE 长连接不够——一次问答可能跑 20–60s，默认值会在回答中途 SIGKILL。

进程侧配合的是：执行器 `shutdown(timeout=30)` 停止接新任务、等在飞任务到期限，TaskManager 再 30s 等后台任务。60s 与这套退出的最坏耗时对齐，且**小于**前端 nginx 的 600s 与 ingress 的 300s——反代先超时会把连接变成 504，那比"主动断开并让前端重连"难看得多。

### Q18. 三种探针为什么分别打 `/livez`、`/livez`、`/readyz`？

**回答：** 分工是"该不该重启"与"该不该接流量"必须分开：

| 探针 | 端点 | 判断 | 失败后果 |
| --- | --- | --- | --- |
| `startupProbe` | `/livez` | 进程是否起来（`initialDelay 5s` × `failureThreshold 30` ≈ 150s） | 超时后**重启容器** |
| `livenessProbe` | `/livez` | 进程是否还活着（不查依赖） | 连续 3 次失败**重启容器** |
| `readinessProbe` | `/readyz` | 能否接流量（装配缺失、共享状态退化） | **摘流量，不重启** |

关键是 liveness **绝不能用 `/healthz` 或 `/readyz`**：Milvus 抖动 30 秒是常态，若 liveness 查依赖，所有 Pod 会同时重启，而重启并不能修好 Milvus——只会把"部分降级"放大成"全站不可用"。

`/readyz` 的判据也刻意克制：**索引为空只告警不判红**。新部署时索引还没建完，若 readiness 判红，Pod 永远不 Ready，也就永远没有流量去触发建索引，形成死锁。

参数上 liveness 用 `periodSeconds 20 / timeoutSeconds 3 / failureThreshold 3`（约 1 分钟才重启，避免瞬时抖动），readiness 用 `10s / 3s / 2`（更快摘流量，成本低）。

### Q19. HPA 为什么用「CPU 70% + 在飞请求 28」双指标？`maxReplicas: 6` 怎么来的？

**回答：** 单指标都会失灵：

- 只看 CPU：本服务大量时间在**等上游**（LLM、重排、Milvus），CPU 不高但并发已经打满，HPA 不会扩容，请求开始排队；
- 只看在飞数：冷启动时单实例并发 1 也占比很高，会误扩容。

所以两个指标取**较大值**。`kquery_inflight_requests` 的目标 `averageValue: 28`，是执行器上限 32 的 **87%**——留 4 个槽位给"扩容生效前到达的请求"，避免扩到阈值那一刻就开始 503。

`maxReplicas: 6` 不是拍脑袋：**上游 LLM 的账号配额决定了总并发**。单副本 12 个 LLM 许可，6 副本就是 72，已接近配额上限；再扩只会把超限错误从"本服务 503"变成"上游 429"，更难排查。这也解释了为什么 `minReplicas: 2`：单副本无法在滚动发布时保持 `maxUnavailable: 0`。

### Q20. PDB 与 PVC 在多副本下各带来什么约束？

**回答：** 两个约束方向相反：

- **PDB `minAvailable: 1`**：节点排水（drain）或集群升级时，至少保留 1 个 Ready pod。没有 PDB，节点维护可能一次性驱逐两个副本，全站断流。
- **PVC `ReadWriteOnce`**：数据目录只能被一个节点挂载。所以"2 副本"在数据目录这一层**并没有真正并行**——第二个 Pod 要么挂不上卷卡在 ContainerCreating，要么（如果用 local path/宿主目录）读到另一份互不相干的数据。

本项目的解法是把"必须共享的状态"外移到 Redis 与 Milvus：限流桶、语义缓存、幂等记录、会话都在 Redis；向量与文档元数据在 Milvus。`data/` 里剩下的 SQLite（图库/检查点）本质是"单写者"，所以部署约束是**后端只能有一个写者**，多副本时以 Redis 为准、本地库作为可重建缓存。

这也是一个可以主动讲的缺口：要让多副本完全无状态，需要把图库与检查点也迁到服务端数据库，`data/` 退化为纯临时目录。当前清单只做到了"能跑 2 副本"，没做到"2 副本完全等价"。

### Q21. NetworkPolicy 允许谁访问后端？不配会怎样？

**回答：** `networkpolicy.yaml` 只放通两条入站：**同命名空间的 frontend Pod** 和 **monitoring 命名空间的抓取器**，端口都是 8000。其余一律拒绝。

不配的后果不是"不能用"，而是**横向暴露**：默认 K8s 网络是扁平可达的，集群里任何一个被攻陷的 Pod（哪怕是别人的测试 Pod）都能直连后端 8000 端口，绕过 ingress 的限流与审计，还能直接打 `/admin/*`。

这条策略的实际价值在于把"入口收敛"变成集群强制而非应用自觉——前端是唯一入口（见 Q5）。代价是排障时要记得 `kubectl run` 一个临时 Pod 是**发不出请求的**，必须 `kubectl exec` 进 frontend 或临时给调试命名空间加策略，否则很容易误判成"服务挂了"。

### Q22. Service、ConfigMap、Secret 三者在清单里怎么分工？

**回答：**

- **Service**（`backend-service.yaml`）：`ClusterIP`，端口 8000，命名端口 `http`，`selector` 打 `app: kquery-backend`。ingress 与 ServiceMonitor 都靠这个命名端口引用，避免"改了端口号要改三处"。
- **ConfigMap**（`configmap.yaml`）：非敏感运行参数，如 `MODEL_PROVIDER`、`VECTOR_STORE`、`DATA_DIR`、日志格式、各 `*_ENABLED` 开关。它是**环境级**的，不随镜像变。
- **Secret**（`secret.example.yaml`）：`DASHSCOPE_API_KEY`、`REDIS_URL`（含密码）、`METRICS_TOKEN`，用 `secretKeyRef` 注入。

关键取舍是**配置不写进镜像**：同一镜像从 dev 到 prod 只换 ConfigMap/Secret，这也是"镜像可复现"的前提。`secret.example.yaml` 只是**结构示例**（占位值），真实 Secret 由 `kubectl create secret` 或外部密钥管理注入，绝不入库——仓库里 `deploy/k8s/base/secret.example.yaml` 顶部就写明这一点。

### Q23. `requests 500m/1Gi`、`limits 2/4Gi` 这组资源配额怎么定的？不符会怎样？

**回答：** CPU 与内存的语义完全不同：

- **CPU requests 500m** 决定调度与 HPA 的百分比基数（HPA 70% 就是 350m）。设太小会挤在一台节点上，设太大则 Pending。
- **CPU limits 2** 是硬节流（CFS quota）：超了就被 throttle，表现为 p99 抖动。所以给 4 倍余量，让突发（并发 32 线程同时摘要）不被掐。
- **内存 requests 1Gi / limits 4Gi**：本服务的峰值内存来自**文档解析与 BM25 索引**（几万 chunk 的倒排表 + jieba 词典），4Gi 是"单文档 50MB 上限 + 索引常驻"的经验上限。超限是 OOMKill，不是节流——所以内存 limits 必须留足，且 `memory` 类指标要进告警。

已知不严谨处：这组数字是经验值而非压测标定（`doc/analysis/11` 明确记了"未做内存剖面"）。正确做法是跑一次"上传 200 篇 × 5MB"的压测，看 `container_memory_working_set_bytes` 曲线再定 limits。

### Q24. `data/` 用 PVC，`/tmp` 用 emptyDir，为什么这么分？

**回答：** 按**数据是否需要跨 Pod 重启存活**来分：

- `data/`（PVC `kquery-data`）：向量索引元数据、图谱 SQLite、Agent 检查点、上传文件——必须活过重启，且要能被 cron 的 init 与备份脚本访问。
- `/tmp`（`emptyDir`）：解析中间产物（PDF 拆页图、Office 转 Markdown 的临时文件）、上传分片落盘。它**只在本 Pod 生命周期内有意义**，用 emptyDir 有三个好处：随 Pod 删除自动清理、不占 PVC 空间、写入走节点本地盘更快。

坑在于 `emptyDir` 默认吃节点磁盘：单个 50MB 文档解析会写几十 MB 临时文件，并发高时不清理会打爆节点 `disk-pressure`，把 Pod 驱逐。所以清单里可加 `sizeLimit`（如 2Gi），让超限变成"写失败"而不是"节点崩"。

### Q25. `CronJob` 版 init 的关键字段有哪些讲究？

**回答：** 清单里四个字段都是有意为之：

- `schedule: "0 3 * * *"`：业务低峰，避免建索引时抢占在线请求的 CPU；
- `concurrencyPolicy: Forbid`：上一次没跑完就跳过本次。建集合/别名切换不是幂等并发安全的，两个 Job 同时跑会出现"别名指向中间态"；
- `restartPolicy: Never` + `backoffLimit`：失败就停，让 `kubectl get jobs` 显式看到红色，而不是无限重试把日志刷没；
- `command: ["python", "-m", "app.cli.init_index"]`：用同一镜像，不额外维护一个 init 镜像。

补一个容易被问到的点：CronJob 会起一个完整后端进程（import 全部依赖），冷启动约 10–20s，但它的资源 requests 应设得比后端小（如 100m/512Mi），否则每次定时任务都会触发一次"资源不足"的调度峰值。

### Q26. `/metrics` 为什么要加 `METRICS_TOKEN`？ServiceMonitor 怎么带？

**回答：** 因为 Prometheus 指标里有**业务信息**：租户维度、分支比例、缓存命中、错误类型分布。裸暴露等于把内部运行状况对所有能访问 8000 端口的对象开放（见 Q21 的横向风险）。

实现是：`METRICS_TOKEN` 从 Secret 注入，`/metrics` 校验 `Authorization: Bearer`；ServiceMonitor 用 `bearerTokenFile` 指向挂载的 token 文件，`interval: 30s`、`scrapeTimeout: 10s`。

`scrapeTimeout < interval` 是硬要求，否则 Prometheus 会报 `context deadline exceeded` 并把 target 标 `up=0`，看起来像"服务挂了"其实是抓取超时。30s 的采集间隔对应告警的 `for: 5m`——**告警窗口必须远大于采集间隔**，否则一条瞬时抖动就能触发。

### Q27. 为什么用 kustomize 而不是 Helm？

**回答：** 因为本项目要的是**环境差异最小化**，不是"参数化一切"：

- `base/` 放完整可运行的一组对象，`overlays/dev`、`overlays/prod` 只用 `patches` 改副本数、资源、镜像 tag、环境变量；
- 部署命令就是 `kubectl apply -k deploy/k8s/overlays/prod`，没有 `values.yaml` 里几十个 `if` 分支；
- Helm 的模板渲染会隐藏"最终生效的 YAML"，而 `kubectl kustomize` 输出的就是**可以直接 diff 的成品**，Code Review 时能看到真实差异。

代价是缺少 Helm 的 release 版本管理（`helm rollback`）：回滚要靠"改镜像 tag 再 apply"或 `kubectl rollout undo`。对本项目这种单服务、少量对象的规模，这个代价小于维护一套 chart 的成本。

### Q28. dev overlay 与 prod overlay 差在哪？为什么 dev 要删掉 HPA 与 Ingress？

**回答：** 差异集中在四类：

| 项 | dev | prod |
| --- | --- | --- |
| 副本 | 1（`replicas: 1` patch） | 2 起，HPA 到 6 |
| 资源 | memory requests 512Mi | 1Gi / limit 4Gi |
| 依赖地址 | Milvus 指向 `host.docker.internal:19531` | 集群内 Service 或托管地址 |
| 模型 | deepseek + minimax `embo-01`（1536 维） | 同 prod 配置，走 Secret |

dev **删除** HPA、Ingress、ServiceMonitor 是刻意的：本地/开发集群没有 cert-manager 与 Prometheus Operator，留着这些 CRD 会导致 `kubectl apply` 报 `no matches for kind`，让"一键起 dev"失败。同理，`embo-01` 是 1536 维——dev 与 prod 的向量维度必须一致，否则切环境要重建索引，这是 dev overlay 里最容易踩的隐性约束。

### Q29. canary 清单里 `track: canary` 标签为什么必须加？端口有个什么隐患？

**回答：** `track: canary` 是**灰度隔离的前提**。Deployment 的 `selector` 与 canary Service 的 `selector` 都带这个标签，才能做到"canary 的 Pod 只被 canary Service 选中"；如果只靠 `app: kquery-backend`，base Service 会把新 Pod 一起纳入 Endpoints，**灰度立刻变成全量**——这是最常见的一类灰度失效，且从指标上看不出来（因为流量已经混了）。

端口隐患是真实的清单不一致：canary 的 `containerPort`/Service `targetPort` 写成了 **8100**，而镜像实际监听 **8000**（Dockerfile 的 `EXPOSE 8000` + `--port 8000`）。按现清单部署，canary Pod 会一直 NotReady（探针打不通），灰度压根启动不起来。正确做法是统一 8000，与 base 保持一致；这类"复制 base 清单改两处忘了第三处"的问题，靠 `kubectl diff` 与部署前 lint 才能拦住。

### Q30. K8s 清单里为什么完全没有 Milvus 与 Redis？

**回答：** 因为它们是**有状态的外部依赖**，不该跟应用同生命期：

- Milvus 依赖 etcd + MinIO + 自身三件套，运维复杂度远高于应用；社区推荐独立集群或 Zilliz Cloud；
- Redis 承担限流/缓存/幂等/会话，是**多副本共享状态**的核心，通常由云托管（或哨兵/集群）提供；
- 应用侧只通过 `KQUERY_MILVUS_URI`、`REDIS_URL` 接入，且都实现了**降级**：Milvus 不可用 → `/readyz` 判红但进程不重启；Redis 不可用 → 限流/缓存 Fail-Open 转本地（见 Q136）。

代价是"部署清单不完整"：新环境必须先手工准备 Milvus/Redis，`deploy/k8s/README.md` 把这一步写成前置条件。这个取舍是清晰的——把有状态服务的运维交给专业组件，好过在应用清单里塞三个 StatefulSet 然后没人敢升级。

### Q31. 线上 Pod 起不来，你的排障顺序是什么？

**回答：** 按"从调度到应用"四层逐层排除，每层只看一个信号：

1. **Pending** → `kubectl describe pod` 看 Events：资源不足（Q23 的 requests 太大）、PVC 挂不上（RWO 被占）、镜像拉不到（私有 registry 缺 imagePullSecret）。
2. **CrashLoopBackOff** → `kubectl logs --previous`：配置校验失败（`validate_startup` 抛错，见 Q52）、缺 Secret 导致 `KeyError`、`.env` 里的模型 Key 无效。
3. **Running 但 0/1 Ready** → 打 `startupProbe`/`readinessProbe` 失败：端口写错（Q29 的 8100）、`/readyz` 因索引为空或共享状态退化判红、`securityContext` uid 与卷属主不一致（Q13）。
4. **Ready 但请求 5xx/504** → 已进入应用层：看 ingress 的 `upstream timed out`（300s 超时）、看 `kquery_shed_total`（过载）、看上游熔断是否打开。

这条顺序的价值是**避免一上来就翻应用日志**：K8s 里 80% 的"服务挂了"其实是调度/配置问题，日志里什么都看不到。

### Q32. 集群配置层面还缺什么？

**回答：** 三处已知缺口，都能在面试里主动交底：

1. **没有拓扑分布约束**：两个副本可能落在同一节点，节点故障即全站断流。应加 `topologySpreadConstraints`（`topologyKey: kubernetes.io/hostname`，`maxSkew: 1`，`whenUnsatisfiable: ScheduleAnyway`）。
2. **没有 Velero 级别的集群备份**：现在的 `scripts/backup.py` 只备 `data/` 目录（Q81），备份文件仍在本机/同集群 PV，属于"同域备份"，机房级故障一起没。
3. **没有资源配额与 LimitRange**：命名空间层面没有 `ResourceQuota`，canary 与压测 Job 可能挤占生产配额。

这三条都不是"写起来难"，而是**没有演练就不会被发现**——所以它们被登记在 `doc/analysis/13-部署与运维.md` 的缺口清单里，而不是含糊地说"已具备生产就绪能力"。

## 四、Ingress / nginx / SSE

### Q33. `proxy-buffering: "off"` 到底关掉的是什么？不关会怎样？

**回答：** 它关的是 nginx 的**响应缓冲**：默认 nginx 会先把上游返回的 body 收进自己的 buffer（或临时文件），攒够一个 buffer 或收完再转发给客户端。

对 SSE 的后果是致命的：前端会看到"请求发出后长时间无输出，然后整段答案一次性出现"，或者干脆在 60s 时被断开——因为 nginx 认为"上游还没返回完整响应"。这不是性能问题，而是**流式语义被抹掉**，用户感知就是"卡住了"。

同一注解在 ingress 层（`deploy/k8s/base/ingress.yaml`）与容器内 nginx（`frontend.nginx.conf` 的 `proxy_buffering off`）各写了一次，**两层都要关**：只关一层，另一层照样缓冲。这是 SSE 排查里最常见的"改了一处没用"的原因。

### Q34. 既然有心跳 15s，为什么还要把 `proxy-read-timeout` 调到 300s？

**回答：** 因为两者解决的是**不同阶段的空闲**：

- 心跳 15s 保证的是"**已经有输出之后**，连接上始终有字节流动"，让反代的读超时不断被重置；
- `proxy-read-timeout` 管的是"**从发出请求到收到第一个字节**"这段空窗：检索 + 重排 + 首 token 可能十几秒，若超时设成默认 60s，遇到慢上游就会在**首字节前**被切断——此时心跳还没开始，救不了。

300s 是给"最坏首字延迟 + 生成时长"留的余量，同时**小于**前端 nginx 的 600s（Q39），保证超时总是由更靠前的代理先触发、返回可解释的 504，而不是后端连接被无声掐断。这个"超时逐层放大"的设计原则是反代链路的核心：`后端内部 120s < ingress 300s < 前端 nginx 600s < 客户端 900s`。

### Q35. 为什么还要 `proxy-request-buffering: "off"`？

**回答：** 它管的是**请求方向**的缓冲，而不是响应方向。

对普通 JSON 请求，开不开无所谓；但对两类场景是必需的：① **流式上传**（大文件边收边写盘，避免占内存）；② **请求体很大的 SSE/长轮询**（前端上传大文档时同时携带长 query）。

关掉之后 nginx 会把请求体**立刻转发**给上游，而不是攒满才发。代价是：如果上游处理慢，nginx 会一直占着与上游的连接（连接数略增），且**后端无法在请求体没收完之前快速拒绝**（比如 413 语义只能靠 `client_max_body_size` 提前拦）。

本项目把它和 `client_max_body_size 64m` 一起配，形成"入口就拦住超大请求、拦住之前不做无谓缓冲"的组合。

### Q36. 前端 nginx 用变量 `set $backend` 做 `proxy_pass`，为什么必须配 `resolver`？

**回答：** 这是 nginx 的经典陷阱：当 `proxy_pass` 里出现**变量**时，nginx 无法在配置加载阶段解析域名，必须在**运行时**通过 DNS 解析；而 nginx 自带的 resolver 不认 Docker 内嵌 DNS（127.0.0.11），会直接报：

```text
no resolver defined to resolve backend
```

所以容器内 nginx 必须显式写 `resolver 127.0.0.11 valid=10s;`（Docker）或集群 DNS（K8s 的 `kube-dns.kube-system.svc.cluster.local`）。

用变量的好处是**容器重启后 IP 变了也不用 reload nginx**（每次请求重新解析）；代价是每个请求多一次 DNS 查询（`valid=10s` 有缓存）且报错更晚（运行期才失败）。不用变量则相反：配置里写死 upstream 名，启动时解析一次，backend 换 IP 就 502 到下次 reload。

### Q37. `try_files $uri $uri/ /index.html` 为什么会 404？`@spa` 解决什么？

**回答：** 这是 nginx 的**内部重定向会重新走 location 匹配**导致的：`try_files` 最后一段是内部跳转，会重新匹配 location。如果后端代理用的是正则 location（`location ~ ^/(ask|knowledge|...)`），那么 `/index.html` 本身不匹配，但某些带后缀的 SPA 路由（如 `/sessions/abc` 里有前缀命中）会再次落进代理分支，被转发到后端 → 后端没有这个静态文件 → 404。

正确做法是把兜底写成**命名 location**：

```nginx
location / { try_files $uri $uri/ @spa; }
location @spa { try_files /index.html =404; add_header Cache-Control "no-cache, must-revalidate"; }
```

命名 location 只能被 `try_files` 显式调用，**不参与正则匹配**，从而切断"兜底又落回代理"的循环。同类坑还有：`^~ /static/` 用 `^~` 前缀优先（匹配到就不再看正则），否则 `/static/xxx.js` 也会被代理正则抢走。

### Q38. `client_max_body_size 64m` 与后端 `max_upload_mb` 为什么是 64 vs 50？

**回答：** 因为**两层都要有上限，且外层必须更宽**：

- 后端 `max_upload_mb=50` 是业务上限（Q47 的配置校验项之一），超出返回 413 并给出明确错误码；
- nginx 的 `client_max_body_size 64m` 必须**大于** 50，给 multipart 边界、表单字段、Base64 编码留余量（`curl -F` 加上 base64 会膨胀约 33%）。

如果反过来（nginx 设 50m、后端 50MB），用户上传"刚好 50MB"的文件会因为在 nginx 层计算的是**整个请求体**（含边界与头部）而被拒，且 nginx 的 413 页面**不是**后端的 JSON 错误结构，前端拿不到可读提示——这是典型"错误语义在网关层被截断"。

注释里也写了这个因果：`client_max_body_size 必须大于后端 max_upload_mb，否则大文件在 nginx 层就被拒`。

### Q39. ingress 300s、容器内 nginx 600s，为什么不是反过来？

**回答：** 因为超时必须**从内到外逐层放大**，让最外层先超时：

- 后端自己的 `ask_deadline_ms=120s` 是最内层预算，最先放弃并返回结构化错误；
- ingress 300s 是集群入口；
- 容器内 nginx 600s 在 ingress **后面**（客户端 → ingress → frontend Pod → 后端），它的超时如果小于 ingress，就会出现"内层先断、外层还在等"，外层只能报 504 而且拿不到内层的错误信息。

所以顺序必须是 `120 < 300 < 600`。反过来的后果是：ingress 先 504，前端 nginx 仍在等后端，用户看到的是"网关超时"，而后端其实还在正常生成——既浪费算力又难排查。

### Q40. upstream 里的 `keepalive 32` 是干什么的？

**回答：** 它是 nginx 到后端的**长连接池大小**：默认 nginx 对每个上游请求新建 TCP 连接，高 QPS 下会出现大量 TIME_WAIT、握手开销与端口耗尽；`keepalive 32` 保留最多 32 条空闲连接复用。

要真正生效，还必须同时设置：

```nginx
proxy_http_version 1.1;
proxy_set_header Connection "";
```

否则 nginx 默认发 `Connection: close`，keepalive 指令形同虚设——这是"配了没效果"的高频问题。

对 SSE 而言，长连接池的意义要打折：流式请求本身占住连接直到结束，复用只对**短请求**（探针、检索、配置读取）有效。32 这个数字对应"单副本 32 并发"的同量级估计，够用且不浪费后端连接槽。

### Q41. 为什么 `gzip_types` 里没有 `text/event-stream`？

**回答：** 因为 gzip 会**破坏 SSE 的实时性**：压缩算法需要攒够数据才能输出一个压缩块，nginx 虽然支持 `gzip_flush`/`proxy_buffering off` 组合，但压缩器自身的缓冲仍会让事件延迟数十毫秒到数秒，且 `EventSource` 客户端按行解析，压缩块边界与事件边界不一致时容易出"半条事件"。

所以配置里只压静态资源与 JSON：

```nginx
gzip on;
gzip_types text/css application/javascript application/json image/svg+xml;
gzip_min_length 1024;
```

`text/event-stream` 不在列表里，且它在 `location ~ /stream$` 分支中还额外 `proxy_buffering off`。代价是 SSE 响应不压缩、占用更多带宽（token 流本身是文本），但换来的是"逐字输出"的体感——这是在线问答里最值得的带宽交换。

### Q42. 静态资源 `expires 1y` 与 `index.html` `no-cache` 是怎么配合的？

**回答：** 这是 SPA 发布的**缓存失效双轨制**：

- 打包产物（`/static/`）文件名带内容哈希（`index-abc123.js`），内容变了名字就变，所以可以 `expires 1y` 强缓存，永不回源；
- `index.html` 是**入口**，它引用哪个哈希文件名是会变的，所以必须 `Cache-Control: no-cache, must-revalidate`——每次都回源校验（用 ETag/Last-Modified 协商），保证用户拿到新的引用关系。

这套组合的效果是：发布后用户第一次打开会拿到新 `index.html`，它引用新的静态文件（浏览器没缓存过，直接拉）；旧静态文件留在缓存里也不再被引用。

坑：如果 `index.html` 也被强缓存（比如统一加了 `expires 1y`），用户会**一直用旧版**，且无论后端怎么发版都不生效——这类问题只能靠改 URL 或让用户强刷，是前端发布事故的常见来源。

### Q43. 两份 nginx 配置的 location 前缀不一致，会造成什么后果？

**回答：** 仓库里有两份：`deploy/docker/frontend.nginx.conf`（容器内）与 `deploy/nginx/nginx.conf`（本机直跑）。前缀清单有差异——本机版漏了 `quickask`，容器版漏了 `auth`（认证下线后已无 `/auth` 路由，影响较小；`/quickask` 是活跃路由，影响真实）。

后果是**同一份前端代码在不同环境表现不同**：本机直跑时 `fetch("/quickask")` 不匹配任何后端前缀，落到 `try_files` 兜底，返回 `index.html`（200 但内容是 HTML），前端解析 JSON 失败，报"接口异常"——而不是 404，所以特别难查。

正确做法是把前缀清单做成**单一真相源**（例如由后端 OpenAPI 派生生成 `location` 块，或至少两边共用一份 include 文件），并在 CI 里断言两份清单一致。这类"配置双写"的漂移，靠人眼 review 基本拦不住。

### Q44. 为什么本机是 8100/8090、Milvus 19531、Redis 6381，而不是默认端口？

**回答：** 因为**宿主端口被别的项目占了**，容器内监听不变（后端 8000、前端 80、Milvus 19530、Redis 6379），只做宿主映射：

```yaml
ports:
  - "8100:8000"     # backend
  - "8090:80"       # frontend
  - "19531:19530"   # milvus
  - "6381:6379"     # redis
```

这样设计的好处是**端口冲突只影响入口，不影响镜像内部约定**——镜像永远监听 8000，K8s 也按 8000 配探针（Q29 的反例就是把这个搞混了）。

排查套路：`lsof -nP -iTCP:8000 -sTCP:LISTEN` 找出占用进程；`docker compose ps` 看映射是否生效；如果改映射，记得同步 `frontend.nginx.conf` 里的 `proxy_pass` 目标与 `KQUERY_API_TARGET`，否则前端仍打旧端口。

### Q45. TLS 在清单里怎么体现？为什么本地用假证书？

**回答：** ingress 的 `tls` 段引用 `secretName: kquery-tls`，证书**不由清单生成**，而由 cert-manager 的 `Certificate`/`ClusterIssuer` 自动签发并轮换（生产用 Let's Encrypt 或企业 CA）。

本地验证（kind / minikube）没有公网域名，申请不到证书，所以创建**自签 Secret**：

```bash
kubectl create secret tls kquery-tls --cert=selfsigned.crt --key=selfsigned.key
```

浏览器会报"证书不受信任"，但 TLS 链路、SNI、HTTP/2 协商都能验证——这对排查"SSE 在 https 下不工作"是必要的（有些浏览器对 http/1.1 长连接有不同的连接数限制）。

代价是自签证书有有效期，过期后 ingress 会报 `x509: certificate has expired`，表现为全站 502，容易被误判成后端故障。

### Q46. 如果要把 SSE 换成 WebSocket，反代侧要改什么？

**回答：** 三处必改，且都容易漏：

1. `Upgrade`/`Connection` 头：ingress 要加 `nginx.ingress.kubernetes.io/configuration-snippet` 里的 `proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";`；
2. 超时必须关掉或放到很大（WS 是永久连接，`proxy-read-timeout` 会周期断开）；
3. 容器内 nginx 同样要配（Q33 的双层原则）。

本项目选 SSE 的理由正是**省掉这一整套**：SSE 是普通 HTTP 响应，只要关缓冲、放大超时即可，探针、限流、鉴权、日志全部复用现有链路；且 `EventSource` 自带重连（配合 `Last-Event-ID` 做断点续传）。

SSE 的代价是**单向**：工具调用过程中的"用户中断"这类上行动作走不了同一连接，本项目用独立的中断接口解决，而不是升级成 WS。

## 五、配置与环境

### Q47. 配置的唯一真相源是什么？`.env`、ConfigMap、Dockerfile 谁说了算？

**回答：** 唯一真相源是 `backend/app/core/config.py` 的 `Settings`（pydantic-settings），其余都是**输入**：

```text
Dockerfile ENV < ConfigMap env < .env < 真实环境变量
```

优先级由 pydantic-settings 决定（环境变量 > `.env` > 字段默认值）。所以：字段名、类型、默认值、校验规则只写在 `config.py`；`.env.example` 是它的**生成物**（Q51）；K8s 的 ConfigMap 只是"往环境变量里塞值"的一种手段。

这条纪律的实际收益是**可审查**：任何人想知道"某个开关的默认值"，只需看 `config.py` 一处，不用去翻 compose、清单、文档三处对不上号。反过来，任何在 `.env.example` 里手写的新变量都不会被 `Settings` 认识，属于无效配置——这是新手最常踩的坑。

### Q48. `config_items()` 是干什么的？为什么每个字段要带 `required` 与 `hint`？

**回答：** `config_items()` 把 `Settings` 的字段反射成**结构化清单**（`key/value/required/hint/profile`），供三处消费：

1. `validate_startup()`：遍历清单，`required` 且为空就报"必填项缺失"；
2. 管理面 `/admin/config`（若开启）：展示"当前生效配置"，脱敏后返回；
3. 生成 `.env.example`：`scripts/gen_env_example.py` 用 `hint` 当注释。

`hint` 的价值在**错误可自解释**：例如 `MINIMAX_BASE_URL` 的 hint 明确写"必须含 `/v1`"，因为漏了 `/v1` 时上游返回的是 404 而不是参数错误，肉眼极难定位。把"踩过的坑"固化进 hint，等于把排障经验写进配置元数据。

### Q49. `effective_summary()` 与 `provider_notes()` 分别解决什么问题？

**回答：** 两个都是**启动期可观测性**，但回答不同问题：

- `effective_summary()`：返回"最终生效的关键配置"（provider、模型名、维度、开关位、执行器规模），启动时打一条 INFO 便于对齐"我以为配了"和"实际生效了"。排查"为什么走的是 mock"时，这一条日志往往直接给出答案。
- `provider_notes()`：返回**"配了但不生效"的提示**。典型例子：配了 `DASHSCOPE_API_KEY` 但 `model_provider=deepseek`，那么 DashScope 凭据存在却不会被用于生成；或 `rerank_provider=dashscope` 但重排模型名是 DeepSeek 的。它不做拦截，只在日志里提示，避免"配了三个 Key 只有一个是活的"这种沉默浪费。

两者都不改配置，只读——这是关键：**启动日志不能有副作用**，否则重试启动会产生不同的状态。

### Q50. 为什么 `model_provider=auto` 且没有任何凭据时，要求启动失败而不是降级成 mock？

**回答：** 因为"静默降级成 mock"在生产里是最坏的失败模式：服务**看起来健康**（`/readyz` 绿）、能返回答案（假答案），监控只有一条 INFO 日志。用户拿到的是"编造的内容"，比 500 危险得多。

所以 `validate_startup()` 里专门有一条：

```python
if self.model_provider == "auto" and not (dashscope or deepseek or minimax or zhipu 凭据):
    add("dashscope_api_key", "model_provider=auto 但未提供任何生成凭据，将静默降级为 mock", ...)
```

`create_app` 拿到非空 issue 清单就**抛错中止启动**。要跑测试环境必须显式写 `model_provider=mock`——把"我知道我在用假模型"变成一次显式声明，而不是让默认值替你决定。

### Q51. `backend/.env.example` 为什么是生成物？手改会怎样？

**回答：** 它由 `scripts/gen_env_example.py` 从 `config_items()` 反射生成，CI 里有一步 `gen_env_example.py --check`：生成结果与仓库中文件不一致就**判红**。

手改的后果不是"文件坏了"，而是"改了会被下次生成覆盖"，且 CI 立刻失败。这个设计的目的是防止**文档与代码漂移**：新加一个配置字段忘了写进示例，用户就不知道有这个开关；示例里留着一个已删除的字段，用户配了却毫无作用。

正确的修改流程是：改 `config.py`（字段 + 注释 hint）→ 跑生成器 → 提交生成结果。`tests/unit/test_env_example.py` 会在单测层面再兜一次，所以"只改代码不改示例"在本地就会被拦。

### Q52. 启动期硬校验都校验了什么？为什么要让坏配置拒绝启动？

**回答：** 四类，都是"晚发现必然出事"的：

1. **必填缺失**：`required` 字段为空。
2. **枚举非法**：`model_provider` 只允许 `auto|dashscope|deepseek|minimax|zhipu|mock`；`embedding_provider` **不含 deepseek**（DeepSeek 没有 embeddings 端点）——这一条防止"以为能配，结果首次入库才 404"。
3. **凭据与模型一致性**：`embedding_provider=minimax` 却用千问模型名（只需 `embo-01`，1536 维）、`embedding_dim` 不是 1536、`minimax_base_url` 缺 `/v1`、`zhipu` 用了非 `embedding-3`（2048 维）等。
4. **并发硬约束**：各上游许可之和 ≤ `pipeline_workers`（Q145）；`llm_timeout_s × (max_retries+1) ≤ ask_deadline_ms`（Q186）。

拒绝启动的理由很直接：这些错误在运行期表现为**难解释的上游 400/404 或死锁**，而启动期表现为**一行可读的中文提示**。代价是"配置错一个字符就起不来"，所以每条 `add()` 都必须带 `hint`（Q48），把修复动作写清楚。

### Q53. `profile` 是干什么的？为什么生产要关掉 `/docs`？

**回答：** `profile` 是粗粒度的环境档位（`dev` / `prod`），用来表达"生产不该有的东西"：交互式 API 文档（`/docs`、`/redoc`、`/openapi.json`）、详细错误堆栈、宽松的 CORS。

关 `/docs` 的理由是**降低攻击面**：OpenAPI 文档会把所有路由、参数名、枚举值、示例值一次性交出去，等于免费提供侦察地图；且 Swagger UI 依赖外部 CDN，在生产网络里通常加载失败，形成"半坏页面"。

不一刀切的原因是可运维性：排查时临时打开 `/openapi.json` 对照字段很实用。所以它由配置控制而非编译期删除——但要配合访问控制（只允许内网/管理员），否则关掉又开回来等于没关。

### Q54. 19 个 `*_enabled` 开关怎么管？为什么很多默认关？

**回答：** 按**层次**分四组，每组解决一类风险：

| 组 | 例子 | 默认 | 关的理由 |
| --- | --- | --- | --- |
| 检索增强 | `crag_enabled`、`preprocess_enabled`、`image_vector_enabled` | 多数开 | 影响答案质量，已标定 |
| 生成可靠性 | `selfcheck_enabled`、`llm_fallback_enabled`、`parametric_fallback_enabled` | 开 / 谨慎 | 兜底会多一次调用，成本与延迟换正确率 |
| Agent | `agent_enabled`、`agent_hitl_enabled`、`agent_verify_enabled`、`memory_enabled` | 部分关 | 需要审批流/校验预算，未就绪时开=不可控 |
| 运维手段 | `degrade_ladder_enabled`、`canary_auto_rollback_enabled`、`otel_enabled`、`sse_resume_enabled` | **默认关** | 会自动改变线上行为，必须先演练 |

"默认关"的原则是：**会自主改变系统行为的开关，默认必须是关的**。例如 `degrade_ladder_enabled` 一旦打开，系统会按预算自动跳过预处理与改写，答案质量下降但用户不知道；`canary_auto_rollback_enabled` 会在判据命中时自动回滚，误判一次就是一次事故。它们必须由人先验证判据、再显式打开。

### Q55. 敏感配置怎么注入？轮换一次 Key 要动哪些地方？

**回答：** 注入方式分环境：本地走 `backend/.env`（gitignore），K8s 走 Secret + `secretKeyRef`，CI 走仓库 Secrets。代码里只通过 `Settings` 读取，从不落日志（`/admin/config` 返回时脱敏）。

轮换一个 Key 的实际动作链：① 新 Key 写入 Secret/.env；② **滚动重启**（配置在进程启动时读取一次，见 Q56），否则老进程仍用旧 Key；③ 若轮换了 `METRICS_TOKEN`，必须同步更新 Prometheus 侧挂载的 token 文件，否则 `/metrics` 全 401、target 变 `up=0`（表现为"监控全挂"）；④ 若轮换了 Redis 密码，`REDIS_URL` 变更后需确认所有副本都重启，否则新旧密码共存期间限流/缓存会 Fail-Open 到本地（Q136），指标上看到缓存命中率骤降。

最容易漏的是 ②：改了 Secret 但没触发滚动，`kubectl get secret` 显示新值，应用行为却毫无变化。

### Q56. 改配置需要重启吗？哪些配置能热生效？

**回答：** 分两类：

- **进程级配置**（`Settings`）：`import` 时读取一次，之后是普通属性。改 `.env`/ConfigMap **必须重启**（`kubectl rollout restart`）。这是有意为之：pydantic 校验只在启动做一次，运行期不变才能让"启动期校验通过 ⇒ 运行期配置合法"成立。
- **检索/生成策略配置**：走管理面的 `pending` 机制——提交后进入待生效区，人工点"生效"才切到活跃配置，也可以"重置"回退。生效时会把 `config_digest` 计入缓存键（Q169），所以**改配置会自动让旧缓存失效**，不会出现"改了参数还在命中旧答案"。

热配置的代价是要处理并发读写（Q158 的读写锁）与"部分副本先生效"的不一致窗口。所以它只覆盖检索参数，不覆盖模型凭据与执行器规模。

### Q57. 怎么发现"配置漂移"？

**回答：** 三道检查，各管一层：

1. **代码与模板**：CI 的 `gen_env_example.py --check`（Q51）——字段集合漂移立刻红。
2. **模板与运行时**：启动日志打 `effective_summary()`（Q49）——"我以为配了 minimax，实际生效 dashscope"这类问题一眼看出。
3. **配了但不生效**：`provider_notes()`（Q49）——多 Key 并存时的沉默浪费。

还有一个隐性检查是**启动期校验**（Q52）：维度、枚举、凭据组合的漂移会在启动时直接失败，而不是等到第一次检索。

缺的一层是**集群与仓库的漂移**：`kubectl get deploy -o yaml` 与 `deploy/k8s/base` 的 diff 没有自动化。正确做法是 `kubectl diff -k deploy/k8s/overlays/prod` 纳入发布前置检查——这条已登记为缺口，不是已实现能力。

### Q58. 换 embedding 模型时，为什么必须重建集合？

**回答：** 因为**向量维度与语义空间都变了**：

- 维度：`embo-01` 是 1536，智谱 `embedding-3` 是 2048。Milvus 集合的 schema 在建集合时就固定了维度，写入 2048 维会直接报错；即便强行改 schema，旧向量也是 1536 维的，混合检索会崩。
- 语义空间：同维度不同模型（如两家的 1536）也无法混用——向量之间的余弦相似度失去意义，检索结果会变成噪声，但**不报错**，这是最危险的情况。

所以启动校验把"provider 与模型名/维度"绑死（Q52），切换路径固定为：改配置 → 新集合（新名字/新别名）→ 全量重嵌入 → 别名切换 → 观察 → 删旧集合。`index_version` 会进缓存键（Q169），保证切换后不会命中旧向量算出的缓存结果。

## 六、发布与灰度

### Q59. 灰度为什么要独立 Deployment + 独立 Service，复用 base 不行吗？

**回答：** 不行，因为**流量选择靠 selector**。base 的 Service `selector` 是 `app=kquery, component=backend`，canary 若打同一组标签，会被 base Service 直接选中，形成"新旧 Pod 共享同一组 Endpoints"——灰度比例变成"按 Pod 数随机"，而你想控制的比例、想单独观测的指标都不存在了。

所以 canary 单独起 `track: canary` 标签 + 独立 Service + 独立 Deployment（`replicas: 1`）。这样：① 灰度流量由 ingress/网关按比例或按 header 导到 canary Service；② canary 的指标天然带 `track` 维度，可以直接和 base 对比；③ 回滚只需删 canary，不动稳定版。

代价是**两份清单要保持同步**（镜像、配置、探针、资源）。本项目用"同镜像同配置、只差副本数与标签"的纪律来降低漂移风险，且 `kustomize` 的 base 被两边共同引用。

### Q60. 灰度为什么要"同镜像、同配置"，只改标签与副本？

**回答：** 因为灰度的目的是**验证新版本**，不是验证新配置。若 canary 同时换了镜像和配置，一旦指标劣化，你无法区分是代码问题还是配置问题——归因失败会让回滚变成"回滚了但不知道有没有回滚对"。

所以 canary 清单顶部就写明"与 base 同镜像、同配置，副本数 1"。镜像 tag 由发布流水线统一注入（同一个 digest），配置通过 `envFrom` 引用同一份 ConfigMap/Secret。

唯一的差异是 `replicas: 1`（省资源、够统计）与 `track` 标签（隔离流量）。这个纪律还带来一个副作用好处：canary 与 base 的对比是**单变量实验**，指标差异可以直接归因到代码。

### Q61. CanaryRule 的 `min_samples: 30` 是什么？样本不足时会怎样？

**回答：** 它是**统计显著性下限**：样本数低于 30 时，`evaluate_rule` 直接给出"不判劣化"的结论（`samples < rule.min_samples → "样本数 N < 下限 30：不判劣化"`）。

原因是最小样本下的比率极不稳定：10 个请求里 1 个 500 就是 10% 错误率，会立刻触发"错误率 > 5%"的判据，把一次随机抖动误判成劣化。30 是经验阈值（中心极限定理的粗用）。

代价是**小流量灰度必须熬时间**：canary 只有 1 副本、每分钟几十个请求时，30 个样本要等几分钟——这段时间里劣化会真实影响用户。所以判据设计成"样本不足就不动"，宁可慢，不可误杀；同时用 `min_samples` 之外的第二道保护（Q63 的自动回滚默认关）。

### Q62. 灰度判据怎么配？举一个能真正拦住事故的规则

**回答：** `canary_promote.py` 接受 JSON 规则数组，每条是 `{metric, direction, threshold, min_samples}`，默认示例：

```json
[{"metric": "error_rate", "direction": "gt", "threshold": 0.05, "min_samples": 30}]
```

即"5xx 占比超过 5%（且样本够 30）判劣化"。这条能拦住的事故形态是**新版本引入的确定性错误**（改错接口、序列化失败、配置读取异常）——它们在 canary 上会立刻表现为 5xx 升高。

更完整的一套还该有：`p95_latency gt 30s`（性能回退）、`cache_hit_rate lt 0.3`（缓存键改错导致命中率崩）、`shed_total` 增长（过载提前）。判据的方向（`gt`/`lt`）必须与指标语义匹配，写反了就是"越劣化越通过"，这是配置灰度时最危险的错误。

### Q63. `canary_auto_rollback_enabled` 为什么默认关？

**回答：** 因为自动回滚是一个**会自己动手改变线上状态**的动作，误判的代价是"把好版本撤了"。判据依赖的指标本身有噪声：上游抖动会让错误率瞬间越过 5%、Milvus 慢查询会让 p95 越线、样本数刚过 30 时置信度依然很低。

所以设计是"判据先只读，人工确认后再打开自动执行"：默认 `False` 时，`canary_promote.py` 只输出判定结果与建议；显式打开后才会在命中判据时调用 `--action rollback`。

这与 Q54 的"会自主改变行为的开关默认关"是同一条纪律。打开前必须做的两件事：① 用历史数据回放，确认判据不会在正常波动上误触发；② 演练一次真实回滚，确认回滚后的 Pod 确实恢复旧镜像且流量切回。

### Q64. `canary_promote.py` 的一次发布流程是怎样的？

**回答：** 四步，且默认**干跑**：

1. **采集**：`MultiReplicaMetricSource` 从 Prometheus 拉 canary 与 base 的同一指标（`track` 维度区分），按 scope 对齐；
2. **判定**：逐条规则调 `evaluate_rule`，样本不足则"不判劣化"（Q61）；输出每条规则的 `samples / value / threshold / verdict.reason`；
3. **建议**：全部通过 → `promote`；任一劣化 → `rollback`；
4. **执行**：只有带 `--apply` 才真正设置 Deployment 镜像/权重，否则只打印计划。

干跑默认这一点很关键：灰度判据属于"会看错"的判断，先让人看到"它想做什么"再放行。脚本还支持 `--baseline` 传历史基线，避免用"当前 base 的瞬时值"当基线导致误判。

### Q65. 放量的阶梯怎么设计？为什么不能一次 50%？

**回答：** 推荐 `1 副本 → 10% → 50% → 100%`，每档至少观察**一个完整的流量周期**（通常 15–30 分钟），且每档都重新跑判据而不是复用上一档结论。

不能直接 50% 的理由是**爆炸半径**：如果新版本有确定性 bug（例如某个 provider 分支报错），10% 时有 90% 流量仍正常、用户可感知影响有限；50% 时一半用户受影响，且回滚需要把一半流量再切回来，期间缓存/连接池都被污染。

阶梯设计还要配**入口一致性**：本项目按 Pod 数做比例（canary 1 副本 / base N 副本），所以 10% 需要 base 约 10 副本——而 HPA 上限 6，实际能做到的最小灰度是约 1/7。这是"副本数即权重"方案的固有精度限制，要更细粒度得靠 ingress 的 `canary-weight` 注解。

### Q66. 回滚要回滚哪些东西？镜像回退就够了吗？

**回答：** 通常不够，要按"代码 → 配置 → 数据/索引 → 缓存"四层检查：

1. **镜像**：`kubectl set image` 回旧 digest（必须用 digest 而非 tag，tag 可能被覆盖）；
2. **配置**：若本次发布同时改了 ConfigMap（如 `chunk_size`、`top_k`），必须一起回；否则旧代码配新参数，行为仍是新的；
3. **索引/集合**：若发布包含"新 embedding 模型/维度"，**不能**简单回滚——旧代码读新集合会维度不匹配。正确顺序是先切别名回旧集合（Q58），再回滚代码；
4. **缓存**：`config_digest`/`index_version` 进缓存键（Q169），所以配置回退后旧缓存自动失效，不需要手工清；但**语义缓存**在 Redis 里仍可能命中"用新配置生成的答案"，需要按前缀删。

真正危险的是第 3 层：**代码可回滚，数据不可回滚**。所以涉及索引 schema 的发布必须走"双写/双集合"路径，而不是指望回滚。

### Q67. 滚动发布时，正在流式输出的回答怎么不被切断？

**回答：** 靠四层配合，缺一层就会有用户看到"答案输出到一半没了"：

1. **摘流先于停机**：`preStop: sleep 10` 让 Pod 在收到 SIGTERM 前继续服务，等 kube-proxy/ingress 把它从 Endpoints 摘掉（Q17）；
2. **总预算足够**：`terminationGracePeriodSeconds: 70`，给 SSE 连接 60s 完成时间；
3. **进程内优雅退出**：`lifespan` 里执行器 `shutdown(timeout=30)` 停止接新任务、等在飞任务收尾（Q112）；
4. **客户端可恢复**：`sse_resume_enabled` + `Last-Event-ID`，前端断线后能续上（Q68）。

真正的兜底是第 4 层——前三层只能提高"平滑结束"的概率，网络抖动、节点驱逐、OOM 都会让连接硬断。

反面做法是"发布时直接 `kubectl delete pod`"：SSE 立刻 502/中断，且因为 `maxUnavailable: 0` 会先起新 Pod 再删旧，问题被掩盖成"偶发中断"，很难定位。

### Q68. `Last-Event-ID` 续传怎么工作？它的能力边界在哪？

**回答：** 服务端在每个 SSE 事件里发 `id:`，浏览器重连时自动带 `Last-Event-ID` 请求头，服务端据此从该事件之后继续推送，避免重复与丢事件。

边界有三处：① **只有 `EventSource` 自动重连**才带这个头，`fetch` 手写流式读取需要自己实现；② 续传要求服务端**按请求保存事件缓冲**（本项目把已完成事件落在会话/检查点里），超出保留窗口就无法续；③ 跨副本续传需要缓冲共享（Redis），否则重连落到另一个 Pod 就接不上。

所以 `sse_resume_enabled` 默认是关的（Q54 的纪律）：它需要额外的存储与清理逻辑，且在没有验证过"跨副本续传"前打开，会给用户"有时能续、有时不能"的不确定体验。

### Q69. 发布后缓存全冷，会不会把上游打爆？

**回答：** 会，这是"发布引发的雪崩"：新版本 Pod 的本地缓存（内存 LRU）是空的，同一批热点问题会同时穿透到检索与 LLM；若 2 个副本同时发布，穿透量翻倍。叠加 `maxSurge: 1` 的第三个 Pod，瞬时上游调用可能是稳态的 2–3 倍，直接触发上游 429 或本服务许可排队。

三道缓解：① **共享缓存**：语义缓存放 Redis（`cache_backend=auto/redis`），新 Pod 直接复用，不穿透；② **灰度发布**（Q65）：一次只放一部分流量，穿透量可控；③ **预热**：发布后用离线脚本重放 Top-N 问题（本项目有评测集，可作为热查询来源），把缓存填回。

最不该做的是"发布完立刻全量切流 + 同时清缓存"。清缓存应该是独立动作，不能和发布耦合。

### Q70. 发布时 HPA 与 PDB 会怎么影响你？

**回答：** 两个方向相反的力：

- **HPA 会扩容**：`maxSurge: 1` 让发布瞬时多一个 Pod，HPA 看到 CPU/在飞上升可能再拉副本，导致"发布期间副本数超标、`maxReplicas: 6` 提前打满"，之后再缩容又触发一次滚动。
- **PDB 会阻挠驱逐**：`minAvailable: 1` 意味着节点 drain 时至少留 1 个 Ready Pod；如果两个副本恰好都在同一节点（Q32 缺拓扑分布），drain 会被 PDB 卡住，运维只能 `--force`，等于绕过保护。

实操建议：发布期间**暂停 HPA 的缩容**（`behavior.scaleDown.stabilizationWindowSeconds` 调大），并把 `kubectl rollout status` 与 `kubectl get pdb` 一起看。如果 PDB 显示 `ALLOWED DISRUPTIONS: 0`，说明此刻做节点维护会阻塞——这是要提前发现的，不是等运维来问。

## 七、可观测与告警

### Q71. 可观测的四个层次各自回答什么问题？

**回答：**

| 层 | 载体 | 回答 |
| --- | --- | --- |
| 指标 | `/metrics`（Prometheus） | **整体是否健康**（速率、比例、分位、并发） |
| 日志 | stdout JSON / text + `X-Trace-Id` | **这一次为什么失败**（异常栈、上游返回体） |
| 链路 | `otel_enabled` → OTLP | **时间花在哪一段**（检索/重排/生成/工具） |
| 业务事件 | `rag_*` 计数与分支比例 | **产品行为是否正常**（CRAG 分支、缓存、工具调用） |

四层不能互相替代：指标能告诉你"p95 30s"，但不能告诉你是 Milvus 慢还是 LLM 慢；trace 能定位到段，但采样有丢失；日志最全但无法聚合。

本项目把"请求级排障"收敛到一条：响应头 `X-Trace-Id` 同时出现在日志、指标 exemplar（若开启）与前端错误提示里，从用户报障到定位只需一个 ID。

### Q72. 八条告警的阈值是怎么来的？逐个说依据

**回答：**

| 告警 | 阈值 | 依据 |
| --- | --- | --- |
| `InflightNearLimit` | `>28` for 5m | 32 的 87%，留 4 槽给扩容前的到达请求 |
| `QueueDepthHigh` | `>150` for 3m | 队列 200 的 75%，超过即"排队→503"邻近 |
| `UpstreamCircuitOpen` | `==1` for 1m | 熔断只要有 1 个上游打开就 critical，因为它会持续失败 |
| `CacheHitRateLow` | `<0.3` for 15m | 低于 30% 等于缓存没起作用，成本不可控 |
| `ToolSuccessRateLow` | `>0.1` for 5m | 工具失败率 10% 是"工具链退化"的经验线 |
| `AgentIterationLimit` | `>3` for 10m | 验收口径平均 ≤3 轮，打满说明在空转 |
| `HighErrorRate` | `5xx >5%` for 5m | 真实失败语义（已在代码里修成真 5xx） |
| `LatencyHigh` | `p95 >30s` for 10m | 接近 `ask_deadline_ms=120s` 的四分之一，用户已明显等待 |

两条可讲的取舍：**`for` 时长与本服务的请求节奏强相关**（一次问答几十秒，5m 窗口才够积累样本）；**`clamp_min(..., 0.001)` 防除零**，否则无流量时表达式变成 `0/0 = NaN`，告警既不触发也不报错，静默失效。

### Q73. 为什么 `KqueryUpstreamCircuitOpen` 是 critical，而 `InflightNearLimit` 只是 warning？

**回答：** 因为两者的**自愈能力**不同：

- `InflightNearLimit` 是**容量信号**：系统还在正常工作，只是接近上限。HPA 会扩容（Q19），只要观察即可，属于 warning。
- `CircuitOpen` 是**功能已经降级**：某个上游被熔断后，相关能力直接不可用（例如 embedding 熔断 → 无法入库；rerank 熔断 → 检索质量降级）。它不会自愈，只会每 30s 探一次半开（Q147），需要人介入查上游或换 provider。

分级的意义在于**定义值班动作**：critical 要求"立即查看并按处置卡操作"，warning 允许"下一个工作时间处理"。如果所有告警都是 critical，值班会迅速脱敏——这是告警设计里最常见的失败。

### Q74. 为什么有两套指标前缀（`kquery_*` 与 `rag_*`）？

**回答：** 因为它们的**维度模型不同**：

- `kquery_*`：进程/网关层，偏"基础设施"——`http_requests_total{method,route,status}`、`http_latency_seconds`、`inflight_requests`、`queue_depth`、`upstream_in_use/permits`、`shed_total{reason}`。
- `rag_*`：业务链路层，偏"RAG 语义"——`rag_cache_total{result}`、`rag_retrieval_stage_ms`、`rag_branch_ratio`、`rag_agent_tool_*`、`rag_agent_iterations`。

两套拆开的好处是**聚合时不混淆**：算"接口错误率"只用 `kquery_http_*`，不会被业务计数污染；算"缓存命中率"只用 `rag_cache_total`，不受 HTTP 维度影响。

代价是排查时要跨两套查询，所以命名规范必须稳定（`rag_*` 由检索/生成链路统一发，不按模块随意起名）。

### Q75. 直方图分桶怎么选？为什么不干脆用超细粒度？

**回答：** 分桶要覆盖**SLO 关注区**，且有上界：

- `kquery_http_latency_seconds`：从 `0.01` 到 `60`，因为本服务的延迟跨度极大——探针 1ms、检索 200ms、完整问答 30s+。分桶在 1s/5s/10s/30s 附近加密，正好对应告警阈值（p95 > 30s）。
- `rag_retrieval_stage_ms`：按毫秒 `1~1000`，因为单阶段（BM25、向量、融合、重排）都在几十到几百毫秒量级，用秒级桶会全落在第一个桶里，分位毫无意义。

不细化的原因是**成本**：每多一个桶就多一条时间序列，桶数与标签组合相乘。`histogram_quantile` 的精度受桶边界限制，够用即可——追求 1% 精度换来 10 倍存储不划算。

反面坑：桶上界太小（比如只到 10s）会让所有慢请求落进 `+Inf` 桶，p95 直接算成 10s，看起来"很快"，实际全是超时请求。

### Q76. 指标标签怎么控制基数？`<unmatched>` 是什么？

**回答：** 三条硬规则：

1. **route 用模板不用真实路径**：`/knowledge/doc/{doc_id}` 而非 `/knowledge/doc/8f3a...`。否则每个文档 ID 一条序列，几千文档直接把 Prometheus 打爆。
2. **不放高基数维度**：`tenant/user/query/trace_id` 一律不进标签（trace_id 进日志与响应头）。
3. **必须有兜底桶**：未匹配到模板的 route 归入 `<unmatched>`，而不是新建标签值。

`<unmatched>` 的价值是**可发现**：它的计数如果持续增长，说明有新路由没登记模板——这本身就是一个需要修的 bug，而不是让它悄悄制造基数。

代价是排障时按 route 聚合会丢掉 URL 里的 ID 细节；需要具体 ID 时用 `X-Trace-Id` 回查日志，而不是靠指标。

### Q77. 日志与 trace 怎么关联？为什么默认不是 JSON？

**回答：** 关联靠 `X-Trace-Id`：请求进入时生成（或透传上游），写进日志的每个结构化字段，同时回写给客户端。

日志格式由 `LOG_FORMAT` 控制（`text` / `json`）：

- **默认 `text`**：本机开发直接看得懂，`tail -f` 友好；
- **生产建议 `json`**：便于 Loki/ELK 按字段检索（`trace_id`、`route`、`status`、`duration_ms`）。

不默认 json 的理由是本地体验：开发时满屏 `{"level":"INFO","ts":...}` 反而难读。代价是生产若忘了切，日志检索只能靠正则——这是一个"部署时必须显式设置"的配置项，已登记在 `.env.example` 的 hint 里。

### Q78. `scripts/metrics_cardinality.py` 是干什么的？

**回答：** 它是**部署前的基数预估器**：给定路由数、租户数、模型数等维度组合，算出"这套标签设计会产出多少条时间序列"，超过阈值就提示收敛。

为什么需要它：基数爆炸是**上线后才爆**的问题——开发环境只有几条序列，生产一放量（几百租户 × 十几个 route × 多个 status）就变成几十万条，Prometheus 内存飙升、抓取超时、告警延迟。等到那时再改标签，历史数据全断。

所以正确做法是把"标签设计"当代码评审项：新增一个标签维度时，先跑一遍预估，确认乘出来的量级可接受。这条工具的存在本身就是"我们把基数当设计约束"的证据。

### Q79. 有没有正式定义 SLO？没有的话怎么回答？

**回答：** 诚实的回答是：**没有正式 SLO 文件**，只有告警阈值与验收口径（Agent 平均迭代 ≤3、检索回退 >2pp 判红、p95 参考 30s）。

没有 SLO 的后果是"告警有了，但说不清多差算违反承诺"：99.9% 可用性对应每月 43 分钟不可用，而当前告警是"5xx > 5% 持续 5 分钟"，两者无法换算。

如果要补，最小可用的一套是：可用性 `99.9%`（按 `kquery_http_requests_total` 非 5xx 计）、首字节 p95 `≤5s`、完整回答 p95 `≤30s`、错误预算按周结算。之所以没写，是因为没有真实流量基线——**先有测量再定 SLO** 比抄一套数字更负责。

### Q80. 成本怎么观测？有什么缺口？

**回答：** 现有能力是**计量**而非**告警**：每次 LLM/embedding/rerank 调用按 token 与单价折算成本（`INTENT_TOKEN_PRICE_YUAN`、`ESTIMATED_TOKENS_PER_CALL`），管理面能看"按租户/按意图"的花费；预算有软/硬阈值（超软阈值提示、超硬阈值拒绝）。

缺口有三个：① 没有"成本速率"告警（例如"每小时花费 > X"），只有事后查看；② token 是**估算**（用 `ESTIMATED_TOKENS_PER_CALL` 兜底），与账单有偏差；③ 成本指标没有进 Prometheus，无法和历史趋势对比。

这正是 `cache_hit_rate < 30%` 告警存在的原因：缓存是最大的成本杠杆，命中率掉了成本就翻倍——用一个**能反映成本的间接指标**替代直接成本告警，是在缺少计费接入时的务实选择。

## 八、备份、恢复、演练

### Q81. `scripts/backup.py` 覆盖哪些数据？哪些不在覆盖范围内？

**回答：** `TARGETS` 清单里是**关键元数据与状态**：`metadata.json`、`graph.db`、`resolver.json`、`sessions/`、`agent_checkpoints.db` 等五类，每项带 `required` 标记——缺失即报错（而不是静默跳过）。

不在范围内的有：**docstore 原始解析结果、Milvus 集合、`uploads/`、`assets/`、`index_alias`、图片向量集合**。这个划分的依据是"**可再生 vs 不可再生**"：解析结果和向量索引可以从上传的原文件重新解析、重新嵌入得到；而元数据、图谱、会话、检查点是业务产生的新信息，丢了无法重建。

诚实的风险：`uploads/` 里的原文件如果没备份，索引就无法重建——所以"索引可重建"的前提是"原文件另有备份"。这条依赖在文档里写明了，属于**必须与存储层备份配合**的设计，而不是"备份脚本已完备"。

### Q82. 为什么每个备份要写 `manifest.json` 与 `RESTORE.md`？

**回答：** 两个文件解决两个不同问题：

- `manifest.json`：记录每个文件的 `sha256` 与 `size`，以及备份时间、项数。它让"备份是否完整"变成**可验证**的（`--verify` 逐文件比对哈希），而不是靠"目录存在"判断。备份介质损坏、拷贝截断这类问题，只有哈希能发现。
- `RESTORE.md`：把**恢复步骤随备份一起走**。灾难恢复时最怕的是"备份在，但没人记得怎么恢复、要恢复哪些文件、依赖顺序如何"——尤其当备份被拷到另一台机器、原运维不在场时。

这是"备份的价值在恢复，不在生成"的具体体现。代价是每次备份多写两个小文件、多算一遍哈希（几 GB 数据约几十秒），完全值得。

### Q83. `--keep 7` 的保留策略怎么实现的？为什么不是越多越好？

**回答：** `_prune()` 按目录内 `manifest.json` 的存在识别有效快照，按时间排序后**只保留最近 `keep` 份**，超出删除。`--keep 0` 表示不删（调试用），默认 7 份。

7 的取舍：按日备份覆盖一周，能应对"上周改坏了数据但现在才发现"这类延迟发现的问题；再多则占空间且**恢复时选择困难**（人也倾向于挑最新的，旧备份形同虚设）。

关键细节是**只删带 manifest 的目录**：避免把 `out_dir` 下其他文件（比如手工放进去的导出文件）误删。另外删除是按"份"而非按"天"，如果一天跑了两次，7 份只覆盖 3.5 天——所以定时任务应保证每天一次（与 Q25 的 CronJob 对应）。

### Q84. 恢复演练做了什么？边界在哪？

**回答：** `scripts/restore_drill.py` 的流程是：在**临时目录**里造数据 → 备份 `--keep 3` → **清空**临时数据 → 从备份回填 → 逐文件校验哈希 → 断言关键文件非空。

它验证的是"**备份-恢复闭环可用**"，不是"生产可恢复"：① 数据是脚本造的小样本，不是真实几 GB 数据，恢复耗时不可外推；② 恢复目标是临时目录，不涉及改配置、重启服务、切别名；③ 不覆盖"备份介质本身损坏"的情况。

这个边界必须讲清楚：演练通过只说明脚本逻辑对，**不等于**RTO 达标。要验证真实 RTO，需要在预发环境用生产规模数据完整走一次"删库 → 恢复 → 服务起来 → 抽查问答"。

### Q85. 这个项目的 RPO / RTO 是多少？

**回答：** 按当前实现只能给出**上限估计**，不能说"达标"：

- **RPO ≈ 24h**：备份按天跑（CronJob `0 3 * * *`），最坏丢一天的数据。若要压到 1h，需要改成小时级增量备份 + 变更日志。
- **RTO 未实测**：恢复脚本能跑通（Q84），但没有在真实数据量上测过耗时。粗估由三段组成：拉取备份（网络/介质）、解压回填（磁盘 IO）、重建索引（若需要重新嵌入，成本最高，取决于文档数与调用配额）。

诚实的结论是：**RPO 由调度周期决定，可计算；RTO 由数据规模与重建成本决定，未标定**。面试里这样回答比报一个"RTO < 30 分钟"的数字可靠——后者在没有演练的情况下就是编的。

### Q86. 备份存在同一块盘上，问题有多大？

**回答：** 等于**没有备份**。同盘意味着单一故障点覆盖两者：磁盘坏、文件系统损坏、误 `rm -rf`、勒索软件加密，都会同时干掉数据与备份。当前 `--out` 默认是 `data/backups/`，正好在 `data/` 里面——这是最危险的默认值。

正确配置是 `--out /mnt/backup/kquery`（独立卷/网络盘），脚本帮助里也给了这个例子。进一步要求是**异地**（另一可用区/对象存储），否则机房级故障仍然一起没。

这条是"配置正确性依赖使用者"的典型：脚本提供了能力，但默认值不安全。更好的做法是默认就要求显式传 `--out`，且拒绝落在 `--data-dir` 之内——目前没有这层校验，属于已知缺口。

### Q87. 哪些数据"可再生"？重建代价多大？

**回答：** 分三档：

| 数据 | 可再生 | 代价 |
| --- | --- | --- |
| 向量集合（Milvus） | 是 | 全量重嵌入：文档数 × chunk 数 × 单价，最贵 |
| BM25 索引 | 是 | 本地重建，秒级到分钟级（取决于 chunk 数） |
| 解析结果（docstore） | 是 | 重新解析原文件，CPU 密集，OCR 更慢 |
| 元数据/图谱/会话/检查点 | **否** | 丢失即永久丢失 |

所以备份策略应优先保"不可再生"的部分（当前 `TARGETS` 正是这么选的），而"可再生"的部分靠**保留原文件 + 可重放流水线**来保障。

一个关键前提：重建必须是**幂等且可重放**的（这也是 init 容器要幂等的原因，Q3）。如果重建脚本跑两次产生两份 chunk，那"可再生"就是假的。

### Q88. 演练暴露了哪些真实缺陷？怎么补？

**回答：** 五条，按严重度排：

1. **备份与数据同盘**（Q86）——改为默认外置，并校验 `out` 不在 `data/` 内；
2. **不覆盖 `uploads/`**——原文件丢失则索引不可重建，应把上传目录纳入备份，或明确要求对象存储托管；
3. **无异地副本**——加一次 `rclone`/`aws s3 sync` 到异地；
4. **演练规模过小**（Q84）——在预发用生产规模跑一次，标定 RTO；
5. **恢复后无自动校验问答**——恢复完应跑一组固定问题，确认检索链路可用，而不只是"文件哈希对"。

这五条都登记在 `doc/analysis/13-部署与运维.md` 的缺口台账里。面试时主动交底比被追问出来好：**知道自己的备份能恢复到什么程度**，本身就是运维成熟度的体现。

## 九、安全与合规

### Q89. 这个项目有身份认证吗？没有的话安全边界靠什么？

**回答：** **没有**。认证与 ACL 已整体移除：`backend/app/api/` 下没有 `auth.py`，`config.py` 里 `auth_*` / `acl_enabled` / `kb_enabled` 一并删除（只留注释说明），请求身份恒为 `default`/`local`。

所以安全边界完全靠**部署层**：

1. **网络**：NetworkPolicy 只允许 frontend 与 monitoring 访问后端（Q21），ingress 是唯一入口（Q5）；
2. **入口**：`client_max_body_size`、非 root、`/docs` 关闭、`/metrics` 带 token（Q26）；
3. **应用内**：提示注入风险检测（内容打标 + 融合阶段降权）、敏感词拦截、输出不落盘。

必须诚实说明：这是**单租户内网工具**的定位，不是多租户 SaaS。一旦要开放到公网或多客户，认证是第一优先级——当前状态被明确登记为"最危险的部署缺口"，而不是"简化设计"。

### Q90. 为什么把认证下线了？代价是什么？

**回答：** 因为它是**未被使用的复杂度**：本项目的实际形态是"团队内部知识库问答"，部署在内网、入口由网关守；而认证模块带来的是登录页、会话、令牌刷新、ACL 表、审计日志、配额、用户管理一整套，测试面与故障面都很大（历史上 `/auth/login` 的限流桶、口令档、身份头三套模式就长期混用）。

下线之后代码量与配置项减少，链路更短。代价有三个，必须讲清：

1. **多租户语义退化**：限流桶、缓存键、配额都按"租户"设计，但租户恒为 `default`——等于**全站共享一个桶**，一个用户打满就是所有人受限；
2. **审计缺失**：谁上传了什么、谁问了什么，没有可信身份，日志只能记 IP；
3. **不能直接对外**：任何"开放公网试用"的想法都要先补认证，否则等于把内部知识库挂到互联网。

### Q91. 提示注入与内容安全，部署层能做什么？

**回答：** 部署层只能做**边界与资源**层面的事，语义层面必须靠应用：

- 部署层可做：请求体上限（防超大 payload）、限流（防批量探测）、网络隔离（防横向从别的服务注入）、`/metrics` 与 `/docs` 关闭（减少侦察面）、日志脱敏（不进日志的内容就不会被二次泄露）。
- 部署层**不能**做：判断"这段文档里是否藏着指令"。这类判断在应用层——入库时对 chunk 打风险标记、融合阶段按内容复判并惩罚 0.25（`INJECTION_RISK_PENALTY`）、生成时用系统提示约束、输出前做敏感词与合规检查。

答这类题的关键是**分清职责边界**：不要声称"有 WAF 就安全了"，WAF 拦不住"把指令写进 PDF 再上传"。

### Q92. 敏感信息可能从哪几个地方泄露？分别怎么防？

**回答：** 四条路径：

1. **代码仓库**：`.env` 误提交。当前做法是 `.env` 进 `.gitignore`、只提交 `.env.example`（生成物、无真实值）；风险是历史上曾提交过真实 Key，**只能靠轮换而不是删文件**解决。
2. **镜像层**：`docker build` 时把 `.env` 拷进去，即使后续删除，历史层里仍在。防法是 `.dockerignore` 排除 `.env`，且构建参数不落 `ENV`。
3. **日志**：异常栈里带出 `Authorization` 或 URL 里的 token。防法是日志只记 `route` 与状态码，密钥字段统一脱敏（`/admin/config` 返回值也脱敏）。
4. **指标**：把 token 写进 label（Q76 的基数问题同时是安全问题）。防法是标签白名单。

K8s 侧再加一条：Secret 用 `secretKeyRef` 注入而非明文 env，且不要 `kubectl describe` 到处贴。

### Q93. 容器最小权限还差什么？

**回答：** 已做：非 root（`USER kquery` + `runAsNonRoot: true`）、`fsGroup` 修卷权限、NetworkPolicy 限制入站、Secret 注入凭据。

还差的四条（都可直接加到 Deployment）：

1. **`readOnlyRootFilesystem: true`**：根文件系统只读，阻止运行时落马（需给 `/tmp` 与 `/data` 单独挂可写卷，Q24 已有 `/tmp`）；
2. **`allowPrivilegeEscalation: false`**：阻止 `setuid` 提权；
3. **`capabilities.drop: ["ALL"]`**：本服务不需要任何 Linux capability；
4. **`seccompProfile: RuntimeDefault`**：限制危险系统调用。

之所以没一股脑加上，是 `readOnlyRootFilesystem` 会暴露"某处偷偷写了当前目录"的问题（Python 的 `__pycache__`、临时文件），必须先确认所有写入都落在挂载卷上。这是"先让它跑起来、再逐步收紧"的务实顺序，但收紧这件事不能永远不做。

### Q94. 合规层面有哪些必须正视的问题？

**回答：** 三个绕不开的点：

1. **数据出境**：文档 chunk 与 query 会发给第三方模型 API（DashScope/DeepSeek/MiniMax/智谱），这意味着**知识库内容离开本地**。企业内网部署通常要求"敏感文档不入云"，当前实现的防线只有敏感词拦截，没有按文档密级阻断——这是真实缺口。
2. **日志保留**：会话与检查点落 SQLite、日志落 stdout，保留多久、谁能看、是否需要脱敏，都没有策略化配置。
3. **删除权**：删除一个文档时，需要同时清 Milvus 向量、BM25 倒排、docstore 解析结果、缓存（含语义缓存里引用它的答案）。当前有 `offline()` 下线流程，但**缓存中的历史答案不会被主动清理**，属于"删除不彻底"。

回答这类问题的正确姿势是：**说清数据流向，而不是说"我们合规"**。数据流向图谱（浏览器 → ingress → 后端 → 向量库 → 第三方模型）本身就是可交付的合规材料。

## 十、CI/CD 与交付质量

### Q95. CI 有哪些阶段？为什么把"配置模板一致性"放进 lint 阶段？

**回答：** `.github/workflows/ci.yml` 分五个 job：

1. `lint`：ruff + `gen_env_example.py --check`（配置模板漂移即红）；
2. `test`（矩阵：多个 Python 版本）：起 etcd + Milvus standalone，pytest + 覆盖率上传；
3. `test-quality`：静态检查"禁止恒真断言与死代码"、`conftest.py` 必须显式清理环境变量、根配置必须有 pytest 超时；
4. `retrieval-eval`：启动期配置校验、检索评测相对基线回退 >2pp 判红、成本-质量帕累托、生成质量门禁、切块实验、多模态评测、Agent 过程评测、索引重建演练（沙箱）；
5. `image`：锁文件一致性、构建镜像、smoke。

把配置一致性放 lint 的理由是**反馈速度**：它是纯字符串比对，秒级完成，没必要等到测试阶段；而且它失败意味着"文档承诺的配置项与代码不一致"，属于最该在 review 阶段暴露的问题。

### Q96. 为什么 CI 要跑"索引重建演练"和"检索评测"？

**回答：** 因为这两件事**在生产上做错的代价最高，而在 CI 里最容易被跳过**：

- **索引重建演练**（沙箱）：验证"删掉集合 → 重新建 → 数据一致"这条路径可执行。它防的是"代码能跑但重建脚本早就坏了"——真出事时才发现，等于没有恢复能力。
- **检索评测**：用固定评测集跑真 BM25 + mock 向量 + 真 RRF/重排，与基线比 **>2pp 回退判红**。它防的是"改一行融合逻辑，检索质量静默下降"——这类回退不会报错，只会让答案变差。

关键设计是**相对基线**而非绝对阈值：绝对分数会随评测集变化而漂移，相对回退才是"这次改动有没有伤到质量"的直接信号。代价是每次改基线要人工确认，否则会把回退当新基线。

### Q97. 镜像 tag 怎么打？为什么发布要用 digest？

**回答：** 三层命名：

- **代码版本 tag**：`kquery/backend:1.4.2`（人可读，用于回滚时指定目标）；
- **提交哈希 tag**：`kquery/backend:sha-8f3a1c7`（与代码一一对应，排查时精确）；
- **digest**：`kquery/backend@sha256:...`（内容寻址，绝不变）。

部署清单里**必须用 digest 或不可变 tag**：如果 Deployment 里写 `:latest`，`kubectl apply` 后 Pod 拉到的可能是缓存旧镜像（`imagePullPolicy: Always` 也只保证"重新拉"，不保证"拉到的是你以为的"），回滚时更是无法确认回退到了哪个版本。

CI 的 `image` job 会跑"锁文件一致性"（Q95），保证镜像构建输入的依赖是确定的；配合 digest，才算"发布可复现"。

### Q98. CI 里那三条"质量门禁"分别在防什么？

**回答：** 三条都是**防测试造假**：

1. **禁止恒真断言与死代码**：`assert True`、`assert result is not None`（永不失败的断言）、注释掉的代码块。恒真断言会让覆盖率很好看而实际什么都没验。
2. **`conftest.py` 必须显式清理环境变量**（`os.environ.pop`）：否则一个用例设的 `MODEL_PROVIDER=mock` 会泄漏到后面的用例，导致"单跑通过、全跑失败"或更糟的"假通过"。
3. **根配置必须有 pytest 超时**：没有超时，一个死锁（比如等一个永不返回的线程池）会让整套测试静默挂住，CI 卡到超时被杀，看起来像"基础设施问题"。

三条共同点是：**它们检的不是业务正确性，而是"测试是否可信"**。用 grep 实现的检查很土，但能拦住最常见的三类自欺。

### Q99. 一个新人拿到仓库，最短路径怎么跑起来？

**回答：** 两条路，都收敛在 `deploy/`：

- **全栈**：`docker compose -f deploy/docker/docker-compose.yml up -d --build` → 前端 8090、后端 8100、Milvus 19531、Redis 6381；`init` 容器自动建集合。
- **本机开发**：`uv sync --project backend --group dev --extra dev` → 填 `backend/.env`（从 `.env.example` 复制）→ `uv run --project backend uvicorn app.main:app --reload`；前端 `npm install && npm run dev`（Vite 代理到 `KQUERY_API_TARGET`）。

最容易卡住的三处：① 忘了 `--extra dev`，`pytest` 收集阶段缺 playwright 整片红；② `.env` 里没 Key 且没显式 `model_provider=mock`，启动被校验拒绝（Q50，这是**故意**的）；③ 宿主端口被占（Q44），需改映射或先腾端口。

### Q100. 部署层已知的 7 个缺口里，最危险的是哪个？怎么排优先级？

**回答：** 按"影响面 × 发生概率 × 可恢复性"排：

1. **无身份校验**（Q89）——影响面最大、且不可恢复（数据被任意读取/删除）。第一优先级，但需要产品决策而非纯技术。
2. **备份与数据同盘、且不覆盖 `uploads/`**（Q86/Q81）——一旦发生就是永久数据丢失，第二。
3. **两份 nginx 前缀漂移**（Q43）——活跃路由 `/quickask` 在某一环境不可用，属于"功能静默缺失"，第三。
4. **canary 端口 8100 与镜像 8000 不一致**（Q29）——灰度根本起不来，但**不造成生产事故**（只是发布手段失效）。
5. **uid 与镜像不一致**（Q13）——靠 `fsGroup` 兜住，属隐患。
6. **无拓扑分布 / 无异地备份**（Q32）——机房级概率低，但影响全站。
7. **清单注释过期**——纯文档问题。

这个排序本身可以讲成一个原则：**先修"不可恢复"（数据、权限），再修"不可用"（功能、发布手段），最后修"不舒服"（注释、告警噪音）**。

# 第二部分 · 高并发（Q101–Q200）

## 一、并发模型与漏斗

### Q101. 这个服务的并发由哪几类执行体构成？

**回答：** 五类，各有明确配额：

| 执行体 | 规模 | 承载 |
| --- | --- | --- |
| AnyIO 事件循环 | 1 | 所有 HTTP/SSE 处理、`await` 非阻塞逻辑 |
| AnyIO 默认线程池 | 40（注释所述默认值） | FastAPI 同步依赖、少量同步 IO |
| `PipelineExecutor` 问答执行器 | 32 线程 + 200 队列 + 50 低优先队列 | 整条 RAG 链路（同步阻塞） |
| 检索召回池 | 4 | BM25 与向量检索（隔离，见 Q156） |
| Agent run 池 / 工具池 | 16 / `max(8, run×2)` | Agent 循环与工具调用 |

此外还有后台任务池（入库、图谱构建）与存储层 `data/build` 锁。这个结构的核心思想是：**入口统一走一个有限队列，避免不同类型任务互相饿死**——所有问答共享 32 个槽，而不是各自开池。

### Q102. 为什么不把整条链路改成 async？

**回答：** 因为链路上的关键组件都是**同步阻塞**的：Milvus 的 `pymilvus` 客户端、BM25 的倒排表遍历、jieba 分词（CPU 密集）、本地 SQLite。

把链路改成 async 有三种做法，都有硬伤：

1. **换成异步客户端**：Milvus 有 async 接口，但 BM25 与 jieba 没有；改造后仍需要在某处 `to_thread`。
2. **全 `await to_thread(...)` 包一层**：等于把同步代码放进默认池（40），丢失了"问答并发上限 32"的闸门——池满时任务在 AnyIO 池里排队，你**无法区分**"排队中"和"执行中"，也无法做 503 快速失败。
3. **重写成纯异步**：BM25 遍历与 jieba 是 CPU 密集，async 化不改变 GIL 争用，只会把阻塞点从线程移到事件循环，**更糟**。

所以选择是"**异步的 HTTP 边界 + 有界线程池的同步内核**"，用显式队列换来可观测的过载语义。这是取舍，不是偷懒。

### Q103. 一次请求要穿过几层闸门？

**回答：** 六层，从外到内：

1. **连接层**：ingress/nginx 连接数与读超时（Q34）；
2. **AnyIO 线程池 40**：同步依赖与少量阻塞调用；
3. **执行器 32**：问答链路真正并行数（`pipeline_workers`）；
4. **队列 200**（低优先 50）：拿到了槽之外的第二道缓冲，满了立刻 503（Q118）；
5. **上游许可 28**：llm 12 + embedding 4 + rerank 2 + milvus 8 + multimodal 2（Q143）；
6. **上游配额**：provider 账号的 RPM/TPM，最后一道，也是最不可控的一道。

这个漏斗的意义是**每层都能独立设限并独立观测**：`kquery_inflight_requests` 看第 3 层、`queue_depth` 看第 4 层、`kquery_upstream_in_use{upstream}` 看第 5 层。出问题时能立刻判断"卡在哪一层"，而不是笼统地说"系统慢"。

### Q104. 32 / 200 / 50 这组数字怎么定的？

**回答：**

- **32**：由上游许可反推。各上游许可之和 28，必须 ≤ `pipeline_workers`（启动校验强制），留 4 个槽给"不占上游许可"的纯本地计算（缓存命中、闲聊短路）。32 也是 2 副本 × 4 pod 量级下不把上游打爆的上限。
- **200**：约 **6 倍**于执行器。理由是一旦队列过长，排队时间会超过用户耐心与 `ask_deadline_ms=120s` 的预算——按平均 8s/请求、32 并行算，200 个排队最后一个要等约 50s，已经在超时边缘。
- **50**：低优先队列（`pipeline_queue_low`）供后台类请求（入库、重建）使用，占主队列的 1/4，保证"后台饿死在线"不会发生，但也不能让后台占满。

这组数字的真实依据是**算术与约束**，不是压测标定——`doc/analysis/11` 明确记了"未做吞吐拐点实测"。所以正确表述是"按约束推导 + 保守取值"，而不是"压测得出"。

### Q105. 队列满时为什么返回 503，而不是继续阻塞排队？

**回答：** 因为**排队会放大延迟而不是吸收流量**：本服务的单请求耗时是秒级（检索 + 重排 + 生成 8s+），排队 N 个的最后一个要等 `N/32 × 8s`。让用户等 60 秒再失败，体验比立刻失败更差，且这 60 秒里连接、内存、线程都被占着。

所以 `PipelineExecutor.submit` 的三条分支（Q117）中，"队列满"直接 `raise_overloaded()` → 503 + `Retry-After`。快速失败的收益是：

- 资源立刻释放，系统不会因为排队而雪崩（排队是正反馈：越慢越积压）；
- 客户端能做**有意义的退避重试**，而不是傻等；
- 指标上 `kquery_shed_total{reason}` 直接反映"主动放弃量"，容量规划有据可依。

代价是**必须把"503 不是错误"讲清楚**：压测判据、前端重试、告警口径都要区分 5xx 与 503 过载（Q96/Q190），否则会误判成服务故障。

### Q106. "在飞去重"和"幂等键"有什么区别？为什么要两道？

**回答：** 两者解决的问题不同，实现也不同（`api/ask.py`）：

| | 在飞去重 | 幂等键 |
| --- | --- | --- |
| 键 | 按**内容**（`content_key(tenant, question, session, doc_id)`） | 调用方显式传 `Idempotency-Key` |
| 目的 | 防"同一问题被重复计费/出现两个不一致答案" | 防"网络重试导致重复提交" |
| 命中行为 | 立刻 **409**（不排队） | 已完成则 **回放**结果（`X-Idempotent-Replay: true`） |
| 生命周期 | 请求结束即释放 | 结果保留 24h |

两道都要的理由：前端在 429/503 后会**自动重试一次**，如果没有内容级去重，同一问题会算两次钱；而幂等键解决的是"客户端明确知道这是同一次提交"的重放，能返回**同一个结果**而不是 409。只留一道，要么重复计费，要么重试拿不到结果。

### Q107. 403 / 409 / 429 / 503 在这个服务里分别代表什么？

**回答：** 四种"拒绝"，语义严格区分：

- **403**：无权限（例如访问不属于自己的 document/scope）——请求本身不合法，重试无用；
- **409** `REQUEST_IN_PROGRESS`：**同一请求正在处理中**（在飞去重或幂等键在飞）——**稍后重试有效**；
- **429** `RATE_LIMITED`：超限流或 Agent 并发闸门（16）——带 `Retry-After`，退避后有效；
- **503** `OVERLOADED`：执行器队列满——系统过载，退避后可能仍失败，取决于负载。

区分的价值在**客户端策略**：409/429 可以自动重试（有限次），503 需要指数退避，403 应该直接提示。如果全部返回 500，客户端只能一律重试，把过载放大成雪崩。错误码映射集中在 `_ERROR_STATUS` 一处（`ask.py:343`），避免各路由各自解释。

### Q108. 单副本只有 32 并发，2–6 副本怎么"叠加"？哪些东西不能叠加？

**回答：** 能叠加的是**执行槽**：每个 Pod 独立 32 线程、独立 200 队列，2 副本就是 64 并发、6 副本 192。HPA 按 `inflight_requests` 28/副本扩容（Q19）。

**不能**简单叠加的有三样：

1. **上游配额**：所有副本共享同一个 provider 账号的 RPM/TPM，6 副本 × 12 llm 许可 = 72 并发，可能直接顶到配额，表现为上游 429 而不是本服务 503（Q189）。
2. **限流额度**：令牌桶在 Redis 里按租户共享（Q134），所以多副本不会"额度翻倍"——这是共享状态的主要价值。
3. **本地缓存**：每个副本的内存缓存各自独立，命中率随副本数下降；语义缓存必须放 Redis 才能跨副本。

所以"扩副本"对吞吐是线性的，对**成本效率**不是：副本越多，缓存命中越分散，上游调用越多。

### Q109. 如果有人在协程里直接调用同步阻塞函数，会发生什么？怎么发现？

**回答：** 后果是**单次阻塞就冻住整个进程**：事件循环是单线程的，一个 3 秒的同步调用会让这个 Pod 上所有 SSE 停止推送、所有探针超时、所有请求排队——表现像"服务假死"，但 CPU 可能不高。

发现手段：① **事件循环延迟**指标（`asyncio` 回调排队时长）；② readiness 探针在阻塞期间一起超时（因为探针也是协程）；③ 日志时间戳出现"整段空洞"。

本项目的规避方式是结构性的：所有可能阻塞的工作都在 `PipelineExecutor` 的线程里跑，协程侧只做 `await` 与队列读写（Q119 的桥接）。所以 `ask.py` 里能看到的都是 `async for event, payload in executor.stream_events(...)`，没有直接调用 `llm.generate()` 的地方。

代价是**不能用同步库的便利**：写新功能时必须显式判断"这段代码会不会阻塞"，这属于团队纪律，无法靠类型系统强制。

### Q110. 有 GIL，多线程还有意义吗？

**回答：** 有，因为这条链路是**IO 密集为主**：等 LLM、等 embedding、等 Milvus、等重排——线程在等网络时释放 GIL，多线程并行完全有效。

真正受 GIL 限制的是 CPU 段：jieba 分词、BM25 倒排遍历、RRF 融合与排序、上下文拼接。它们的时间占比决定了理论上限：如果 CPU 段占单请求 10%，32 线程并发时 CPU 段排队会成为瓶颈（`32 × 10% = 3.2` 个核满载）。

所以 32 这个数字既有上游约束，也有 CPU 约束；`requests 500m / limits 2` 的 CPU 配额（Q23）大致对应"2 核能承载 32 线程的 CPU 段"。要进一步扩，正确方向是**把 CPU 段下推到检索池（4 线程）或拆成独立服务**，而不是把 32 调大。

### Q111. 在线请求与后台任务（入库、重建）怎么隔离？

**回答：** 三层隔离：

1. **队列隔离**：后台类进入低优先队列（`pipeline_queue_low=50`），主队列 200 不受影响；
2. **让路阈值**：后台任务提交前检查主队列占用率，超过 `background_reject_queue_ratio=0.8` 就直接 503 拒绝后台任务（"现在忙，稍后再传"），把槽留给在线请求；
3. **资源隔离**：检索召回池独立 4 线程（Q156），后台批量检索不会把在线检索挤死。

设计原则是**在线优先，后台可推迟**。后台任务（入库、图谱构建）的特点是"晚几分钟没影响"，所以让它成为**可被牺牲的一方**。

代价是批量导入体验会变差：高峰期上传 500 篇文档会大量收到 503，需要客户端排队重试。这是有意的——总比在线问答被拖垮好。

### Q112. 优雅停机时，执行器里正在跑的 32 个请求怎么办？

**回答：** `lifespan` 关闭阶段调 `executor.shutdown(timeout=30)`：

1. 置"停止接单"标志，新 `submit` 立刻 503；
2. 等在飞任务自然完成，最多等 30s；
3. 超时后不再等待（线程是守护语义），进程退出；
4. 顺序上，执行器**先**关，然后才是 Agent 池、图谱池、TaskManager、checkpointer、存储——必须逆着启动顺序关（Q175），否则任务会调用已关闭的依赖。

30s 与 `terminationGracePeriodSeconds: 70` 的关系是：10s preStop + 30s 执行器 + 30s TaskManager ≈ 70s（Q17）。

关键取舍：**不做强制 kill**。Python 线程无法安全中断，强制杀会留下半写的检查点/索引。所以宁可超时放弃少数请求（客户端可重试），也不破坏数据一致性。

## 二、有界执行器与 SSE 桥接

### Q113. 为什么自建 `PipelineExecutor`，不用 `ThreadPoolExecutor` 或 AnyIO 默认池？

**回答：** 三个能力它们都不提供：

1. **有界准入 + 快速失败**：`ThreadPoolExecutor` 的工作队列是**无界**的（`SimpleQueue`），提交多少收多少，过载时表现为"延迟无限增长"而不是 503。本执行器用自定义 `_waiting` 计数（高优先 200 / 低优先 50），`_waiting >= limit` 即拒。
2. **同步/异步双入口**：同一个执行器既要给同步调用方 `acquire()`，又要给协程 `await acquire_async()`（不占线程等待，Q121）。
3. **优先级与心跳**：低优先队列（50）、流式心跳（15s）、协作式取消（`CancelToken`）——这些都需要自己写。

代价是要自己保证线程安全与关闭语义（Q124），且没有 `ThreadPoolExecutor` 那么成熟的测试覆盖。`doc/analysis/11` 的取舍写得很直白：**"要的是准入控制，不是线程池"**。

### Q114. `acquire()` 的三条分支分别是什么？

**回答：** 在 `self._cond` 锁内按顺序判断（`pipeline_executor.py`）：

1. **有空槽** → `_inflight < _workers` 就直接 `_inflight += 1` 返回 True（不排队）；
2. **排队已满** → `_waiting >= limit`（高优先 200 / 低优先 50）就 `_rejected += 1`、记 `on_reject` 指标、返回 False（**不阻塞**）；
3. **可排队** → `_waiting += 1`，在 `Condition` 上循环 `wait(remaining)` 直到 `_inflight < _workers`（拿到槽）或 deadline 到期（放弃），`finally` 里必减 `_waiting`。

三条分支对应三种确定性行为：立刻成功、立刻失败、有限期等待。**没有"无限等待"这一条**，这是它和普通线程池最大的区别——过载必须有边界。

`priority="low"` 只改 limit（50），不改槽位数量：后台任务和在线任务抢同样的 32 个槽，只是排队位置更少。这是"降低后台排队上限"而非"独立配额"，取舍是简单，代价是后台仍可能占住槽（由 Q111 的 0.8 让路阈值兜）。

### Q115. 为什么用 `_waiting` 计数，而不是给线程池配一个有界任务队列？

**回答：** 因为需要把"**排队**"和"**执行**"两个状态分开统计与限制：

- `_inflight`：真正在跑的（≤32），对应 `kquery_inflight_requests`；
- `_waiting`：已准入但在等槽的（≤200），对应 `kquery_queue_depth`。

如果用一个有界队列，你只能看到"队列长度"，无法知道"多少在跑、多少在等"，HPA 的两个指标（Q19）也就无从区分。而且 `ThreadPoolExecutor` 的队列不可替换为有界队列（内部 `SimpleQueue`），硬换要重写整个池。

代价是要自己维护 `Condition` 与计数的一致性（Q117 的 release 必须成对），并且**准入与提交之间有窗口**：`acquire` 成功后若 `pool.submit` 抛错，必须 `finally: release()`，否则槽永久泄漏。

### Q116. `acquire_async` 为什么用 20ms 轮询，而不是 `await condition.wait()`？

**回答：** 因为 `threading.Condition` **不能跨线程 await**：它绑定 OS 线程的锁，直接 await 会阻塞事件循环；而用 `run_in_executor(cond.wait)` 又会占掉一个 AnyIO 线程去干等——32 个并发请求排队就会吃光 40 个默认线程，把整个工控链路的线程池拖死。

所以实现是：只在**持锁瞬间**检查状态，等待用 `await asyncio.sleep(0.02)`，循环到 deadline 或拿到槽。20ms 的取舍是**延迟 vs CPU**：

- 太大（如 200ms）：拿到槽最多晚 200ms 才被唤醒，平均排队延迟增加 100ms；
- 太小（如 1ms）：每个排队请求每秒 1000 次抢锁，事件循环被无效唤醒占满。

20ms 对应"用户感知不到的延迟（< 25ms）且每秒 50 次检查可忽略"。这是典型的"用轮询换线程"，在 asyncio 生态里比"用线程等 Condition"更安全。

### Q117. `release()` 为什么要 `notify()`？只 notify 一次够吗？

**回答：** `release()` 在锁内 `_inflight -= 1`、`_completed += 1` 后调 `self._cond.notify()`，唤醒**一个**等待者。

一次 `notify()` 够用的前提是：**每次释放只腾出一个槽**，所以只需唤醒一个等待者；被唤醒者拿到槽后不会 notify 别人。如果一次释放多个（比如 shutdown 批量清空），才需要 `notify_all()`。

用 `notify()` 而非 `notify_all()` 是为了避免**惊群**：200 个等待者同时被唤醒抢一个槽，199 个白跑一轮（重新检查、重新 wait），在高并发下会放大 CPU。

同一把 `_cond` 还负责 `shutdown` 的等待（`while _inflight > 0: wait(0.5)`），所以 `release` 的 notify 也顺带唤醒了停机流程——这是**一把锁承担两个语义**的紧凑设计，代价是 shutdown 期间会周期性空转（0.5s 一次），可以接受。

### Q118. 拒绝的理由为什么要分 `overloaded` 与 `low_priority`？

**回答：** 因为两者的**责任方**不同，处置动作也不同：

- `overloaded`：高优先级队列满，说明**在线流量真的超了容量** → 需要扩容或限流，告警要升级；
- `low_priority`：低优先队列（50）满，说明**后台任务太多** → 该推迟导入，不需要扩容。

`_note_reject(reason)` 把原因记进 `kquery_shed_total{reason}`，这样"今天掉了 200 个请求"能立刻区分是"用户太多"还是"运维在批量导数据把队列刷满"。

如果不区分，看到拒绝量上升只能盲目扩容，而真实原因可能是凌晨导入任务撞上了早高峰。这个区分成本极低（一个字符串），价值在排障时的第一分钟。

### Q119. `stream_events` 是怎么把同步生成器桥接成异步流的？

**回答：** 三个角色：

1. **worker 线程**：跑 `event_iter_factory()` 这个**同步**迭代器（内部是整条 RAG 链路），每拿到一个 `(event, payload)` 就 `queue.put_nowait(item)`；
2. **`asyncio.Queue(maxsize=512)`**：跨线程的唯一通道（`put_nowait` 是线程安全的）；
3. **async 侧**：`while True: await asyncio.wait_for(queue.get(), timeout=15)` 逐条 `yield`。

收尾用哨兵：worker 的 `finally` 投 `_SENTINEL` 表示"没有更多事件"；异常也通过队列传递（`queue.put_nowait(exc)`，async 侧 `raise item`），保证**上游抛错能变成 SSE 的 error 事件**而不是静默断开。

关键点是 `run_in_executor(self._pool, produce)`：worker 用的是执行器自己的 32 线程池，所以**流式请求同样受 32 并发约束**，不会因为"是 SSE"就绕过准入。

### Q120. 队列满（消费者太慢）时为什么"停止生成"而不是"阻塞生产者"？

**回答：** 因为阻塞生产者会**锁死一个执行线程**：`queue.put` 阻塞时，worker 卡在 put 上，无法检查 `cancel`、无法响应取消，这 32 个槽里的一个就被一条慢连接长期占住——慢客户端（手机弱网）会逐条吃掉算力。

所以实现是 `except asyncio.QueueFull: cancel.set(); break`：**放弃这条流，释放槽位**。512 的容量本身已经给了很大的缓冲（正常流式事件是几十条），能填满 512 只有两种情况：客户端完全不读（TCP 窗口为 0）或链路卡死——这两种都该放弃。

代价是"慢用户可能被截断"，但保住了整体可用性。这是"尾部牺牲"策略，与 Q105 的 503、Q111 的后台让路是同一条原则。

### Q121. 心跳为什么是 15s？和前端 60s 看门狗怎么配合？

**回答：** 15s 是"**远小于所有反代读超时**"的值：

| 层 | 超时 |
| --- | --- |
| 心跳间隔 | 15s |
| ingress `proxy-read-timeout` | 300s |
| 前端 nginx `proxy_read_timeout` | 600s |
| 前端看门狗（无事件即重连） | 60s |

心跳的作用是**在没有任何 token 产出的长思考期**（检索 + 重排可能十几秒）持续写字节，避免反代误判"上游卡死"。`await asyncio.wait_for(queue.get(), timeout=15)` 超时就 yield 一个 `("__heartbeat__", {})`，前端收到后只更新"最后活跃时间"，不渲染内容。

前后端的比例关系是 4 倍：心跳 15s → 看门狗 60s，允许**连续丢 3 个心跳**才判定断线，避免一次网络抖动就重连（重连意味着重新发起一次完整问答，代价很高）。

### Q122. 客户端断开后，服务端怎么知道？为什么不能靠"写失败"发现？

**回答：** 必须**主动轮询** `await request.is_disconnected()`（`ask.py:377`，间隔 `interval_s`）。原因是：服务端在一段时间内可能**根本不写**（检索阶段十几秒无输出），此时连接已被客户端关闭，但没有任何写操作会失败——你完全感知不到，那 32 个槽里的一个就这样被一条死连接占住到生成结束。

只靠写失败的问题有两个：① 发现太晚（下一次 yield 才失败）；② SSE 的写是"投队列"，`queue.put_nowait` 永远不会因为客户端断开而失败——真正写出去是在 ASGI 层。

所以桥接循环里额外开了一个检测协程：每 `interval_s` 检查一次 `is_disconnected()`，命中就 `cancel.set()`，worker 在下一个事件前退出。`interval_s` 的取舍是"检测灵敏度 vs 无效轮询"。

### Q123. 断开之后，正在进行的上游调用能立刻取消吗？

**回答：** **不能**。这是明确的技术边界，写在 `stream_events` 的注释里：取消是**协作式**的——`cancel.set()` 后，worker 会在**下一个事件产出前**检查并退出，但"已经发出的 LLM 请求/重排请求"会继续跑完（同步 HTTP 客户端无法从外部打断）。

后果是：用户点了"停止"或关掉页面，服务端仍可能完成当前这一次上游调用并计费。所以界面上"停止生成"的文案不能承诺"立即停止计费"。

能做的优化有两层：① 把取消检查点放在**阶段边界**（检索后、重排后、生成前），让"取消"至少能省下后续阶段；② 流式生成时按 chunk 检查，能做到"下一个 token 前停止"。这已经是当前实现的结构（事件迭代器逐条检查 `cancel.is_set()`）。

### Q124. 为什么取消信号用 `threading.Event`，不用 `asyncio.Event`？

**回答：** 因为**跨线程**：设置取消的是 asyncio 侧（检测到客户端断开），检查取消的是 worker 线程（同步链路）。`asyncio.Event` 不是线程安全的，跨线程 `set()` 会绕过事件循环的调度机制，行为未定义。

`threading.Event` 的 `set()/is_set()` 在两个世界都安全：async 侧调用它不阻塞（只是置标志位），worker 侧把它当普通布尔量读。代价是**不能 await 它**——async 侧若要"等取消"需要轮询或配合 `asyncio.Event`。

这个选择是"以最小原语解决跨边界通信"的典型：不需要通知机制，只需要一个**可见的标志位**，因为 worker 本来就在每个事件边界检查。

### Q125. 响应头 `X-Accel-Buffering: no` 是干什么的？

**回答：** 它是给 nginx 的**应用层指令**：即使 nginx 配置里没有 `proxy_buffering off`，看到这个响应头也会对该响应关闭缓冲。

价值在于**部署解耦**：应用不依赖运维是否正确配置了 nginx/ingress（Q33 的两层都要配）。只要响应头在，绝大多数 nginx 部署都会流式转发。

边界也要说清：① 它只管 nginx 系（HAProxy/Envoy 不认）；② 若中间层显式 `proxy_buffering on` 且忽略该头（少数云 LB），仍需配置层解决；③ 它不影响 gzip（Q41）。

所以本项目是"**响应头 + 配置层双保险**"，任一层漏了另一层还能兜住——这是 SSE 能在多种部署形态（compose/本机 nginx/K8s ingress）下都工作的原因。

### Q126. 直接 `StreamingResponse` 里 `yield`，和我们这套桥接有什么区别？

**回答：** 三种做法对比：

1. **`yield` 同步逻辑**：生成器函数如果是普通 `def`，FastAPI 会用线程池跑它——但你**失去了对并发数的控制**（线程池是 40 的默认池），也无法统一做心跳与取消。
2. **`yield` 里 `await to_thread(...)`**：同上，且每个请求会占一个事件循环任务 + 一个线程，过载时表现为"线程池打满、所有接口一起慢"。
3. **本项目：显式 `acquire_async` + 自建线程池 + `asyncio.Queue` 桥接**：并发数 = 32（统一准入）、有心跳、有取消、有队列背压。

差别的本质是**过载时的行为**：前两种在过载时会"拖慢一切"，第三种会明确返回 503。这也是为什么 `stream_events` 必须先 `acquire_async`，而不是先开生成器。

代价是代码量：桥接函数约 60 行，且要小心 `SENTINEL`、异常透传、`finally` 置 cancel 三处细节。

### Q127. SSE 事件协议怎么设计的？为什么所有事件都用统一 envelope？

**回答：** 每个事件是 `event: <name>` + `data: <json>` 两行，事件名是**阶段语义**：`query_analysis`、`evidence`、`crag`、`confidence`、`token`、`followups`、`done`（Agent 模式还有 `plan`、`tool`、`iteration`、`reflect`）。

统一 envelope 的好处是**前端只写一个解析器**：所有 payload 都有 `trace_id`（贯穿日志）、可选 `elapsed_ms`、结构化字段；新增事件类型时老前端不认识就忽略，不会崩。

不用"一个 event 里塞所有字段"是因为**增量渲染**：`token` 事件要高频小包，`evidence` 是低频大包，混在一起会让每个 token 都带一遍证据列表，带宽翻倍。

事件命名的纪律是**只增不改**：改名等于破坏前端兼容，属于协议变更，要按版本走。

### Q128. 流到一半上游报错，怎么让前端知道"这不是正常结束"？

**回答：** 两条路径，取决于错误发生在哪个阶段：

1. **生成器内部抛异常** → worker 把它 `put_nowait(exc)` 进队列，async 侧 `raise item`，由路由层统一转成 SSE 的 error 事件（带 `trace_id` 与错误码）再发 `done`；
2. **队列满/取消** → 直接 `break` 并置 cancel，前端只会看到连接结束（无 `done`），据此判定"异常中断"。

关键是**不能静默断流**：SSE 的正常结束必须有 `done` 事件，前端据此区分"答案完整"与"连接断了"。缺这个约定，前端只能靠超时判断，用户会看到"答案停在一半但界面显示已完成"。

代价是错误信息要脱敏：error 事件里只放错误码与用户可读文案，堆栈进日志（用 `trace_id` 关联），避免把上游返回体（可能含内部信息）透给浏览器。

## 三、限流与幂等

### Q129. 令牌桶是怎么实现的？为什么不用固定窗口计数？

**回答：** 实现是**懒回填**：每次取令牌时按"距上次补充的时间 × 速率"算出应补数量，`min(capacity, tokens + elapsed*rate)` 后再判断是否 ≥ 1，够则扣减并放行。

参数是**每租户** `capacity=60`、`refill=60/min`（即 1 QPS 平均速率、60 的突发额度），键为 `ratelimit:{tenant}`。

不用固定窗口的原因是两个已知缺陷：① **边界双倍**——窗口末尾与开头各打满一次，瞬时可达 2 倍速率；② **不平滑**——窗口开始的一瞬间允许 60 个并发，之后再无额度。令牌桶天然平滑且允许突发，更适合"用户连续追问几个问题"的真实形态。

不用漏桶是因为漏桶会**排队**，而本服务的选择是快速拒绝（Q105）。

### Q130. 为什么令牌桶必须用 Lua 脚本？不用会怎样？

**回答：** 因为"读令牌数 → 算回填 → 判断 → 扣减 → 写回"是**五步读改写**，在 Redis 上必须原子：

- 不用 Lua：两个副本同时 `HGET` 到 `tokens=1`，各自判断"够"，各自 `HSET` 成 0，结果**一次额度放行两个请求**。并发越高，超额越严重。
- 用 Lua：整个脚本在 Redis 单线程里原子执行，`EVALSHA` 一次往返完成判断与扣减，超额窗口消失。

实现是 `_TOKEN_BUCKET_LUA`：`HGET tokens/ts` → `min(capacity, tokens + (now-ts)*rate)` → 判断 ≥1 则减 1 → `HSET` 回写 → 返回 `{allowed, tokens}`。用 hash 而非两个 string，是为了减少 key 数量与一次往返。

代价是**调试困难**（脚本里出错只能看 `redis.call` 报错）与**不支持动态扩缩容语义**（capacity 存在 ARGV，改了配置不影响已存在的桶，需要 key 版本化）。

### Q131. Redis 挂了，限流怎么办？Fail-Open 的代价是什么？

**回答：** 策略是 **Fail-Open + 本地降级**：`RedisStore` 的操作在失败时抛 `StoreUnavailable`，上层捕获后回落到**进程内令牌桶**（`LocalRateLimiter`，`threading.Lock` 保护），限流继续生效但**只对本副本有效**。

代价很具体：

- **额度按副本数放大**：2 副本时实际额度变成 2 倍，6 副本变成 6 倍。所以 Fail-Open 期间的限流**不能当作真实保护**，真正的保护是执行器 32 槽位（Q103 第 3 层）——它是每副本独立的，不依赖 Redis。
- **更隐蔽的副作用**：缓存、幂等、会话也一起降级（Q136），表现为"缓存命中率下降、幂等只在本副本有效"。

反过来的选择是 **Fail-Close**（Redis 挂了就全部 503）：对内部知识库工具，这会把"限流组件抖动"放大成"全站不可用"，明显不划算。所以 `shared_state` 的注释里专门强调"降级必须能自愈"——`_reconnect()` 按冷却时间 ping，避免一次偶发失败永久毒化进程（Q137）。

### Q132. 令牌桶的时间戳是谁给的？多副本时钟不一致会怎样？

**回答：** 时间戳由**调用方传入**（Lua 的 `ARGV[1]` 是 `now`），不是 Redis 的 `TIME`。这是一个可讨论的实现选择：

- 用客户端时间：少一次 `redis.call('TIME')`，脚本更简单；但多副本时钟漂移会直接变成额度误差——若 A 副本时钟快 2s，它在 2s 内算出"该回填 2 个令牌"，实际多放了 2 个。
- 用 Redis `TIME`：所有副本共享同一时钟，误差归零，代价是脚本里多一次调用（同实例内开销极小）。

对 60/min 的额度，秒级漂移影响有限（1 秒 = 1 个令牌）；但如果将来把额度收紧到 10/min，这个误差就不可忽略。**正确做法是用 Redis TIME**，当前实现的取舍是简单优先——这类地方面试时主动指出，比假装没有更可信。

### Q133. 每租户 1 QPS 的限流，够保护服务吗？真正的保护在哪？

**回答：** 不够，而且**它本来就不是主保护**。理由：

- 1 QPS/租户 只限制"单个账号的请求速率"，防的是**脚本刷接口**与**误写死循环**；
- 一次问答本身要 8s，用户正常操作极限也就 0.1 QPS，所以 60 的突发额度对真人几乎无感；
- 真正的容量保护在执行器：32 槽 + 200 排队 + 503 快速失败（Q105），它限制的是**全体并发**，不看是谁。

两者分工是"**限流管公平，执行器管总量**"。如果只有限流没有执行器，100 个租户各 1 QPS 就是 100 并发，直接打爆上游；如果只有执行器没有限流，一个恶意租户可以把 200 个排队位全占满，让其他租户全部 503。

所以答这类题的关键是：**说清每层防的是什么攻击/故障形态**，而不是罗列参数。

### Q134. 多副本下限流额度会不会翻倍？靠什么保证？

**回答：** 不会，因为桶在 **Redis** 里按 `ratelimit:bucket:{tenant}` 共享（`shared_state` 提供 `incr/get/set/zadd` 等原语，限流用 Lua 做原子更新）。2 副本时两个 Pod 打的是同一个 hash key，额度总量不变。

这正是把限流放进共享状态的主要价值（Q108）：如果桶在进程内存里，副本数就是额度的倍数，扩容会意外放大额度——HPA 一扩容，限流就等于失效了。

保证的前提有两个：① Redis 可用（降级时回到 Q131 的"按副本放大"）；② 所有副本用同一 `prefix`（默认 `kquery:`）与同一 `redis_url`。后者看起来显然，但 dev overlay 里指向不同 Redis 时会出现"各自计数"的诡异现象。

### Q135. 幂等为什么需要两个 TTL（60s 与 24h）？

**回答：** 因为两个记录的生命周期完全不同：

- **在飞占位**：`incr` 得到一个"门"，TTL **60s**。它只活到"这个请求结束"，60s 是兜底（进程崩溃时占位必须自动过期，否则这个 key 永远占着，同一问题永远 409）。请求正常结束会 `release`/`fail` 主动清。
- **结果记录**：完成后把响应 envelope 存 24h（`DONE` 状态），供 `Idempotency-Key` 重放。

两个 TTL 的设计意图是**失败恢复**：60s 覆盖绝大多数请求（典型 8s），远小于结果保留期；同时它又足够短，让"进程崩溃遗留的占位"能自动过期，而不是永久阻塞同一问题。

代价是：极端长请求（>60s）期间占位可能先过期，此时第二个相同请求能进来——但两者最终由执行器的 32 槽保证不会打爆，只是可能算两次。这是"可接受的重复"换"不会永久锁死"。

### Q136. Redis 降级后，"幂等"还成立吗？怎么避免假幂等？

**回答：** **只在单副本内成立**。降级到 `LocalStore` 后，每个 Pod 有自己的占位与结果记录：客户端带同一 `Idempotency-Key` 打到另一个副本，会**重新执行一次**而不是回放——这就是"假幂等"。

风险分级：① 在飞去重（按内容）失效 → 同一问题可能被算两次钱；② 幂等回放失效 → 客户端重试拿到两份结果（内容可能不同）。

缓解手段：① **客户端侧**把 `Idempotency-Key` 与问题绑定并在本地记结果，重试时先查本地；② **监控**：`/readyz` 在共享状态退化时会提示，配合 `kquery_cache_total` 命中率骤降告警（Q72）；③ **恢复优先级**：Redis 故障应视为 P1（它承载的是一致性语义，而不仅是缓存）。

根本解法是把"幂等记录"写到更强一致的存储（如数据库唯一约束），代价是复杂度上升。当前选择是"接受退化 + 显式暴露"。

### Q137. `_reconnect()` 的冷却时间解决什么问题？

**回答：** 解决"**一次偶发失败永久毒化进程**"：

如果一次操作失败就把 `_healthy = False` 并一直降级，那么之后所有操作都走本地——缓存不再跨副本、限流额度按副本放大、幂等只在本地生效，而**日志里只有一条 debug**。这种"静默永久降级"比直接报错更危险，因为它会让系统带着错误语义长期运行。

所以 `_reconnect()` 按 `_RECONNECT_COOLDOWN_S` 冷却后重试：先 `ping` 现有连接（多数失败是操作层/脚本问题，连接本身没问题），失败再重建客户端。恢复成功时打 INFO 日志，让"降级—恢复"在日志里成对出现。

这是"降级必须有出口"的原则：**Fail-Open 不是终点，是临时状态**。同理，`/readyz` 把"共享状态退化"作为判红条件之一（Q18），让编排层也知道自己处于降级态。

### Q138. 幂等的状态机有哪些状态？哪一步最容易写错？

**回答：** 四个状态：`INFLIGHT`（占位）→ `DONE`（结果已存，可回放）；异常路径 `fail`（清掉占位，允许重试）；正常退出 `release`（释放内容级占位）。

最易写错的是**异常路径必须同时回滚两层**：`ask.py` 里 `idem.acquire(inflight_key)` 失败时要 `idem.fail(replay_scope)`（否则这次请求在幂等键上留下"在飞"假象，用户 60s 内重试全被 409）；`finally` 里必须 `release(inflight_key)`，否则同一问题永久 409。

这两处都是"看起来成功、实际把用户锁死 60s"的 bug，且**测试不易发现**（单请求用例看不出）。所以代码里有明确注释（`ask.py:224`："回滚上面为幂等键占的位置"），这类注释的存在本身就是踩过坑的证据。

### Q139. 重复请求为什么返回 409 让客户端等，而不是服务端排队等前一个结果？

**回答：** 因为**排队的收益是负的**：前一个请求可能跑 30s 甚至失败，让后一个连接挂在这等，等于把"重复请求"变成"双倍占用"（两个连接 + 两个槽位机会）。

`ask.py:209` 的注释写得直白："拿到占位就执行，否则立刻 409——不排队（排队等于'再等一轮'，更贵更慢）"。返回 409 后客户端可以：① 走幂等键回放拿结果（如果带 key）；② 稍后重试；③ 直接展示"正在处理中"。

这也是"快速失败优于排队"的又一次体现（Q105/Q120）。三种"等"的区别值得说清：排队等槽（执行器内部，有界）、409 拒绝（重复请求，不排队）、503 拒绝（队列满，不排队）。

### Q140. 前端拿到 429/503 后应该怎么退避？

**回答：** 三条纪律：

1. **只自动重试一次**：`ask.py:207` 的注释明确"前端在 429/503 后会自动重试一次"。为什么只一次——重试本质是把压力重新打回去，过载时多次重试会让雪崩更快。
2. **遵守 `Retry-After: 5`**：`raise_overloaded()` 统一带这个头（503），限流 429 也带；不遵守就是在服务端明确说"等 5 秒"时仍然立刻重打。
3. **重试要带 `Idempotency-Key`**：否则重试可能触发两次计费（Q106）；带 key 时第二次能拿到 `X-Idempotent-Replay` 的回放结果。

还要注意**用户可见性**：重试期间界面显示"繁忙重试中"而不是错误；最终失败时给出 `trace_id`，便于排障时对日志。

反面做法是"指数退避 + 无上限重试"：在浏览器里会表现为"页面一直转圈"，把用户困住。

## 四、上游隔离与熔断

### Q141. 为什么要有 per-upstream 的信号量（Bulkhead）？

**回答：** 因为**共享线程池会被慢上游拖死**：如果不隔离，检索（几十 ms）与 LLM（几秒）抢同一批 32 个槽，一次 LLM 变慢会把所有槽占满，连"只查向量库"的请求也拿不到槽——故障从一个上游扩散到全部功能。

Bulkhead（隔离仓）给每个上游独立许可：llm 12、embedding 4、rerank 2、milvus 8、multimodal 2（`config.py`，合计 28 ≤ 32）。效果是 LLM 卡住时，最多占 12 个槽，剩下 20 个仍能服务其他链路；multimodal 出问题最多影响 2 个。

代价是**可能出现"许可空闲但整体排队"**：12 个 llm 许可满、其他上游都空闲时，新请求仍要等 llm 许可。这是隔离的固有成本，用"许可之和 ≤ workers"（Q145）保证不会出现死锁式的空转。

### Q142. Bulkhead 具体怎么实现？拿不到许可时是什么行为？

**回答：** 核心是一个**带超时的信号量**：

```python
class Bulkhead:
    def acquire(self, timeout_s: float) -> bool:  # 内部用 Condition 计数
    def release(self) -> None
```

- 拿不到许可且超时 → 抛 `BulkheadBusy`（或返回 False），上层转成"该能力暂不可用"的降级，而不是排队死等；
- 许可用 `with` 或 `try/finally` 保证释放，避免异常路径泄漏导致许可永久减少（这是隔离仓最典型的 bug）。

与执行器槽位的区别：执行器管"整条链路并发"，Bulkhead 管"单个上游的并发"。所以一次请求会**先后占两类名额**（先占执行器槽，再占上游许可），这也是必须满足 Q145 约束的原因。

### Q143. 12 / 4 / 2 / 8 / 2 这组许可数怎么定？

**回答：** 按"**单请求内的调用形态**"倒推：

- **llm 12**：最重、最贵、最慢（3–15s），且一次请求可能多次调用（改写、生成、自检、意图）。给 32 的 37%，保证多请求并发时不至于全挤在 LLM 上。
- **embedding 4**：只在入库与查询向量化时用，单次几十 ms，且常批量（一个批算一次）；4 足够，多了会挤占 llm。
- **rerank 2**：外部重排最快也最容易被限流（DashScope `gte-rerank-v2`），且失败可降级（回落融合序），给最少。
- **milvus 8**：本机检索快，但连接数有限；8 与连接池匹配。
- **multimodal 2**：图片向量化是长尾功能（`image_vector_enabled`），给最小配额，坏了也不影响主链路。

合计 28，低于 32 的 4 个余量留给"不占上游许可"的路径（缓存命中、闲聊短路、纯本地计算）。

### Q144. 什么情况下会用 `NullBulkhead`？不隔离不行吗？

**回答：** `NullBulkhead` 是**空实现**（acquire 永远成功），用于两类场景：① 单测/本地开发时不需要配额语义；② 上游只有 mock、不存在真实限流时。

生产不能用 Null 的原因很直接：**没有隔离，一个慢上游会吃掉所有槽**（Q141）。Null 的价值是提供接口一致性——配置层可以整体关掉隔离而不改调用方代码，属于"可关闭的保护"，但要显式配置（默认是启用真实 Bulkhead）。

这类"Null 对象"模式在本项目里很常见（还有 NullCache、NullMetrics 等），好处是**调用方不需要写 `if bulkhead is not None`**，代价是"关掉保护"变得太容易——所以配置项的命名要让人看出后果。

### Q145. 为什么"许可之和 ≤ workers"必须是硬约束？

**回答：** 要防的是**嵌套等待造成的死锁**。设想：32 个槽全被占，每个请求都需要 llm 许可；而 llm 许可只有 12 个。若某些请求已经持有 llm 许可**又**在等另一个上游许可（比如 rerank），而 rerank 许可被另一批"占着槽等 llm"的请求持有，就可能形成环——所有槽都占着，谁也无法推进。

保证"许可之和 ≤ 32"后，最坏情况也只是"占满 32 个槽的请求各自都能拿到它需要的许可"，因为**总需求量不超过槽位数**。这条约束在 `validate_startup()` 里检查，不满足直接拒绝启动（Q52）。

它还有一个隐含前提：**单请求不重复持有多份同名许可**（不能在一次 llm 调用里嵌套另一个 llm 调用并各占一个）。目前链路是串行的阶段式调用，满足这个前提；将来若做并行分支（一次请求并发调 3 个工具），必须重新推导。

### Q146. 熔断的状态机与参数是怎样的？

**回答：** 三态，参数在 `upstream.py`：

| 项 | 值 | 含义 |
| --- | --- | --- |
| `window` | 20 | 用 `deque(maxlen=20)` 记最近 20 次结果 |
| `fail_ratio` | 0.5 | 最近 20 次里失败率 ≥50% |
| `open_seconds` | 30 | 打开后 30s 才允许探测 |
| `half_open` | 3 | 半开期允许 3 个并发探测，且需 3 次连续成功才关闭 |

状态迁移：`closed` →（满窗且失败率超阈）→ `open` →（满 30s）→ `half_open` →（连续 3 成功）→ `closed`；半开期**任一失败立刻回 open**（`upstream.py:102`）。

关键细节：**只有窗口填满（20 次）才判定**，避免刚启动时 2 次失败就把上游判死。这个"需要足够样本"的原则与灰度的 `min_samples=30`（Q61）是同一个统计思想。

### Q147. `open` 期间为什么"立即失败"这么重要？

**回答：** 因为它把**一种故障（上游不可用）从"延迟故障"变成"瞬时故障"**：

- 没有熔断时：每次请求都要等 `llm_timeout_s`（几十秒）才失败，32 个槽在 30s 内被占满 → 整个服务不可用；
- 有熔断时：open 期间 `acquire` 直接抛 `CircuitOpenError`，**不占许可、不等超时**，请求毫秒级失败，槽位瞬间释放。

所以熔断的本质不是"少发请求"，而是**保护本服务的并发资源**。注释里那句"打开期间快速失败（不占线程、不等超时）"就是这个意思。

代价是**部分请求本来可能成功**（上游只是抖动）也被直接拒绝——用 50% 失败率 + 30s 冷却来平衡：抖动通常几十秒内恢复，而真故障时快速失败明显更优。

### Q148. 半开为什么要求"连续 3 次成功"？1 次不够吗？

**回答：** 1 次探测的风险是**假恢复**：上游可能只是恰好这一次成功（负载均衡打到健康节点、抖动间隙），立刻全面恢复会把大量流量重新打回故障上游，形成"打开—恢复—再打开"的抖动循环（flapping）。

3 次的作用是**要求恢复具有持续性**，并且半开期**只允许 3 个并发探测**（`_in_use < half_open`），把探测流量控制在极低水平——即使这 3 个都失败，也只损失 3 个请求，不会冲击业务。

"任一失败立刻回 open"（而不是清零重来）是更保守的选择：它放弃"3 次里 2 次成功也算恢复"的可能，换来"不会在故障期反复试错"。取舍偏向稳定而非快速恢复。

### Q149. 熔断窗口为什么用"最近 20 次"而不是"最近 1 分钟"？

**回答：** 因为**流量不均匀**：本服务在低峰期可能 1 分钟只有 5 个请求，用时间窗会导致"样本太少也算失败率"（1 失败 / 2 请求 = 50% → 熔断）；而"最近 20 次"在低流量时自然延长了观测时间，保证判定基于足够样本。

代价是**高流量时反应变慢**：若 QPS 是 50，20 次窗口只覆盖 0.4s，一次瞬时抖动就能触发熔断；反之在 0.2 QPS 时，20 次要 100s 才判定，故障会被拖很久才被切断。

所以窗口大小与流量强相关。更精细的做法是"时间窗 + 最小样本数"双条件（如"最近 60s 且样本 ≥ 20"），本项目选了更简单的一种，属于已知的可优化点。

### Q150. AIMD 自适应并发为什么默认关？

**回答：** 因为它是**会自己改并发上限**的机制：检测到上游慢就降许可（乘性减），稳定后再缓慢加（加性增）。默认关（`upstream_adaptive_enabled=False`）的理由与 Q54 一致——上线前必须验证它的判据：

- 判据依赖 p95 延迟，而 p95 在低流量下噪声很大，容易"误降"；
- 降了之后恢复很慢（加性增），一次误判会让系统长时间跑在低并发下，吞吐莫名下降；
- 与熔断叠加时可能互相干扰（熔断在 open 期间没有样本，AIMD 看不到延迟信号）。

所以它被实现但默认关闭，需要时显式打开并观察。这是"高级保护默认关，基础保护默认开"的一贯取舍：槽位/队列/熔断是硬保护，AIMD 是软优化。

### Q151. LLM 重试和熔断会不会互相打架？

**回答：** 会，如果重试不加约束：一次失败重试 3 次，等于把 1 个请求变成 4 个上游调用——上游已经过载时，重试会**放大流量**，让熔断更快打开，形成"越重试越糟"的正反馈。

所以三条约束必须同时成立：

1. **重试总耗时 ≤ 请求预算**：`llm_timeout_s × (max_retries+1) ≤ ask_deadline_ms`，这条在 `validate_startup` 里强制（Q52）。否则重试还没结束，整个请求已经超时。
2. **熔断 open 期间不重试**：`CircuitOpenError` 直接上抛，不再消耗重试次数（Q147）。
3. **只对可重试错误重试**：超时、5xx、429 可重试；400/401（参数/鉴权）重试无意义，只会浪费时间。

指数退避（`2**attempt`）的作用是错开重试时刻，避免多个请求同时重打。代价是延迟增加——所以退避上限必须受预算约束，不能退到几十秒。

### Q152. 上游 429 和本服务 503 有什么区别？怎么避免把上游限流转成用户可见错误？

**回答：**

- **上游 429**：provider 账号的 RPM/TPM 超限，责任在"我们调用太猛"；
- **本服务 503**：执行器队列满，责任在"我们容量不够"。

前者应该被**内部消化**：① 由 Bulkhead 限制并发（Q141），从源头减少触发；② 收到 429 后按 `Retry-After` 退避重试（Q151）；③ 若持续 429，说明配额不够，应触发熔断（把"慢失败"变"快失败"）并告警，让人去提配额或换 provider。

如果直接透传 429 给浏览器，用户体验是"这个产品很卡"，且前端会以为是限流、做无意义的重试。所以设计上：**上游 429 → 内部重试/降级 → 最终失败时统一为本服务的错误码**（并保留 `trace_id` 供排查）。

唯一例外是"配额类硬限制"（例如租户级 token 预算耗尽），这属于业务错误，应明确告知用户。

## 五、线程池边界与死锁

### Q153. 检索召回池为什么必须独立？

**回答：** 因为检索是"**短调用但高频**"：一次问答可能触发 2–3 次（向量、BM25、图片），每次几十毫秒。如果它和 LLM 共用 32 槽，一旦 LLM 变慢占满槽位，检索也被堵住——而检索是**所有请求的第一步**，堵住它等于全站无响应。

独立池（4 线程）的效果：检索不被 LLM 拖累，且 4 个线程足以支撑 32 并发下的检索吞吐（单次 50ms × 32 并发 = 1.6 QPS 的检索负载，4 线程绰绰有余）。

代价是多一层线程与队列，以及"池间不能互相借线程"——如果检索池被打满（例如大量并发 BM25 重建），请求会在检索池排队而不是复用空闲的 LLM 线程。这是隔离的必然成本。

### Q154. Agent 的 run 池与工具池为什么必须分开？

**回答：** 因为**图线程会同步等待工具 future**：如果工具也跑在同一个池里，8 个 run 线程各占一个线程后，每个都在等自己的工具调用——而工具任务在队列里排不到线程（池被 run 占满），于是**所有线程互相等待，永远不动**。这是典型的**线程池嵌套死锁**，`tools.py:501` 的注释直接写了这句："必须与运行 Agent 图的池分离——图线程等待工具 future，同池会嵌套死锁"。

配置是：run 池 `max_workers=8` + run 闸门 `run_permits=16`（在飞 run 上限，超出 429，`retry_after=5`）；工具池独立 `max_workers=8`。

注意 16 > 8 不是矛盾：**16 是在飞 run 的数量上限，8 是同时执行的线程数**——多出来的 8 个 run 在排队，等线程空出。这样设计是为了让"排队"与"执行"分离可观测，同时用 429 兜住超出 16 的部分。

### Q155. AnyIO 默认线程池那 40 个线程承载什么？有什么风险？

**回答：** 承载 FastAPI 的**同步依赖函数**（`def` 而非 `async def` 的 dependency）与少量 `run_in_threadpool` 调用。也就是说，任何在依赖里做了同步 IO（读文件、查 SQLite）的代码都会落在 40 个线程里。

风险有三：① 它**不受执行器 32 槽约束**，如果某条路径误用同步依赖做重活，会绕过准入直接吃满 40 线程；② 40 是 AnyIO 默认值，`workers=1` 时没有人为它做容量规划；③ 它和执行器的 32 线程是**两套独立资源**，总线程数 = 72+，线程栈内存与上下文切换都要算进资源预算。

所以纪律是：**重活一律走 `PipelineExecutor`，不要写在同步依赖里**。审查 PR 时看到 `def get_x()` 里做网络调用就要拦——这类问题不会在低并发下暴露。

### Q156. 判断"会不会死锁"的通用规则是什么？

**回答：** 三条，本项目都踩过：

1. **同池嵌套必死**：A 任务在池 P 里同步等 B 任务，而 B 也提交到 P → 池满即死（Q154）。规则是"**等待方与被等待方不同池**"。
2. **总需求 ≤ 总资源**：所有并发请求可能同时持有的许可数之和，不能超过可用槽位（Q145），否则出现"人人持有一部分、人人等下一部分"。
3. **锁的获取顺序固定**：多把锁必须全局同序（如先 `_cond` 后 `budget_lock`），否则 ABBA 死锁。本项目的锁很少交叉持有，这是刻意的设计约束。

补充一条实践规则：**任何"阻塞等待"都必须有超时**（执行器 `acquire` 有 deadline、Bulkhead 有 `timeout_s`、`future.result()` 应带 timeout）。无超时的等待在生产里等价于死锁——它不会立刻炸，而是在流量上来时静默卡住。

### Q157. `rwlock` 用在哪？为什么写者优先？

**回答：** 用在"**读多写少且读必须一致**"的场景：BM25 倒排表与文档元数据索引。读是每次检索（高频），写是重建索引/增删文档（低频）。

写者优先（`writer_preferred=True`）的理由是**避免写饥饿**：如果读优先，持续不断的检索请求会让重建永远拿不到锁——而重建被卡住意味着新文档一直不可检索，用户看到"上传成功但搜不到"。

代价是写者等待时新的读者会被挡住（延迟尖峰）。所以写操作本身要尽量短：重建时**先在新结构上构建，最后用一次极短的写锁切换引用**，而不是全程持写锁。这也是本项目的做法：耗时部分在锁外，锁内只做指针替换。

### Q158. `rwlock` 的实现细节是什么？可重入吗？

**回答：** 基于 `threading.Condition` + 三个计数器：`_readers`、`_writer`、`_waiting_writers`。

- `acquire_read`：`while _writer or _waiting_writers > 0: wait()`——只要**有写者在等**，新读者也挡在门外（这就是写者优先的实现点）；
- `acquire_write`：`_waiting_writers += 1`，`while _writer or _readers > 0: wait()`，拿到后 `_writer = True`；
- `release_read`：最后一个读者退出时 `notify()`（唤醒等在写者优先队列里的写者）；
- `release_write`：`_writer = False` 后 `notify_all()`（唤醒所有读者）。

**不可重入**：同一线程重复 `acquire_read` 会自增 `_readers`（这个没事），但重复 `acquire_write` 会自等（`_writer` 已是 True）→ 死锁。所以使用纪律是"**不在持锁区内再取同一把锁**"，且写锁区必须极短（Q157）。

### Q159. 有 GIL 了，BM25 重建为什么还需要读写锁？

**回答：** GIL 保证"字节码不会真正并行"，但**不保证复合操作原子**：重建是"清空倒排表 → 逐条插入"的多步操作，GIL 可以在任意字节码边界切换线程。于是检索线程可能看到"清空后、插入一半"的中间态——要么查不到任何结果，要么结果错乱。

所以锁保护的是**数据结构的逻辑一致性**，不是"防止内存竞争"。这是 Python 里非常容易搞错的一点：很多人以为 GIL 让加锁变得多余。

正确做法（本项目采用）：重建在锁外构建新结构，锁内只做"引用替换"（`self._index = new_index`），把写锁持有时间压到微秒级，读者几乎无感。

### Q160. `Pipeline` 是单例，怎么保证请求之间不串数据？

**回答：** 通过 `bind_principal()` 返回**请求级副本**：单例持有进程级共享部分（store、cache、metrics、config），而 `bind_principal(tenant, user, scope)` 生成一个轻量副本，其请求级缓存是独立 dict（`pipeline.py:236` 注释："请求级缓存天然按请求隔离，无需 contextvar"）。

关键设计是"**共享引用 vs 独立容器**"：`bind_principal` 副本**共享**底层 store 的 dict 引用（这样缓存能跨请求命中，`pipeline.py:124` 提到"等待者复用结果共享同一 dict 引用"），但请求级元数据（tenant/user/scope）各自独立。

为什么不用 `contextvar`：`contextvar` 在 `to_thread` 与线程池里**不会自动传播**（需要显式 copy_context），而本服务的链路全在线程池里跑，用副本对象比用隐式上下文更可靠。

### Q161. 这类"单例 + 请求级状态"最容易出什么 bug？

**回答：** **状态泄漏**：把请求级字段写进单例的实例属性，于是 A 请求的 tenant 影响了 B 请求。典型表现是"两个用户同时提问，答案串了"或"缓存串租户"——这类 bug 在单请求测试里完全看不出来。

本项目的两条防线：① `bind_principal` 只返回副本，请求级字段（`_principal_*`）在副本上初始化；② 缓存键里显式带 `principal_user` 与 `scope`（不只是 tenant），即使发生泄漏，也会因为键不同而不命中错误数据。

第三道防线是测试：并发用例（多线程同时 `bind_principal` 不同租户）断言各自的缓存不互相可见。没有这种测试，"单例共享"就是一个随时会响的雷。

### Q162. 一个 Pod 里到底有多少线程？内存账怎么算？

**回答：** 粗算：uvicorn 主线程 + AnyIO 事件循环 + AnyIO 默认池 40 + 执行器 32 + 检索池 4 + Agent run 池 8 + 工具池 8 + 后台任务池若干 + Redis/HTTP 客户端内部线程 ≈ **100 上下**。

内存账：每个线程默认栈上限 8MB（虚拟内存，实际 RSS 通常远小于），100 线程的虚拟地址空间约 800MB，但真实 RSS 更多来自 Python 对象与缓存。所以 `limits: memory 4Gi`（Q23）的主要消耗者不是线程栈，而是**索引与解析中间产物**。

真正的风险是**线程与内存的耦合**：32 并发解析 50MB 文档时，每个线程持有一份解析中间态，4Gi 会被迅速吃满 → OOMKill。所以"并发上限"同时是"内存保护"，调大 32 之前必须先算内存。

## 六、缓存与 single-flight

### Q163. `cache_backend=auto` 的选择逻辑是什么？

**回答：** 优先级是 **Redis > 内存**：`auto` 模式下若配置了 `redis_url` 且连得上，就用 `RedisCache`（跨副本共享、可持久）；否则退回进程内 LRU（`cache_max_entries=10000`），并在日志与 `/readyz` 上体现"单副本语义"。

为什么不默认 memory：单副本缓存命中率随副本数**线性下降**（Q108），2 副本时命中率约减半，4 副本时几乎等于没有——成本会翻倍。

为什么不强制 redis：本地开发不该依赖 Redis；`memory` 是显式的选择（`cache_backend=memory`，启动校验允许），语义是"我承认只有单副本效果"。启动校验会拦住"`cache_backend=redis` 但没配 `redis_url`"（`config.py:1130`），避免"以为共享了其实没有"。

### Q164. 语义缓存的"近似命中"是怎么做的？

**回答：** 两步：先精确匹配，未命中再做**近似检索**：

1. 精确键：`hash(tenant, question, user, scope, model_version, config_digest)`，O(1)；
2. 近似：把新问题向量化，在候选集里比相似度，`cache_sim_threshold=0.95`（`config.py:231`）才认为命中；单次请求最多比对 `cache_max_scan=2000` 个候选条目。

0.95 的取舍很关键：低到 0.9 会把"意思相近但答案不同"的问题混起来（例如"如何退款"与"如何退货"），用户拿到错误答案比没缓存更糟；高到 0.99 几乎只能命中完全改写，收益很低。

`max_scan=2000` 是**延迟上限**：候选再多也只扫 2000 个，把"缓存查询"控制在几十毫秒内。代价是条目超过 2000 后老条目可能永远不被近似命中（除非精确命中），属于"用有限扫描换稳定延迟"。

### Q165. 缓存键为什么必须带 `user` 与 `scope`？

**回答：** 因为缓存是**跨请求共享**的，键少一个维度就会串：

- `tenant`：多租户隔离的基础；
- `user`（`principal_user`）：同一租户内不同用户可能对不同文档有权限，缺它会**越权返回**别人文档的答案；
- `scope`（`doc_id or ""`）：区分"快问单文档"与"全库问答"——同一个问题在两种模式下答案完全不同；
- `model_version`（`provider:llm + embedding + rerank`）与 `config_digest`：换了模型或检索参数，旧答案不再代表当前系统行为。

漏掉任何一个，表现都是"偶发答非所问"，且**测试很难覆盖**（需要构造两个维度不同的请求）。所以缓存键的维度清单本身应当被测试固定住，新增维度必须同步改测试。

### Q166. 为什么没有做"等待式 single-flight"，而是用 409 替代？

**回答：** 因为等待式 single-flight（后到的请求挂起等第一个的结果）需要**跨请求的结果广播**：要有一个可等待的 future/事件、要处理"第一个请求失败/超时/被取消"的传播、还要考虑等待者超时。在同步线程池里实现这套，等于自己写一个任务编排框架。

本项目的替代方案是**两道非阻塞去重**（Q106）：内容级在飞去重（重复即 409）+ 幂等键回放（有 key 则返回缓存结果）。效果上覆盖了 90% 的真实场景——前端重试、用户连点、网络重发。

代价是**客户端必须能处理 409**：它要自己决定"等一下重试"还是"用幂等键拿结果"。对于不能改的第三方客户端，409 会表现为一次失败。

真正的收益是**实现复杂度低且没有"等待者拖垮线程"的风险**：等待式方案里，1000 个重复请求会挂住 1000 个连接，而过载时这正是不能接受的。

### Q167. 缓存穿透、击穿、雪崩，这个项目分别怎么处理？

**回答：** 三个问题的现状不一样，要分开说：

- **穿透**（查不存在的数据，每次都打到底层）：本项目**没有显式负缓存**。缓解靠"检索本身有代价上限"（top_k 固定、扫描 2000）与限流，而不是靠空值缓存。真实影响是"恶意构造不存在的问题"会持续消耗检索资源。
- **击穿**（热点 key 过期瞬间大量并发回源）：没有互斥重建机制，所以热点问题过期时会出现一波同时回源。缓解靠 60 的突发额度（Q129）与执行器 32 槽——不会打死，但会有一波延迟尖峰。
- **雪崩**（大量 key 同时过期）：`cache_ttl_s=3600` 是**固定值**，如果缓存是批量写入的（如导入后集中预热），确实会在 1 小时后集中过期。标准解法是 TTL 加随机抖动（如 `3600 ± 300`），本项目未做。

诚实结论：缓存层是"能省成本"的优化，不是"必须命中"的正确性依赖——所以这三类问题的影响是成本与延迟，不是数据错误。这也解释了为什么它们的优先级低于 Q100 里那些不可恢复的问题。

### Q168. 命中率低于 30% 为什么值得告警？

**回答：** 因为它是**成本与延迟的先行指标**：命中率 60% → 30% 意味着同样的流量要打 1.75 倍的上游调用，成本同比例上升，且 p95 延迟上升（上游调用比缓存读取慢两个数量级）。

`CacheHitRateLow` 的规则是 `<0.3 for 15m`（Q72），窗口取 15m 是因为**缓存命中率本身波动大**：一次批量导入会写入大量一次性条目、拉低命中率，15m 能过滤掉这种短时波动。

命中率骤降的常见根因（按概率）：① 缓存键多了一个每次都变的维度（如把 `timestamp` 或 `trace_id` 混进键）；② `config_digest` 频繁变化（每次启动生成随机值）；③ Redis 降级到本地（副本间不共享）；④ TTL 设得太短。这四条都可以从"键是否稳定"一条线索查起。

### Q169. `config_digest` 与 `index_version` 是怎么让缓存自动失效的？

**回答：** 它们是**缓存键的一部分**，变了键就变，旧条目自然不再命中（无需主动清理）：

- `config_digest`：对影响答案的配置做哈希——检索参数、`chunk_size`、`temperature`、CRAG 开关、`index_version` 等。改一个参数 → digest 变 → 全量缓存失效。
- `index_version`：索引的代次（新增/删除文档、重建后递增）。新文档入库后，旧答案可能已经不完整，必须失效。

这个设计的价值是**避免"清缓存"这种危险操作**：不需要 `FLUSHDB`，不需要跨副本协调，也不会误删别人的数据。

代价是**旧条目会占着内存直到 TTL 过期**（`cache_ttl_s=3600`）。如果一天改十次配置，会有十批互相不可见的条目共存，内存压力上升。所以频繁调参的环境应把 TTL 调短。

### Q170. 内存缓存的淘汰策略是什么？为什么不是逐个 LRU？

**回答：** 实现是"**超限后批量淘汰 10%**"：`if len(_entries) >= _max_entries: 删掉 max_entries // 10 条`（`cache.py:303`）。`cache_max_entries=10000`，即每次淘汰约 1000 条。

不逐个 LRU 的理由是**写路径延迟**：严格 LRU 要在每次 `get` 时维护双向链表（或 `OrderedDict.move_to_end`），而本缓存的读是高频路径；批量淘汰把成本摊到"每 1000 次写入触发一次"，写路径绝大多数时候是 O(1)。

代价是**淘汰不精确**：可能删掉刚写入的热点条目（近似 FIFO），命中率略低于严格 LRU。对"知识库问答"这类**问题分布长尾**的场景，差别不大——绝大多数问题的答案只被问一两次。

### Q171. 语义缓存的近似查询为什么必须把扫描放在锁外？

**回答：** 因为它是 `O(N × D)`（N 个候选 × D 维余弦），2000 条 1536 维就是 300 万次乘加。如果整段在 `self._lock` 里，**缓存就成了全局串行点**：所有并发请求排队等同一把锁，QT 从"缓存加速"变成"缓存瓶颈"。

代码里为此专门留了注释（`cache.py:355`，标了 KQ-17）：此前整段扫描 + 余弦都在锁内，2000 条时把缓存变成串行点。现在的做法是：

1. 锁内只取候选列表（拷贝引用/快照）；
2. 锁外算相似度；
3. 若要提升命中条目（LRU 位置），再短暂进锁一次。

这套"**锁内取快照、锁外算、锁内提交**"的模式是并发优化的通用手法，代价是要接受"计算期间条目可能被淘汰/覆盖"的弱一致——对本场景无害。

### Q172. 文档删除后，缓存里还留着它的答案，怎么办？

**回答：** 这是**缓存与事实不一致**的真实问题，当前处理的完整度取决于两个机制：

1. **`index_version` 递增**：删除文档会让索引代次变化（Q169），从而让"含该文档证据的答案"键失效——这是主防线；
2. **TTL 兜底**：`cache_ttl_s=3600`，最坏 1 小时后旧答案自动消失。

残留风险：若删除没有触发 `index_version` 变化（例如只删了某个 chunk 但索引代次未更新），旧答案仍会在 TTL 内被返回，且**引用编号会指向已删除的内容**。用户的感受是"点开引用发现文档不存在"。

正确做法是删除流程显式做三件事：删向量、删 BM25 条目、**递增索引代次**（并可选地按文档前缀清缓存）。这也是 Q94 提到的"删除不彻底"的一部分。

### Q173. 缓存为什么不缓存流式中间态？

**回答：** 因为中间态**没有复用价值且体积大**：`token` 事件是几十到几百个小包，存下来既占内存又需要重放逻辑（还要处理"用户中途停止"的不完整流）。

所以只缓存**终态 envelope**：完整答案 + 证据列表 + 置信度 + followups。命中时直接返回完整结果（非流式），前端一次性渲染——这对用户是可接受的（缓存命中意味着秒回），对流式体验的损失很小。

代价是"缓存命中时没有逐字效果"，看起来不如实时生成"高级"。产品上通常用"已命中缓存"标识来化解这个感知差异。

### Q174. Redis 缓存的"精确命中"和"语义命中"在多副本下有什么不同？

**回答：** 这是 `RedisSemanticCache` 里写进文档字符串的边界（`cache.py:428-446`），两者范围完全不同：

| 命中类型 | 生效范围 | 原因 |
| --- | --- | --- |
| **精确命中** | **跨副本** | 条目连 payload 一起存在共享存储，A 副本写入，B 副本能直接命中 |
| **语义（近似）命中** | **仅本副本** | 余弦全表扫描在 Redis 上不可行——会把 O(N) 扫描变成 N 次网络往返 |

所以"多副本共享缓存"这句话只对**完全相同的问题**成立：语义索引留在各进程的 `_index` + LSH 里（`cache.py:463-465`），每个副本自己建、自己命中。代码注释对此的表述很直接："跨副本能省下完全相同的问题，语义相近的改写仍需各副本自己命中"。

**代价**：多副本时语义命中率被摊薄约 N 倍（N = 副本数），且副本重启后本地语义索引是空的（需要重新积累）。**为什么不做共享语义索引**：要在存储层做近邻检索，等于把缓存变成一个向量数据库——那是 Milvus 的职责，缓存不该长成第二个检索引擎。

写入失败的处理也值得说：`set` 里 `except Exception` 只记 debug 日志（`cache.py:549-551`），因为"缓存写失败"最多让命中率下降，绝不该让请求失败。这与 `build_cache` 的硬约束一致（`cache.py:648`）：**Redis 不可用必须降级为内存**。

## 七、异步 IO 与阻塞边界

### Q175. 一个 `/ask` 请求在进程内一共穿过几层线程？

**回答：** 五层，每层都有明确职责，不能合并：

1. **事件循环**（uvicorn 的 asyncio）：只做协议解析、准入判定、SSE 写出；
2. **问答执行器** `PipelineExecutor`（`pipeline_workers=32`）：承载整条同步管线，是"每请求占一个位置"的容量单位；
3. **检索池** `_RETRIEVAL_POOL`（4 线程，`hybrid.py:26`）：多查询并行召回；
4. **Agent run 池 / 工具池**（`agent_run_permits=16` 与 `max(8, 16×2)`，`runtime.py:188-193`）：只在 Agent 模式用，且**必须分离**（图线程等工具 future，同池会嵌套死锁）；
5. **AnyIO 默认池**（调到 100，`runtime.py:103`）：管理面、探针、`prepare_process` 等非问答调用。

设计意图是**按"等待什么"分层**：等 Milvus、等模型、等工具各自独立配额，一类慢不拖另一类。代价是线程总数不少（32 + 4 + 16 + 32 + 100 ≈ 184 上限），内存与上下文切换成本真实存在——所以调参不能只看"加线程"，要看加的是哪一层。

### Q176. 为什么问答管线是同步实现 + 线程池，而不是全链路 async？

**回答：** 因为链路上有大量**只有同步客户端**的依赖：pymilvus 的同步连接、本地 BM25 索引、同步 HTTP 的重排器，以及最关键的——**事件是同步生成器**（`factory()` 返回 `Iterator[tuple[str, dict]]`，见 `pipeline_executor.py:163`）。

三个可选方案里选了这个：

| 方案 | 问题 |
| --- | --- |
| 全链路 async 化 | 要换 Milvus/向量库客户端、重写生成器为 async generator，改动面覆盖检索层全部实现，风险与回归成本极高 |
| 每请求一线程（现状） | 简单、边界清楚、同步栈可读；代价是"每请求独占一个线程 8 秒" |
| 混合 | 现在就是这样：事件循环只做 IO 与桥接 |

**代价必须说清**：32 线程 × 平均 8 秒 ⇒ 上限约 4 QPS（`并发容量基线.md:24`）。这不是实现缺陷，是"用线程换简单"的显式付费。真要提吞吐，正确的下一步是把上游调用 async 化（让线程不被网络等待占用），而不是继续加线程。

### Q177. `acquire_async` 为什么用 20ms 轮询，而不是 `Condition` 异步等待？

**回答：** 因为 `threading.Condition` **不能 await**。要在 async 侧等它只有两条路：

1. `await anyio.to_thread.run_sync(cond.wait)` —— **占掉一个线程**，而这正是我们要避免的（等槽位的请求不该消耗线程）；
2. 轮询 —— 不占线程，代价是最多 20ms 的额外唤醒延迟（`pipeline_executor.py:130`）。

选了轮询，因为它有一个前提让成本可控：**等待者数量有上限**（高优先 200 / 低优先 50，`:79`）。最坏情况 250 个协程 × 50Hz = 每秒 1.25 万次锁内判断，每次只做一次整数比较，相对于 8 秒的单请求耗时完全可忽略。

**如果重做**：会用 `asyncio.Semaphore` + 一个由 `release()` 通过 `loop.call_soon_threadsafe` 唤醒的等待队列，做到零轮询。当前不做是因为 `release()` 在工作线程里调用，跨线程唤醒需要持有 loop 引用，而执行器在装配期就要能构造（那时还没有 loop）——轮询是"不引入生命周期耦合"的简化。

### Q178. AnyIO 默认线程池为什么调到 100？为什么不是无限？

**回答：** 默认 40 的池是**全局共享**的，问答路径不占它（由独立的 `PipelineExecutor` 承载），但管理面、探针、`prepare_process` 这些都会用。如果问答高峰把 40 个位置占满，管理端点（配置读取、指标查询、探针）会排队——**观测面被业务面拖死**，这是最不该发生的耦合。

所以 `runtime.py:99-103` 把它调到 100，注释写得很明确："共享池调到 100，避免管理端点在问答高峰期排队"。

为什么不是无限：每线程约 8MB 栈（虚拟地址空间）+ 上下文切换成本；且这个池没有优先级，池越大越难判断"为什么变慢"。100 这个数没有推导过程——它是"够用即可"的经验值，属于**可调但未标定**的参数，这一点在文档里没有过度包装。

另一个硬约束：必须在 `lifespan` 内设置（`runtime.py:96`），因为导入期没有事件循环，调 `current_default_thread_limiter()` 会抛 `NoEventLoopError`。

### Q179. 健康探针为什么要自己建线程池，而且 `shutdown(wait=False)`？

**回答：** 三个决定都有具体原因（`probes.py:60-115`）：

1. **并行而非串行**：9 个依赖串行时，总耗时是各项之和；任一依赖慢 5 秒，整个探针就 5 秒，K8s 的 `timeoutSeconds` 会误杀 Pod。并行后总耗时 = 最慢的一项。
2. **单项超时**：`fut.result(timeout=1.0)`，慢依赖记 `status=down` 而不是拖长整体。
3. **`shutdown(wait=False, cancel_futures=True)`**：探针**不能被慢依赖拖住**，超时后残留线程在池回收后自然退出。如果 `wait=True`，一次依赖卡死就会让 `/readyz` 自身超时——探针失效比依赖失效更危险。

还有一个安全细节：错误只回**异常类型名**（`type(exc).__name__`），不回 `str(exc)`——因为原文可能含 `redis://:pwd@host`、内部路径与库表名。排障靠 `trace_id` 反查日志，而不是把连接串写进探针响应。

### Q180. `run_in_executor` 和 `asyncio.to_thread` 有什么区别？为什么项目两处都用？

**回答：** 机制相同（都往线程池提交），差别在**用哪个池**：

- `asyncio.to_thread` 用 loop 的默认 executor（无界、默认 `min(32, cpu+4)` 线程），**无法注入优先级、排队上限、拒绝计数与指标**；
- `loop.run_in_executor(self._pool, ...)` 用自建的有界池（`pipeline_executor.py:155`），才能做到"排队满即 503""后台让路""`shed_total` 计数"。

所以问答与流式路径一律用后者。项目里只有两处用 `to_thread`：`quickask.py:213` 与 `:228`（解析文档、临时索引）。理由是那是**低频、非核心链路**的一次性操作，为它接执行器属于过度设计；代价也明确——它和 AnyIO 池共享配额，批量快问时可能和管理面抢线程。

判断标准可以总结成一句：**需要"可观测 + 可拒绝"就用自建池，只是"别阻塞事件循环"就用 to_thread。**

### Q181. 事件循环里哪些阻塞点最危险？怎么发现？

**回答：** 最危险的是**看起来很快但会 fsync 或解析大对象**的操作：

| 阻塞点 | 表现 |
| --- | --- |
| 同步 HTTP / DB 客户端（pymilvus、requests） | 整个进程卡住，所有并发请求一起慢 |
| 大 JSON 序列化（几 MB 的证据列表） | 单次几十到几百毫秒 |
| 文本处理（正则回溯、大字符串拼接） | 不可预测的尖刺 |
| 日志同步写盘（含 fflush） | 在容器里被限流时尤其明显 |

发现手段：`PYTHONASYNCIODEBUG=1` 会打印慢回调警告；更实用的是看 `inflight_requests` 与 p95 的关系（事件循环被卡时 inflight 不涨但延迟暴涨），以及 `py-spy dump` 抓主线程栈。

本项目的边界是**结构化的**：所有阻塞调用都在管线线程内（同步生成器），事件循环只做 SSE 写出、`is_disconnected()` 轮询与 20ms 睡眠轮询，没有一个是 CPU 密集型。这个约束比"记得写 await"更可靠——它是靠线程模型强制的，不是靠自律。

### Q182. 客户端断开后，上游调用真的被中断了吗？

**回答：** **没有**，这是明确的技术边界，代码里也如实写了："已发出的上游调用无法中断"（`pipeline_executor.py:173-174`）。

实际语义是：

1. `cancel` 是一个 `threading.Event`；
2. worker 线程在**每个事件产出之前**检查 `if cancel.is_set(): break`（`:185`）；
3. 消费端（SSE 生成器）退出时在 `finally` 里 `cancel.set()`（`:219`）；
4. 非流式路径靠 `_watch_disconnect` 任务每 0.5 秒轮询 `is_disconnected()`（默认 `interval_s=0.5`，`ask.py:351`），断连后置 `cancel`（`ask.py:273`）。

所以取消**节省的是"后续阶段"**（不用再跑 CRAG、再调重排、再生成），但**当下正在进行的那个 HTTP 调用会跑完**。收益仍然很大：一次断开的请求可能从 8 秒缩到 3 秒，槽位提前释放。

配套的两个设计：断开返回 **499** 且**不计入 5xx 错误率**（`ask.py:296-300`），因为"用户取消"不是故障，计入会污染告警阈值。

## 八、容量与压测

### Q183. 32 个 worker 是怎么定出来的？能验证吗？

**回答：** 32 是**配置值，不是实测最优值**。`scripts/capacity.py` 能做的是"参数自洽性校验"，不是容量标定，它把推导过程写死成四步：

1. **Little's Law**：`in_flight = QPS × L`（`:76`）；
2. **建议 workers** = `in_flight × 1.2`（`:79`，留排队缓冲）；
3. **各上游许可** = `in_flight × 该段耗时占比`（`:91`）；
4. **硬约束**：许可之和 ≤ workers（`:96-100`）。

反推：`workers=32` 对应 `in_flight≈26.7`，即 8 秒/请求时约 **3.3 QPS**；文档按 4 QPS 记为上限口径（`并发容量基线.md:24`）。也就是说 32 更像是"按目标 4 QPS 反推 + 留余量"的结果，而不是压测出来的拐点。

**能验证到什么程度**：脚本能验证"参数不违反硬约束"（退出码非零即违规，可直接进 CI），但**不能证明**"32 是最优"。要证明需要真机压测——而这一项在基线文档里是明确空着的（见 Q188）。

### Q184. 为什么不直接把 workers 加到 200？

**回答：** 四个理由，从硬到软：

1. **硬约束会直接拒绝启动**：上游许可之和必须 ≤ workers（`config.py:1083`）。许可和是 28，如果只把 workers 从 32 加到 200 而不动许可，配置能过校验，但**线程会大批堆在等许可上**——线程加了、并发没加，只是多了 168 个阻塞中的线程。
2. **上游配额才是真上限**：模型平台给你的 QPS 是固定的。加线程只是把"在本机队列里等"变成"在上游超时里等"，用户感受到的延迟一样甚至更差（超时还浪费了预算）。
3. **GIL 与内存**：管线里有真实的 CPU 段（BM25 打分、文本处理、JSON 序列化），这些不吃多线程；每线程 8MB 栈 × 200 也是实打实的。
4. **故障半径**：线程越多，单次 GC / 日志刷盘 / 事件循环卡顿影响的并发请求越多。

正确的扩容顺序是：**先解决"线程被网络等待占用"（async 化上游）→ 再提高上游配额（多 key / 多 provider）→ 最后才调 worker 数**。

### Q185. 队列上限 200 和准入超时 30 秒是什么关系？

**回答：** 两者共同决定"实际有效队深"，200 只是**上限，不是目标**。

算一下：若 `L=8s`、32 个 worker，则一个请求在队列里最多等 30 秒（`acquire(timeout_s=30)` 默认）；30 秒内的服务能力是 `32 × 30 / 8 = 120` 个请求。也就是说当队列真排到 200 时，**前面 120 个之内的会成功，后面的必然超时返回 False → 503**。

所以：

- `queue_size=200` 的作用是"给等待者一个明确的拒绝边界"，避免无限排队把内存和用户耐心都耗光；
- 真正的拒绝发生点由 **30 秒 deadline** 决定（`:91-93`）；
- 低优先队列 50（`:49`）是同一逻辑的收紧版——后台任务可以等，但不该占满交互的排队位（`C-11`）。

一个容易被面试官追问的点：为什么不让超时更短？因为 `ask_deadline_ms=120s`，用户侧允许 2 分钟；准入只等 30 秒是"排队 30 秒还没轮到我，就别让用户再等了"的产品判断，不是技术必然。

### Q186. 压测脚本为什么用 `httpx.AsyncClient` 而不是多线程 + urllib？

**回答：** 因为**线程模型会污染被测对象**。`load_test.py` 开头写得很直白："urllib 线程模型测不了 500 条 SSE 长连接"。

具体来说，如果用"每并发一个线程"，测 SSE 连接保持时得到的是**压测机的线程上限**，不是服务端的连接能力；500 条长连接意味着 500 个压测线程，压测机自己先崩了。`AsyncClient` 用少量线程持有大量连接，才测得出"SSE 不占服务端线程池"这个结论。

这也顺带说明了一个方法论：**压测工具的选择必须匹配被测系统的并发模型**。被测端是 async 的，压测端还停留在"线程 = 并发"，测出来的所有数字都不可信。

### Q187. 压测的五个场景分别验证什么？

**回答：** 五个场景各自回答一个不同的问题（`load_test.py:6-13`）：

| 场景 | 验证什么 | 期望 |
| --- | --- | --- |
| `/healthz` 阶梯（1→10→30） | 框架/事件循环上限 | 并发上升时延迟基本不变（无共享锁） |
| `/knowledge/files` 阶梯 | 纯读路径 | 同上，验证读路径不碰执行器 |
| `/ask` 定速（限流以内） | 真实问答延迟 + 缓存行为 | 首次慢、重复问题秒回（缓存命中） |
| `/ask` 超流 | 60/min 闸门与背压语义 | 超额返回 429，**不是** 5xx |
| `/ask/stream` 连接保持 | SSE 是否占线程 | 大量连接打开时 `/ask` 延迟不恶化 |

第 4 和第 5 个最有价值：前者证明"过载时系统是明确拒绝而不是崩溃"，后者证明"长连接不消耗执行器槽位"——这两条正是"背压设计有效"的直接证据。脚本还会顺带测 **TTFT**（首个 `token` 事件到达时间），因为流式体验的瓶颈通常在首包而不是总时长。

### Q188. 容量基线文档里的"真机吞吐"为什么是空的？

**回答：** 因为**用 mock 环境测出来的数字比没有数字更危险**。`并发容量基线.md:71-79` 把这一点写成纪律：

> "把 mock 环境的数字写进『容量基线』，比没有基线更危险——它会被当成生产容量。"

具体不可外推的原因：

1. **模型是 mock 的**：真实 LLM 的首包延迟、并发退化曲线完全不同于 mock；
2. **索引是本地小规模**：HNSW 参数（`m=32`/`ef=64`）在真实规模下未标定；
3. **本机核数与负载噪声**：单机数字会被环境支配（文档要求至少三次取中位数并写机器负载）。

所以文档里只登记"当前生效参数 + 如何测"，把待补项（真机吞吐、多副本吞吐、HNSW 标定）列为显式缺口。这种"宁缺勿假"的处理，在面试里比报一个漂亮数字更能体现工程判断力——**知道什么数字不能信，是容量工作的前提**。

### Q189. 为什么说"限流比执行器更紧"？

**回答：** 算一下就清楚：

- 执行器：`32 / 8s ≈ 4 QPS`（`并发容量基线.md:24`）；
- 令牌桶：容量 60、回填 60/min ⇒ **1 QPS**（突发 60，`:25`）。

也就是说**单租户永远压不到执行器的上限**：稳态 1 QPS 时只占 8 个线程（1×8），剩下的 24 个位置是空的。这带来两个结论：

1. 想做容量压测**必须用多租户**（或临时调高 `ratelimit_refill_per_min`），否则测出来的是"限流器的容量"而不是"系统的容量"；
2. 执行器真正的作用是**扛突发 + 跨租户共享**——60 个突发令牌瞬间打进来，执行器让它们排队而不是全部涌向上游。

`capacity.py:107-113` 把这个陷阱写成了自动告警：`单租户令牌桶上限约 1.00 QPS < 目标 4 QPS：单租户压不到执行器上限，容量是多租户合计出来的（压测需多租户）`。这是"参数互相约束"的典型例子——单独看每个参数都合理，组合起来会得出错误结论。

### Q190. 一次并发容量变更要改哪些地方？顺序是什么？

**回答：** 六个落点，顺序不能反：

1. **`core/config.py`**：改 `pipeline_workers` / 许可数 / 队列上限；
2. **`validate_startup()`**：硬约束校验会拦下非法组合（许可和 > workers，`config.py:1083`）；
3. **`scripts/capacity.py --qps --latency`**：反算"新参数下能承载多少"，顺便暴露限流面与上游配额告警；
4. **HPA `averageValue`**：`deploy/k8s/base/hpa.yaml:32` 的 `28` 就是许可和——许可和变了这里必须同步，否则扩容阈值与进程内饱和点脱节；
5. **告警阈值**：`InflightNearLimit > 28`、`QueueDepthHigh > 150`（队列 200 的 75%）；
6. **基线作废并重测**：`并发容量基线.md:53` 明确要求"改了 worker/许可/队列后旧基线作废并备注原因"。

第 4、5 步最容易漏：它们是**同一组数字在不同系统的副本**（进程内 / K8s / Prometheus 规则），没有单一真相源，只能靠清单约束。这类"跨系统重复常量"是配置漂移的高发区。

### Q191. HPA 为什么用 `inflight_requests=28` 而不是 CPU 或 QPS？

**回答：** 因为三类指标对"IO 等待型负载"的表达力完全不同：

| 指标 | 问题 |
| --- | --- |
| CPU 70% | 瓶颈在等网络，CPU 可能一直很闲；等到 CPU 起来时已经严重排队 |
| QPS | 被租户限流压平（1 QPS 上限），扩副本不会让 QPS 上升，只会让每副本更闲 |
| `inflight_requests` | 直接反映"有多少线程被占用"，与容量单位一致 |

28 这个数的意义是：**在许可被耗尽（28 = 许可和）之前就该扩**——因为一旦触到 28，剩下的 4 个线程（32-28）只够维持本地处理，任何一个慢上游都会立刻把队列推高。所以它是个"提前量"阈值，不是饱和点。

前置条件必须说清：`External` 自定义指标需要 **prometheus-adapter**（`deploy/k8s/README.md:154`），没装的话这条 HPA 规则不生效，只剩 CPU 一条腿。这也是"配置存在 ≠ 能力生效"的典型例子。

### Q192. 指标基数为什么会变成容量问题？

**回答：** 因为每条时间序列在 Prometheus 里都是独立存储 + 独立索引，序列数爆炸会直接把监控打挂（内存/磁盘/查询全崩）。而基数爆炸的根因几乎都是**把业务主键写进了 label**：`tenant`、`user`、`doc_id`、`query`、`trace_id`、`path`。

项目用的是**两条可证伪的性质**而不是"序列数 < N"（`并发容量基线.md:57-62`）：

1. **不随请求量增长**：同样形状的流量打 5 倍后，`{指标名: label 组合}` 集合完全不变；
2. **取值有界**：`route` ∈ 路由模板集合 ∪ `{<unmatched>}`，任何 label 都不得出现业务主键。

执行点有两处：进程内 `tests/integration/test_metrics_cardinality.py`（CI 每次都跑），真机 `scripts/metrics_cardinality.py --rounds 5`（退出码 1 表示膨胀）。收敛实现是 HTTP 中间件把未匹配路由统一记成 `<unmatched>`（`bootstrap.py`），**日志仍保留原始路径**——可观测性不该以基数为代价。

## 九、过载保护与降级

### Q193. 过载时一共有几道闸？顺序是什么？

**回答：** 五道，从外到内：

1. **租户令牌桶**（`dependencies.py:63-89`）：超额 → **429 + Retry-After**，最便宜的一道，不碰任何线程；
2. **后台让路**（`dependencies.py:93-130`）：`waiting ≥ 0.8 × queue_size` 时，`/knowledge/ingest`、`/graph/build`、`/knowledge/rebuild` → **503 + Retry-After 5**；交互端点继续接纳；
3. **准入**（`pipeline_executor.py:71-98`）：`inflight ≥ 32` 且 `waiting ≥ 200`（低优先 50）→ 立即 **503**，不等；或排队超 30 秒 → 同样 503；
4. **上游隔离仓**：许可满则等待（有超时）；熔断打开则 `CircuitOpenError` 快速失败，**不占线程**；
5. **功能降级**：限流/缓存/共享状态 Fail-Open；重排失败跳过精排并标 `reranked=False`；语义缓存未命中就正常走链路。

顺序的设计原则是"**越便宜越靠前**"：能在令牌桶拒绝的，绝不让它进队列；能在准入拒绝的，绝不占线程；能熔断快失败的，绝不等超时。

### Q194. 429 和 503 的分工是什么？为什么不用同一个码？

**回答：** 因为**语义与客户端行为完全不同**：

| 状态码 | 触发点 | 含义 | 客户端应做什么 |
| --- | --- | --- | --- |
| **429** | 令牌桶（`dependencies.py:84-88`） | "你这个租户请求太多" | 按 `Retry-After` 退避，**换租户可绕过** |
| **503** | 准入拒绝 / 后台让路（`pipeline_executor.py:248-253`） | "整个服务现在满载" | 退避 + 重试，**换谁都没用** |

两者的错误码都是 `RATE_LIMITED`，但 HTTP 状态不同——这样前端的分支判断基于状态码（429 = 你自己的问题，503 = 服务的问题），而错误码保持信封一致性。

`503` 还额外携带 `retry_after=5`。有意思的细节：**后台让路的 503 文案是专用的**（"后台任务队列已接近上限"，`dependencies.py:127`），不是笼统的"服务繁忙"——运维从响应里就能判断这是背压而不是故障。

### Q195. 为什么限流和缓存选择 Fail-Open，执行器却是 Fail-Fast？

**回答：** 因为判据不同：**依赖不可用 ≠ 本地资源耗尽**。

- **限流 / 缓存 / 共享状态依赖 Redis**：Redis 挂了如果 Fail-Close，等于"缓存故障导致全站不可用"——故障被放大了一个数量级。所以 `SharedState` 自动降级到进程内，`build_cache` 硬约束"Redis 不可用必须降级为内存"（`cache.py:648`）；降级本身**可自愈**——每次操作前若后端不健康，会按冷却窗口尝试 `_reconnect()`（`shared_state.py:201`、`:438`），避免一次偶发失败把共享状态永久毒化。代价是**暂时失去跨副本保护**：多副本时每个副本各自 60/min，实际总量翻倍——这个风险必须写在文档里而不是藏着。
- **执行器是本地资源**：线程满了没有"降级通道"可用（不排队就是拒绝），Fail-Fast 才是保护——继续接纳只会让所有请求一起变慢，最后一起超时。

一句话总结：**外部依赖故障要"降级可用"，本地资源饱和要"快速拒绝"**。搞反任意一个，都会把小故障变成大故障。

### Q196. 熔断打开后请求去哪了？

**回答：** 分三种情况，取决于调用方有没有降级路径：

1. **有降级**（最理想）：重排熔断 → 跳过精排，用 RRF 融合结果，响应里 `reranked=False`；语义缓存不可用 → 视作未命中，正常走链路；
2. **有替代**：LLM 主通道熔断 → 若配了备用 provider 则切备用（多厂商路由）；
3. **无降级**：抛 `CircuitOpenError`，转成用户可见的错误——但**没有消耗线程等超时**，这是熔断的核心价值（`upstream.py:21-27` 的注释："调用方应映射为降级错误，而不是占用线程等超时"）。

状态机是：`closed` → 窗口 20 次内失败率 ≥ 0.5 → `open` 30 秒 → `half_open`（**只允许 3 个并发探测**，`_in_use < half_open`）→ **连续 3 次成功**才 `closed`，任一失败立即回 `open`（`upstream.py:69-104`）。

为什么半开要限并发：如果不限，30 秒后所有排队的请求会一起冲向还没恢复的上游，等于二次打击。

### Q197. AIMD 自适应并发为什么默认关闭？

**回答：** 三个原因（`upstream.py:9-10`、`config.py:469`）：

1. **与 HPA 形成双环耦合**：AIMD 在进程内缩许可（-30%），HPA 在集群层加副本；两个控制环的观测对象相同（延迟/失败率）但动作方向相反，容易震荡——副本越多，每副本越闲，AIMD 又把许可降下来，HPA 看到 inflight 低就不再扩。
2. **缺真实上游数据**：默认参数（连续 50 次成功 +1，超时 -30%）是通用启发式，没有针对具体 provider 的延迟曲线标定过；开启可能在小流量下频繁抖动。
3. **固定上限的可预测性更高**：出问题时能一眼算出"28 个许可、32 个线程"，而不是"当前许可数是自适应算出来的，需要看指标才知道"。

所以它是**留了开关但没打开的能力**，属于"设计到位、证据不足"——这正是文档要显式标注的那类状态（见 Q200）。

## 十、并发风险与复盘

### Q198. 这套并发设计里最脆的三个点是什么？

**回答：**

1. **上游配额是唯一的真上限**，而且**不可观测于本机**。所有本机参数（32 线程、28 许可、200 队列）加起来都绕不过 provider 的 QPS；扩容若不同步提配额，只是把等待位置从队列搬到超时。这是系统性风险，不是代码缺陷。
2. **32 与 28 的隐式耦合**。许可和必须 ≤ workers，靠 `validate_startup()` 兜底（`config.py:1083`）；但 HPA 的 `averageValue: 28` 和告警 `InflightNearLimit > 28` 是这两个数的**手工副本**，改一处漏两处就会静默漂移。
3. **单进程内存状态在多副本下失效**。语义缓存只在本副本命中（Q174）、`_LshIndex` 各建各的、未配 Redis 时会话/配置存在本地文件——横向扩容后"状态不见了"。这也解释了为什么"多副本吞吐"在基线里是未测项（前置条件是状态外置）。

补充一个更隐蔽的：**`cancel` 无法中断已发出的上游调用**（Q182）。极端情况下 32 个槽位可能全被"已断开但还在跑上游"的请求占着，直到该调用自然结束。

### Q199. 如果要把吞吐提升 10 倍，改动顺序是什么？

**回答：** 顺序错了会白干，正确顺序是"先测量、再解耦、最后扩"：

1. **先测**：`load_test.py` 五个场景跑一遍，确认瓶颈到底在限流、准入、上游还是 CPU。不做这步，后面全是猜。
2. **解开限流**：单租户 1 QPS 是当前最紧的约束，多租户/调 `ratelimit_refill_per_min` 才有意义。
3. **提上游配额**：多 key、多 provider 分流（项目已有 LLM 网关基础），这是唯一能真正提高"每秒能生成多少答案"的手段。
4. **async 化上游调用**：把"线程等网络"变成"事件循环等网络"，同样 32 个线程能扛 10 倍在飞请求——**这是提升幅度最大的一步**，也是改动最大的一步。
5. **状态外置**：Redis 承载会话/配置/缓存，让多副本真正等价（现在语义缓存是各副本独立的）。
6. **最后调 workers / 队列 / HPA 阈值**，并按 §四 作废旧基线。

注意第 4 步之后 `pipeline_workers` 的语义会变（不再是"并发上限"而是"CPU 并发上限"），所有相关文档和告警阈值都要重写——这也是为什么这一步要放到最后确认。

### Q200. 这套设计里，哪些是"配置意图"而不是"已验证事实"？

**回答：** 明确列出来，因为这正是面试里最容易被追问的地方：

| 项 | 状态 |
| --- | --- |
| 真机吞吐 / P50 / P95 | **未产出**（mock 模型 + 本地向量，不具外推性） |
| 多副本吞吐 | **未测**（前置：状态外置） |
| HNSW 参数（`m=32`/`ef=64`） | **未标定**（出厂默认，缺规模数据） |
| AIMD 自适应并发 | 代码就绪，**默认关闭** |
| 灰度自动回滚 | 代码就绪，**默认关闭**（`canary_auto_rollback_enabled=False`） |
| Prometheus 自定义指标 HPA | 需 prometheus-adapter，**未在真实集群验证** |
| 备份 RTO | **未标定**（RPO≈24h 有据，RTO 只有流程没有计时） |

表述方式建议：**"设计上如何保证" + "实测到哪一步" + "没测的为什么没测"**。比如线程模型可以说"32 线程按 Little's Law 反推，参数自洽性由 `capacity.py` 在 CI 校验；真机吞吐未产出，因为 mock 模型的延迟分布不具外推性"。

这比"我们支持 4 QPS"要可信得多——前者给出的是**可复算的推导 + 诚实的边界**，后者是一个无法验证的数字。
