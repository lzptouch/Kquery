# 05 测试与评测

## 1. 测试目录职责

全部测试集中在仓库根 `tests/`，按**依赖成本**分层：越靠上的层越便宜、越应该多写。

```
tests/
├── unit/            纯逻辑：分块策略、RRF 计算、解析器、错误码映射、导入边界
├── integration/     FastAPI + 存储替身：路由契约、领域错误响应、指标埋点
├── format/          50+ 种扩展名的解析契约（每个扩展名一组用例）
├── contract/        OpenAPI schema 与前端类型/客户端的一致性
├── security/        提示词注入、越权、敏感信息等护栏回归
├── e2e/             需要真实后端：全链路 API 用例 + 运行器
│   ├── test_api.py
│   ├── test_all_endpoints.py
│   ├── ui/          浏览器端到端（playwright，需运行中的前端与后端）
│   └── scripts/     需要真实服务的巡检脚本（见 §4）
├── frontend/        前端单测（vitest + jsdom，17 个文件）
└── data/            测试资产：评测语料、金标 qrels、样本问答、基线快照
```

分层规则：

- **不写"需要外部依赖才能跑"的单元测试**。unit/integration/format/contract/security 全部免外部服务，CI 上直接跑。
- **e2e 只在有真服务时跑**，无服务时自动 skip，不制造假失败。
- **测试数据只进 `tests/data/`**，不允许在用例里内联大段语料。

## 2. 本地运行

```bash
# 后端全量（自动跳过需要服务的 e2e）
uv run --project backend python -m pytest

# 只跑便宜的一层
uv run --project backend python -m pytest tests/unit -q
uv run --project backend python -m pytest tests/integration -q

# 前端
cd frontend && npm install && npm test

# e2e（先起服务）
KQUERY_API_BASE=http://127.0.0.1:8100 uv run --project backend python -m pytest tests/e2e -v
KQUERY_UI_WEB=http://127.0.0.1:8090 uv run --project backend python -m pytest tests/e2e/ui -v
```

前端测试物理位置在 `tests/frontend/`，但依赖从 `frontend/node_modules` 解析：`tests/node_modules` 是指向 `frontend/node_modules` 的相对符号链接，`npm install` 后即可用。不要在 `frontend/vitest.config.ts` 里用 `resolve.alias` 指向包目录——那会绕过 `package.json` 的 `exports` 映射，`@testing-library/jest-dom/vitest` 这类深路径会解析失败。

## 3. CI 门禁

`.github/workflows/ci.yml` 在 PR 上跑：

| Job | 内容 |
| --- | --- |
| lint | `ruff check` + 配置模板一致性（`.env.example` 与 `Settings` 不漂移） |
| backend-test | pytest 全量；先用 `docker compose -f deploy/docker/docker-compose.yml up -d etcd milvus` 起真实 Milvus，测试连 `127.0.0.1:19531` |
| frontend | `tsc` 类型检查 + `vitest run` + `vite build` |
| image | 构建后端镜像（验证 Dockerfile 可用） |
| doc-refs | 公开文档里的相对链接必须存在 |

覆盖率门槛 85%（`pyproject.toml` 中配置）。新增模块没有用例会拉低覆盖率导致失败。

## 4. 巡检脚本（`tests/e2e/scripts/`）

这些是**需要真实服务**的诊断脚本，不是 pytest 用例，放在 tests 下因为它们同样是"验证行为"：

| 脚本 | 用途 |
| --- | --- |
| `e2e_full.py` | 全链路：入库 → 检索 → 问答 → 引用 → 会话 |
| `e2e_browser.py` | 浏览器端全流程巡检（playwright） |
| `e2e_new_features.py` | 新特性回归（Agent、多模态、图谱等） |
| `api_sweep.py` | 遍历所有端点做冒烟，输出通过/失败矩阵 |
| `smoke_api.py` | 最小冒烟：探针 + 一次问答 |
| `browser_verify.py` | 页面元素与可见文本断言 |
| `console.py` / `http_client.py` / `browser_helpers.py` | 上述脚本共用的小工具（HTTP、终端着色、浏览器启动） |

运行方式（在仓库根）：

```bash
uv run --project backend python tests/e2e/scripts/smoke_api.py --base http://127.0.0.1:8100
uv run --project backend python tests/e2e/scripts/api_sweep.py --base http://127.0.0.1:8100
```

## 5. 评测（离线，质量基线）

评测资产在 `tests/data/eval/`，运行器在 `scripts/eval/`。

| 资产 | 内容 |
| --- | --- |
| `corpus/`、`corpus_img/` | 评测语料（Markdown / 图片） |
| `queries*.jsonl` + `qrels*.tsv` | 查询与金标相关性标签 |
| `baseline.json` | 基线指标快照（改动前后要对比这个） |
| `rubric.v1.json` | LLM 判分细则 |
| `injection_cases.jsonl` | 提示词注入回归集 |
| `agent_cases.jsonl` | Agent 多步任务回归集 |

| 脚本 | 用途 |
| --- | --- |
| `scripts/eval/run_eval.py` | 检索 + 生成主评测，产出 report |
| `scripts/eval/run_agent_eval.py` | Agent 任务评测 |
| `scripts/eval/chunk_experiment.py` | 分块策略 A/B |
| `scripts/eval/partition_ab.py` | 索引分区 A/B |
| `scripts/eval/reindex.py` | 重建索引并核对方差 |
| `scripts/eval/cost_quality.py` | 成本 vs 质量曲线 |
| `scripts/eval/build_goldset*.py` | 构建/扩充金标集 |

运行示例：

```bash
uv run --project backend python scripts/eval/run_eval.py --limit 50
```

`report*.json`、`runs_*.jsonl` 是**运行产物**，已在 `.gitignore` 中，不要提交；需要留证据时贴关键指标到 PR 描述。

## 6. 提交前检查清单

- [ ] `uv run --project backend python -m pytest` 通过（或说明哪些层因缺服务被 skip）
- [ ] `cd frontend && npm test` 与 `npm run build` 通过
- [ ] `ruff check backend tests scripts` 干净
- [ ] 改动检索/生成逻辑时，附上评测集前后对比（`baseline.json` 口径）
- [ ] 新增端点/错误码时，同步 `tests/contract/` 与前端映射
- [ ] 新增脚本时，放进 `scripts/`（运维/评测）或 `tests/e2e/scripts/`（验证），不要混放
