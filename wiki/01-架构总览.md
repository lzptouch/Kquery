# 01 架构总览

## 1. 系统定位

Kquery 是一个面向**企业文档库**的检索增强问答（RAG）系统：把 PDF / Word / PPT / Excel / Markdown / 图片等资料入库，提供带引用的问答、快问、会话存档、图谱视图与检索诊断。

它解决的不是"接一个大模型"，而是三件事：

1. **召回得准**：混合检索（向量 + BM25）+ 查询改写/分解 + 重排，而不是单路向量召回。
2. **答得可查**：每条结论都能回到原文分块，前端可点开引用。
3. **跑得住**：入库异步、请求有截止时间、外部依赖有降级、全链路有指标。

## 2. 代码分层

```
backend/app/
├── api/            10 个 APIRouter：HTTP 边界，只做参数校验 → 调服务 → 组装响应
├── assembly/       应用装配：容器、路由注册、生命周期、钩子、pipeline 串联
├── services/       业务能力（可按能力域独立演进）
│   ├── parsers/    50+ 种扩展名的文档解析
│   ├── chunkers/   分块策略（按 chunk_policies 选型）
│   ├── retrieval/  bm25 / vector / hybrid / fusion / rerank / filters
│   ├── query/      意图识别、查询改写（expanders）、问题分解（decomposer）、编排
│   ├── generation/ 检索→缓存→证据→生成→护栏 的 stage 化流水线
│   ├── agent/      LangGraph 状态机（Plan / Tool / Reflect / Replan / Answer）
│   ├── graph/      图谱构建与检索
│   ├── evaluation/ 离线评测与指标计算
│   ├── context/    会话上下文与摘要
│   └── validation/ 引用校验、幻觉兜底
├── domain/         领域模型与仓储接口（不依赖 FastAPI / Milvus 细节）
└── core/           配置、错误码、日志、指标、链路追踪、并发原语
```

`frontend/` 是 React 18 + TypeScript + Vite 的单页应用，按 feature 组织在 `src/features/`（chat / knowledge / admin / shell / common），HTTP 与 SSE 客户端封装在 `frontend/src/lib/`。

### 为什么这样分层

- **api 不含业务**：路由层只做协议适配。要加一个端点，改动应只在 2 个文件（router + 服务方法），而不是横穿全仓。
- **assembly 承担"接线"**：服务实例的构造、依赖注入、路由注册、启动/关闭顺序集中在一处。`main.py` 保持薄壳，只 re-export `create_app`，避免"入口文件什么都干"。
- **services 按能力域切，而不是按技术类型切**：`retrieval/` 内部同时有 bm25、vector、fusion、rerank，改检索逻辑只在一个目录内闭环。
- **core 不反向依赖 services**：配置、错误码、指标是底座，任何层都可以用；反过来不行。

## 3. 一次问答请求的流转

以流式 `/ask` 为例：

```
POST /ask (SSE)
  │
  ├─ api/ask.py               解析 AskRequest、绑定 request_id、选流式/非流式
  ├─ services/query          意图分类 → 查询改写 / 多跳分解
  ├─ services/retrieval      向量召回 + BM25 召回 → RRF 融合 → 重排 → 过滤
  ├─ services/generation     缓存命中检查 → 证据装配 → 提示词组装 → 生成 → 护栏
  ├─ services/validation     引用对齐、无依据内容降级
  └─ SSE 事件                 evidence → answer → done（异常走 error）
```

关键设计点：

- **每个阶段可观测**：`core/metrics.py` 暴露 Prometheus 指标，`/metrics` 输出；阶段耗时可在链路追踪里看到。
- **请求有截止时间**：`core/deadline.py` 让下游 LLM / 检索调用共享同一个 deadline，避免长尾拖死连接。
- **降级而非报错**：向量库不可用时回退 FAISS 本地索引；LLM provider 失败时按配置切备用通道（见 [06 配置参考](./06-配置参考.md)）。

## 4. 运行时组件

| 组件 | 作用 | 缺省形态 |
| --- | --- | --- |
| FastAPI + Uvicorn | HTTP / SSE 服务 | `backend` 容器，8100 |
| Milvus 2.6（etcd 元数据） | 向量检索 | `milvus` + `etcd` 容器 |
| FAISS | 无 Milvus 时的本地向量后端 | 进程内 |
| Redis | 缓存、会话/任务等外部状态 | `redis` 容器 |
| SQLite | 会话存档与 LangGraph checkpoint | 容器卷 |
| React 前端 | 管理台与问答界面 | `frontend` 容器，8090 |

存储的具体降级顺序与配置项见 [04 部署与运维](./04-部署与运维.md) 与 [06 配置参考](./06-配置参考.md)。

## 5. 技术选型

| 选择 | 理由 |
| --- | --- |
| FastAPI | 原生异步 + SSE，OpenAPI 自动生成，契约测试可直接基于 schema |
| Milvus | 标量过滤与向量检索能在一条语句里表达；生产与测试连同一个服务，避免离线/在线的行为差异 |
| FAISS 兜底 | 无 Milvus 的单机演示场景仍可跑通检索链路（`VECTOR_STORE=faiss`） |
| jieba + BM25 | 中文短查询下 BM25 与向量互补，融合后召回率提升明显 |
| LangGraph | Agent 流程需要显式状态与可回放的 checkpoint，不用手写状态机 |
| React 18 + Vite | 流式增量渲染与引用面板需要细粒度更新；Vite 的开发代理便于前后端分开调试 |
