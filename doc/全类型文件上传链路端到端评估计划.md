# 全类型文件上传链路端到端评估计划

> - **性质**：实施计划（非现状分析，不放入 `doc/analysis/`）
> - **目标**：清空 `data/` 运行时数据 → 按项目支持的文件类型建目录、生成测试语料 → 走通「上传 → 解析 → 索引 → 提问 → 回答」全流程 → 用**金标事实**比对原始文档内容与问答输出，量化评估上传解析质量与问答表现
> - **代码基线**：`70360ec` + 工作区未提交改动（快问/附件面板/多副本共享语义已下线）
> - **产出物**：`tests/data/upload_eval/`（语料 + 事实表 + 报告）、`scripts/eval/upload_corpus_gen.py`（落盘生成器）、`scripts/eval/upload_e2e_eval.py`（执行与评分器）
> - **修订说明**（对照代码核实后的更正）：
>   1. **L0 链路自测已基本存在**——`tests/format/`（2699 行）已有 50 扩展名契约、格式 e2e（上传→indexed→预览→提问召回特征串）、PDF-01~30、跨格式一致性；本计划**不重建 L0**，只补 5 个缺口（§1.3）。
>   2. **生成器复用 `tests/format/fixtures.py`**（已有 20+ 个 `make_*`，含中文 PDF 字体与扫描件），不另起一套（§4.3）。
>   3. `.doc` 不是「直连 docx 解析器」——需 LibreOffice 转换，无 soffice 时明确报错（§4.2）。
>   4. compose 的 `init` 服务只建集合、**不删除已有集合**；且 compose 场景 `DATA_DIR=/data` 是 named volume，宿主机 `data/` 不参与（§3.1）。
>   5. `/ask` 的拒答字段是 `verdict`（`answered`/`refused`），没有 `refused` 布尔字段；上传成功要断言 `status=="indexed"` 而非仅 HTTP 200（§5.2）。
>   6. mock LLM 是**抽取式**合成、mock OCR 是**固定文本**（不含图中真实文字）；live 档 `DASHSCOPE_API_KEY` 同时承担 embedding/rerank/OCR 回落（§6）。

## 一、需求拆解与关键结论

### 1.1 需求拆解

| 需求 | 对应批次 |
| --- | --- |
| 删除 `data/` 中的现有数据 | B1（含 Milvus 集合同步清理——**向量不在 `data/` 里**，只删目录清不掉） |
| 按文件类型建文件夹（项目支持的类型） | B2（按**解析器路由**分 10 类目录含 `negative/`，见 §4.1） |
| 每个文件夹生成各种测试文件 | B2（正向 ~28 个 + 反向 5 个，复用 `fixtures.py` 夹具，见 §4.2） |
| 测试上传、解析、提问、回答全流程 | B3（执行器三阶段：upload → ask → score） |
| 比对原始内容与问答内容，评估项目性能 | B3/B5（证据/答案事实召回 + 拒答正确性 + 分类型汇总报告） |

### 1.2 已核实的项目事实（逐条对照代码）

1. **支持 50 个扩展名**（`backend/app/services/parsers/router.py:26-36`；`tests/format/test_all_extensions.py:56-61` 有「恰好 50 个」守卫）：Markdown `.md/.markdown`；文档 `.pdf`（扫描页自动 OCR）、`.docx`（`.doc` **经 LibreOffice headless 转换**，`parsers/docx.py` docstring，无 soffice 明确报错）；表格 `.xlsx`；演示 `.pptx`；图像 `.png/.jpg/.jpeg`；纯文本 10 种（`.txt/.csv/.tsv/.json/.jsonl/.yaml/.yml/.log/.ini/.toml`）+ HTML 2 种（剥标签、丢 script/style）；代码 28 种（全文入索引）。
2. **不支持的行为**：`.xls`/`.ppt` 给「另存为新格式」提示，音频给「不含语音转写」提示，其余（如 `.zip`）兜底消息**会把 50 个扩展名全量列出**→ 断言只匹配前缀；错误码 `UNSUPPORTED_FILE_TYPE=3101`，HTTP **400**（`ApiError` 默认 `http_status=400`）。
3. **上传入口**：`POST /knowledge/upload`（同步单文件，**同样走令牌桶限流**）与 `POST /knowledge/ingest`（异步多文件任务制）。上传响应字段：`file_id/filename/doc_id/size/uploaded_at/chunks/status/error`——**必须断言 `status=="indexed"`**，不能只看 200。
4. **鉴权已下线**：`get_principal` 恒为固定身份，**无需任何请求头**；`DELETE /knowledge/files/{doc_id}` 可用于批次前清理。
5. **问答入口**：`POST /ask`（`question`，`top_k` 上限 10）。响应含 `answer/evidence[]/verdict/refusal_reason/answer_source/confidence/trace_id`；`Evidence` 含 `content/source/doc_id/filename/chunk_id/score`（`domain/schemas.py:149-171`）。拒答用 `verdict=="refused"`，**没有 `refused` 布尔字段**。
6. **"上传成功 ≠ 内容可用"是项目既有纪律**（`tests/format/test_format_e2e.py` 头注释），本计划的评分口径与之一致。
7. **生成器依赖全部现成**（backend venv 验证）：`pymupdf 1.28.2`、`python-docx 1.2.0`、`openpyxl 3.1.5`、`python-pptx 1.0.2`、`Pillow 12.3.0`。**不新增依赖**。
8. **OCR 只允许 `dashscope` | `mock`**（`parsers/ocr.py:187`，不支持本地模型）；`OCR_PROVIDER=auto` 跟随生成 provider（DeepSeek/MiniMax/智谱 回落 dashscope），无千问 key 启动校验即拦下。
9. **限流与默认配置**：按租户令牌桶 `RATELIMIT_CAPACITY=60` + `REFILL_PER_MIN=60`（`.env.example:186-188`）；`MAX_UPLOAD_MB=50`、`PDF_OCR_ENABLED=True`、`PARAMETRIC_FALLBACK_ENABLED=True`（可配为纯拒答）。
10. **mock LLM 是抽取式合成**（`services/llm.py:746-760`）：按问句关键词与证据句重合度挑 ≤3 句并带 `[#n]` 引用；无证据回 `NO_INFO_ANSWER`；意图/校验/改写/兜底各有确定性应答。→ mock 下**证据召回与拒答判定可测**，但答案只是证据子集，不代表生成质量。
11. **mock OCR 是固定文本**（`parsers/ocr.py:105-114`，返回「[OCR 模拟识别结果] 图像文件 xxx 中包含一段示例文字」）——**不含图中真实文字**。→ 图像/扫描件内容级评估必须 live + dashscope；mock 下只验路由、块数、资源存档。
12. **同名重传幂等语义**（`services/knowledge.py:203-208`）：内容哈希相同→同 `doc_id`（覆盖）；内容不同→`doc_id` 加 `-hash8` 后缀**累积新版本**并占检索位。→ 语料改动后应清库再跑。

### 1.3 与现有 `tests/format/` 体系的边界（本计划最重要的约束）

**已存在、不重建**：50 扩展名契约（`test_all_extensions.py`）、5 类主格式 e2e（`test_format_e2e.py`：上传→`indexed`→预览→提问召回特征串）、PDF-01~30 矩阵（`test_pdf_matrix.py`）、各格式专项 DOCX/XLSX/PPTX/MD/TXT/HTML/CODE/IMG-01~04（`test_other_formats.py`）、跨格式一致性 XFM-01~10（`test_xformat.py`）、夹具工厂 20+ 个 `make_*`（`fixtures.py`，含 CJK 字体与扫描件）、真实 OCR 人工签字用例 IMG-05（skip）。

**本计划补的 5 个缺口**：

1. **答案内容**：现有 e2e 只断言证据召回特征串，从不检查 `answer` 说了什么；
2. **真实 OCR**：IMG-05 是手工用例，图像/扫描件从未进过自动化内容评估；
3. **物理目录语料**：现有夹具是现场构造 bytes 不落盘，无法用 UI 手工逐个上传，也没有按类型目录的数据集；
4. **分类型汇总与基线**：`run_eval.py` 只算检索指标（recall/nDCG/MRR），没有「上传→解析→问答」端到端报告；
5. **live 生成质量**：现有全链路只在 mock 模型下跑，真实 LLM 的答案事实命中/拒答兜底无度量。

| --- | --- | --- | --- |

## 三、B1：数据清理与复位

### 3.1 先分清两种运行形态（初稿此处有误）

| 形态 | `DATA_DIR` 实际位置 | 向量存储位置 | 清理对象 |
| --- | --- | --- | --- |
| **裸机 / 本地开发** | 宿主机 `<仓库>/data/` | Milvus 服务端（`KQUERY_MILVUS_URI`）或 FAISS 文件 `data/index/` | 删宿主机 `data/` + 处理 Milvus 集合（`kquery_chunks`） |
| **docker compose** | **named volume `backend_data`（容器内 `/data`）** | named volume `milvus_data`（`deploy/docker/docker-compose.yml`） | 宿主机 `data/` **根本没被使用**；须删两个卷 |

> 关键事实：compose 的 `init` 服务（`docker-compose.yml:88-127`）只做 `MilvusVectorStore.load()`（建集合/加载），**不会 drop 已有集合**——初稿「`up init` 幂等重建」不成立，跑完旧向量仍在。

### 3.2 清理流程

**裸机**：

```bash
# 1) 停后端后备份并清空
mv data data.bak.$(date +%Y%m%d)   # 确认后删除；users.json 为认证遗留死数据，一并清
# 2) 处理 Milvus 集合（旧 uitest 文档向量仍在服务端）
#    python -c "from pymilvus import MilvusClient; c=MilvusClient(uri=...); c.drop_collection('kquery_chunks')"
# 3) 启动后端（FAISS 模式自动重建 data/index/）
```

**compose**：

```bash
docker compose -f deploy/docker/docker-compose.yml down
docker volume ls | rg 'milvus_data|backend_data'    # 确认卷名（默认 <项目名>_xxx）
docker volume rm <项目名>_milvus_data <项目名>_backend_data
docker compose -f deploy/docker/docker-compose.yml up -d init backend
```

**验收**：`/healthz` 全 up；`/knowledge/stats` 的 `documents / indexed_documents / total_chunks` 三项均为 0；`/knowledge/files` 为空数组。

### 3.3 顺序纪律：先定 provider，再建集合

`resolved_embedding_dim` 随 provider 变化，Milvus 集合按维度建 schema（配置启动提示明确「维度变化必须重建索引并重新入库」）。因此顺序固定为：

```text
确定 L0/L1 的 provider 组合 → 起一次确认 resolved_embedding_dim → 再清库/建集合 → 再上传语料
```

中途切换 provider 导致维度变化时必须重跑 B1，否则 upsert 维度不匹配。

## 四、B2：语料库设计与生成器

### 4.0 位置决策：语料不放运行时 `data/`

需求原话是「删除 `data/` 中的数据，按类型建文件夹」。但 `data/` 是运行时目录：B1 会清空它，上传后系统自身还要往里写（`uploads/`、`metadata.json` 等），测试语料放进去会与运行时数据混在一起、且下次清理即丢。因此**语料放在 `tests/data/upload_eval/corpus/`**（与 `tests/data/eval/` 同构，可入库、可 diff）。若希望「在 `data/` 下直观看到分类文件夹」，B2 完成后建软链即可：

```bash
ln -s ../../tests/data/upload_eval/corpus data/upload_eval
```

### 4.1 目录结构（10 类，按解析器路由分组）

```text
tests/data/upload_eval/
├── corpus/
│   ├── markdown/     # .md .markdown
│   ├── text/         # .txt .csv .yaml .json .log
│   ├── html/         # .html
│   ├── pdf/          # 文本型 / 表格型 / 扫描型 / 混合型
│   ├── word/         # .docx
│   ├── excel/        # .xlsx（多 sheet）
│   ├── ppt/          # .pptx（含表格页）
│   ├── image/        # .png .jpg（OCR 通道，需 dashscope key）
│   ├── code/         # .py .ts .java
│   └── negative/     # 反向用例（期望 400 + 3101）
├── facts.jsonl       # 金标事实表（§4.4，生成器与评分器唯一真源）
├── runs/             # 上传/问答记录（可 diff）
└── report.json       # 汇总报告（B5 产出）
```

### 4.2 文件清单（正向 28 + 反向 5，全部复用 `fixtures.py` 的 `make_*`）

| 目录 | 文件 | 生成方式 | 覆盖点 |
| --- | --- | --- | --- |
| markdown | `guide.md` / `notes.markdown` | `make_markdown()`（扩展传自定义正文） | 标题层级、表格、代码块、`.markdown` 别名 |
| text | `faq.txt` / `metrics.csv` / `config.yaml` / `events.json` / `app.log` | `make_text()` + 自定义字节 | 纯文本族 5 种 |
| html | `page.html` | `make_html()` + 自定义正文 | 剥标签、丢 script/style |
| pdf | `report.pdf` / `table.pdf` / `scan.pdf` / `mixed.pdf` | `make_text_pdf(pages=3, cjk=True)` / `make_table_pdf(rows=5, cols=4)` / `make_scanned_pdf(pages=2)` / `make_mixed_pdf()` | 中文文本层、几何表格、**扫描页 OCR**、逐页判定 |
| word | `contract.docx` | `make_docx(with_table=True, headings=3)` | 标题样式、段落、表格 |
| excel | `budget.xlsx` | `make_xlsx(sheets={...3 sheet...})` | 多 sheet、数字保真 |
| ppt | `roadmap.pptx` | `make_pptx(with_table=True, slides=6)` | 文本框、表格页 |
| image | `poster.png` / `photo.jpg` | `make_png()` / `make_jpg()`（改为可传自定义文字） | 图像 OCR（需 dashscope） |
| code | `app.py` / `service.ts` / `Main.java` | `make_code(ext)` | 代码全文保留 |
| negative | `legacy.xls` / `legacy.ppt` / `song.mp3` / `archive.zip` | 任意字节 | 400 + 3101 + 专门提示（`.zip` 只匹配前缀） |
| negative | `corrupt.pdf` | `make_corrupt_pdf()` | 明确失败，非静默入库 |
| negative（备注） | `.doc` 老式二进制 | `make_doc_like_binary()` | 有 LibreOffice→成功；无 soffice→**明确报错**（按环境二选一断言） |

> 夹具生成的两个既定坑直接沿用 `fixtures.py` 的处理：① 中文 PDF 必须用内置字体 `CJK_FONT="china-s"`；② 文本页字符数 **≥30 字**，否则会被判成扫描页（`_pdf_text_for` 注释）。

### 4.3 生成器设计：薄层 + 对 `fixtures.py` 的最小扩展

**不新造生成逻辑**。`scripts/eval/upload_corpus_gen.py` 只做三件事：

1. 调 `tests/format/fixtures.py` 的 `make_*`（返回 bytes）写入 `corpus/<类型>/<文件>`；
2. 生成 `facts.jsonl`——与正文注入共用同一份事实常量，保证「写进去的」与「要断言的」同源；
3. 打印清单（类型 / 大小 / 事实条数 / sha256）供抽查与报告溯源。

**对 `fixtures.py` 的扩展**（向后兼容，既有 2699 行格式测试零改动）：给 `make_markdown / make_text_pdf / make_table_pdf / make_docx / make_xlsx / make_pptx / make_html / make_png / make_jpg` 增加可选 `body` / `sections` / `text` 参数，默认值维持现状。

**幂等**：事实常量固定，重复运行产物字节级一致（可 diff），不写随机数。

### 4.4 金标事实设计（`facts.jsonl`）

每个正向文件注入 2~3 条**可机检的唯一事实**（自造实体 + 精确数字 + 专属编号，避开训练语料）。每文件一条记录，`l0_mode` 与 `expect_verdict` 是必填字段：

```json
{"file": "excel/budget.xlsx",
 "l0_mode": "full",
 "facts": [
   {"fact_id": "F-XL-01",
    "fact_text": "猎隼计划（Project-Falcon-2026）的年度预算上限为 47.3 万元",
    "question": "猎隼计划的年度预算上限是多少？",
    "expected_contains": ["47.3万", "47.3 万", "47.30万元"],
    "expect_verdict": "answered"}
 ],
 "negative_questions": [
   {"question": "猎隼计划的火星着陆窗口是哪天？", "expect_verdict": "refused_or_parametric"}
 ]}
```

设计纪律：

- `l0_mode`：`full`（mock 下全可测）/ `link_only`（image、scan——mock OCR 无真实文字，事实必不命中，只验链路与块数）；
- `expect_verdict`：`answered` / `refused` / `refused_or_parametric`（后者按 `PARAMETRIC_FALLBACK_ENABLED` 实际值二选一，脚本启动时从配置确认）；
- `expected_contains` 列多个等价写法，匹配前做归一化（去空白、全半角）；
- 事实分布在标题 / 正文 / 表格 / 页脚 / 代码注释等不同位置，覆盖"切块后仍能召回"；
- 正向问题须与事实句有实词重合（mock 抽取式合成依赖关键词重合，否则 L0 会假失败）；
- 人工只审 `facts.jsonl`，不逐个审二进制文件。

### 4.5 版本库策略

语料入库（与 `tests/data/eval/corpus/` 的「快照冻结」纪律一致）：单文件 1~5KB，全量约 300~500KB，可 diff、可直接用 UI 手工上传。生成器与产物均入库；`runs/` 入 gitignore，`report.base.json` 入库（§5.3）。

## 五、B3：执行与评分器（`scripts/eval/upload_e2e_eval.py`）

### 5.1 三阶段流水线

```text
reset(可选) → upload(逐文件同步上传) → ask(按 facts.jsonl 提问) → score(评分汇总)
```

| 阶段 | 动作 | 落盘 |
| --- | --- | --- |
| `--reset` | 前置清理（§3）：删除已入库文档（`DELETE /knowledge/files/{doc_id}`），或仅校验 `/knowledge/stats` 为零 | — |
| upload | 遍历 `corpus/**` 逐文件 `POST /knowledge/upload`；记录 `status`、`chunks`、耗时、`doc_id`；反向用例记录状态码与错误码 | `runs/upload.jsonl` |
| ask | 按 `facts.jsonl` 逐条 `POST /ask`（`top_k=10`）；记录 `answer / evidence / verdict / answer_source / refusal_reason / trace_id / 耗时` | `runs/answers.jsonl` |
| score | 离线评分（`--score-only` 可脱离服务复算） | `report.json` + 终端 Markdown 表 |

**并发与节流**：串行下 ~90 次问答受生成延迟主导（约 8~22 分钟），令牌桶 60/min 不是瓶颈；建议 `--concurrency 2~4`（上游 `upstream_llm_permits=12` 与管线线程池足够），保留 429 重试。

### 5.2 指标体系（口径按实际字段重写）

| 维度 | 指标 | 口径 |
| --- | --- | --- |
| 上传解析 | 上传成功率（分类型/整体） | HTTP 200 **且** `status=="indexed"` **且** `chunks>0` |
| | 反向用例正确性 | HTTP 400 + `error.code==3101` + 提示可读（`.zip` 仅匹配前缀） |
| | 解析耗时 p50 / p95 | upload 阶段客户端计时（同步端点含解析+索引） |
| 检索（证据） | **证据事实召回率** | 该问题 `expected_contains` 任一子串出现在 `evidence[].content` 拼接文本中的比例 |
| | **溯源正确率** | 命中证据中至少一条的 `filename` 等于目标文件（防"答对了但不是这份文档"） |
| 答案 | **答案事实召回率**（仅 L1） | `expected_contains` 任一子串出现在 `answer`（归一化后）的比例 |
| | 正向问题拒答率 | `verdict=="refused"` 的比例，应为 0 |
| | 超范围正确率 | `expect_verdict=refused`→`verdict=="refused"`；`refused_or_parametric`→`refused` 或 `answer_source=="parametric"` |
| | 引用一致性 | `answer` 中的 `[#n]` 都能在 `evidence` 中找到且不越界（防编造引用） |
| 忠实度（可选） | 抽 10% 人工核对 | 答案中的事实能否在 evidence 中原样找到；不进门禁 |

**L0 / L1 断言分工**：

- L0（mock）：上表除「答案事实召回率」「引用一致性」外均可测；`l0_mode=link_only` 的文件（image/scan）跳过事实类指标，只验 `status/chunks`；正向问题 `verdict` 应为 `answered`，超范围问题应 `refused`（mock 有确定性拒答/兜底）。
- L1（live）：全量指标。mock 的抽取式答案等于证据子集，**答案召回没有独立信息量，列为 L1 专属**。

### 5.3 报告与门禁

- `report.json`：`{mode, provider, corpus_sha256, by_type, by_file, totals}`——语料哈希保证报告可比；
- 终端 Markdown 汇总表（类型 / 上传成功 / 证据召回 / 溯源 / 答案召回 / 超范围 / p95 耗时）；
- **基线门禁**：沿 `run_eval.py` 的 `--baseline --max-drop` 风格（该脚本默认 0.02），新脚本默认 0.05，证据召回或答案召回回退超阈值即非零退出。

## 九、风险与注意事项

| 风险 | 缓解 |
| --- | --- |
| **只删宿主机 `data/` 清不掉 Milvus 旧向量**；compose 场景 `init` 不 drop 集合，且宿主机 `data/` 不参与 | §3.1 按形态清理；用 `/knowledge/stats` 三项归零验收 |
| 换 provider 导致 embedding 维度变化，集合 schema 不匹配 | §3.3 顺序纪律：先定 provider 再建集合；变更后重跑 B1 |
| 语料改动后同名重传产生 `-hash8` 新版本占检索位 | 复跑前 `--reset` 或按 `DELETE /knowledge/files/{doc_id}` 清空 |
| 误删非运行时数据 | `data/` 全目录 gitignore；先 `mv` 备份再删，保留一次回滚 |
| 图像/扫描用例无 OCR key 时变 fail | 按 key 有无自动 `skip` 并单列；L0 用 mock OCR 只覆盖路由与块数 |
| mock 档误当内容评估 | mock LLM 是抽取式、mock OCR 是固定文本；脚本输出明示「答案召回仅 L1」 |
| `.doc` 环境依赖差异 | 用 `make_doc_like_binary()`：有 LibreOffice 断言成功、无则断言明确报错（known-limit，二选一） |
| live 档真实计费 | 单文件 1~5KB、PDF ≤3 页、PPTX ≤6 页；问题 ~90 次；并发 2~4 + 429 重试 |
| 字面匹配误判（如"47.3万"↔"47.30万元"） | `expected_contains` 列等价写法 + 归一化；误判样本进报告明细供人工复核 |
| 语料事实与训练语料撞车 | 事实全部自造（专属名词 + 精确数字），保证"答对只能来自上传文档" |
| 报告含敏感信息 | 不落 key、不落完整答案原文（只落命中布尔与截断片段），与日志脱敏纪律一致 |
