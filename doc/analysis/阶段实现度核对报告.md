## 一、总体结论

### 1.1 一句话结论

**主干算法能力（阶段 1~9）绝大部分真实落地，但存在三类系统性缺陷：① 默认 UI 走 Agent 路径，导致阶段 2/5 的检索可观测与自反思能力在运行时全部不可达；② 阶段 9 的 ACL/审计/敏感词只挂在 Agent 路径上，线性 `/ask` 路径完全绕过；③ 阶段 10 部署运维整体为 0 实现（0 个 Dockerfile、0 个 K8s 清单、0 个 `/ops/*` 端点）。**

### 1.2 各阶段实现度评分

### 1.3 三类系统性缺陷（按影响面排序）

#### 缺陷 A：默认 UI 走 Agent 路径，阶段 2/5 能力在运行时不可达 —— P0

`ChatPage` 恒传 `mode: "agent"` 且必带 `sessionId`：

```210:210:frontend/src/features/chat/ChatPage.tsx
      }, { sessionId, mode: "agent" }).finally(() => setStreaming(false));
```

而后端 `_use_agent` 在 `session_id` 非空时恒真：

```37:38:backend/app/api/ask.py
def _use_agent(req: AskRequest, settings: Settings) -> bool:
    return settings.agent_enabled and (req.mode == "agent" or req.session_id is not None)
```

Agent 路径 `_build_result` 不产 `retrieval` / `from_cache`，前端又把四个 handler 写成空函数：

```132:136:frontend/src/features/chat/ChatPage.tsx
        onRetrievalStats: () => undefined,
        onQueryAnalysis: (analysis) => patchMessage(assistantId, { analysis }),
        onCragBranch: () => undefined,
        onRefine: () => undefined,
        onConfidence: () => undefined,
```

**后果**（全部经过交叉验证）：

| 失效对象 | 失效原因 |
| --- | --- |
| `RetrievalTracePanel` | `stats` 恒 null，组件首行 `return null` |
| 缓存命中徽章 `.cache-badge` | `message.fromCache` 从不赋值；Agent 路径 `ask.py:95` 硬编码 `"from_cache": False` |
| CRAG 分支高亮 + 精炼对比 | Agent 路径不跑 CRAG，`message.crag` 永不赋值 |
| `ConfidenceBar` | Agent 路径不产出 `confidence` |
| 指标 `rag_retrieval_stage_ms` | 只在 `RagPipeline._observe_retrieval` 观测，Agent 路径绕过 pipeline |

#### 缺陷 B：阶段 9 护栏只接在 Agent 路径，线性 `/ask` 完全绕过 —— P0（越权风险）

## 五、建议补齐顺序

1. **先修 P0-1/2/4**（越权 + 合规 + 死代码）—— 这三项是「已实现的能力实际不生效」，修复成本低、收益最大：

   - Agent 路径补 `retrieval`/`from_cache`/`confidence`/`crag` 产出，或前端改走线性路径；最简方案是让 `AgentRunner` 复用 `pipeline` 的检索与 CRAG 组件
2. **再修 P0-5/6/7/9/10**（数据正确性与运维陷阱）—— 均为小改动、高杠杆。
