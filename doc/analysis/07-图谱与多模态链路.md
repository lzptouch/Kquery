## 〇、摘要

1. **图谱链路是「块 → LLM 抽取 → 消歧归一 → upsert → 社区检测 → 摘要入同一向量空间」**六步（`backend/app/services/graph/builder.py:1-7`）。社区摘要写入 `doc_id="__communities__@{tenant}"` 的普通块，与正文同库同编码器，**抽象问题命中高层摘要、具体问题命中实体**（`backend/app/services/graph/builder.py:117-152`）。
2. **消歧的硬约束是「只在同类型之间合并」**（`backend/app/services/graph/resolver.py:6-10`、`:82-93`）：同名的公司与产品合并会在多跳检索中被放大成错误。合并走三级优先——规范化精确 → 别名表 → 向量相似 ≥ 阈值。
3. **实体向量索引刻意用「向量化精确检索」而不是 ANN**（`backend/app/services/graph/vector_index.py:14-26`）：消歧**不允许**近似——漏合并是乱合并，而漏合并与误合并的代价不对称。
4. **载入消歧表时必须重建向量索引**，否则重启后消歧与种子召回**静默失效**（索引是空的，`resolve` 退化为「全部新建」）（`backend/app/services/graph/resolver.py:162-174`）。
5. **多模态的路线是「生成式描述 + 文本向量」**，不为图像另起向量空间（`backend/app/services/graph/images.py:1-11`）：放弃 CLIP 双塔，改用 qwen-vl-max 生成固定四段描述，再用正文同一个编码器编码入库。
6. **OCR 只有云服务 API 一条路**：非法 provider 直接报错，不静默降级（`backend/app/services/parsers/ocr.py:164-180`）。留本地口子的后果是「部署后 OCR 静默不可用」，比报错更难排查。**语音能力已于 2026-11-14 整体下线**（项目不需要），音频文件不再支持入库。

## 一、图谱构建链路

### 1.1 六步总览

| 步 | 动作 | 实现 | 代码位置 |
|---|---|---|---|
| ① 取块 | 以块为最小更新单位 | `store.all_chunks()` 或按 `doc_id` 过滤 | `backend/app/api/graph.py:184-190` |
| ② 抽取 | 逐块 `extractor.extract(chunk.content)` → `{entities, relations}` | `LLMExtractor` / `ScriptedExtractor` | `backend/app/services/graph/builder.py:80-81` |
| ③ 消歧 | 逐实体 `resolver.resolve(name, type, description, tenant_id)` | `EntityResolver` | `backend/app/services/graph/builder.py:83-88` |
| ④ upsert | 实体与关系幂等写入图存储 | `upsert_entity` / `upsert_relation` | `backend/app/services/graph/builder.py:89-108` |
| ⑤ 社区检测 | 连通分量（+ 层级重叠合并） | `build_communities` | `backend/app/services/graph/community.py:151-186` |
| ⑥ 摘要入向量空间 | 摘要块写入 `__communities__@{tenant}` | `rebuild_communities` | `backend/app/services/graph/builder.py:117-152` |

### 1.2 两条触发路径

| 触发 | 入口 | 增量范围 | 代码位置 |
|---|---|---|---|
| **入库联动** | `_post_index` 钩子（索引成功后自动触发） | 单文档，`rebuild_doc_id=record.doc_id` | `backend/app/assembly/hooks.py:24-61`、`backend/app/services/ingest.py:389-403` |
| **手动构建** | `POST /graph/build` | 指定 `doc_id` 或全量 | `backend/app/api/graph.py:175-206` |

手动构建端点有两条租户纪律（**数据分区纪律，不是权限**——身份已恒定为 `tenant=default`，`POST /graph/build` 无任何角色门禁）：

- 指定 `doc_id` 时**先做租户断言**，不匹配直接 404——防的是「用别的租户的 doc_id 建图」，原注释里的 "否则 admin 可替其它租户建图" 已过时（admin 角色已随认证下线删除，2026-11-12）（`backend/app/api/graph.py:198-202`，注释在 `:199`）。
- 全量构建**只建本租户的块**——跨租户全量构建会把其它租户的图改写掉（`backend/app/api/graph.py:210-211`）。

### 1.3 重建模式：先删该文档的旧贡献

```python
if rebuild_doc_id:
    removed = self._store.delete_doc_chunks(
        {c.chunk_id for c in chunks if c.doc_id == rebuild_doc_id}
    )
```

（`backend/app/services/graph/builder.py:73-77`）

**以块为最小更新单位**——重建文档时先删该文档块贡献的关系，再重新抽取。存储契约明确要求 `delete_doc_chunks` **只删「当前版本」的块对应实体**，历史版本块仍需留在图里（`backend/app/services/graph/store.py:38`）。

### 1.4 租户纪律

实体 / 关系写入**块所属租户**的图分区。租户取值优先级：调用方显式传入 → 第一个块的 `tenant_id` → 构造时的租户。**绝不跨租户混写**（`backend/app/services/graph/builder.py:67-72`）。

### 1.5 关系端点兜底：按 Concept 补建，不丢关系

```python
source = name_map.get(r["source"])
target = name_map.get(r["target"])
if not source or not target:
    # 关系端点未在实体表中 → 按 Concept 补建（关系不丢弃）
    source = source or self._resolver.resolve(r["source"], "Concept", tenant_id=tenant)[0]
    target = target or self._resolver.resolve(r["target"], "Concept", tenant_id=tenant)[0]
```

（`backend/app/services/graph/builder.py:94-102`）

模型有时会抽出**关系但没抽出对应实体**。此时不是丢弃这条关系，而是把端点按 `Concept` 类型补建成实体，保证图不断链。

### 1.6 社区摘要入同一向量空间

```python
community_doc = f"{COMMUNITY_DOC_ID}@{tenant}"     # __communities__@{tenant}
self._vector_store.delete_doc(community_doc)        # 先删旧摘要
summary_chunks = [Chunk(chunk_id=f"{community_doc}#{c.community_id}", …)]
vectors = self._embeddings.embed_texts([c.content for c in summary_chunks])
self._vector_store.add(summary_chunks, vectors)
```

（`backend/app/services/graph/builder.py:23`、`:129-147`）

- **摘要块用与正文同一个 `Embeddings` 实例编码**，因此与正文向量在同一空间、同一索引——抽象问题命中摘要，具体问题命中实体（`backend/app/services/graph/builder.py:5-6`、`:130`）。
- 摘要内容包含前 10 个成员实体名，便于命中时知道涉及谁（`backend/app/services/graph/builder.py:140`）。
- **按租户独立 `doc_id`**，重建一个租户的社区不会清掉其它租户的摘要（`backend/app/services/graph/builder.py:120-121`）。
- 重建前先 `delete_doc(community_doc)`，避免旧摘要残留（`:131`）。

### 1.7 消歧表持久化

`GraphBuilder._persist()`（`backend/app/services/graph/builder.py:154-160`）在每次写图后把消歧表导出到 `data/graph/resolver.json`。装配时若该文件存在则用 `EntityResolver.load()` 载入（`backend/app/assembly/agent.py:121-132`）。

## 二、实体关系抽取

### 2.1 五类实体

```
Person（人物）/ Org（组织·公司·机构）/ Product（产品·工具·项目）
Concept（概念·术语·理论）/ Event（事件）
```

（`backend/app/services/graph/extractor.py:19-29`、`backend/app/domain/schemas.py:199`）

抽取提示词同时要求：实体名用文中出现的规范名称；关系必须有方向（`source` 是主语方，`target` 是宾语方）；每条关系必须附 `evidence`（支撑该关系的原文句子，verbatim 摘录）；没有关系可抽取时返回空列表，**不要编造**（`backend/app/services/graph/extractor.py:24-29`）。

### 2.2 抽取上限

提示词要求「**最多抽取 8 个实体、8 条关系**，取最重要的」（`backend/app/services/graph/extractor.py:29`）。

**这是一条 prompt 级约束，代码层没有二次裁剪**——`parse_extraction` 只做结构校验，不按数量截断（`backend/app/services/graph/extractor.py:44-75`）。实际约束来自「每块一次调用」的粒度，而不是硬编码的条数上限。已登记于第十三章。

### 2.3 非法实体类型归并不自丢

```python
etype = str(e.get("type", "Concept"))
if etype not in ENTITY_TYPES:
    etype = "Concept"   # 非法类型归并到 Concept（不丢实体）
```

（`backend/app/services/graph/extractor.py:55-57`）

模型偶尔会返回六类之外的类型。处理方式是**归并到 `Concept` 而不是丢弃**——丢实体等于丢关系（关系端点不在实体表里只能按 Concept 补建）。

同理，空 `name` 的实体被跳过（`:52-54`）。

### 2.4 自环关系丢弃

```python
if not source or not target or source == target:
    continue
```

（`backend/app/services/graph/extractor.py:69-70`）

`source == target`（自环）直接丢弃。自环对多跳检索没有信息量（BFS 会绕圈），且会让度计算失真。

### 2.5 证据截断且截断必留痕

- **关系描述 = 支撑原文**：`description=r["evidence"]`，保证可溯源（`backend/app/services/graph/builder.py:105`）。
- **evidence 截断到 300 字**（`backend/app/services/graph/extractor.py:73`）、**实体描述截断到 200 字**（`:61`）。
- **输入截断必留痕**：

```python
truncated = len(text) > self._max_chars
if truncated:
    logger.info("实体抽取输入被截断：%d → %d 字（超长块后半段的实体不会被抽取）", len(text), self._max_chars)
```

（`backend/app/services/graph/extractor.py:94-99`）

默认 `max_chars = 2000`。此前是硬编码 `text[:2000]` 且**静默**——长表格块的后半段实体直接消失，排查「为什么这个实体没进图谱」时毫无线索（`backend/app/services/graph/extractor.py:78-84`）。

### 2.6 失败不阻塞入库

```python
logger.warning("实体抽取最终失败（按空结果降级）: %s", last_error)
return {"entities": [], "relations": []}   # 抽取失败不阻塞入库
```

（`backend/app/services/graph/extractor.py:108-109`）

解析失败会重试 `max_retries + 1` 次，仍失败则按空结果降级。

## 三、消歧归一

实现文件：`backend/app/services/graph/resolver.py`。

### 3.1 三级优先

| 级 | 规则 | 代码位置 |
|---|---|---|
| 1 | **规范化精确匹配**（NFKC 全半角统一 + 去空白 + 小写） | `backend/app/services/graph/resolver.py:26-28`、`:77-81` |
| 2 | **别名表命中** | `backend/app/services/graph/resolver.py:41-42`、`:77-81` |
| 3 | **向量相似度 ≥ 阈值**（默认 0.85，`backend/app/core/config.py:391`） | `backend/app/services/graph/resolver.py:82-100` |

规范化精确匹配是**确定性路径**；别名表命中后还会再校验类型一致（`:80`）。

### 3.2 硬约束：只在同类型之间合并

- 第 1 级：别名命中后检查 `self._entities[canonical_key]["type"] == etype`，类型不同则**不合并**，继续往下走（`backend/app/services/graph/resolver.py:79-81`）。
- 第 3 级：向量检索时把类型过滤传进索引（`want_type=etype` + `type_of` 映射），索引内部先按类型过滤再算相似度（`backend/app/services/graph/resolver.py:87-90`、`backend/app/services/graph/vector_index.py:162-168`）。

理由写在模块 docstring：**同名的公司与产品合并在多跳检索中会被放大成错误**（`backend/app/services/graph/resolver.py:10`）。

### 3.3 租户分区 key

```python
def _k(tenant_id: str, name: str) -> str:
    return f"{tenant_id}\x00{name}"
```

（`backend/app/services/graph/resolver.py:31-32`）

| 结构 | key 形态 |
|---|---|
| 实体表 | `{tenant}\x00{name}` |
| 别名表 | `{tenant}\x00{规范化名/别名}` → `{tenant}\x00{规范名}` |
| 向量索引 | 按租户各持一个 `EntityVectorIndex`（`backend/app/services/graph/resolver.py:43-44`、`:49-54`） |

**不同租户的同名词互不消歧，也不互相成为检索种子**（`backend/app/services/graph/resolver.py:12-14`）。

图存储侧用同样的思路：`_k(tenant_id, name)` 用单元分隔符 `\x1f` 连接（`backend/app/services/graph/store.py:57-67`）。

### 3.4 载入时必须重建向量索引

```python
# KQ-41：必须重建向量索引——只恢复实体表会让重启后的向量消歧与
# 种子向量召回静默失效（索引是空的，resolve 退化为"全部新建"）。
for key, info in resolver._entities.items():
    tenant_id = key.split("\x00", 1)[0] if "\x00" in key else "default"
    name = key.split("\x00", 1)[1] if "\x00" in key else key
    resolver._index_of(tenant_id).add(name, info["vector"])
```

（`backend/app/services/graph/resolver.py:162-174`）

**这是本域最容易被漏掉的一条**：`load()` 恢复了实体表与别名表，但若不重建索引，`resolve` 的第 3 级（向量相似）永远召不到候选，于是**每次消歧都退化为「全部新建」**——同义实体会分裂成多个节点，图谱质量静默下降，而且**没有任何报错**。

### 3.5 类型表缓存

`_type_of(tenant_id)` 构建 `name → type` 映射供索引做类型过滤，**惰性重建**（实体数变化或缓存缺失时重建），避免每次消歧都扫全表（`backend/app/services/graph/resolver.py:56-69`）。

## 四、社区检测

### 4.1 连通分量（零依赖默认实现）

`ConnectedComponentsDetector`（`backend/app/services/graph/community.py:32-59`）：

- 只做**无向弱连通分组**（`:33`）。
- **只纳入本租户关系**——跨租户实体不得并入同一社区（`:37-38`）。
- 节点排序归一化（`sorted(adjacency.keys())`）是**编号稳定的前提**（`:41-42`）。
- 按「**最小成员名**」排序赋号 → 同一份图重复跑出相同编号（否则摘要挂错社区）（`:57-58`）。

### 4.2 层级重叠合并

`HierarchicalCommunityDetector`（`backend/app/services/graph/community.py:62-148`）。

**为什么要有层级**：单层连通分量里，社区内所有实体直接相连，于是「某某产品的保修政策」和「某某产品的退货政策」会被塞进同一个社区——因为它们都跟「产品」相连。单层图谱天然分不出主题层级，只有把 L1 社区按成员重叠度逐级合并，才能得到 L2（产品线）、L3（全库主题）这种粒度（`backend/app/services/graph/community.py:65-68`）。

合并规则（贪心重叠合并）：

| 规则 | 说明 | 代码位置 |
|---|---|---|
| 重叠比例 ≥ `merge_threshold` 才合并 | 默认 0.3（`backend/app/core/config.py:190`） | `backend/app/services/graph/community.py:138` |
| 重叠率 = 交集 / min(\|A\|,\|B\|) | 用「小社区被覆盖比例」而不是 Jaccard：一个大社区与几十个小社区共享一个枢纽实体时，Jaccard 极低导致永远合并不了，而小社区其实已基本被吞并 | `backend/app/services/graph/community.py:111-120` |
| 候选按重叠度降序 + 成员名字典序做 tie-break | 编号稳定 | `backend/app/services/graph/community.py:132-139` |

## 六、存储后端

### 6.1 SQLite 增量（默认）

`SqliteGraphStore`（`backend/app/services/graph/sqlite_store.py`）。

**为什么换掉 JSON 落盘**（`backend/app/services/graph/sqlite_store.py:3-16`）：

| 问题 | 后果 |
|---|---|
| 全量重写 | 10 万关系的图每次入库都要序列化 + 写盘全部 10 万条 |
| 非原子 | 写一半崩溃 → 文件损坏 → 下次启动「加载失败，从空图启动」，**全部图谱丢失** |
| 全量读入内存 | 启动时整个图驻留内存；多副本各自持一份，互不同步 |
| 无并发保护 | 多进程同时写必然互相覆盖 |

SQLite 解决前三条（事务原子性、增量写、按需查询），代价是每次查询要走 SQL 而不是内存指针——但图谱查询是「按实体名找邻边」，有索引后是 O(度)，与内存版同级。

**三张表 + 索引**（`backend/app/services/graph/sqlite_store.py:43-67`）：

| 表 | 主键 | 索引 |
|---|---|---|
| `entities` | `(tenant_id, name)` | — |
| `relations` | `(tenant_id, source, relation, target)` | `idx_rel_source`、`idx_rel_target` |
| `communities` | `community_id` | `idx_comm_tenant` |

**列结构取舍**：`tenant_id` / `name` 等**查询用字段**建独立列并加索引；其余属性（aliases / description / degree / extra）存 JSON 列——这些字段只读不查，为它们建列会让 schema 演进变成迁移负担（`backend/app/services/graph/sqlite_store.py:18-22`）。

**不使用 ORM**：只需要 3 张表与少量固定查询，手写 SQL 更透明（`backend/app/services/graph/sqlite_store.py:24-25`）。

**WAL**：读不阻塞写（图查询频繁、入库偶发，这个取舍很值）（`backend/app/services/graph/sqlite_store.py:84-86`）。

**`save()` 是空操作**：数据在每次写操作时就已提交，不存在「忘记保存」的可能——这是相比 JSON 版最实质的改进（`backend/app/services/graph/sqlite_store.py:27-28`、`:368-369`）。

**幂等合并**：`upsert_entity` 命中已有行时保留已有描述、别名取并集（与内存版语义一致）（`backend/app/services/graph/sqlite_store.py:99-107`）。

**线程安全**：内部一把锁串行化写（SQLite 单写者语义），读走同一连接（`backend/app/services/graph/sqlite_store.py:71-74`）。锁已改为 **`_TimedLock`**（计时），暴露 `kquery_graph_lock_wait_seconds` / `kquery_graph_lock_hold_seconds`——判据「锁等待 P95 > 锁持有 P95 的 1/3 → 图写入成为瓶颈」（`C-08`；`C-09` 后台化待此结论）。

## 七、实体向量索引

### 7.1 向量化精确检索而非 ANN

`EntityVectorIndex`（`backend/app/services/graph/vector_index.py`）。

**方案选择的理由**（`backend/app/services/graph/vector_index.py:14-26`）：

| 方案 | 适用条件 | 本项目情况 |
|---|---|---|
| HNSW / IVF（ANN 近似） | 百万级向量，可容忍召回损失，有训练 / 构建预算 | ❌ 实体量级千级；且图谱消歧**不允许**近似（漏合并 = 乱合并） |
| **向量化精确检索** | 万级以内，要求精确 | ✅ |

`np.dot(matrix, vec)` 一次调用完成 N 次点积（BLAS 内循环），比 Python 循环快 1~2 个数量级，且**结果与逐个点积完全一致**——消歧的「不误合并」约束要求精确性，近似索引在这里反而危险。

### 7.2 查询路径

```python
sims = self._matrix[:n] @ q          # 一次矩阵乘完成 N 次点积
if want_type is not None and type_of is not None:
    order = [i for i, nm in enumerate(names) if type_of.get(nm) == want_type]
    …
k = min(max(1, top_k), len(sims))
if k >= len(sims):
    top = np.argsort(-sims)
else:
    part = np.argpartition(-sims, k - 1)[:k]      # O(N)
    top = part[np.argsort(-sims[part])]
```

（`backend/app/services/graph/vector_index.py:142-179`（`search`））

- **类型过滤在索引内部做**：`want_type` + `type_of` 映射，把消歧的类型硬约束下推到检索层（`backend/app/services/graph/vector_index.py:162-168`）。
- `argpartition` 是 O(N)，比全排序 O(N log N) 快；再对 k 个候选排序（`:173-175`）。
- 向量维度不匹配时返回空（`:157-158`）。

### 7.3 容量翻倍预分配

```python
elif self._size >= self._matrix.shape[0]:
    # 容量翻倍：均摊 O(1)，避免每次 add 都整表拷贝
    grow = max(64, self._matrix.shape[0])
    new = np.zeros((self._matrix.shape[0] + grow, dim), dtype=np.float32)
```

（`backend/app/services/graph/vector_index.py:116-121`）

- 初次分配至少 64 行（`:111`、`:97`）。
- 追加式矩阵（`vstack` 摊销）比「每次新增实体重建 FAISS 索引」的维护成本更低（`backend/app/services/graph/vector_index.py:26`）。
- **`suspend()` / `resume()`** 供批量写入使用：批量期间只暂存向量，`resume` 时一次性落矩阵（`backend/app/services/graph/vector_index.py:61-92`）。
- **suspend 期间不修改 `_rows` / `_names`**——中间态查询到「尚未落矩阵的名字」会拿到错误的行号（-1），那比查不到更糟（`backend/app/services/graph/vector_index.py:64-68`）。

- **路径安全**：用 `is_relative_to` 而不是 `startswith` 前缀比较——后者会被同名前缀的兄弟目录绕过（`assets2/...`）（`backend/app/api/graph.py:295-297`）。

## 九、OCR（云服务 API）

### 9.1 架构约束：不提供任何本地 / 自部署路径

`backend/app/services/parsers/ocr.py:3-24` 的模块 docstring 把这条写成硬约束：

| 项 | 规定 |
|---|---|
| 生产 | 千问 `qwen-vl-ocr`（阿里云百炼）——**云服务 API** |
| 测试 | `MockOcrEngine`，返回确定性文本（不联网） |
| 本地模型 | **不支持** |

**四条理由**（`backend/app/services/parsers/ocr.py:11-24`）：

1. **模型权重分发**：本地 OCR 需要在镜像构建期烤入权重，或运行时从 HuggingFace 下载——内网 / 离线环境两者都不可行，于是「支持本地模型」最终变成「部署后 OCR 静默不可用」。
2. **镜像与 CI 膨胀**：ONNX Runtime + 多个模型权重会让镜像大出一个量级。
3. **可复现性**：本地模型路径与 Mock 是两套实现，测试覆盖到的和线上跑的不是同一段代码。
4. **识别质量**：中文复杂版面（倾斜、多栏、表格线）下云端视觉语言模型通常更稳。

结论写得很直接：「想加本地模型，请先推翻这条架构约束，而不是在这里塞一个开关」（`backend/app/services/parsers/ocr.py:23-24`）。

### 9.2 非法 provider 直接报错，不静默降级

```python
ALLOWED_OCR_PROVIDERS = ("dashscope", "mock")

def build_ocr_engine(provider, api_key, max_retries=3) -> OcrEngine:
    if provider == "dashscope": return QwenVlOcr(...)
    if provider == "mock":       return MockOcrEngine()
    raise ApiError(ErrCode.INVALID_INPUT,
        f"不支持的 OCR provider={provider!r}：OCR 一律走云服务 API"
        f"（{ '、'.join(ALLOWED_OCR_PROVIDERS) }），不支持本地/自部署模型")
```

（`backend/app/services/parsers/ocr.py:159-180`）

理由：**静默降级会让「配错了」看起来像「跑通了」**，生产上表现为「图片入库了但没有文字」，极难排查（`backend/app/services/parsers/ocr.py:168-170`）。

provider 取值由 `resolved_ocr_provider` 决定（`backend/app/core/config.py:704-721`）：`auto` 跟随 `model_provider`；显式 `dashscope` 时强制走云端，且**必须**有平台凭据，否则启动期校验拦下（`backend/app/core/config.py:392-398`）。

> 本篇涉及的「有机制无度量」「有代码无调用点」「口径与实现不符」逐条登记。**确有缺口的共 6 处**。

| # | 缺口 | 证据 | 影响 | 当前处置 |
|---|---|---|---|---|
| 1 | **`remove_doc` 的共享 doc_id 残留**：删文档后，图像描述块仍存活在统一向量库（`doc_id="__images__"`），存储层无按 `chunk_id` 删除的接口 | `backend/app/services/graph/images.py:183-196` | 通用向量检索理论上仍可能命中已删文档的图像描述，答案引用一张已不存在的图片 | 元数据条目已移除、`image_search` 不再返回；**向量层残留未清** |
