## 〇、摘要

1. **检索是本项目唯一「三条硬规则全满足」的重能力**：`HybridRetriever.search_multi` 是管线内唯一的检索入口（`backend/app/services/retrieval/hybrid.py:101`），BM25 与向量两路默认同时开启，且有覆盖主路径的集成测试（`backend/tests/integration/test_stage2.py`）。
2. **五段流水线的顺序不可交换**：双路召回 → **融合前**版本过滤 → RRF 融合 → 重排 → 上下文组装。版本过滤被刻意放在融合前（`backend/app/services/retrieval/hybrid.py:188-202`），因为让三个后端各自过滤会让 FAISS / Milvus / BM25 的行为出现分叉。
3. **RRF 只用排名不用分数**（`backend/app/services/retrieval/fusion.py:3`）：BM25 分数无上界、向量分数落在 0~1，强行归一化会引入校准难题；k=60 是论文默认值，rank 从 0 起，单路第 1 名贡献 1/61 ≈ 0.0164。
4. **ACL 下推是三档降级而不是一档**：表达式下推（可见清单 ≤ 500）→ 放弃 doc 级下推（> 500）→ 应用层后过滤（deny 优先）。三档都有留痕，`pushdown_degraded()` 专门用于观测（`backend/app/services/retrieval/filters.py:89-95`）。
5. **上下文组装有保底策略**：一条都没留下时保留最高分那条的**截断版**（`backend/app/services/context.py:112-124`）——「空上下文」比「截断的证据」更糟。
6. **检索质量是「有机制无度量」的典型**：混合检索、RRF、重排降级、ACL 下推一应俱全，但**不存在检索金标集**，recall@k / nDCG 无从测量，混合检索相对单路的增益没有任何数据支撑。

## 一、五段流水线总览

### 1.1 段落划分

| 段 | 输入 | 产出 | 代码位置 |
|---|---|---|---|
| ① 双路召回 | 查询集合（原文 / 改写 / 子问题 / refined）× 已启用的路 | 每路 Top-N 候选 + 每路毫秒数与候选数 | `backend/app/services/retrieval/hybrid.py:115-183` |
| ② 索引版本过滤 | 召回候选 | 仅当前索引版本的块 | `backend/app/services/retrieval/hybrid.py:188-202` |
| ③ RRF 融合 | 多路候选 + 路权重 | 融合序 Top-N | `backend/app/services/retrieval/hybrid.py:207-212` |
| ④ 重排 | 融合集 + 用户原话 | 精排 Top-K（失败退回融合序） | `backend/app/services/retrieval/hybrid.py:214-232` |
| ⑤ 上下文组装 | 最终候选 + 父块回查 | 预算内的上下文条目 + 丢弃留痕 | `backend/app/services/context.py:51-159`、`backend/app/services/pipeline.py:516-572` |

### 1.2 路的划分与并行

- 路名只有两个基础路：`keyword`（BM25）与 `vector`（语义向量）。启用与否由运行时配置 `RetrievalConfig.bm25_enabled` / `vector_enabled` 决定（`backend/app/services/retrieval/hybrid.py:118-121`）。
- **每条查询 × 每条启用路各召回一次**，共 `len(queries) × len(enabled)` 个任务；多查询并行用**独立的检索线程池**（`backend/app/services/retrieval/hybrid.py:23-26`）。之所以不复用问答执行器：`search_multi` 本身就在管线线程内被调用，复用同一池会在池满时形成「线程等自己池」的嵌套死锁。
- 多查询的向量**批量编码一次**（`embed_texts`），失败则退回逐条编码而不放弃向量路（`backend/app/services/retrieval/hybrid.py:124-133`）。
- **单路失败必须降级而不是拖垮整次检索**：失败的路记入 `stats.degraded_routes` 并跳过；只有全部路都挂掉才抛 `RetrievalError`（`backend/app/services/retrieval/hybrid.py:161-186`）。

### 1.3 产出结构

`HybridResult{candidates, stats, reranked, rejected}`（`backend/app/services/retrieval/hybrid.py:49-55`）：

| 字段 | 含义 |
|---|---|
| `candidates` | 最终进入上下文的候选，已按相关度排序 |
| `stats` | 各路毫秒数、候选数、融合毫秒、重排毫秒、降级路列表 |
| `reranked` | `False` 表示本次**未**精排（重排降级或被关闭） |
| `rejected` | 在融合集内但未进 Top-K 的前 3 条，随响应返回供用户判断有无遗漏 |

## 二、BM25 关键词路

实现文件：`backend/app/services/retrieval/bm25.py`。

### 2.1 分词

- 中文分词用 **jieba**（`backend/app/services/retrieval/bm25.py:11`、`:21-22`）。不用按字切，因为「电池」与「电池电压」按字切开后无法匹配。
- jieba 日志级别被压到 20，避免分词日志污染应用日志（`backend/app/services/retrieval/bm25.py:18`）。
- 分词缓存策略：**块级预分词在索引构建时完成，查询分词量小不缓存**（`backend/app/services/retrieval/bm25.py:17`）。实际实现是每次 `rebuild` / `add` / `delete_doc` 时对全量语料重新分词并重建打分模型（`backend/app/services/retrieval/bm25.py:77-88`）。

### 2.2 打分公式（Lucene 风格）

**IDF（恒正）**（`backend/app/services/retrieval/bm25.py:44-46`）：

```
idf(t) = ln(1 + (N - n + 0.5) / (n + 0.5))
```

其中 `N` = 语料文档数、`n` = 含词文档数。取 `ln(1 + …)` 而非 `ln(…)` 的目的是**保证 IDF 恒正**：共享任一查询词的文档得分必然 > 0，无关文档恰为 0 分。这是「零分文档过滤」语义成立的前提——`rank_bm25` 那套负 IDF 下界处理在小语料下会产生负分，把相关文档误杀（`backend/app/services/retrieval/bm25.py:26-31`）。

**单文档对单查询的贡献**（`backend/app/services/retrieval/bm25.py:48-60`）：

```
score(d) = Σ_t  idf(t) × (f(t,d) × (k1 + 1)) / (f(t,d) + k1 × norm(d))
norm(d)  = 1 - b + b × doc_len(d) / avgdl
```

- `f(t,d)`：词在文档中的词频；`doc_len(d) = max(len(d), 1)`（`backend/app/services/retrieval/bm25.py:37`），避免空文档把 `avgdl` 拉成 0；`avgdl` 为语料平均长度（`:38`）。
- 参数固定 **k1 = 1.5 / b = 0.75**（`backend/app/services/retrieval/bm25.py:33`、`:66`）。
- 语料为空时 `norm` 退化为 1.0（`backend/app/services/retrieval/bm25.py:51`）。

### 2.3 先过滤再排序

`search()` 的顺序是**先过滤、后排序**（`backend/app/services/retrieval/bm25.py:117-142`）：

```python
ranked = sorted(
    ((cid, score) for cid, score in zip(self._order, scores) if _visible(cid)),
    key=lambda x: x[1], reverse=True,
)
```

过滤谓词 `_visible`（`backend/app/services/retrieval/bm25.py:128-136`）依次判定：**租户** → **单文档范围（`doc_id`）** → **ACL 允许清单（`filters.allows`）**。

这一顺序的语义价值：结果集与旧实现（先排序再跳过不合格）**相同**，但显式过滤把 ACL 判定收敛到一处，让「可见集合」成为排序的**输入**而非事后剔除（`backend/app/services/retrieval/bm25.py:117-122`）。同时它消除了 BM25 的「后过滤吃掉名额」问题——**这也是 BM25 路不需要像 FAISS 那样迭代扩取的原因**。

### 2.4 零分文档不入 RRF 排名

```python
for cid, score in ranked:
    if score <= 0:   # 零分文档过滤：不进入 RRF 排名
        break
```

（`backend/app/services/retrieval/bm25.py:144-146`）

因为分数已降序排列，遇到第一个非正分即可 `break`。**零分文档不进入 RRF 的 rank 序列**——否则它们会占据 rank 位次，把真正相关的文档往后挤。

### 2.5 并发：读写锁

- 索引侧用**读写锁**（`ReadWriteLock`），读共享 / 写独占（`backend/app/services/retrieval/bm25.py:70`）。注释明确指出此前用普通 `Lock`，导致所有关键词检索**串行**。
- `add()` 先拷贝再重绑 `_order`（`backend/app/services/retrieval/bm25.py:92-100`）：读锁只保证「写者不打断读者」，不保证读者看到一致的列表长度；拷贝后重绑让读者要么看到旧列表、要么看到新列表。
- 任何一次索引变更（`rebuild` / `add` / `delete_doc`）都会**全量重建 BM25 模型**（`backend/app/services/retrieval/bm25.py:77-88`）。

## 三、向量路

### 3.1 两个后端的分工

| 后端 | 索引结构 | 距离语义 | 过滤能力 | 代码位置 |
|---|---|---|---|---|
| FAISS（默认） | `faiss.IndexFlatIP` | 向量已 L2 归一化 → 内积即余弦 | **不支持表达式**，靠迭代扩取 | `backend/app/services/vectorstore.py:49-56` |
| Milvus | `FLAT` + `metric_type=COSINE` | 库内 COSINE | **支持表达式下推** | `backend/app/services/milvus_store.py:71-75` |

- **切换点**在 `build_vector_store()`（`backend/app/services/vectorstore.py:262-268`）：`settings.vector_store == "milvus"` 时返回 `MilvusVectorStore`，否则返回本地 `VectorStore`。
- FAISS 的「内积即余弦」依赖**向量入库前已归一化**这一前提（`backend/app/services/vectorstore.py:1-6`、`:113`）。
- 两个后端的**启动失败都是 fail-fast**：FAISS 索引行数与元数据不一致、或文件损坏 → 拒绝启动（`backend/app/services/vectorstore.py:71-75`）；Milvus 集合 schema 不符 → 重建集合；连不上 → 拒绝启动（`backend/app/services/milvus_store.py:78-97`）。

### 3.2 Milvus 表达式下推

```python
if filters is not None:
    expr = filters.to_milvus_expr()
else:
    expr = f'tenant_id == "{tenant_id}"'
    if doc_id is not None:
        expr += f' and doc_id == "{doc_id}"'
```

（`backend/app/services/milvus_store.py:147-152`）

下推的效果是**不可见文档根本不参与 top-k 竞争**——从根上消除「后过滤吃掉名额」（`backend/app/services/milvus_store.py:141-146`）。集合 schema 里 `tenant_id` / `doc_id` / `chunker` / `level` / `parent_id` / `modality` 都是独立列并建索引（`backend/app/services/milvus_store.py:56-70`）。

向量库的调用被包在**上游隔离仓**内（`bulkhead("milvus").acquire(timeout_s=30.0)`，`backend/app/services/milvus_store.py:153-154`），与 LLM 通道的熔断状态互不干扰。

### 3.3 Milvus 分页拉取 1000

```python
_QUERY_PAGE_SIZE = 1000  # Milvus 单次 query 硬上限 16384，分页拉取避免静默截断
```

（`backend/app/services/milvus_store.py:175-201`）

`doc_chunk_ids` / `doc_versions` / `all_chunks` 等全量查询一律走 `_query_all()` 循环分页。此前这些方法用 `limit=16384` 硬编码，**超过 16k 块后静默只取前 16k**——BM25 重建、版本清理、`doc_versions` 会全部不完整。超限时还会打一条告警日志（`:199-200`）。

### 3.4 FAISS 迭代扩取

FAISS 没有表达式过滤，只能靠**按实际过滤结果迭代扩大候选池**（`backend/app/services/vectorstore.py:113-161`）：

```python
state = OverfetchState()          # factor 初值 4
while True:
    k = min(top_k * state.factor, total)
    ...
    if len(collected) >= top_k or k >= total:
        break
    if state.factor >= MAX_OVERFETCH_FACTOR:   # 32
        logger.warning("FAISS 检索扩取达上限 …")
        break
    if not state.can_continue(top_k, len(collected), total):
        break
    state.next_limit(top_k)        # factor 翻倍，32 封顶
```

- `OverfetchState` 定义在 `backend/app/services/retrieval/filters.py:103-131`：初值 factor=4（`:107`），`next_limit` 每次翻倍并以 `MAX_OVERFETCH_FACTOR = 32` 封顶（`:113-116`、`:39`）。
- **三个终止条件**：已取满 / 候选已耗尽（`exhausted`）/ 达到最大倍数（`can_continue`，`:118-131`）。区分「取不到」与「本来就少」靠 `exhausted` 标志。
- 扩取达到上限时会**显式告警**「可能因过滤导致召回不足」（`backend/app/services/vectorstore.py:148-153`）——这是一个**已登记的缺口**（见第十二章）。

### 3.5 向量路的包装

`VectorRetriever` 只是薄包装：把 `filters` 透传给存储层，由存储层自己决定「Milvus 下推」还是「FAISS 扩取」（`backend/app/services/retrieval/vector.py:21-28`）。`search_with_vector` 用于复用批量编码结果（`:25`）。

## 四、索引版本过滤

### 4.1 版本块命名

```
chunk_id = {doc_id}@v{n}#{seq}
```

- 工具函数：`chunk_version`（`backend/app/services/vectorstore.py:30-33`）、`with_version`（`:36-40`）、`is_current_version`（`:43-46`）。
- **序号空间按版本隔离**，因此重新解析不会与历史版本的块撞号，历史答案里的引用仍能命中旧块做溯源（`backend/app/services/vectorstore.py:25-27`）。
- 存量数据没有版本标记（解析为 0），`is_current_version` 把 0 一律视为「当前版本」，避免升级后预览突然空白（`backend/app/services/vectorstore.py:43-46`、`backend/app/services/knowledge.py:197-198`）。

### 4.2 过滤发生在融合前

```python
if self._version_of is not None:
    route_results = [ (route, [c for c in cands
                    if is_current_version(c.chunk.chunk_id, c.chunk.doc_id,
                                          self._version_of(c.chunk.doc_id))], origin)
                      for route, cands, origin in route_results ]
    route_results = [r for r in route_results if r[1]]
```

（`backend/app/services/retrieval/hybrid.py:188-202`）

**为什么放在融合前而不是让三个后端各自过滤**：统一在编排层过滤，保证 **FAISS / Milvus / BM25 三路行为完全一致**。若下推给后端，各后端对「版本」的判定实现不同（Milvus 的 `doc_id` 相等语义、FAISS 的逐条判定、BM25 的应用层谓词），会出现「同一查询在不同后端召回不同版本块」的静默分叉。

过滤后若某一路的候选被清空，该路被整体丢弃（`:202`）；若全部路被清空，直接返回空结果且 `reranked=False`（`:204-205`）。

### 4.3 与索引版本文件的关系

「索引版本」在本项目里有两个不同含义，**不要混淆**：

| 概念 | 载体 | 作用 | 代码位置 |
|---|---|---|---|
| **文档级索引版本** | `chunk_id` 里的 `@v{n}` | 区分同一文档的多次解析产物，支撑溯源 | `backend/app/services/vectorstore.py:25-46` |
| **全局数据版本** | `data_dir/index_version` 单文件 | 知识库任何变更 → 版本 +1 → 语义缓存键自然失效 | `backend/app/services/knowledge.py:72-91` |

- 全局版本由 `_bump_version()` 自增并写盘（`backend/app/services/knowledge.py:84-87`），`version_of(doc_id)` 返回的是**文档级**版本号（`backend/app/services/knowledge.py:97-104`，未收录的文档按 1 处理）。
- 全局数据版本进入语义缓存键的 `config_digest`（`backend/app/services/pipeline.py:252-264`），因此**任何入库 / 重建 / 重新解析都会让旧缓存条目自动失效**，无需手动清缓存。
- 预览侧用的是同一套版本判定（`backend/app/services/knowledge.py:187-198`）。

## 五、RRF 融合

### 5.1 公式

```
score(d) = Σ_i  w_i / (k + rank_i + 1)
```

（`backend/app/services/retrieval/fusion.py:3`）

- **rank 从 0 起**（`enumerate(candidates)`，`backend/app/services/retrieval/fusion.py:35`）。
- **k = 60**，为论文默认值（`backend/app/services/retrieval/fusion.py:18`）。
- `weights` 缺省各路权重 1.0（`backend/app/services/retrieval/fusion.py:28`）。

### 5.2 为什么只用排名不用分数

BM25 的分数无上界（可到几百），向量相似度落在 0~1；两套分布强行归一化会引入校准难题，且**校准参数一旦随语料漂移，排序就会跟着漂**。RRF 把「某路第 1 名」统一视为同一贡献度，从而只依赖**序**而非**值**（`backend/app/services/retrieval/fusion.py:5-6`）。

### 5.3 权重按基础路名查找

路由名形如 `keyword@original`、`vector@rewrite1`（`backend/app/services/retrieval/hybrid.py:177`）。融合时先剥掉 `@` 之前的后缀取**基础路名**，再查权重：

```python
base_route = route_name.split("@", 1)[0]
weight = weights.get(base_route, 1.0)
```

（`backend/app/services/retrieval/fusion.py:33-34`）

因此**同一基础路的多条查询共享权重**——改写词不会因为「路名叫 `vector@rewrite1`」而拿不到 `vector_weight`。权重来源是运行时配置 `RetrievalConfig.bm25_weight` / `vector_weight`（`backend/app/services/retrieval/hybrid.py:209`）。

同时，路的来源标注（`origin`，记录该路结果由哪条改写 / 子问题带回）随路传递并汇总到候选的 `origins`（`backend/app/services/retrieval/fusion.py:44-45`），供证据溯源使用。

### 5.4 数值自检锚点

上线前必须手工验算的三个锚点（`backend/app/services/retrieval/fusion.py:8-11`）：

| 场景 | 计算 | 结果 |
|---|---|---|
| 单路排第 1 | 1/(60+0+1) | ≈ 0.0164 |
| 两路都排第 1 | 2 × 0.0164 | ≈ 0.0328 |
| 一路第 1 + 另一路第 3 | 1/61 + 1/63 | 0.0164 + 0.0159 ≈ 0.0323 |

第三个锚点说明：**两路同时靠前（哪怕不是双第一）胜过单路极靠前**——这正是「双路召回」相对单路的增益来源。

### 6.2 失败降级：绝不让重排阻断检索

```python

else:
    final = fused[: config.top_k]
    stats.reranked_count = 0
```

（`backend/app/services/retrieval/hybrid.py:214-232`）

1. **降级后仍返回结果**，不是报错——`final` 退回融合序的前 `top_k` 条。
2. **`reranked=False` 显式标记**，调用方据此知道本次未精排（下游 CRAG 的证据评分依赖重排分，降级时校验链路一并降级，见 `backend/app/services/pipeline.py:769-773`）。

模块 docstring 把这条写成硬纪律：「绝不让重排失败阻断整次检索」（`backend/app/services/retrieval/hybrid.py:6-7`、`backend/app/services/retrieval/rerank.py:5-6`）。

### 7.3 可见清单从哪来

`ACLService.visible_doc_ids(principal, docs)`（`backend/app/services/security/acl.py:107-119`）：

- 这是 **O(文档数) 的枚举**，因此调用方应对大库保持克制。
- **文档数 > 5000 返回 `None`**（`:117-118`），语义是「不建议下推」——调用方据此退回 tenant 粗过滤 + 应用层后过滤。

清单由管线侧构造（`backend/app/services/pipeline.py:370-404`）：

- ACL 未启用时返回 `None`（行为与改造前一致），**但快问的 `doc_id` 过滤必须保留**——否则「只检索这一个文件」的要求会被整个丢掉（`:371-386`）。默认部署与测试环境恰好都不启用 ACL，所以这是**主路径**而非边界情况。
- 快问场景**不再叠加可见清单**：快问文档不在知识库里，可见清单里根本没有它，两个条件叠加会让快问永远检索不到东西（`:381-386`）。
- 清单获取抛异常 → 退回后过滤，不中断（`:389-394`）。

### 7.7 知识库授权在链路中的位置

知识库（KB）是文档的上位容器，管理员按用户授权某个 KB（判定树见 `08-安全与治理.md` §5.4）。它在检索链路上的落点与文档 ACL **同一条闭包**，不新增独立过滤路径：

| 环节 | 位置 | 说明 |
|---|---|---|
| 判定执行 | `backend/app/dependencies.py:92-111`（`acl_filter_of` 的 `check(doc_id)` 闭包） | ACL 判定在前、KB 判定在后（`:104`、`:107`），两者都通过才可见；`__` / `quick_` 前缀豁免在两者之前（`:93-96`） |
| 下推清单 | `backend/app/services/pipeline.py:171-190`（`bind_principal` 的 `_provider`） | 优先用**同一个闭包**枚举可见文档，保证下推与后过滤判定同源；闭包未就绪时退回 ACL 自身枚举 |
| 后过滤兜底 | `backend/app/services/pipeline.py:450-467`（`_visible_candidates`） | 遍历候选逐条调闭包——provider 降级时这是唯一闸门 |
| 过滤条件对象 | `backend/app/services/retrieval/filters.py:42-64` | **不变**：KB 不进入 `RetrievalFilters`，靠可见清单（doc_id 集合）间接表达 |

因此 KB 授权**不产生**新的 Milvus 表达式段，也不要求给 `Chunk` 增字段——可见文档集合已经表达了 KB 归属（方案取舍见 `doc/plan/知识库实体与授权-分析与实施计划.md` §4.4）。

**空结果探测的边界**：§7.6 的只读探测用 tenant 级 filters（`backend/app/services/pipeline.py:416`），会命中其它知识库的内容。因只返回布尔值、不外带内容，泄露面有限，但「有权看但内容真没有」与「无权限」的区分力被削弱——已知限制，登记在 `08-安全与治理.md` §十一。

## 八、上下文组装

实现文件：`backend/app/services/context.py`。四段式流水线**按顺序执行**，每段都可能把候选数降下来（`backend/app/services/context.py:12-13`）。

### 8.1 四段式

| 段 | 做什么 | 留痕 reason | 代码位置 |
|---|---|---|---|
| ① 去重 | 按 `key` 去重（父块回查后同一 `parent_id` 会重复出现） | 「重复块（父块展开/多路命中）」 | `backend/app/services/context.py:72-84` |
| ② MMR 挑选 | 在 `max_items × factor` 的候选池里做最大边际相关性选择 | 「多样性挑选未入选（MMR）」 | `backend/app/services/context.py:86-96`、`:162-191` |
| ③ token 预算裁剪 | 按分数从高到低装填，超预算的**跳过但继续装后面的** | 「超出 token 预算（N）」 | `backend/app/services/context.py:98-110` |
| ④ 硬截断 | 单条就超预算时按顺序填满，最后一条切一半 | 「硬截断丢弃」/「硬截断（保留前段）」 | `backend/app/services/context.py:126-153` |

MMR 的目标函数：`val = λ × score − (1 − λ) × sim`（`backend/app/services/context.py:184`）。相似度用**字符 n-gram 的 Jaccard** 近似而非 embedding——目的是「别让同一段话说五遍」，词面重合度已经够用，且零成本、无外部依赖（`backend/app/services/context.py:162-169`、`:194-207`）。`λ ≥ 1.0` 时退化为纯按分数排序（`:88-89`）。

### 8.2 保底策略

```python

    top = selected[0]
    keep_chars = max(1, int(token_budget * CHARS_PER_TOKEN))
    result.dropped = [d for d in result.dropped if d.key != top.key]
    kept = [ContextItem(**{**top.__dict__, "content": top.content[:keep_chars],
               "reason": "超预算，保留截断版（否则上下文为空）"})]

```

（`backend/app/services/context.py:112-124`）

触发场景：只有一条候选且它本身就超预算（长表格块很常见），③ 会把它整条丢掉 → 上下文为空 → 答案完全没有证据。**「截断版证据」比「空上下文」更糟**，因此保留最高分那条的前段。

### 8.3 token 估算：保守折算

```python

```

（`backend/app/services/context.py:22`）

中文为主的语料约 1.5 字符/token，英文约 4 字符/token；取 2.0 是**保守估计**——宁可低估容量、提前裁剪，也不要算完发现超限被上游截断（`backend/app/services/context.py:20-21`）。估算函数 `estimate_tokens` 只用于预算判定，**不用于计费**（`:25-27`）。

### 8.4 reason 回传的现状

`ContextItem.reason` 字段的注释写的是「被淘汰/被截断的原因（回传给前端解释"为什么没进上下文"）」（`backend/app/services/context.py:40`）。管线侧确实把 `assembled.dropped` 收集到 `self._context_dropped`（`backend/app/services/pipeline.py:569-572`），该字段在实例上有定义（`backend/app/services/pipeline.py:145-146`）。

**但**：全仓检索 `context_dropped` 只有这两处引用——该列表**从未被读出并放进任何响应体**。这是「有机制无接线」的实例，已登记于第十二章。

### 8.5 与父块回查的关系

父块回查在组装**之前**完成：命中子块 → 按 `parent_id` 从 DocStore 取父块全文 → 以 `parent:{parent_id}` 为去重 key 构造 `ContextItem`（`backend/app/services/pipeline.py:543-557`）。因此 ① 的去重正是为了消除「多个命中子块替换成同一父块全文」的重复。

## 九、语义缓存

实现文件：`backend/app/services/cache.py`，键的构造在 `backend/app/services/pipeline.py:250-276`。

### 9.1 缓存键五维


（`backend/app/services/cache.py:21-42`）

| 维度 | 作用 |
|---|---|
| `tenant` | 防止跨租户串答案（**数据越权**） |
| `question` | 问题原文 |
| `model` | 模型版本标识——换模型后旧条目自然失效 |
| `config` | 检索与生成配置摘要——改配置即换键 |
| `scope` | **检索范围**维度（快问的 `doc_id`） |

`scope` 是 F4 快问引入的：快问只检索某一个临时文档，与全库检索的问题文本可能完全相同（「这个文件讲了什么」）。少了这个维度，两种范围的答案会互相命中——**属于正确性事故**（`backend/app/services/cache.py:26-29`、`backend/app/services/pipeline.py:272-273`）。

`config_digest` 的内容包含：检索配置全文、`chunk_size`、`temperature`、**`index_version`**、CRAG 是否启用、**`user`**、**`acl_version`**（`backend/app/services/pipeline.py:252-264`）。

### 9.2 近似命中的三道闸

精确命中失败后进入语义近似查找（余弦 ≥ 阈值），命中前必须**同时**满足三道闸：

| 闸 | 条件 | 代码位置 |
|---|---|---|
| 租户闸 | 同租户 | `backend/app/services/cache.py:181-183`（内存）、`:390-391`（Redis） |
| 维度签名闸 | `signature` 完全一致（模型版本 + user + acl_version + index_version + 配置摘要） | `backend/app/services/cache.py:184-186`、`:394-396` |
| 范围闸 | `scope` 一致 | `backend/app/services/cache.py:187-189`、`:392-393` |

**签名含 ACL 版本与索引版本，因此权限撤销或知识库变更后旧缓存条目自然失效**——这正是把 `acl_version` / `index_version` 放进 digest 的原因（`backend/app/services/pipeline.py:250-266`）。

签名本身是 `f"{model_version}:{digest}"`（`backend/app/services/pipeline.py:266`）。

### 9.3 Redis 与内存的命中边界

| 命中类型 | 内存实现 | Redis 实现 |
|---|---|---|
| **精确命中** | 本进程 | **跨副本**（条目连同 payload 存在共享存储，A 副本写入 B 副本可命中） |
| **近似（语义）命中** | 本进程 | **仅本副本** |

原因：共享存储里存了向量，但**按余弦全表扫描在 Redis 上不可行**——会把 O(N) 扫描变成网络往返。因此近似索引留在本进程（`backend/app/services/cache.py:233-246`）。实际后果是：跨副本能省下**完全相同**的问题，语义相近的改写仍需各副本自己命中。

### 9.5 single-flight

相同 cache key 的并发请求合并为一次真实计算：

```python
def _sf_acquire(self, cache_key: str) -> tuple[threading.Event, bool]:
    with self._inflight_lock:
        ev = self._inflight.get(cache_key)
        if ev is None:
            ev = threading.Event()
            self._inflight[cache_key] = ev
            return ev, True
        return ev, False
```

（`backend/app/services/pipeline.py:1088-1102`）

- 首个请求负责真实计算并在 `finally` 里 `_sf_release`；后续请求等待同一个 `Event` 复用结果。
- **等待上限 `_SF_WAIT_S = 30.0` 秒**（`backend/app/services/pipeline.py:1086`），超时自行执行，避免等待者占满线程。
- `bind_principal` 产生的是**副本语义**（同一请求内共享 `_inflight` dict 引用，`backend/app/services/pipeline.py:148-150`），所以 single-flight 的作用域是「同一请求内的并发调用 + 同 key 的多请求」。

| 容量配置变更 → **重置为满桶** | `if bucket is None or bucket.capacity != capacity:` | `backend/app/services/ratelimit.py:33-36` |
| 回填**不得超过容量** | `min(capacity, tokens + elapsed * rate)` | `backend/app/services/ratelimit.py:37-40` |
| 令牌可为小数，消费 1 枚 | `if bucket.tokens >= 1.0: bucket.tokens -= 1.0` | `backend/app/services/ratelimit.py:41-43` |
| 拒绝时给出 Retry-After 秒数 | `wait = (1.0 - tokens) / (rate/60)`，下限 1 秒 | `backend/app/services/ratelimit.py:44-46` |

「回填不超容量」的理由：否则空闲期会积累出无限额度（`backend/app/services/ratelimit.py:37`）。

### 10.2 Redis Lua 保证原子

```lua
local tokens = tonumber(redis.call('HGET', key, 'tokens'))
local ts = tonumber(redis.call('HGET', key, 'ts'))
if tokens == nil then tokens = capacity end
if ts == nil then ts = now end
if now > ts then
  tokens = math.min(capacity, tokens + (now - ts) * rate)
end
local allowed = 0
if tokens >= 1 then tokens = tokens - 1 allowed = 1 end
redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, ttl)
return {allowed, tostring(tokens)}
```

（`backend/app/services/ratelimit.py:67-88`）

**回填与扣减在同一段 Lua 内完成**，因此不会出现「两个副本同时读到同一份 tokens 并各自扣减」的竞态。桶键为 `ratelimit:bucket:{tenant_id}`，TTL 300 秒（`backend/app/services/ratelimit.py:108-109`）。

### 10.3 Redis 不可用 → Fail-Open

```python
except Exception:  # noqa: BLE001 - Fail-Open：降级为进程内
    self._degraded += 1
    return self._fallback.allow(tenant_id, rate_per_min, capacity)
```

（`backend/app/services/ratelimit.py:113-115`）

降级纪律写得很明确：「绝不把『Redis 挂了』变成『请求全被限流』或『请求全被放行』」（`backend/app/services/ratelimit.py:94-95`）。降级次数通过 `stats()` 暴露（`:125-126`）。

### 10.4 多副本注意

> 多副本部署时桶状态必须跨副本共享（如 Redis），否则每个副本各算一份，**实际放行量是配置值的 N 倍**——这是限流最常见的失效原因。

（`backend/app/services/ratelimit.py:7-9`）

`build_limiter(state)` 按 `state.redis_enabled` 选择实现（`backend/app/services/ratelimit.py:52-60`）。**未配置 Redis 时回落到进程内实现**，此时上述倍数效应成立。

参数取值优先级：**运行时热配置 > 全局配置**（`resolve_bucket_limits`，`backend/app/services/ratelimit.py:129-137`）。此前两个配置项声明后从未被读取，实际生效的永远是 `RetrievalConfig` 的硬编码默认——改环境变量没有任何效果。

### A. 公式速查

**BM25**（`backend/app/services/retrieval/bm25.py:26-60`）

```
idf(t)  = ln(1 + (N - n + 0.5) / (n + 0.5))            # 恒正
score(d)= Σ_t idf(t) × (f(t,d) × (k1 + 1)) / (f(t,d) + k1 × norm(d))
norm(d) = 1 - b + b × doc_len(d) / avgdl
k1 = 1.5    b = 0.75    doc_len(d) = max(len(d), 1)
```

**RRF**（`backend/app/services/retrieval/fusion.py:3`）

```
score(d) = Σ_i w_i / (k + rank_i + 1)      # rank 从 0 起，k = 60
自检：单路第 1 = 1/61 ≈ 0.0164；两路都第 1 ≈ 0.0328
```

**MMR**（`backend/app/services/context.py:184`）

```
val = λ × score − (1 − λ) × sim(Jaccard(字符 4-gram))
```

**token 估算**（`backend/app/services/context.py:22`）

