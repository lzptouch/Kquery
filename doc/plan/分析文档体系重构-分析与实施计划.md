## 〇、结论速览

### 0.1 一句话结论

> **`doc/analysis/` 的十篇文档不是"内容过时一点"，而是**组织骨架已经失效**——它们全部按「十阶段递进」写成，而阶段 8（多智能体报告）与阶段 9 的评测平台已在 2026-10-17 从代码里删除，阶段 10 从未实施，2026-10-25/26 又整合进 11 项 doc-qa 独有能力；骨架一失效，"某能力属于哪一阶段"这个唯一的编排轴就没有答案了，文档只能靠"横幅声明已失效"来打补丁，于是每篇都留着一段死内容，新能力却没有一篇覆盖。**

因此本次不是"更新几篇文档"，而是**换一套编排轴**：从「阶段递进」改为「**能力域（Capability Domain）**」，并按新骨架重写 15 个文件。

## 一、背景与目标

### 1.1 触发原因

`doc/analysis/` 的十篇文档建于 2026-10-05 ~ 2026-10-19，当时项目正按 `doc/series/` 的十阶段设计文档推进。此后代码发生了三次结构性变动：

| 时间 | 变动 | 对文档骨架的冲击 |
|---|---|---|
| 2026-10-17 | 删除报告中心与评测平台（原阶段 8 + 阶段 9 半） | 阶段序列出现空洞；6 篇文档内容失效 |
| 2026-10-19 ~ 10-25 | 批次 B/C/D/E 安全与能力改造（`知识库对照优化分析.md` 产出的 42 条缺陷大部分已修） | 缺陷清单与现状脱节；文档仍在描述缺陷态 |
| 2026-10-25 ~ 10-26 | 整合 doc-qa 独有能力 F1~F11；合并「高并发」分支（`2eaaec0`） | 新增 8 个端点、4 个配置组、11 项前端能力，文档层零覆盖 |

三变动叠加的结果：**文档编排轴（阶段）与代码组织轴（能力域）彻底脱钩**，且没有任何一篇文档能作为"Kquery 现在能做什么"的唯一入口。

### 1.2 目标

| # | 目标 | 可验证判据 |
|---|---|---|
| G1 | 文档能回答"Kquery 当前有哪些能力、入口在哪、现状是否可用" | `01-能力全景.md` 一页内可列全 D1~D10 全部能力及其入口端点/页面 |
| G2 | 每篇文档单一职责、无重叠 | 任意一个代码事实只允许出现在一篇文档里（§3.3 覆盖矩阵可查：每个事实只允许有一个 ●） |
| G3 | 现状与计划可判别 | 每篇开头有统一「文档口径」块；失效内容使用统一标记并集中登记在 `README.md` |
| G4 | 事实可追溯 | 关键结论带 `文件:行号`；文首有「代码基线」字段（SHA 统一定义在 README，见 §3.8） |

| G6 | 篇幅可控 | 单篇单一职责、结构清晰；体量上限 **70 KB**（v1.2 校准，原 45 KB 基于低估的内容量）。`知识库对照优化分析.md` 136 KB 是"单篇混装多职责"的反面样本，与"单篇单职责但内容充实"是两回事 |

### 1.3 非目标

- 不追求"文档即教程"：每篇的目标读者是**要基于代码做决策的工程师**，不是新手。
- 不重写设计文档：`doc/plan/` 下的设计与实施记录保持原样，`doc/analysis/` 只描述**已落地**的现状 + 明确的缺口。
- 不引入文档生成器：本次用手工核 + 脚本校验，不做自动生成（成本高于收益）。
- 不追求一次到位：B0~B5 交付后允许个别章节留 `TODO(待补)` 标记（但必须在 `14-差距与演进.md` 登记），B6c 全量校验时清零。

### 1.5 与「方案文档单篇整合」偏好的关系（重要）

> 本项目此前有过明确偏好：**评估/方案类文档要单篇整合，不要拆成 00~07 那种多篇结构**。本计划提出 15 篇，表面上与这条偏好冲突，因此必须正面说明，而不是当作"低概率风险"含糊过去。

**结论：本计划不违背该偏好，因为两者的文档类型不同。**

| 维度 | 方案文档（单篇整合） | 现状分析体系（本计划） |
|---|---|---|
| 产出目标 | 说服读者接受**一个结论与一条路线** | 支撑读者**按需检索任意子系统的事实** |
| 生命周期 | 一次性：结论被采纳后文档即归档 | 长期：代码演进就持续维护 |
| 失效方式 | 结论被推翻 → 整篇过时，单篇重写成本低 | 某个域改动 → 只需改对应一篇，拆分反而降低单次维护成本 |
| 阅读方式 | 从头读到尾 | 按需跳读（"我想知道 ACL 怎么判"） |
| 与代码的对应 | 不要求逐域对齐 | 必须与代码目录/能力域一一对应 |

**反过来看，单篇整合恰恰是当前文档出问题的原因之一**：`知识库对照优化分析.md` 136 KB 单篇里同时装着"现状 + 42 条缺陷 + 演进路线 + 并发设计"，任何一处代码变动都无法只更新其中一段——结果就是整篇集体过期（基线钉在 `b40f053`）。

**若用户仍倾向更少的篇数**，可执行 §5.5 给出的合并映射（15 → **13 篇**：`10+11`、`12+13`）。**不建议再往下压**：压到 9 篇需放弃某域完整覆盖或突破 45 KB 上限（与 G1/G6 直接冲突），这个代价必须由决策者明确接受，不应由实施者临时决定。

### 2.5 处置判定：重写 / 改写 / 迁移

### 3.7 能力状态判定标准（v1.1 新增）

> `01-能力全景.md` 要求给出"状态"，但 v1.0 没定义判定标准，实施时必然出现"有代码就写 ✅"。本节是唯一标准，`01` 必须照此打标。

| 状态 | 判据 | 示例 |
|---|---|---|
| ✅ **可用** | ① 有生产调用点（非仅测试）② 走默认配置即可工作 ③ 有覆盖其主路径的测试 —— **三条全满足** | 混合检索（`hybrid.search_multi` 被 pipeline 调用，默认开启，有 `test_stage2.py`） |
| ⚠️ **有条件可用** | 满足 ①③ 但**默认关闭**（需改配置）/ **有机制无度量** / **已知缺口内** —— **满足其一即降级** | ReAct（`agent_mode` 默认 `plan_execute`）/ HITL（默认 `False`）/ 图谱（`graph_enabled` 可关）/ 检索质量（无金标集） |
| ⛔ **不可用** | 无生产调用点，或依赖外部系统未配置且无降级 | SQL 工具（`sql_dsn` 空则不注册）/ Web 搜索（`web_search_endpoint` 空则不注册） |
| 🚫 **已下线** | 代码已删除 | 报告中心、评测平台 |

**三条硬规则**：

1. **"有代码"不等于"可用"**：只被测试调用的能力最高只能标 ⚠️。
2. **默认关闭一律 ⚠️**：即便打开后完全可用（如 HITL、ReAct、verify 节点、OTel、降级阶梯）。
3. **"有机制无度量"一律 ⚠️**：典型是检索质量与 Agent 自主性——机制齐全，但无评测集，无法证明有效（这是本项目最需要诚实的地方）。

> 判定结果必须有代码依据（配置项 + 调用点），不允许凭印象。`01` 的每一行状态都要能指到 §3.7 的某条判据。

### 5.2 每篇文档的标准作业流程（SOP）

1. **取证**：只读当前代码，用 `grep`/打开文件确认真实行号；不采信旧文档的结论。
2. **搭骨架**：按 §3.4 模板建文件（含「维护触发」章），缺失章节先占位。
3. **判处置**：查 §2.5 的逐篇判定表——标「📦 迁移」的整段搬、标「✏️ 改写」的只换失效章节，避免无谓重写。
4. **填内容**：优先迁移 §2.5.1 的 18 项可复用资产，其余新写。
5. **打状态标**：能力类描述一律按 §3.7 的 ✅/⚠️/⛔ 标准判定，禁止凭感觉。
6. **标缺口**：任何"看起来有但实际没接线/口径不符"写进该篇的「边界与已知缺口」章。
7. **交叉引用**：用 `→ 0X-xxx.md §n` 形式指向其它篇；关键数值引用 README 关键数字表，不重复写数字。
8. **自检**：跑 §5.4 的校验脚本（V1~V12）。
9. **登记**：把该篇新增的缺口汇总到 `14-差距与演进.md` 的对应小节（`14` 未写完时先记在临时清单）。

### 5.8 基线冻结与回写约定（v1.1 新增）

**冻结语义**：文档写作期间以 git `2eaaec0` 为**事实快照**。代码继续演进不阻塞写作，但必须遵守回写规则。

|---|---|

**影响映射表**（供回写时定位，避免全篇重读）：

**基线戳的唯一位置**：`README.md` 的关键数字表。其它篇写「代码基线：见 README」，不各自钉 SHA——**避免 15 处 SHA 需要同步更新**（这是 N6 的一次具体应用）。
