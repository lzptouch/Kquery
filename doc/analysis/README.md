# Kquery 分析文档索引

> - **代码基线**：git `0363f12`（2026-10-28）— **全仓唯一钉基线 SHA 的位置**
> - **对象**：Kquery 智能 RAG 系统（FastAPI 单端口后端 + Milvus + React 前端）
> - **本目录定位**：系统**现状分析**的文档集合——回答"Kquery 现在有什么能力、怎么工作、有哪些缺口"。**不是**设计文档（设计/计划在 `doc/plan/`）。
> - **核心约定**：现状分析按**能力域（D1~D10）**编排，不按开发阶段；每篇单一职责、无重叠；事实带 `文件:行号`。

## 〇、一句话定位

Kquery 是一个**能力域完整、但质量尚不可度量**的生产级 RAG 系统：混合检索、Agentic 编排、GraphRAG、多模态、企业护栏、共享存储、**知识库实体与逐用户授权**均已落地（见 `01-能力全景.md`），但**没有检索金标集**，检索质量与 Agent 自主性无法用数据证明（见 `14-差距与演进.md` §七 S1）。

## 七、维护约定

1. **何时更新哪篇**：以代码变动为准，查各篇文末「维护触发」章列出的文件；改到了哪个文件，就更新对应的篇。
2. **基线戳如何回写**：代码基线变化时，**只改本文 §1.5 的 git SHA 与日期**（N2）；受影响篇的「维护触发」章同步更新 SHA。
3. **新增能力**：新增端点 → `03` 端点表 + `01` 能力入口 + 本文§1.2；新增配置 → `13` 配置矩阵 + `11` 参数表 + 本文§1.3；新增指标 → `10` + 本文§一。新增**权限维度**（如知识库授权）→ `08` 判定树章 + `09` 数据模型章 + `05` 检索过滤章 + `03` 端点章 + 本文§1.2。
4. **新增缺口**：一律先登记在 `14` §三，再视修复进度移到 §二。
4b. **未实现项有目标态设计**：在 `14` 或各域文档登记缺口后，若该缺口需要方案设计（不只是修一个 bug），同步在 `doc/design/` 建档；三处必须同步——`doc/design/`（设计）· `doc/plan/`（状态）· `doc/analysis/14`（现状缺口）。
5. **文档互链**：保持 `→ NN-xxx.md` 形式有效；改文件名必须同步全文引用。
