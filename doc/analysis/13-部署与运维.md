## 〇、摘要

- 根目录 `docker-compose.yml` 一键全栈：6 个服务，依赖顺序 **etcd → milvus → init → backend → frontend**，redis 与 milvus 并行但作为 backend healthy 依赖（`docker-compose.yml:14-164`）。
- `init` 是一次性建表服务（`restart: "no"`）：建 Milvus 集合只发生一次且可见，多副本同时建表会失败（`docker-compose.yml:109-148`）。
- 后端镜像：uv venv 构建 + 非 root（uid 1001）运行 + `HEALTHCHECK curl /healthz` + `CMD uvicorn --workers 1`（`backend/Dockerfile:35-71`）。
- 两份 nginx 配置**不一致**：`deploy/nginx/nginx.conf` 的 API 前缀正则不含 `quickask`，`frontend/nginx.conf:41` 含——本地独立 nginx 形态下快问会 404（登记为缺口 G1）。
- 密钥只经 `backend/.env` 的 `env_file` 注入，不进镜像层；compose `environment` 只覆盖面向本机的地址（`docker-compose.yml:85-93`）。
- 启动期 `validate_startup()` 返回问题清单，非空必须中止启动——宁可 boot 时崩也不带坏配置对外服务（`backend/app/core/config.py:963-1152`，结构化声明在同文件 `config_items()` `:875-961`）。
- **访问边界全在部署层**：认证与授权已于 2026-11-12 整体下线，应用不再有任何访问控制（语义 → `08-安全与治理.md`）。部署到公网 = 任何人可读全部数据，反向代理 / 内网 / 网关是**唯一**的访问边界，**不要把服务直接暴露在公网**。

## 一、四种运行形态

| 形态 | 起法 | 入口 | 适用 |
|---|---|---|---|
| 本地 uv 直跑 | `cd backend && uv sync && uv run uvicorn app.main:app --port <见 README>` + `cd frontend && npm run dev` | `backend/app/main.py`、`frontend/vite.config.ts` | 开发 / 调试 |

## 二、compose 编排

| 服务 | 镜像 / 构建 | 端口映射 | depends_on | healthcheck | 卷 |
|---|---|---|---|---|---|
| `etcd` | `quay.io/coreos/etcd:v3.5.18` | 无（容器内网） | — | `etcdctl endpoint health`（30s/20s×3） | `etcd_data` |
| `milvus` | `milvusdb/milvus:v2.6.4`（standalone，`COMMON_STORAGETYPE=local`） | gRPC + 健康端口（映射值见 README 关键数字表；容器内恒为 19530/9091） | `etcd`（healthy） | `curl -f localhost:9091/healthz`，`start_period: 90s`（冷启动加载本地存储，30s 会误判 unhealthy） | `milvus_data` |
| `redis` | `redis:7-alpine`（appendonly + `save 60 1`） | 有（见 README） | — | `redis-cli ping`（10s/5s×5） | `redis_data` |
| `init` | 构建 `./backend`（同后端镜像） | 无 | `milvus`（healthy） | 无（一次性进程，退出码即状态） | `backend_data` |
| `backend` | 构建 `./backend` → `kquery-backend:latest` | 有（见 README；容器内 8000） | `init`（completed_successfully）+ `redis`（healthy） | 镜像内 HEALTHCHECK（§三） | `backend_data` → `/data` |
| `frontend` | 构建 `./frontend`（build arg `VITE_API_BASE_URL=/api`） | 有（见 README；容器内 8080） | `backend`（healthy） | 镜像内 HEALTHCHECK | — |

（依据：`docker-compose.yml:16-32`、`:34-57`、`:63-76`、`:111-148`、`:79-107`、`:151-164`、`:166-170`）

关键设计：

1. **依赖顺序靠 healthcheck gate**：backend 必须等 `init` 成功退出——后端启动时会 load 集合，集合不存在直接抛异常进入 restart 循环（`docker-compose.yml:98-102`）。
2. **redis 是 healthy 依赖但语义上可选**：只是避免启动瞬间连不上；连不上时后端自行降级进程内（Fail-Open），服务不中断（`docker-compose.yml:103-106`）。多副本时它不是可选的——限流 / 缓存必须共享（→ `11-并发与容量.md` §七）。
3. **`init` 独立成一次性服务**（`restart: "no"`）：建表只发生一次且可见；`MODEL_PROVIDER=mock` 不需要真实模型；内部带 30 次重试（Milvus 刚 healthy 时端口已开但 collection API 可能还在初始化）（`docker-compose.yml:109-148`）。
4. `docker compose down -v` 会连卷一起清——**向量索引、文档元数据与会话都会丢**（文件头注释，`docker-compose.yml:7`）。原注释里提到的「用户目录」已随用户目录能力下线而不再存在（`data/users.json` 不再被创建或读写；`Settings.users_file` 只是无读取点的死属性，`core/config.py:1167-1173`）。

## 三、镜像构建原理

### 3.1 后端（`backend/Dockerfile`）

| 点 | 现状 | 代码位置 |
|---|---|---|
| 两阶段 | builder（`python:3.12-slim` + build-essential + uv 0.5.11）建 `/opt/venv`；runtime 同基底只拷 venv 与代码 | `backend/Dockerfile:8-31`、`:35-55` |
| 层缓存 | 先只拷 `pyproject.toml` + `uv.lock*`：锁文件变了才算依赖真变，改业务代码不重装依赖 | `backend/Dockerfile:27-31` |
| 非 root | uid/gid 1001 `kquery` 用户运行，容器逃逸拿到的是无特权用户 | `backend/Dockerfile:40-43`、`:63` |
| 默认环境 | `DATA_DIR=/data`、`VECTOR_STORE=milvus`（镜像内默认生产向量库） | `backend/Dockerfile:45-49` |
| 数据挂载点 | `/data` 显式 chown + `VOLUME` | `backend/Dockerfile:57-59` |
| HEALTHCHECK | `curl -fsS localhost:8000/healthz`（30s/5s/start 40s/×3）；curl 显式装——镜像里没有 curl 时探针永远失败的「假阴性」最费排查时间 | `backend/Dockerfile:39-40`、`:68-69` |
| CMD | `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1`（单 worker；并发靠进程内机制 → `11-并发与容量.md`） | `backend/Dockerfile:71` |
| 取舍：容器探针打 `/healthz` 不打 `/readyz` | `/healthz` 判断「进程活着 + 关键依赖可达」；深度就绪判据交编排层——混在一起会让 Milvus 抖动把还能服务读请求的容器杀掉 | `backend/Dockerfile:65-67` |

### 3.2 前端（`frontend/Dockerfile`）

| 点 | 现状 | 代码位置 |
|---|---|---|
| builder | `node:22-alpine`，先拷 `package.json` + lock 再拷源码（依赖层缓存） | `frontend/Dockerfile:7-18` |
| 构建期注入 API 前缀 | `ARG VITE_API_BASE_URL=/api` → `ENV` → `npm run build`；**镜像里不带任何后端地址**，运行时后端主机名由 nginx 解析，同一份镜像多环境复用 | `frontend/Dockerfile:20-25` |
| runtime | `nginx:1.27-alpine` + 静态产物 + `frontend/nginx.conf`；master 也非 root 化改造 + curl（HEALTHCHECK 客户端） | `frontend/Dockerfile:29-37` |
| HEALTHCHECK | `curl -fsS localhost:8080/`（30s/5s/start 10s/×3） | `frontend/Dockerfile:41-42` |

两份 Dockerfile 都**故意不写** `# syntax=docker/dockerfile:1`：那行会让构建器去 Docker Hub 拉前端镜像，在只能走镜像加速站的环境里 build 在「解析构建器镜像」一步就超时；用到的能力（多阶段 / `COPY --from` / `COPY --chown`）BuildKit 内置前端原生支持（`backend/Dockerfile:1-5`、`frontend/Dockerfile:1-5`）。

## 四、两份 nginx 差异对照

| 项 | `deploy/nginx/nginx.conf`（本地独立实例） | `frontend/nginx.conf`（容器版） |
|---|---|---|
| listen | 本地独立实例端口（见 README 关键数字表）（`:57`） | 容器内 8080（`frontend/nginx.conf:15`） |
| upstream | `127.0.0.1:<宿主后端端口>`（避让本机端口段的注释在 `:47-54`） | `backend:8000`（compose 服务名，启动时解析一次）（`frontend/nginx.conf:103-107`） |
| 运维端点 | `^/(healthz\|readyz\|livez\|health\|metrics)$` 永远透传不参与 SPA 分流（`:69-75`） | 同规则（`frontend/nginx.conf:32-38`） |
| **API 前缀** | `ask\|knowledge\|admin\|feedback\|sessions\|graph\|search\|media\|assets\|metrics\|health\|auth`——**不含 `quickask`**，却仍留着**已删除的 `auth` 前缀**（`deploy/nginx/nginx.conf:78`） | 同前缀**含 `quickask`**（`frontend/nginx.conf:41`） |
| SPA 分流 | `Accept: text/html` → `error_page 418 = @spa` 内部跳转（`:80-83`、`:131-135`） | 同（`frontend/nginx.conf:42-46`、`:96-100`） |
| SSE | API 前缀块内 `proxy_buffering off` + read/send timeout 600s；`~ /stream$` 兜底带路径参数的长流式端点（`:93-109`） | 同（`frontend/nginx.conf:56-72`） |
| 静态资源 | `^~ /static/` 永久缓存；`= /index.html` 禁缓存（`:114-123`） | 同（`frontend/nginx.conf:81-88`） |
| SPA 兜底 | `try_files $uri $uri/ /index.html`（`:126-128`） | 同（`frontend/nginx.conf:90-93`） |

两个刻意设计（注释里有完整事故记录）：

1. **运维端点永远透传**：探针可能带 `Accept: text/html`，送进 SPA 分流会拿到 HTML——表现为「探针 200 但内容不是 JSON」，极难排查（`deploy/nginx/nginx.conf:66-68`）。
2. **产物目录是 `/static/` 不是 `/assets/`**：后端的 `/assets/` 是媒体资源端点，两边同名会被 API 正则抢走，页面白屏（`frontend/nginx.conf:74-80`、`frontend/vite.config.ts:19-24`）。

## 六、环境变量与 .env 的关系

- `Settings(BaseSettings)`：`env_file=backend/.env`、`extra="ignore"`、环境变量前缀 `KQUERY_`；`milvus_uri` 例外，用 alias `KQUERY_MILVUS_URI`（避免与 pymilvus 内部变量冲突）（`core/config.py:15-20`、`:237-238`）。
- `backend/.env`：本机密钥与覆盖项的落点；compose 经 `env_file: ./backend/.env` 注入容器——**密钥不进镜像层**（`docker-compose.yml:85-86`）。
- `backend/.env.example`：模板，拷为 `.env` 后填值；镜像里也带一份作参照（`backend/Dockerfile:55`）。
- compose `environment` 只覆盖「面向本机的地址」：`KQUERY_MILVUS_URI=http://milvus:19530`（容器内走服务名不是 localhost）、`VECTOR_STORE=milvus`、`DATA_DIR=/data`、`REDIS_URL=redis://redis:6379/0`、`CACHE_BACKEND=auto`（`docker-compose.yml:87-93`）。优先级：compose environment > env_file > 默认值。

## 八、排障手册

### 8.1 启动失败分类

`validate_startup()` 非空即中止启动（`backend/app/core/config.py:963-1152`），常见类别：

| 症状 | 根因 | 依据 |
|---|---|---|
| 「必填项缺失」 | `config_items()` 里 `required=True` 的项取值为空 → 逐项 `add()` | `core/config.py:975`（清单见 `:875-961`） |
| provider 非法取值 | `model_provider` / `embedding_provider` / `rerank_provider` 出白名单（`auto\|dashscope\|deepseek\|minimax\|zhipu\|mock` 等） | `core/config.py:978-1004` |
| `ocr_provider` 非法取值 / 缺平台凭证 | OCR 只允许云服务 API（`auto\|dashscope\|mock`）；`dashscope` 却没凭据 | `core/config.py:1020-1026` |
| 「将静默降级为 mock」 | `model_provider=auto` 且无 `dashscope_api_key`——宁可启动失败，也不静默裸奔 | `core/config.py:1064-1070` |
| 「各上游许可之和 > pipeline_workers」 | 许可和超过线程数 → 线程全卡在等许可（`LM-03` 的启动期兜底） | `core/config.py:1071-1086` |
| `chunk_policy` 非法预设 / `top_k` ≤ 0 / `chunk_overlap ≥ chunk_size` / `rrf_k` ≤ 0 | 检索参数越界 | `core/config.py:1088-1104` |
| 后端 restart 循环、日志报集合不存在 | `init` 未成功就起了 backend；或 Milvus 没起来 | `docker-compose.yml:98-102` |
| checkpointer 相关异常 | `agent_checkpointer=sqlite` 路径不可写；可改 `memory`/`none` 定位 | `core/config.py` 的 `agent_checkpointer` 定义（以代码为准） |
| `cache_backend=redis` 启动即失败 | 显式要求 Redis 却没给 `redis_url`（配置错误不拖到运行期） | `core/config.py:1120-1123` |
| 宿主端口冲突 | Milvus 宿主 19530 被占 → 改映射不改容器内端口（`KQUERY_MILVUS_URI` 走服务名不受影响） | `docker-compose.yml:43-47` |
| **「认证将无人可通过」这类报错不会再出现** | 原 `auth_enabled` / JWT 密钥长度校验已随认证下线删除（2026-11-12） | 无对应代码；`grep -n "_enabled" core/config.py` 中无 `auth_*` |

### 8.2 本地直连三陷阱

1. **前端必须显式 `KQUERY_API_TARGET`**：vite 代理默认指向本机后端默认端口，后端换了端口而前端没设变量时，页面能开但所有 API 静默打到旧地址（`frontend/vite.config.ts:9-15`）。
2. **vite 代理列表必须与 nginx location 一致**：漏配的前缀会回落 SPA 的 index.html——返回 200 + HTML，看起来「通了」实际拿不到数据（曾漏 `/readyz` 与 `/livez`，注释里有记录）；`/speech`、`/quickask` 在 vite 侧已对齐，deploy/nginx 侧未对齐（缺口 G1）（`frontend/vite.config.ts:29-53`）。
3. **所有出站请求都经 `frontend/src/lib/api-client.ts`**：统一信封解析与错误提示；绕开它手写 fetch 会得到难以归因的失败（认证已下线，`frontend/src/lib/auth.ts` 随之删除）。
