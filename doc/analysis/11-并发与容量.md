## 〇、摘要

- 单进程单体：一个 uvicorn worker（`backend/Dockerfile:71`），全部并发 = 单事件循环协程 + 若干有界线程池。
- 问答路径有独立的进程级有界执行器：`workers=32` + 排队上限 `200`，队列满**立即 503 + Retry-After 5**（快速失败，不阻塞等待到死）（`services/pipeline_executor.py:37-47`、`:58-79`、`:221-230`）。
- Agent 路径独立闸门：在飞 run 上限 `16`，超出立即 429 不排队（`services/agent/runner.py:141`、`:173-178`）。
- 上游隔离仓许可 llm=12 / embedding=4 / rerank=2 / milvus=8，**和 26 ≤ 32**（问答执行器线程数）——这是硬约束，否则线程全被等许可占满（`core/config.py:255-259`、`services/upstream.py:1-11`）。
- 限流与配额双层：令牌桶（capacity=60、refill=60/min，按租户）在前，租户真滑动窗口配额（60/min + 10000/day + token_daily 默认 0 不限）在后；两者都有 Redis 共享实现 + Fail-Open 降级（`core/config.py:57-58`、`:214-216`）。
- 真实容量上限是**上游模型配额**，不是本机 CPU：32 在飞 ≈ 4 QPS 承载（Little's Law，8s/req 时），扩容前先按 §五容量模型核算（`core/config.py:249-250`）。

## 一、并发模型

Kquery 是单进程单端口 FastAPI 应用，并发由四类执行体构成：

| 执行体 | 承载什么 | 边界 |
|---|---|---|
| asyncio 事件循环 | 全部 HTTP 端点协程、SSE 生成器 | 单线程；任何同步阻塞冻结全站 |
| 问答执行器（`PipelineExecutor`） | 问答管线（LLM / Embedding / Milvus 同步 SDK） | 固定 32 线程 + 排队 200，问答路径独占 |
| 独立小线程池 | 检索召回池（4）、Agent run 池（默认 8）、Agent 工具池、ASR 分片池（4） | 各自独立，严禁与问答执行器复用（§四） |
| 上游隔离仓 | llm / embedding / rerank / milvus 四类上游的许可 + 熔断 | 许可之和 ≤ 问答执行器线程数 |

设计目标不是堆 QPS，而是：**RAG 检索稳定 + 多 Agent 任务有序 + 慢上游不拖死快路径 + 已知坏的上游不再消耗线程与超时预算**（`services/upstream.py:1-3`）。

为什么不做全链路异步重写：管线依赖的 SDK（LLM / Embedding / Milvus）是同步实现，`PipelineExecutor` 用「worker 线程跑同步事件迭代器 → `asyncio.Queue` 投递 → async 生成器取出」的桥接替代重写——SSE 连接本身不再占用线程池线程，空闲连接只占内存与 fd（`services/pipeline_executor.py:10-16`、`:141-199`）。

## 二、并发漏斗（自外向内）

| 层 | 机制 | 参数（本篇口径） | 快速失败语义 | 超出后的表现 |
|---|---|---|---|---|
| HTTP | nginx / uvicorn | 单 worker | — | TCP  backlog 排队 |
| 令牌桶 | `TokenBucketLimiter` / Redis Lua 版，按租户成桶 | capacity=60、refill=60/min | 拒绝时显式给 Retry-After 秒数 | 429 + Retry-After（前端倒计时后自动重试一次） |
| 租户配额 | `SlidingWindowQuota` 真滑动窗口 + 日调用 + 日 token | 60/min + 10000/day + token_daily=0（不限） | 三维任一超限即拒 | 429 + Retry-After（按维度给秒数） |
| 问答执行器 | `PipelineExecutor` 在飞信号量 + 排队上限 | workers=32、queue=200 | **队列满 `acquire` 立即返回 False，不阻塞** | 503 + Retry-After 5（`raise_overloaded()`） |
| Agent 闸门 | `threading.Semaphore(run_permits)` | 16 | `acquire(blocking=False)`，拿不到立即抛 | 429 + Retry-After 5（「Agent 并发已达上限」） |
| 上游隔离仓 | 每类上游信号量 + 熔断器 | llm=12 / embedding=4 / rerank=2 / milvus=8（和 26 ≤ 32） | 熔断 open 期间立即抛 `CircuitOpenError`，不占线程不等超时 | 降级错误；半开 3 次探测全成功才闭合 |
| 模型配额 | `PlatformQuotaMonitor` 平台级日预算 | 默认 0 = 只统计不拦截 | 接近上限 WARNING 日志 | 见 README 关键数字表与 `08-安全与治理.md` |

要点：

- **32 / 200 / 16 / 12+4+2+8 / 60 / 60 / 10000 / 0** 这组值是容量模型的输入，改动任一值都要重算 §五。
- 令牌桶与配额是**两层独立判定**：令牌桶防突发，配额管租户公平；登录限流又是独立实例，不消耗问答配额（→ `08-安全与治理.md`）。
- Agent 路径先过问答执行器（SSE 入口），再过 Agent 闸门——两道闸拒绝语义不同（503 vs 429），前端重试策略可据此区分。

## 三、各层实现机制与原理剖析

### 3.1 令牌桶（`services/ratelimit.py`）

- 按租户独立成桶：避免单租户拖垮全局，也防止共享账号绕过用户级限流（模块 docstring）。
- 令牌可为小数，按「距上次回填的时间 × 速率」补足，**回填不超过容量**（否则空闲期会积累出无限额度）（`services/ratelimit.py:37-43`）。
- Redis 版用 Lua 把「读余量 → 回填 → 扣减 → 写回」做成原子操作（`services/ratelimit.py:67-88`）；Redis 异常 → **Fail-Open** 回落进程内桶，绝不把「Redis 挂了」变成「全限流」或「全放行」（`services/ratelimit.py:91-126`）。
- 参数取值优先级：运行时热配置（`RetrievalConfig.ratelimit_*`）> 全局配置（`resolve_bucket_limits`，`services/ratelimit.py:129-137`）。

### 3.2 租户配额：真滑动窗口（`services/security/quota.py`）

- **真滑动**：分钟窗口保存最近 60s 内每次调用的时间戳，出队即释放——任意 60s 内不超上限，没有固定窗口在分钟边界的双倍突刺（`services/security/quota.py:1-10`、`:52-56`）。
- 三维度：分钟窗口 / 日调用次数 / 日 token 消耗（默认 0 = 该维度不限），任一超限即拒并给出对应 Retry-After（分钟维给出最早一条出窗的等待时长，日维给到午夜的秒数）（`services/security/quota.py:126-138`、`:156-159`）。
- 计数与判定原子：锁内完成「查 + 加」，并发不放行超额请求。
- Redis 共享实现用 ZSET（member = 请求标识，score = 时间戳）+ 日 token 计数器（`services/security/quota.py:73-106`）；异常 Fail-Open 降级进程内（`:64-69`）。
- token 维两段式：请求前按预估值扣（`check_and_consume(tokens=)`），结束后 `record_tokens` 按实际用量补记（`services/security/quota.py:58-63`、`:140-154`）。

### 3.3 有界执行器（`services/pipeline_executor.py`）

| 机制 | 行为 | 代码位置 |
|---|---|---|
| `acquire` | 在飞 < workers 直接占槽；否则若等待者 ≥ queue_size **立即返回 False**（拒绝回调上报 `shed_total`）；否则带 deadline 等待 | `:58-79` |
| `acquire_async` | 同样语义但等待不占 AnyIO 线程：轮询 + `asyncio.sleep(0.02)`，两个条件（deadline / 排队上限）任一不满足立即 False | `:88-114` |
| `stream_events` | SSE 桥接：worker 线程跑同步迭代器投入 `asyncio.Queue(maxsize=512)`；超过 **heartbeat 15s** 无事件产出心跳项；消费者断开时置 cancel，worker 在下一个事件前停止（已发出的上游调用无法中断，明确的技术边界）；消费者慢于生产者导致队列满 → 停止生成而不是堵死线程 | `:141-199` |
| `shutdown` | lifespan 收尾：等在飞任务结束（有上限），`cancel_futures=True` 不再接受新任务 | `:212-218` |
| `raise_overloaded()` | 统一出口：503 + Retry-After 5，错误码与信封一致 | `:221-230` |

它解决的三件事：AnyIO 默认线程池全端点共享导致 SSE 长连接吃满线程（改为问答独占固定池）；无界排队导致请求排队到死（改为 32+200 快速失败）；同步管线与 async 端点的桥接（模块 docstring，`:1-16`）。

### 3.4 single-flight（`services/pipeline.py:1074-1092`）

相同缓存键的并发请求合并为一次真实计算：首个请求持 `threading.Event` 负责计算并在 finally 里 `_sf_release`，后来者等待复用结果；等待上限 `_SF_WAIT_S=30s`，超时自行执行——避免等待者占满线程（`services/pipeline.py:1076`）。与语义缓存的关系：single-flight 合并「正在进行」的相同计算，缓存复用「已完成」的结果，两道互补（缓存 → `05-检索链路.md`）。

### 3.5 读写锁与 BM25 并发（`core/rwlock.py`）

BM25 的 scorer 构建完成后不可变（重建是整体替换而非原地修改），读者之间本不需要互斥；此前一把 `Lock` 让**所有关键词检索互相串行**，QPS 上限被钉死在 `1/单次打分耗时`。现在用写者优先的读写锁：读共享 / 写独占，且读请求持续到来不会饿死写者（索引更新被无限推迟比单次查询多等更严重）（`core/rwlock.py:1-23`、`:28-35`）。GIL 让纯计算并行收益有限，但真实瓶颈是 IO 与锁等待，改并发后 QPS 上限由「核数 × 单次耗时」决定。

### 3.6 上游隔离仓（`services/upstream.py`）

> 注意：本模块实际位于 `services/upstream.py`（部分旧资料误标 `core/upstream.py`）。

- **信号量隔离**：每类上游独立许可数，慢上游不拖死快路径（`services/upstream.py:30-63`）。
- **熔断状态机**：`closed → open → half_open`——窗口 `window` 次内失败率 ≥ `fail_ratio` 打开 `open_seconds`；open 期间 `acquire` 立即抛 `CircuitOpenError`（不占线程、不等超时）；到期后半开，`half_open` 次探测**全成功**才闭合并清空窗口，任一失败重新打开（`services/upstream.py:66-112`、`:116-131`）。
- **AIMD 自适应并发（可选，默认关）**：连续 50 次成功 +1，失败 ×0.7，在 [1, permits] 间伸缩；`upstream_adaptive` 开启才生效（`services/upstream.py:82-91`、`core/config.py:264-265`）。
- **NullBulkhead**：未配置该上游许可时直通零开销，不改变既有行为；许可为 0 的上游不进注册表（`services/upstream.py:166-183`、`:200-209`）。
- 熔断与许可参数（window=20 / fail_ratio=0.5 / open_s=30 / half_open=3）集中读取于 `configure_bulkheads`（`services/upstream.py:192-215`、`core/config.py:260-263`）。

## 四、线程池边界与嵌套死锁防护

| 池 | 大小 | 纪律 | 代码位置 |
|---|---|---|---|
| 问答执行器 | 32 | 问答路径独占；管理面 / 探针仍走 AnyIO 默认池，互不抢占 | `services/pipeline_executor.py:37-47`、`:5-7` |
| 检索召回池 | 4 | **独立小池，不得复用问答执行器**：`search_multi` 在管线线程内被调用，同池会在池满时形成「线程等自己池」的嵌套死锁 | `services/retrieval/hybrid.py:23-26` |
| Agent run 池 | 默认 8（装配期可注入） | **必须与工具池分离**：图线程等待工具 future，同池死锁 | `services/agent/runner.py:165-167` |
| Agent 工具池 | 装配注入 | 单步工具超时独立（第三层熔断） | `services/agent/tools.py:689-700` |
| ASR 分片池 | 4 | 再高只会加剧平台限流 | `core/config.py:74` |

通则：**凡「在等待结果的同时还要向同一池提交任务」的结构，必须拆池**。每个嵌套点都在代码里写了注释锚点，改动前先搜「死锁」。

## 五、容量模型

配置注释给出了基准口径：**真实模型 8s/req 时，32 在飞 ≈ 4 QPS 承载（Little's Law）**（`core/config.py:249-250`）。

估算步骤（给定目标 QPS 与平均请求时长 L 秒）：

1. 在飞需求 = QPS × L（Little's Law）。例：目标 4 QPS、L=8s → 32 在飞，正好打满执行器。
2. 校验上游许可：一次问答平均占用 llm 许可 ≈ L 中的 LLM 时长比例 × 在飞数；`upstream_llm_permits=12` 意味着 LLM 段平均并发超 12 就开始排队等许可。
3. 校验硬约束：四类上游许可之和（当前 26）必须 ≤ `pipeline_workers`（32）（`core/config.py:255`）。
4. 校验限流面：单租户令牌桶 refill 60/min ≈ 1 QPS——单租户压不到执行器上限，容量是多租户合计出来的。
5. **真实上限是上游模型配额**（平台 QPS / 日 token 预算）：本机线程与许可都够时，上游限流先成为瓶颈。扩容（加 worker / 加许可 / 加副本）前先按上游配额核算，否则只是把等待从本机队列搬到上游超时。

| 层 | 饱和时的表现 | 观测 |
|---|---|---|
| 令牌桶 / 配额 | 429 占比上升 | `kquery_shed_total{reason}`、429 计数 |
| 问答执行器 | 503 + Retry-After 5 | `kquery_inflight_requests` / `kquery_queue_depth` |
| Agent 闸门 | 429「并发已达上限」 | Agent 拒绝日志 |
| 上游隔离仓 | `CircuitOpenError` 或等许可 | `kquery_upstream_in_use` / `kquery_upstream_circuit_open` |
| 平台配额 | WARNING / 拦截（视配置） | `platform_quota` 探针与日志 |

## 七、多副本语义

部署形态与共享存储接线 → `13-部署与运维.md`；本节只列并发状态的副本语义。

| 状态 | 副本语义 | 机制 |
|---|---|---|
| 语义缓存 | Redis 精确跨副本共享；近似命中仅本副本 | `services/cache.py:233-240` |
| 令牌桶 | 有 Redis 则 Lua 原子共享桶；无则进程内 | `services/ratelimit.py:52-60` |
| 租户配额 | 有 Redis 则 ZSET 全局生效；无则进程内 | `services/security/quota.py:64-106` |
| 快问临时态 | Redis store（Fail-Open 降级内存） | `services/quickask.py:88-140` |
| 会话存档 / 成本账本 / 长期记忆 / Query 分析记录 / 校验历史 / 入库任务队列 | **仍是进程内或本地文件**（登记为缺口 G3，详见 §八） | 各模块本地落盘 |

为什么必须共享：不配 Redis 时每个副本各算一份，**实际放行量 = 配置值 × 副本数**——这是限流最常见的失效原因（`services/ratelimit.py:7-9`、`services/security/quota.py:9-10`）。所有 Redis 路径都是 Fail-Open：Redis 挂了降级为进程内语义，服务不中断。

## 八、边界与已知缺口

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G1 | 降级阶梯默认关闭（`degrade_ladder_enabled`）：按水位收缩改写 / CRAG 与低优先级流量的机制存在但未启用（N5：默认关闭） | `core/config.py:266-268` | 过载时只有「拒绝」没有「降配服务」 |
| G2 | AIMD 自适应并发默认关闭（`upstream_adaptive`） | `core/config.py:264-265` | 许可数静态，上游抖动期靠熔断兜底 |
| G3 | 进程内状态清单：会话存档、成本账本、长期记忆、分析记录、校验历史、入库任务队列均不跨副本 | `services/agent/cost.py:9-13`、`query/analysis_store.py:17` 等 | 多副本下这些状态按副本分裂；扩副本前需逐域确认 |
| G4 | 令牌桶与配额按租户而非按用户：共享账号下用户级公平性不可控 | `services/ratelimit.py:1-9`、`services/security/quota.py:1-10` | 单用户可占满整个租户的桶 |
| G5 | SSE 桥接的 cancel 是协作式：已发出的上游调用无法中断 | `services/pipeline_executor.py:152-155` | 客户端断开后上游费用仍发生 |
| G6 | BM25 打分是纯 Python CPU 计算，读写锁解决互斥但 GIL 下并行收益有限 | `core/rwlock.py:21-23` | 超大语料下关键词路可能成为 CPU 热点 |
| G7 | 问答执行器等待 deadline 30s 超时返回 False 与队列满返回 False 走同一拒绝路径，调用方无法区分「等超时」与「根本没排上」 | `services/pipeline_executor.py:58-79` | 排障时两类拒绝混在一起（均计入 `rejected_total`） |
