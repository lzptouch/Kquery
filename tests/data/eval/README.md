## 1. 为什么要这一层

台账里的最大缺口 S1/KQ-09：**没有金标集 → recall@k 无从测量 → 参数无法调优 →
CRAG 阈值无法标定 → ReAct 不敢默认开**。所有检索侧的优化都卡在这一个前提上。

指标算错比指标缺失更危险（错的数字会被用来做参数决策），所以指标实现放在
`backend/app/services/evaluation/`，纯函数、零依赖，每个都有可手工验算的单测
（`backend/tests/unit/test_eval_metrics.py`）。

## 2. 文件清单

| 文件 | 说明 |
|---|---|
| `queries.jsonl` | **真实金标集**：120 条问题（指向 `corpus/` 的真实文档）；带 `question_type` / `difficulty` / `requires_vision` / `tags` |

| `queries.sample.jsonl` / `qrels.sample.tsv` / `runs.sample.jsonl` | 早期**构造样例**（框架自检用，不代表真实召回） |
| `baseline.json` | 基线报告（CI 回退门禁的比较基准） |
| `report.local.json` | 最近一次本地评测报告 |
| `corpus/*.md` | 语料快照（**冻结**：源文档改动不会影响 chunk_id） |
| `../scripts/eval/run_eval.py` | 运行器（`--mode file / local / live`） |
| `../scripts/eval/build_goldset.py` | 手写 20 条金标的生成脚本（按答案短语定位 chunk_id） |
| `../scripts/eval/build_goldset_ext.py` | **扩容脚本**（`EV-01`）：生成 19 篇语料 + 100 条查询与标注 + 60 条问答金标（幂等，基准集单独存放） |
| `rubric.v1.json` | **评分标准**（`EV-02`）：五维 + 权重 + 关键维度 + 通过线；**加载即校验**（权重和必须为 1） |
| `judge_report.json` | **生成侧判定报告**（`EV-03`）：带 rubric 版本 + 维度分 + 通过率 + 低置信计数 + 归因桶 |
| `../scripts/eval/run_eval.py` 的 `--rubric` / `--judge` | 生成侧判定入口：`--judge none`（默认，跳过并写明原因）/ `--judge heuristic`（CI 安全的**启发式**判定，**非模型判定**） |

`grade` 语义（写死，不允许"感觉相关"）：

- `2` = 该块**独立足以回答**该问题（能逐句指认答案出处）
- `1` = 相关但不足以独立回答
- `0` = 不相关

## 3. 三种运行模式

```bash
# ① 本地离线（零外部依赖，CI 与日常复算用）
python scripts/eval/run_eval.py --mode local \
  --queries backend/data/eval/queries.jsonl --qrels backend/data/eval/qrels.tsv \
  --runs backend/data/eval/runs.local.jsonl --out backend/data/eval/report.local.json

# ② 离线打分（只算指标，不重跑检索）
python scripts/eval/run_eval.py --mode file \
  --runs backend/data/eval/runs.local.jsonl --qrels backend/data/eval/qrels.tsv

# ③ 回退门禁（相对基线劣化 > 2pp 即失败）
python scripts/eval/run_eval.py --mode file \
  --runs backend/data/eval/runs.local.jsonl \
  --baseline backend/data/eval/baseline.json --max-drop 0.02

# ④ 线上采集（真实模型 + 真实 embedding，需要后端在跑）
python scripts/eval/run_eval.py --mode live \
  --base-url http://127.0.0.1:8100 --user admin --password '***'
```

### `--mode local` 的口径（**别把绝对值当线上结论**）

| 环节 | local 模式用的是 | 能否代表线上 |
|---|---|---|
| 关键词路 | **真 BM25**（与生产同一实现） | ✅ 能 |
| 语义路 | mock embedding（特征哈希词袋） | ❌ **不能**——真实 embedding 的语义召回会强得多 |
| 融合 / 精排 | 与生产同一实现（RRF k=60 / 候选池 20 / 重排） | ✅ 能 |

所以 local 模式适合回答"**分路贡献多少、并集上限在哪、缺口卡在哪一环**"，
不适合回答"线上 recall 是多少"。后者要用 `--mode live`。

## 4. 金标集怎么维护

- **标注由脚本生成**（`build_goldset.py`）：按"答案所在段落的判定短语"定位 chunk_id，
  避免手抄 id 抄错（抄错的 id 会让 recall 变成"看起来有数字、实际是错的"）。
  新增问题 = 在 `SPEC` 里加一行（问题 + 语料文件 + 判定短语 [+ grade1 短语]）。
- **判定短语必须唯一命中一个块**，否则脚本直接报错（不会猜）。
- 语料是快照：源文档改动**不会**影响标注；要更新语料就重新拷一份并重跑脚本 + 重标。

## 5. 第一份真实数字（2026-11-12，**基于 20 条** / 444 块）

> ⚠️ **历史结论口径**：本节的全部数字基于 **20 条**金标，
> 样本量小、差异的置信度有限。**扩容后（120 条 / 463 块）的数字见 §五之二**，
> 两组数字**不可直接比较**（语料与题量都变了）。

| 指标 | k=5 | k=10 | k=20 |
|---|---|---|---|
| recall | 0.65 | 0.75 | 0.75 |
| nDCG | 0.5492 | 0.5816 | 0.5816 |
| 分路 recall（keyword） | 0.70 | 0.775 | 0.875 |
| 分路 recall（vector，mock） | 0.575 | 0.675 | 0.775 |
| **并集上限（候选池口径）** | — | **0.925** | — |
| 融合可买空间（上限 − 实际） | 0.275 | **0.175** | 0.175 |

MRR = 0.5389；缺口归因：未召回 2 / 召回未进融合 2 / 进融合未进最终 2（20 条中）。

### ⚠️ 2026-11-12 更正：此前"融合只吃掉 5pp"的结论**是错的**

旧口径把并集上限算成「**各路 top-k 的并集**」（0.80），那不是融合候选池的天花板。
候选池 = 各路**完整**候选的并集（每路 up to per_route_top_n=20），正确的天花板是 **0.925**。
于是"融合还能买的空间"是 **17.5pp**（0.925 − 0.75），不是 5pp。
旧口径甚至会出现"空间 = 负数"的自相矛盾（见 §8 的评测指标口径说明）。

### 修正后的结论（这才是"有数字"的意义）

1. **融合/精排是主要瓶颈**：天花板 0.925 vs 实际 recall@10 0.75 → 空间 **17.5pp**。
   RRF / 精排的排序与候选池切分把约 17.5% 的答案挡在了最终 Top-K 之外 —— 这比"加路"
   的潜在收益大得多，**优先动融合与精排**（加深候选池、调 RRF/精排、放宽截断）。
2. **未召回只有 7.5%**：天花板 0.925 → 池外（任何一路都没捞到）只有约 7.5%。
   加一路召回的边际收益 ≈ 这 7.5%，**小于**修融合/精排的 17.5%。
3. **加深候选在 top-10 之前有效、之后无效**：recall@5 → @10 涨 10pp，@10 → @20 不涨；
   但**分路** recall@20 还在涨（keyword 0.775 → 0.875）——涨的是被**融合池 20** 截断的部分。
   → `per_route_top_n` 与 `fused_top_n` 要**一起**加，只加一个不会进最终 Top-K。
4. **关键词路当前强于向量路**（0.775 vs 0.675）——但**这条不能当结论**：
   向量路跑的是 mock embedding。真实 embedding 下这个差距大概率会缩小甚至反转，
   必须用 `--mode live` 复测才能下判断。

## 五之三、生成侧判定（rubric / judge / 归因，2026-11-13）

检索指标只回答「答案块有没有进上下文」；**生成侧**回答「答案本身好不好」：

| 环节 | 文件 | 说明 |
|---|---|---|
| 评分标准 | `rubric.v1.json` | 五维 + 权重（正确性 0.40 / 引用忠实性 0.25（**关键维度**）/ 完整性 0.15 / 简洁性 0.10 / 拒答正确性 0.10）；加权通过线 0.75，关键维度下限 0.8 |
| 判定器 | `services/evaluation/judge.py` | `ModelJudge`（3 票 → 逐维度中位数；一致性取**最小值**）；`HeuristicJudge`（**CI 用**：确定性、非模型判定，报告标 `judge_kind: "heuristic"`） |
| 归因 | `services/evaluation/citations.py` | 引用抽取 + 支持性判定；五桶：`not_cited` / `misquoted` / `answered_wrong` / `correct` / **`unjudged`** |

跑法：

```bash
# 只看检索（默认）：生成侧「跳过」，报告会写明原因
python scripts/eval/run_eval.py --mode file --runs tests/data/eval/runs.local.jsonl

# 生成侧判定（CI 安全；启发式，不是模型判定）
python scripts/eval/run_eval.py --mode file --runs tests/data/eval/runs.local.jsonl \
    --judge heuristic --rubric tests/data/eval/rubric.v1.json
```

> **三条口径纪律**：
> 1. **「跳过」≠「质量为 0」**——报告里必须写明原因；
> 2. **不同 rubric 版本的分数不可比**——报告带 `rubric_version`；
> 3. **`heuristic` 必须标清身份**——它不是模型判定，拿它当「模型答得好不好」的证据就是自欺欺人。

## 五之四、策略对比的统计显著性（2026-11-13）

扩容后的 120 条金标上，**`recursive-800-100` 显著优于当前默认 `recursive-300-50`**：

| 指标 | 值 |
|---|---|
| nDCG@10 差值 | **+0.048**（0.836 → 0.884） |
| 95% 置信区间 | **[0.012, 0.090]**（不含 0 → 判显著） |
| p 值 | 0.006 |
| 样本量 | 110（配对：同一批查询的两个策略） |
| 块数 | 463 → **172**（embedding 与存储成本同步下降） |

> **口径**：配对 bootstrap（对**同一批查询**的逐条差值重采样，固定 seed 可复现），
> 纯 Python 实现、**零新依赖**。**样本量 < 30 不判显著**（标「样本不足」）。
> 显著性**只用于同一批查询上的两个方案**，不用于跨语料比较。

> **默认切块策略本轮未改**：设计稿「先扩语料再改默认」的前置条件已满足，
> 但改默认会改变线上检索行为，属于需要显式决策的事项，不该由一次实验顺手带过。

## 五之五、成本-质量曲线与帕累托前沿（2026-11-13）

`scripts/eval/cost_quality.py` 把「质量」与「成本」放在一张表上，
并给出**帕累托前沿**（不存在另一套策略**既更便宜又更准**）：

| 策略 | 成本代理 | recall@10 | nDCG@10 | precision@10 | hit_rate@10 |
|---|---|---|---|---|---|
| `recursive-300-50`（当前默认） | 91525 | 0.9545 | 0.8360 | 0.1255 | 0.9636 |
| `recursive-800-100` | **63447** | **1.0000** | **0.8840** | **0.1291** | **1.0000** |

**帕累托前沿只含 `recursive-800-100`**——它在每个维度上都不劣于默认，且成本低 31%。

> **成本口径是代理量**（embedding token 估算 + 块数 × 100），用于**相对比较**，
> 不用于报价（真实账单看 `services/agent/cost.py` 的账本）。

> **两个新指标的口径**：`precision@k` 的分母是 **min(k, 实际候选数)**——
> 检索只召回 3 条时除以 10 会把「候选池不够」算成「模型不准」；
> `hit_rate@k` 是**用户视角**的「答得上吗」（至少命中一个金标）。

## 6. 切块策略实验（2026-11-11）

**问题**：默认 `chunk_size=300 / overlap=50` 是不是最好的？

**做法**：对每套策略用**生产的切块工厂**（`apply_chunk_policy`）切同一语料 →
装配同一套检索栈 → 用**同一份标注**打分。标注存的是**内容锚点**（不是 chunk_id），
所以换切块方式后标注依然有效——这正是"切块策略哪个更好"能被回答的前提。

| 策略 | 块数 | recall@5 | recall@10 | nDCG@10 | MRR | 并集上限（候选池） |
|---|---|---|---|---|---|---|
| parent_child-1200-200-40 | 736 | 0.55 | 0.675 | 0.4694 | 0.4019 | 0.85 |
| raptor-4-3 | 464 | 0.65 | 0.80 | 0.5808 | 0.5189 | 0.925 |
| **recursive-300-50（当前默认）** | 444 | 0.65 | 0.75 | 0.5816 | 0.5389 | 0.925 |
| recursive-500-100 | 265 | 0.775 | 0.90 | 0.7517 | 0.7556 | 0.975 |
| **recursive-800-100** | **153** | **1.00** | **1.00** | **0.8587** | 0.835 | **1.00** |
| semantic-0.4 | 623 | 0.575 | 0.675 | 0.5060 | 0.4731 | 0.675 |

### 结论

1. **默认切得太碎**：块放大到 800/100 后 recall@10 0.75 → **1.00**、nDCG@10 +0.28，
   而**块数反而从 444 降到 153**（块更少、召回更好）——300 字符的块把一个语义单元切散了，
   答案被切到两个块里，任一块都不足以独立回答。
2. **semantic 与 parent_child 更差**（0.675，低于默认 7.5pp）："边界更语义"没有转化为检索收益，
   反而因为块数暴涨（623/736）稀释了候选池。**更聪明的切块 ≠ 更好的检索**。
3. **raptor 略优但性价比差**：recall@10 0.80 vs 0.75，代价是额外的摘要 LLM 调用 + 块数不降。

### 这组数字的边界（必须一起读）

| 局限 | 影响 |
|---|---|
| 语料是 4 篇**有明确章节标题**的 markdown | 大块能完整覆盖一个语义单元 → 结论对"章节清晰的长文档"成立；**对段落密集/表格/代码可能不成立** |
| 向量路是 **mock embedding** | semantic 切块的优势恰好依赖语义能力；真实 embedding 下它的表现可能反转 → 必须 `--mode live` 复测 |
| 只有 20 条问题 | recall 0.75 → 1.00 意味着救回 5 条；样本量小，差异的置信度有限 |
| 未测**答案跨越两个块**的情况 | 当前标注的锚点都在单块内；切块边界正好切在答案中间是最难的情况，未被覆盖 |

### 下一步（改默认参数前必须做）

1. 语料扩到"难切"类型（表格 / 代码 / 无标题长段落 / 扫描件）；
2. `--mode live` 复测（真实 embedding），特别是 semantic 与 raptor；
3. 补"答案跨块"的标注类型；
4. 再决定是否把默认改成 500/100 或 800/100（**先扩语料再改默认**，否则是把 20 条问题的结论当普适结论）。

复跑实验：

```bash
python scripts/eval/chunk_experiment.py            # 全量预设
python scripts/eval/chunk_experiment.py --policies recursive-500-100,recursive-800-100
```


## 7. 多模态（图文）语料与评测（2026-11-12）

**语料**：`corpus_img/` —— 12 张真实开源图片（scikit-image，BSD-3-Clause）+ 3 份开源 README
（Pillow / matplotlib / scikit-image）+ 12 份**逐张看图人工核对**的图注。
来源与许可见 `corpus_img/SOURCES.md`。

**为什么要有图文语料**：文本金标集只测"文搜文"。图文链路（图像描述块入库、以文搜图、
图文混排绑定、原图回显）需要一套**带图**的语料才能被评测覆盖，否则它只能靠单元测试证明"能跑"，
不能证明"找得对"。

**数字**（16 条问题，本地复算，mock embedding）：

| 指标 | k=5 | k=10 | k=20 |
|---|---|---|---|
| recall | 1.00 | 1.00 | 1.00 |
| nDCG | 0.9375 | 0.9375 | 0.9375 |
| MRR | 0.9167 | | |

并集上限（候选池）= 1.0。图文语料的检索**没有缺口**——因为它是干净的：
每个图问题都有一块明确的图注（四段式描述），且语料量小（81 块）。
这组数字的作用是**回归基线**（改动图文链路后不允许它下降），不是"效果有多好"的证明。

**两个口径要点**：
1. 图注是**本项目自写**（四段式，与生产 `ImageIndex` 的 caption 同构），
   所以图问题的答案块在语料里真实存在；生产里它由 VLM 生成。
2. mock embedding 只能验证"图文检索的结构与回归"，**不能**验证真实图像向量（M1）的效果。

## 8. 对抗题集（必须看原图）与「文本可答性」指标（2026-11-12）

**动机**：常规图文题（§7）问的是"图注里写了什么"——文本路也能答。
要证明**跨模态能力**（M1 图像向量路 / M5 VLM 直答）的价值，
得有一组**答案不在图注里**的题。

### 11 道对抗题（`queries_adv.jsonl` + `qrels_adv.tsv` + `corpus_img/annotations/`）

问的是**只有看原图才知道**的细节：数量、方位、颜色、局部结构。例如：

| 图 | 问题 | 期望答案 |
|---|---|---|
| rocket | 一共有几座发射塔架？ | 四座 |
| brick | 砖块是横着铺还是竖着铺？ | 竖着铺 |
| coffee | 杯子的把手在哪个方向？ | 左下方 |
| retina | 血管汇聚的亮斑是什么颜色？ | 黄白色 |
| astronaut | 手臂上的臂章是什么颜色？ | 蓝白色 |

### 新指标：文本可答性（`text_answerable_rate`）

**recall 只说明"找没找到那张图"，不说明"文字里有没有答案"。**
所以把两件事分开量：

| 维度 | 含义 | 对抗集实测 |
|---|---|---|
| 检索前提（recall@10） | 能不能把正确的图捞出来 | **1.00** |
| **文本可答性** | 目标块（图注）里有没有答案关键词 | **0.00** |

**读法**：这 11 道题**全部**必须看原图（文本可答性 0），
而系统**每次都能把正确的图找出来**（recall 1.0）。
→ 结论：**瓶颈不在"找图"，在"看图"**——正是 M5（VLM 直答）要解决的那一环，
也是 M1（图像向量路）能贡献增量的地方。

### 这个不变量必须被守住

"答案不在图注里"是这组题的全部意义，一旦有人把图注写详细了
（或把答案关键词泄进图注），题目就退化成普通题、这个数字就是假的。
守卫：`tests/unit/test_multimodal_corpus.py::TestAdversarialVisionSet`
—— 逐条断言答案关键词**不在**该题图注里，并断言评测跑出来的
`text_answerable_rate == 0`。

> 口径注意：可答性只看**该题的目标块**，不看检索到的全部文本
> （别的图的图注里出现同一个词，不代表这道题能从文字里答出来）。
> 另外 `图文混排.md` **刻意放在 `demo/` 而不是语料目录里**：
> 它把 12 份图注聚在一个文档里，检索到它 = 一次性看到所有图注 → 答案关键词泄漏。

## 9. 评测指标的口径（`metrics.py`）

| 指标 | 口径 |
|---|---|
| recall@k / nDCG@k / MRR | 标准检索指标（按**解析后的**答案块） |
| 分路 recall@k | 每一路单独能召回多少（判断"值不值得加一路"） |
| **并集上限（候选池）** | **各路完整候选的并集**能召回多少 —— 召回策略的理论天花板。⚠️ 不是"各路 top-k 的并集"（那会低估天花板，得出负数空间） |
| 融合可买空间 | 上限 − 实际 recall@k |
| 缺口归因 | 未召回（池外）/ 召回未进融合 / 进融合未进最终 |
| **文本可答性** | 目标块里有没有答案关键词（0 = 必须看原图） |
| 按题型分组 | `by_kind`：text / vision 两组的 recall、nDCG |
