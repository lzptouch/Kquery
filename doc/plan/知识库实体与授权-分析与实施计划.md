## 〇、摘要

1. **现状**：Kquery 没有「知识库」实体——全部文档是 `data/metadata.json` 里的扁平 `DocumentRecord` 集合（`backend/app/services/knowledge.py:71`），`DocumentRecord` 无 `knowledge_base_id`/`owner`/`created_by`（`backend/app/domain/schemas.py:15-37`）。全仓 grep `knowledge_base|kb_id|kb_access|corpora|librar` 在 `backend/app` 与 `frontend/src` **0 命中**。
2. **现有的相邻能力**：完整的多租户闸门 + 文档级 ACL（`backend/app/services/security/acl.py`，判定树 5 步、deny 优先、影响人数反查、风险分级、检索前下推 + 检索后过滤）。这套机制是 KB 授权的直接迁移模板。
3. **对标结论**（ima）：知识库是文档的**强容器**，权限是「库级角色 + 库级开关 + 内容级细粒度」三层叠加。Kquery 目标场景是**管理员主导的企业内授权**（非 ima 的协作共建），故借鉴其「库级授权 + 内容级收紧」模型，不借鉴「协作成员自管理/访客额度/广场分发」（对标文档 §五）。
4. **核心设计**：新增 `knowledge_bases.json`（KB 实体）+ `kb_grants.json`（KB↔用户授权）两个存储；**仅 `DocumentRecord` 加 `knowledge_base_id`（`Chunk` 不加）**；检索过滤从「tenant ∩ doc-ACL」扩展为「tenant ∩ KB 授权 ∩ doc-ACL」三层，**KB 判定合并进 `acl_filter_of` 的兜底闭包**；判定树照抄 ACL 的「租户闸门 → deny 优先 → allow → 库公开 → 默认拒绝」。
5. **改造规模**：后端 20 个文件（新增 4 个）约 +1200 行；前端 9 个文件（新增 3 个）约 +800 行；测试 3 个新文件约 +670 行。无新增依赖。
6. **最大风险（初版判断已修正）**：~~Milvus schema 丢向量~~ **已消除**（方案 B 不给 Milvus 加字段）。真正的头号风险变成 **KB 闸门落到错误的过滤路径 → 降级时确定越权**（X9），其次是 **撤权后缓存仍命中**（X3）。两者都已有明确改点与守护用例（T-I13/T-I14/T-I15）。
7. **默认语义决策**：存量文档自动归属默认 KB（`kb_id="default"`）且默认 KB 对全员可见——**与现有「文档默认租户内公开」语义保持一致**（`schemas.py:37` `acl_public: bool = True`），不做 ima 的「默认私密」，避免升级后现有用户大面积失访。

### 1.2 现有的文档级 ACL（迁移模板）

判定树（`backend/app/services/security/acl.py:81-100`，短路顺序不可换）：

```text
1. 租户不匹配 → 拒绝（跨租户一律不可见）
2. 命中 deny 名单 → 拒绝（deny 优先于 allow）
3. 命中 allow 名单（user:/role:/group: 并集）→ 放行
```

## 二、需求定义

### 2.1 目标需求（用户原话）

> 「管理员可以控制某一些用户可以使用哪些知识库；知识库中包含多个文档的内容。」

拆解为可验收的能力清单：

| # | 能力 | 验收标准 |
|---|------|---------|
| R1 | KB 实体 | 可创建/改名/描述/删除知识库；KB 是文档的上位容器；空库可存在（对标 M1） |
| R2 | 文档归属 KB | 上传文档时可指定 KB；文档详情/列表显示所属 KB；文档可在 KB 间移动 |
| R3 | 按用户授权 KB | 管理员可把某 KB 授予某些用户（含撤销）；未授权用户在检索与问答中**完全不可见**该库内容 |
| R4 | 授权即生效于检索 | 检索/问答的可见范围 = 租户 ∩ KB 授权 ∩ 文档 ACL（三层交集） |
| R5 | 管理界面 | 管理区新增「知识库管理」页：KB 列表 + 授权面板；用户管理页可看「该用户能用哪些 KB」 |
| R6 | 授权操作可审计 | 每次授予/撤销写 `admin.action` 审计，含影响人数与风险分级（照 ACL 先例） |
| R7 | 存量平滑迁移 | 现有文档自动归属默认 KB，默认 KB 全员可见，升级后行为不回归 |

### 2.2 非目标（明确不做）

| # | 不做 | 理由 |
|---|------|------|
| G1 | 库内角色阶梯（创建者/管理员/协作成员/普通成员） | Kquery 是**管理员主导**模型（文档管理全在 `require_role("admin")` 下），协作共建是 P2 以后的事 |
| G2 | 用户自助申请加入 KB | 管理员显式授权即可，申请流引入通知/审批两套新机制，超范围 |
| G3 | 访客问答额度 | 与「未认证不可用」安全模型冲突（对标 N3） |
| G4 | 一文档多 KB | 复制语义引入一致性问题（一处改多处同步）；一文档一 KB + 移动操作覆盖需求 |
| G5 | KB 内文件夹 | 文档级 ACL 已提供内容级收紧；文件夹是纯组织视图，P2 |
| G6 | 公开发布/广场 | 企业私域场景（对标 N2） |
| G7 | 角色↔KB 授权（`role:hr` 粒度授权 KB） | 首版只做**用户粒度**（`user:xxx`）；角色粒度复用 ACL 身份表达式机制即可后置扩展 |

| 能力 | ima | Kquery 现状 | 差距 | 本计划落点 |

| KB 独立实体（先建库再装文档，M1） | ✅ 5 秒建空库 | ❌ 无 KB 实体 | **缺失** | §五 数据模型 |
| 文档归属 KB 且可迁移（F3） | ✅ 个人库→共享库搬运 | ❌ 无归属字段 | **缺失** | §五 `DocumentRecord.knowledge_base_id` |
| 库级授权（成员制） | ✅ 邀请+角色 | ⚠️ 仅文档级 ACL | **粒度错配** | §四 授权模型 |
| 权限管理总开关面板（M3） | ✅ 「···」→权限管理 | ⚠️ ACL 弹窗仅单文档 | **部分** | §八 前端 KbPage |

## 四、概念模型与授权语义设计

### 4.1 实体关系（目标态）

```text
tenant（租户，硬隔离，不变）
 └─ KnowledgeBase（知识库）×N
 │    ├─ kb_id / name / description / is_public / created_by / created_at
 │    └─ Document ×N   ← DocumentRecord.knowledge_base_id（一文档一 KB）
 │         └─ Chunk ×N ← **不加 KB 字段**（方案 B：KB 过滤在应用层完成，
 │                       避免 Milvus schema 变更，见 §4.4）
 │
 └─ KbGrant（授权关系）×N
      └─ { kb_id, user_id, granted_by, granted_at }   ← 用户粒度（G7：角色粒度后置）
```

### 4.2 关键设计决策（每个决策给理由）

| # | 决策 | 选择 | 理由 |
|---|------|------|------|
| D-1 | 文档↔KB 基数 | **一文档一 KB** | 多对多引入「一处改多处同步」与「删除语义分叉」；ima 的「搬运」实测语义不明（对标 §七-3），一文档一 KB + 移动操作即可覆盖「换库」诉求 |
| D-2 | 授权粒度 | **用户粒度**（`user:xxx`） | 需求原话是「控制某些用户」；角色粒度复用 ACL 身份表达式机制后置（G7） |
| D-3 | 授权模型 | **管理员显式授权**（无申请流） | 与现有「文档管理全在 admin」的收敛模型一致；ima 的协作共建是另一套产品形态 |
| D-4 | 默认可见性 | **默认 KB 全员可见**（`is_public=true`） | 与现状 `acl_public=True` 语义对齐（P1 坑）；新建 KB 默认 `is_public=false`（白名单），符合「管理员授权」直觉 |
| D-5 | 与文档 ACL 的关系 | **叠加取交集**：先 KB 授权过滤，再文档 ACL 过滤 | KB 是「能不能进这个门」，文档 ACL 是「进门后能不能看这个柜」；deny 永远优先的判定树不变 |
| D-6 | 快问路径 | **不受 KB 约束** | 快问文档不入库（`quickask.py:199-211` 独立 new，不写 metadata.json），现有注释已明确「ACL 不适用于临时文档」（`pipeline.py:385`），KB 同理 |
| D-7 | KB 删除语义 | **有文档拒绝删除**（非级联删） | 级联删文档 + 向量是灾难级误操作；空库才允许删除，强制管理员先清空 |
| D-8 | 灰度开关 | `kb_enabled`（默认 **true**） | 见 §七风险：Milvus schema 必须变，无法做到「代码改了但行为不变」；开关用于回滚语义而非回滚 schema |
| D-9 | `doc_id` 不变 | KB 字段**不进 doc_id** | `doc_id` 进 `chunk_id`、历史引用、ACL 键，改了就断链（勘察结论 A-2） |

### 4.3 KB 授权判定树（照抄 ACL 五步法）

```text
输入：principal（身份四要素）、kb（目标知识库）
1. 租户不匹配（kb.tenant_id != principal.tenant_id）→ 拒绝
2. kb 不存在 → 拒绝（防探测：与「无权限」同文案）
3. 命中 kb_grants[kb_id] 的 user_id 集合 → 放行
4. kb.is_public == true → 放行
5. 默认拒绝
```

与 ACL 判定树的差异：无 deny 名单（KB 层首版不做拉黑，拉黑走用户 `enabled=false`）、allow 只有 user 粒度（G7）。

### 4.4 检索可见范围公式

```text
现状：可见文档 = { d ∈ 全部文档 | tenant 闸门 ∧ doc_ACL(principal, d) }
目标：可见文档 = { d ∈ 全部文档 | tenant 闸门 ∧ KB授权(principal, d.kb_id) ∧ doc_ACL(principal, d) }
                = { d ∈ （本租户 ∩ 可见KB集合 的文档） | doc_ACL(principal, d) }
```

实现上等价于：**先按 KB 授权算出可见 KB 集合 → 展开为该集合内的 doc_id 集合 → 与现有 `visible_doc_ids` 取交集**。这样 `to_milvus_expr` 无需新增 `knowledge_base_id in [...]` 段（doc_id 集合已经表达了一切）。

### 4.4.1 落地位置修正（2026-10-27 代码核对后）

> **本方案最初的落点是错的，必须修正。** 检索链路上有**两条独立的过滤路径**，只改其中一条会让 KB 闸门在降级时完全失效：
>
> | 路径 | 入口 | 判定来源 | 触发条件 |
> |------|------|---------|---------|
> | **下推（快路径）** | `pipeline.py:360-394` `_build_filters` | `self._visible_docs_provider`（`pipeline.py:171-179`） | 仅在可见清单可低成本枚举时生效 |
> | **后过滤（安全底线）** | `pipeline.py:440-457` `_visible_candidates` | `self._acl_filter` 闭包（`dependencies.py:81-94`） | **无条件生效** |
>
> 只要 provider 返回 `None`（文档数 > 5000、`knowledge.list_files()` 抛异常、ACL/KB 服务未装配），下推就退化为 **tenant 粗过滤**，此时**唯一**的权限闸门是后过滤那条线。
>
> 而现有代码里 `_visible_candidates` **只调 `acl_filter(doc_id)`**（`pipeline.py:451`），不看 provider。若把 KB 判定只加在 provider 上：
>
> ```text
> 私有 KB 的文档（acl_public=True，文档 ACL 放行）+ 未授权用户
> → provider 返回 None（清单过大）
> → Milvus 只按 tenant 过滤，返回该文档的块
> → 后过滤只查 ACL → 放行
> → 越权命中
> ```
>
> 因默认语义下 `acl_public=True`（`schemas.py:37`），文档 ACL 对多数文档**恒为放行**，KB 实际是唯一闸门 —— 这个漏洞会是**默认路径上的确定越权**，不是边界情况。
>
> **正确落点**：把 KB 判定合并进 `acl_filter_of` 返回的 `check(doc_id)` 闭包（`dependencies.py:81-94`）。理由：
> 1. 后过滤与下推**两条路径同时获得 KB 闸门**（`_visible_candidates` 与 `_build_filters` 都消费同一个闭包语义）；
> 2. 闭包内已有 `__` / `quick_` 前缀豁免（`:82-85`），KB 判定天然继承「系统内置块与快问临时文档不参与 KB 校验」，无需重复实现（D-6）；
> 3. `doc` 对象已在闭包内取得（`:89` `knowledge.get(doc_id)`），取 `doc.knowledge_base_id` 零额外成本；
> 4. 调用点零改动：`api/ask.py:190`、`api/quickask.py:110` 已把该闭包赋给 `scoped._acl_filter`。
>
> 同时 provider 也要做同一交集（否则下推清单含 KB 不可见文档，白白占用 top-k 名额，回到 `filters.py` 文件头描述的原始问题）。两处**必须同源**，见 §6.2。

### 4.4.2 方案对比（为什么选「KB→doc 展开」而非「Milvus 表达式加 kb 段」）

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. `to_milvus_expr` 加 `knowledge_base_id in [...]` | 表达式短；不依赖 doc 枚举 | Milvus schema 必须加字段（存量全丢）；`Chunk` 全链路加冗余字段；BM25/FAISS 的 `allows()` 必须扩签名（P2/P3 坑全踩） |
| B. KB 授权 → 展开为可见 doc_id 集合 → 并入现有 `visible_doc_ids` | **零 Milvus schema 变更**；不动 chunker；不动 `allows()` 签名；纯应用层 | 可见文档数受 5000 枚举上限约束（与现状相同，非新增约束） |

**选 B**。代价：KB 字段只在 `DocumentRecord`（元数据层）存在，不进 `Chunk`。检索过滤完全靠「KB→doc_id 展开」在应用层完成。**这把 §七最大的风险（Milvus drop collection）整个消掉了**。`Chunk.knowledge_base_id` 冗余字段列为**可选项**（仅当未来需要按 KB 做统计/运维直查向量库时再加）。

### 4.5 默认 KB 与存量迁移

- 首次启动（或升级后首次启动）若 `knowledge_bases.json` 不存在 → 创建默认 KB：
  `{ kb_id: "default", name: "默认知识库", description: "系统默认", is_public: true, created_by: "system" }`
- 存量 `DocumentRecord` 无 `knowledge_base_id` 字段 → Pydantic 默认值 `""` → 读取时归一化为 `"default"`（在 `KnowledgeService._load_metadata` 的加载循环里做一次性回填并 `_save_metadata()`，与「损坏即拒绝启动」的原子写同路径，`knowledge.py:108-126`）。
- **效果**：升级后所有存量文档在默认 KB 下全员可见，行为与升级前**逐位一致**（R7 验收标准）。

### 6.2 检索链路改造（方案 B，纯应用层）

**改点 A：KB 判定合并进 ACL 闭包（安全底线，必改）**

`backend/app/dependencies.py:66-96` `acl_filter_of`：

```python
def acl_filter_of(request: Request, principal: Principal):
    settings = request.app.state.settings
    if not settings.acl_enabled:
        return None
    acl = request.app.state.acl_service
    knowledge = request.app.state.knowledge
    # 新增：KB 服务与开关
    kb = getattr(request.app.state, "kb_service", None)
    kb_on = bool(getattr(settings, "kb_enabled", True)) and kb is not None
    memo: dict[str, bool] = {}

    def check(doc_id: str) -> bool:
        if doc_id.startswith("__"):      # 系统内置块：不属任何 KB，豁免（原有语义）
            return True
        if doc_id.startswith("quick_"):  # 快问临时文档：不受 KB 约束（D-6）
            return True
        if doc_id in memo:
            return memo[doc_id]
        try:
            doc = knowledge.get(doc_id)
        except Exception:
            memo[doc_id] = False
            return False
        # 先 ACL（原有），再 KB（新增）——两者都必须通过
        ok = acl.check(principal, doc)
        if ok and kb_on:
            ok = kb.check_doc(principal, doc)      # 内部读 doc.knowledge_base_id，空串归一化 default
        memo[doc_id] = ok
        return ok

    return check
```

要点：
- 函数名与签名**不变**（`api/ask.py:190`、`api/quickask.py:110` 的赋值点零改动）；
- `memo` 请求级记忆化保留，KB 判定与 ACL 判定共用一条缓存（同一文档只算一次）；
- `kb_enabled=false` 时 `kb_on=False`，**行为逐位退回现状**（D-8 灰度语义）；
- 空串归一化放在 `KBService.check_doc` 内（不污染 `DocumentRecord` 语义）。

**改点 B：下推清单与闭包同源（性能，必改）**

`backend/app/services/pipeline.py:155-182` `bind_principal` 的 provider 必须与闭包同源，否则会出现「下推清单含 KB 不可见文档 → 白占 top-k 名额」：

```python
# 现状 :171-177
def _provider() -> set[str] | None:
    docs = knowledge.list_files()
    return acl.visible_doc_ids(principal, docs)

# 改为（用同一个合并闭包枚举，两条路径判定必然一致）
def _provider() -> set[str] | None:
    docs = knowledge.list_files()
    if len(docs) > 5000:                  # 阈值与 acl.py:117-118 保持一致
        return None
    judge = self._acl_filter              # 闭包已含 ACL + KB 两道闸门
    if judge is None:
        return None
    return {d.doc_id for d in docs if judge(d.doc_id)}
```

> **前置依赖**：`bind_principal` 在 `api/ask.py:189` 调用，`_acl_filter` 在 `:190` 才被赋值 → provider 是**惰性求值**（首次检索时才执行），执行时 `_acl_filter` 已就绪。必须在代码注释里写明这一时序依赖，否则后续重构可能把 provider 改成立即求值而静默失去 KB 闸门。
>
> **替代方案（若不接受该时序依赖）**：保留 `acl.visible_doc_ids` 做 ACL 部分，再在 provider 内追加 `kb_service` 的交集 —— 需要 `main.py` 额外回填 `pipeline._kb_service = kb_service`。改动多一处，但时序依赖消失。**二者择一，不可两处都不做。**

**改点 C：`_build_filters` 快问分支不变**

`backend/app/services/pipeline.py:360-394`：`doc_id` 分支（`:381-386`）与 `_acl_filter is None` 分支（`:378-380`）**逻辑不变**（D-6：快问不受 KB 约束）。仅 provider 的内容变了（改点 B）。

**改点 D：缓存维度（安全，必改）**

`backend/app/services/pipeline.py:240-256` `_cache_dims` 的签名含 `"acl_version": self._acl_version()`（`:252`），而 `main.py:408` 是 `pipeline._acl_version = lambda: acl_service.version`。**KB 授权变更若不让这个版本变化，撤权后同一用户的旧答案仍会被缓存命中** —— 缓存命中路径完全跳过检索与过滤（`pipeline.py:249-251` 注释已说明这个风险）。

在功能落地后补了一轮「真浏览器点击输入」验证，产出 3 个新测试文件，并**抓出 1 个真实产品缺陷**：

|---|---|---|
| `backend/tests/e2e/test_all_endpoints.py` | 从 OpenAPI 自动枚举**全部 89 个端点**：逐个验证可达性（无 5xx）、统一信封契约、KB 端点注册与 admin 门禁、防探测文案 | 7 |
| `backend/tests/e2e_ui/test_ui_kb.py` | 知识库管理页真实点击/输入：新建 → 授权（勾选用户 + 输入库名二次确认 + 影响人数回显）→ 编辑 → 上传归属 → 用户页反查 | 6 |
| `backend/tests/e2e_ui/test_ui_admin_pages.py` | 12 个页面加载巡检（含 JS 错误捕获）+ 8 项管理交互（配额 / 敏感词 / 用户角色 / 检索配置 / 图谱 / 监控 / 审计 / ACL） | 21 |

**抓出的真实缺陷（已修）**：文档列表的「所属知识库」列展示的是 `knowledge_base_id`（机器 slug，如 `ui测试库97616`）而非 KB 名称——用户看到的是标识不是人读名称。修法：`KnowledgePage` 拉 `GET /admin/kb` 建 `kb_id → name` 映射后展示（`frontend/src/features/knowledge/KnowledgePage.tsx`）。该缺陷靠 API 层测试**无法发现**（响应里只有 id 是正确的），只有真实渲染页面才看得见。

**顺带修的既有缺陷**：`tests/e2e_ui/test_ui_knowledge.py` 的临时文件清理在 Windows 上因浏览器持有句柄抛 `PermissionError`（用例偶发红）；改为重试 3 次后忽略。

**方法论沉淀**（写给后续维护者）：
1. 选择器必须按 **role** 定位——状态标签「仅授权」与按钮「授权」文本同形，按文本定位会撞 playwright 的 strict mode violation；
2. 断言范围必须限定在**表格容器**内——目标知识库 `<select>` 的 `<option>` 文本也含库名，用 `body.innerText` 会立即为真（option 不可见），造成假通过；
3. `placeholder` **不进 `innerText`**——页面内容断言不能用 placeholder 当关键词；
4. 端点巡检的「跳过清单」要显式登记并设上限断言，防止为省事把端点全 skip 掉。
