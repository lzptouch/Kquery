# 04 部署与运维

## 1. 部署资产布局

所有部署相关文件都在 `deploy/`：

```
deploy/
├── docker/
│   ├── docker-compose.yml        # 全栈编排：etcd / milvus / redis / backend / init / frontend
│   ├── backend.Dockerfile        # 多阶段构建，构建上下文 = 仓库根
│   ├── frontend.Dockerfile       # 前端构建 + nginx 静态托管
│   └── frontend.nginx.conf       # 前端容器内的 nginx 配置（SPA 回退 + 前缀反代）
├── nginx/
│   └── nginx.conf                # 可选的统一入口反代（前后端同源部署时用）
├── k8s/
│   ├── base/                     # Deployment / Service / Ingress / ConfigMap
│   ├── overlays/                 # 环境差异化（副本数、资源、镜像 tag）
│   └── canary/                   # 灰度发布
├── milvus/
│   ├── docker-compose.yml        # 只起 Milvus + etcd（本地开发省资源）
│   └── user.yaml                 # Milvus 运行参数
└── prometheus-rules.yaml         # 告警规则（Prometheus rule_files 格式）
```

镜像构建命令（注意上下文是仓库根）：

```bash
docker build -f deploy/docker/backend.Dockerfile  -t kquery/backend:local  .
docker build -f deploy/docker/frontend.Dockerfile -t kquery/frontend:local .
```

## 2. 一键起全栈（Docker Compose）

```bash
cp backend/.env.example backend/.env      # 填入模型 API Key
cd deploy/docker
docker compose up -d --build
docker compose logs -f backend
```

### 2.1 端口

| 服务 | 宿主端口 | 容器端口 | 说明 |
| --- | --- | --- | --- |
| backend | 8100 | 8000 | HTTP / SSE |
| frontend | 8090 | 8080 | 静态站点 + 前缀反代 |
| milvus | 19531 | 19530 | gRPC（pymilvus） |
| milvus 健康/指标 | 9092 | 9091 | HTTP |
| redis | 6381 | 6379 | 缓存 |

> 宿主端口刻意用了非默认值（8100/8090/6381/19531），目的是避免与常见本地服务（8000、8080、6379、19530）冲突。如果这些端口在你的机器上空闲，改 `deploy/docker/docker-compose.yml` 的 `ports` 左侧即可，容器内端口无需动。

### 2.2 启动顺序

`backend` 依赖 `init` 完成建表后才启动（`depends_on.condition: service_completed_successfully`）。首次启动会看到 `init` 容器跑完退出，这是正常的；`init` 失败会让后端一直不启动，先 `docker compose logs init`。

### 2.3 数据卷

| 卷 | 内容 | 说明 |
| --- | --- | --- |
| `milvus-data` | 向量数据 | 删卷 = 丢索引，需重新入库 |
| `etcd-data` | Milvus 元数据 | 与 milvus-data 同生共死 |
| `redis-data` | 缓存/会话状态 | 可清空，代价是缓存命中率下降 |
| `backend-data` | SQLite 会话存档、checkpoint、上传文件 | 删掉会丢会话历史 |

## 3. 裸机运行（开发）

```bash
# 后端
cd backend
uv sync
cp .env.example .env
uv run uvicorn app.main:app --reload --port 8100

# 前端
cd frontend
npm install
npm run dev          # 默认 5173，vite 代理到 8100
```

只想要向量库时，用 `deploy/milvus/docker-compose.yml` 单独起 Milvus + etcd。

## 4. Kubernetes

`deploy/k8s/README.md` 有完整步骤，要点：

- `base/` 是不含环境差异的最小集合；`overlays/` 用 Kustomize 叠加副本数、资源与镜像 tag。
- 探针分别用 `/livez`（liveness）与 `/readyz`（readiness），后者会检查 Milvus/Redis；依赖抖动时只摘流量、不重启 Pod。
- Ingress 的路径前缀必须与 `deploy/docker/frontend.nginx.conf` 的 `location` 清单保持一致（`tests/unit/test_nginx_prefix_parity.py` 会校验这一点）。
- 灰度用 `canary/`，配合 `/admin/index/alias/switch` 做索引级回滚。

## 5. 可观测

| 层面 | 入口 |
| --- | --- |
| 指标 | `GET /metrics`（Prometheus 格式） |
| 汇总看板 | `/admin/metrics/summary`、`timeseries`、`top-queries`、`agent`、`quality` |
| 成本 | `/admin/costs`、`/ask/{trace_id}/cost` |
| 追踪 | OpenTelemetry（`core/otel.py`、`core/tracing.py`），可接 OTLP 后端 |
| 日志 | 结构化 JSON，含 `trace_id`；阶段耗时在 `log_stage_summary` 一行内输出 |

告警规则在 `deploy/prometheus-rules.yaml`（8 条：队列 / 在飞水位、上游熔断、缓存命中率、工具失败率、Agent 迭代、5xx 比例、p95 延迟，每条带阈值与持续时长）。

## 6. 常见故障

| 症状 | 排查顺序 |
| --- | --- |
| 后端容器反复重启 | `logs init` → `logs backend`；多为 `.env` 缺 Key 或 Milvus 未就绪 |
| `/readyz` 一直 503 | 逐个检查 milvus / redis：`docker compose ps`，再看 `/healthz` 明细 |
| 上传成功但搜不到 | 任务是否失败（`/knowledge/tasks/{id}`）；分块是否为空；向量是否入库 |
| 前端 404 / 刷新白屏 | nginx 的 SPA 回退是否生效；`frontend.nginx.conf` 与构建产物是否匹配 |
| 问答超时 | provider 连通性、重排超时、deadline 配置；`/admin/metrics/timeseries` 看长尾 |
| 内存持续上涨 | 解析大文件（PDF/Excel）占内存；限制上传大小与并发入库数 |

## 7. 备份与恢复

`scripts/backup.py`（快照 + 逐文件 sha256 清单 + 保留策略，恢复指引随备份走）与 `scripts/restore_drill.py`（在临时目录做「备份 → 清空 → 恢复 → 校验」闭环演练，不碰生产数据）是备份与恢复的配套脚本。改动存储结构后必须重跑一次演练，确认恢复后检索结果一致。
