### 2.1 项目文件层次规范

#### 2.1.1 顶层布局

| 路径 | 职责 | 规则 |
|---|---|---|
| `README.md` | 面向人的入口：能跑什么、怎么跑、关键数字 | **关键数字必须可核对**（由 `scripts/doc_facts.py` 从代码抽取，测试守卫其与代码一致） |
| `pyproject.toml` | 项目级工具配置：pytest / coverage / ruff | 根目录**唯一**的工具配置入口；不放业务代码 |
| `backend/` | 后端应用（可安装包 `app/`） | 依赖与配置独立于根 |
| `frontend/` | 前端应用 | 与后端同层，非后端子目录 |
| `tests/` | **全部**后端测试（单元 / 集成 / e2e / e2e_ui / format） | 仓库根，与 `backend/` 平级；**不放进 `backend/app/`**——测试代码不得进入发行包 |
| `scripts/` | 运维与开发脚本（压测、冒烟、容量、文档工具） | **非导入型维护脚本**；不应成为公共 API 的一部分 |
| `deploy/` | 部署资产（k8s 清单 / nginx / milvus / Prometheus 规则） | 部署逻辑与业务逻辑分离 |
| `doc/` | 文档（analysis 现状 / design 未实现项 / testing 测试计划，**待建**；原 `plan/` 已撤销，计划类内容并入 design） | 分工见 `doc/analysis/README.md` |
| `data/` | 运行时数据（索引、图谱、元数据、会话） | **必须被 gitignore**；不进版本库 |
| `docker-compose.yml` | 本地一键起依赖 | 与 `deploy/k8s/` 的生产形态分开 |

> **为什么测试在仓库根而不是 `backend/app/`**：若测试代码位于可导入包内，编辑安装（editable install）会把测试模块暴露进导入路径，既污染命名空间，也可能被打进发行包。本项目现状符合这条，且 `tests/` 已有 `__init__.py`（保证跨目录同名模块不冲突）。

#### 2.1.2 后端分层与允许依赖

| 层 | 路径 | 职责 | 允许依赖 | 禁止依赖 |
|---|---|---|---|---|
| 端点层 | `backend/app/api/` | 解析请求、依赖注入、组装统一信封 | `core` · `domain` · `services` | —— |
| 业务层 | `backend/app/services/` | 检索、生成、索引、图谱、Agent、评测 | `core` · `domain` · 同层其它 service | `api` |
| 领域层 | `backend/app/domain/` | Pydantic 模型与常量 | 标准库 · pydantic | `app.*` 其它任何 |
| 基础设施层 | `backend/app/core/` | 配置、信封、日志、指标、共享状态、限流、熔断、任务、超时、追踪 | `core` · `domain` | **`services`** · **`api`** |
| 装配层 | `backend/app/main.py` · `backend/app/dependencies.py` | 应用实例、路由注册、依赖注入、异常处理 | 全部四层 | —— |

**核心纪律**：`core` **不得**反向依赖 `services` 或 `api`。基础设施反向依赖业务，会让基础设施无法独立测试与复用。

**允许的三类例外**（必须显式标注，且数量只减不增）：

| 例外 | 场景 | 约束 |
|---|---|---|
| 可选依赖 | `core/otel.py` 依赖 OpenTelemetry | 依赖未安装时不能导致 import 失败 |
| 条件装配 | 仅在函数内 import 的 provider（如 `pymilvus` 未装时仍能启动） | 必须是**函数内** import，不是模块级 |
| 破环 | 显式标注 `# 破环` 的模块级 import | 循环依赖的**唯一**合法出口，CI 需计数 |

### 2.2 Python 语言与命名规范

#### 2.2.1 命名总则

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块 / 包 | `snake_case`，动词或名词短语，**单数**（`chunkers` 是例外：表示一个策略族） | `parent_child.py` · `image_embedder.py` |
| 类 | `PascalCase`；**不用** `I` 前缀、不用 `_Base` 后缀 | `RetrievalConfig` · `CostLedger` |
| 函数 / 方法 | `snake_case`；动词开头；返回布尔用 `is_` / `has_` / `can_` 前缀 | `resolve_anchors()` · `is_admin` |
| 常量 | `UPPER_SNAKE_CASE` | `HISTORY_CARRY_LIMIT` · `ANSWER_TOKEN_RESERVE` |
| 私有成员 | 单下划线前缀；**双下划线仅用于魔术方法** | `_visible_candidates` |
| 配置项 | `snake_case`，字段名即环境变量名（`Settings` 无 `env_prefix`） | `context_token_budget` → `CONTEXT_TOKEN_BUDGET` |
| 环境变量 | 配置项名的大写形式 | `MODEL_PROVIDER` |
| 指标名 | `kquery_` 前缀 + 下划线小写；`snake_case` | `kquery_errors_total` · `kquery_upstream_in_use` |
| 错误码枚举 | `UPPER_SNAKE_CASE`；**数值全局唯一**（`IntEnum` 重复值会产生别名，按码分流会失效） | `RETRIEVAL_FAILED = 4001` |
| 路由路径 | 小写 + 连字符分隔 | `/knowledge/query-analysis` |
| 文档中的文件路径 | 相对仓库根，反引号包裹 | `backend/app/services/pipeline.py` |

**命名纪律**：一个概念在代码、指标、配置、日志里**必须同名**。同一个东西出现三种叫法（配置叫 A、注释叫 B、告警叫 C）时，下线一处就要跨多份文档追查——历史上真实发生过。

#### 2.2.2 类型标注

| 场景 | 要求 |
|---|---|
| 公开函数签名 | **必须**有完整参数与返回标注；参数默认值不改变类型时用 `X \| None = None` 表达「可空」 |
| 领域模型 | 用 Pydantic 模型（`backend/app/domain/schemas.py`），不在函数签名里手写 dict 结构 |
| 内部私有函数 | 建议标注；复杂结构用 `TypedDict` / `dataclass` 表达，不用裸 dict 传递多层字段 |
| 协议 / 抽象 | 用 `typing.Protocol`（如 `services/llm.py:66` 的 `LLM`，`generate` / `stream` 声明在 `:67`、`:69`），不要用 `abc.ABC` 强制继承 |
| 类型忽略 | 仅在「运行时确实无法静态表达」时使用，并**必须**带 `# type: ignore[具体错误码]` 说明理由 |

**禁止**：把 `dict[str, Any]` 当作跨层数据结构传递——它是「类型信息在这一层丢失」的信号。

#### 2.2.3 注释与文档字符串

| 位置 | 要求 |
|---|---|
| 模块头部 | 说明该模块**为什么存在**与**边界**（什么不做），不是复述文件名 |
| 公开类 / 函数 | 首行一句话说明**做什么**，随后（若有必要）说明**约束**：失败时抛什么、是否幂等、是否阻塞、调用方必须先做什么 |
| 行内注释 | 解释**为什么**，不解释**是什么**。「为什么不用更简单的写法」「这个顺序不能换」是合格注释；「给变量赋值」不是 |
| 关键不变量 | 用固定措辞标注，例如「**顺序不可调换**」「**惰性求值，切勿改成立即求值**」——这类注释是给未来改代码的人看的契约 |
| 失效注释 | 注释与代码不一致时**优先删注释**。本项目已有反例：`sessions.py:7` 写着「摘要压缩默认关闭」，而全仓既无实现也无配置项——**失实注释比没有注释更贵** |

**文档字符串语言**：中文（与代码注释一致），但**保留原文的关键术语**（`tenant` / `deadline` / `trace_id` 等）。

#### 2.2.4 异常与错误处理

| 场景 | 规范 |
|---|---|
| 业务可预期失败 | 抛**领域异常**，由 `core/envelope.py` 的基类携带错误码与 HTTP 状态码；端点不决定状态码 |
| 不可预期失败 | 抛原始异常即可，但必须被全局处理器接住；**禁止**在端点里 `except Exception` 后返回 200 |
| 兜底 `except Exception` | **只允许出现在进程边界**（主循环、后台 worker、第三方 SDK 包装层），且必须①记完整堆栈 ②写明为何能吞 ③不改变对外语义 |
| 错误码 | 每个码要么有 ≥1 个生产抛出点，要么在注释里写明「为何保留」——**不留死位** |
| 异常链 | 需要保留原始原因时用 `raise ... from 原异常`；吞掉时在日志里带原始堆栈 |
| 上游失败 | 区分**可重试**（超时 / 429 / 5xx）与**不可重试**（鉴权 / 参数错误）——不可重试的降级不会成功，只会掩盖配置错误 |

#### 2.2.5 日志

| 规则 | 说明 |
|---|---|
| 统一入口 | 所有 logger 必须经 `core/logging_setup.py` 提供，**不得**直接 `logging.getLogger`——绕过入口就拿不到 `trace_id` 注入与 PII 脱敏 |
| 上下文 | 关键字段走结构化 `extra`（`trace_id` / `tenant_id` / `route` / `latency_ms`），不拼进消息字符串 |
| 级别 | `ERROR` = 需要人介入；`WARNING` = 已降级但服务正常；`INFO` = 生命周期里程碑；`DEBUG` = 排障细节（生产按采样率关闭） |
| 异常 | 记录堆栈用 `logger.exception` 或显式 `exc_info`；**且只在处理异常的那一处记录**——端点与处理器不要各记一次（否则一次故障两条日志） |
| 敏感信息 | 日志层统一脱敏（`key` / `token` / `secret` / `password` 形态、身份证 / 手机 / 邮箱 / 银行卡、Bearer 头） |
| 体积 | `extra` 中的长字段必须截断（建议 512 字符），防止单条日志膨胀到 MB 级 |
| 探针响应 | `/healthz` 只回**错误类别与错误码**，异常原文只进日志（见 §六 `A-05`） |

#### 2.2.6 导入

| 规则 | 说明 |
|---|---|
| 顺序 | 标准库 → 第三方 → 本项目；组间空行分隔（ruff `I` 规则未启用，但人工保持） |
| 形式 | 统一用 `from x import y` 形式，不用 `import x` 再 `x.y` |
| 层级 | 遵守 §2.1.2 的允许依赖表；越界必须走 §2.1.2 的三类例外之一 |
| 模块级 vs 函数内 | 模块级 import 是**默认**；函数内 import 只用于「可选依赖 / 条件装配 / 破环」三类场景，且需注释说明 |
| 别名 | 避免 `import x as y` 造成同名歧义；确需别名时（如 `import numpy as np`）属例外 |
| 副作用 | 被 import 的模块**不得**在导入期做 IO、起线程、连数据库——装配只能在 lifespan / 显式 `install()` 中发生 |

#### 2.2.7 测试代码

| 规则 | 说明 |
|---|---|
| 命名 | 文件 `test_<被测单元>.py`；函数 `test_<行为断言>`，**名字要能独立读懂**（`test_覆盖不足时保留最高分那条的截断版` 优于 `test_1`） |
| 断言 | 禁止恒真断言（`assert True`）与恒假断言；禁止「先实现后让断言迁就」 |
| 隔离 | 每个用例自己准备数据、自己清理；**不依赖用例执行顺序**；环境变量必须 `pop`（否则串味） |
| 时钟 / 随机 | 固定 seed；时间相关断言用可注入的时钟，不 `sleep` |
| 外部依赖 | 单测**不连**外部服务；需要外部的走 `tests/integration/`，并用临时目录与 mock provider |
| 文档守卫 | 「文档里的数字必须与代码一致」这类断言要写成**测试**（本项目已有端点数与用例数守卫） |

### 2.3 前端（TypeScript / React）语言规范

| 对象 | 规则 |
|---|---|
| 组件文件 | `PascalCase.tsx`；一个文件一个主组件 |
| 工具函数 / hook | `camelCase.ts` / `useXxx.ts`；hook 文件统一 `use` 前缀 |
| 类型 | `PascalCase` + `I` 前缀不用；与后端契约字段同名（`acl_filtered` / `context_breakdown`），不做前端侧重命名 |
| API 调用 | **一律**经 `lib/api-client.ts`；**禁止**在组件里裸 `fetch`——裸 fetch 会绕过信封解析、非 JSON 响应兜底、429 倒计时 |
| 身份 | 认证下线后前端**不注入任何身份头**；`localStorage` 不存身份 |
| 状态 | 服务端状态用请求态管理（loading / error / data 三态齐全）；不要用 `useState` 模拟服务端权威状态 |

| 样式 | 与现有类名体系保持一致；不引入新的 CSS 方案 |
| 可访问性 | 表单控件必须有 label；表格必须有 `caption` 与 `scope`；状态不能只用颜色表达 |

### 2.4 文档与写作规范

> 规范不只是代码规范——**文档本身也是产物**，也需要可执行的写法约定。以下条款来自仓库既有的写作规范（并已随本目录整合进 `doc/plan/`）。

| # | 规范 | 落地做法 |
|---|---|---|
| N1 | **事实标注** | 关键结论带 `文件:行号`；**禁止**绝对路径（`/Users/`、`C:\`） |
| N2 | **基线戳** | 文首有「代码基线」字段，值为「见关键数字表」；**不自己钉 git SHA** |
| N3 | **现状 vs 计划** | 现状文档只写**已落地**的；设计意图与未实施的改进一律不写，确需说明设计动机时写成「取舍说明」并明确标注 |
| N4 | **失效标记** | 已下线的能力**一律不写**（唯一例外是现状文档的「已下线留档」小节）；不写「⚠️ 已失效」横幅 |
| N5 | **未接线必须点名** | 「代码存在但生产路径无调用点」「默认关闭」「有机制无度量」必须显式标注 |
| N6 | **口径单一** | 跨篇复用的数字（端点数、用例数、参数默认值、端口）**不写具体值**，写「见关键数字表」；只有本篇独有的细节才写数字 |
| N7 | **无死链** | 文档互链指向的文件必须存在；**禁止**引用已删除的目录 |
| N8 | **篇幅上限** | 单篇 ≤ 70 KB；**单篇单一职责**是硬约束，超限且内容重复时才拆 |
| N9 | **表格优先** | 端点、配置、模型、指标、状态一律用表格 |
| N10 | **维护触发** | 文末必须有「维护触发」章节，列出触发更新的代码文件 |

**单篇文档的强制结构**（现文档集统一采用）：

| 段 | 名称 | 必含内容 |
|---|---|---|
| 1 | 文档口径 | 覆盖的未实现项编号 · 源计划 · 代码基线 · 对应代码 · 状态 · 姊妹篇 |
| 2 | 摘要 / 问题陈述 | 三到五个硬数据（现状 → 目标），让人 10 秒判断要不要读下去 |
| 3 | 正文 | 每条未实现项四段式：**现状证据 → 目标态 → 落点文件 → 验收** |
| 4 | 实施顺序 | 梯队表 + 依赖关系 + **反模式警告** |
| 5 | 验收清单 | 可机械核对的条目 |
| 6 | 边界与维护触发 | 诚实登记本篇自身的局限 + 触发复核的代码文件清单 |

**能力状态判定标准**（四态，全目录统一）：

| 状态 | 判定 | 写法要求 |
|---|---|---|
| ✅ 已实现 | 机制存在**且**生产路径有调用点 | 不进设计目录；现状写进 `doc/analysis/` |
| ⚠️ 部分实现 | 机制存在但有明确缺口（默认关闭 / 无调用点 / 有度量无判定） | 进设计目录，缺口编号必须具体 |
| ❌ 未实现 | 机制完全不存在 | 进设计目录 |
| 🚫 已下线 | 曾存在，现已移除 | **不进设计目录**；只在现状文档的「已下线留档」留一句 |

> **「有代码 ≠ 有能力」**：判定按**生产路径是否有调用点**算，不按「类/函数是否存在」算。本篇 §八之三 的死代码清单就是这条标准的产物——11 条「有定义无调用点」中 9 条判为未修，2 条（`A-21.10` 审批写回、`A-21.11` `clear_cancel`）本次复验已修。

### 10.6 `C-13` · 真流式（TTFT）专项 ✅ 已实现（2026-11-13）

> **落地小结**：线性路径已改真流式（方案 A），`ask_stream` 走 `_core_events(stream_tokens=True)`，生成阶段逐块 `yield "token"`；聚合路径（`/ask`）行为不变。本节保留为决策记录，落地形态见 §10.6.4。

#### 10.6.1 现状确认（2026-11-13 前）

流式接口的实现是**整段生成完成后，按固定字符数切片重放**——TTFT 等于全链路耗时。协议层早已声明 `stream()`（`llm.py:69`），但线性路径走的是阻塞 `generate()`。

#### 10.6.2 唯一的语义冲突：自检重写

原计划列了两条冲突：①**输出侧安全**（敏感词跨 chunk 漏检）——该模块**已整体下线**，护栏不存在，这条冲突随之消失（若将来重新引入输出侧护栏，`holdback` 窗口长度必须 ≥ 最长敏感词长度 + 1，属条件项）；②**自检可能整段重写答案**——先发 token 再重写会造成「用户看到的与最终记录不一致」。**因此本条只剩下「要不要允许重写」这一个决策。**

| 决策 | 方案 | 语义 | 代价 |
|---|---|---|---|
| **A · 真流式 + 禁重生成**（建议） | 首发 token 直接外发；自检只下调置信度，**不重写** | 语义最简单、最一致 | 答案质量可能下降（无据声明可能残留） |
| **B · 真流式 + 撤回协议** | 生成完 → 自检 → 需重写则撤回已发 token | 质量不降 | 需前端支持替换已渲染内容，复杂度高 |
| **C · 保持伪流式** | 不改 | 零风险 | TTFT 仍是全链路耗时 |

**建议选 A**：自检的价值主要在「不给无据声明」，而**证据在进上下文前已被过滤**，重写触发率本就低；用「不重写」换 TTFT 是划算的。**但必须把「置信度下调」明确呈现给用户**。**Agent 路径本期不改**——工具调用会产生多次中间输出，真流式语义复杂得多。

#### 10.6.3 分阶段落地

| 阶段 | 内容 | 风险 |
|---|---|---|
| 1 | 线性路径改真流式（方案 A），前端消费真 token | 中 |
| 2 | 压测验证 TTFT 改善，并确认自检跳动不出现在流中间 | 中 |
| 3 | （条件项）若重引入输出侧护栏，再补 holdback 增量扫描阶段 | 低 |

**验收**：TTFT < 全链路耗时的 50%；自检判定为「需重写」的请求**不发生**已发 token 的撤回；前端 SSE 事件白名单不变。

#### 10.6.4 落地形态（2026-11-13）

| 维度 | 实现 |
|---|---|
| 入口 | `api/ask.py` 的流式端点 → `services/pipeline.py:1564` `ask_stream()` → `_core_events(stream_tokens=True)` |
| 生成 | `_llm_stream()`（`pipeline.py:498`）逐块 `yield`；适配器没有 `stream()` 时 `TypeError` **静默退回** `generate()`（伪流式但不报错，见 `pipeline.py:515-520`） |
| 事件 | 生成阶段发 `token`（`services/pipeline.py:1143-1154`），收尾仍发一次 `_final`（含全文，供前端对账/持久化）；SSE 事件白名单未变 |
| 自检 | 方案 A：`_finalize_streamed_answer()` 只下调 `confidence` / `unsupported_claims_count`，`regenerated=False`，并新增 `streamed_no_regen=True` 标记（`pipeline.py:538-620`） |
