## 零、复核结论（本次修订的原因）

初版计划方向正确，但有 3 处设计不成立、2 处数字高估、4 项关键遗漏。修订后总工作量从 7 人日调整为 **11.5 人日**。

| # | 初版内容 | 复核判定 | 修订 |
|---|---|---|---|
| 1 | "SSE 连接 40 → 2000" | ❌ **不成立**：管线是同步的，每条**正在生成**的流仍占 1 个工作线程；2000 只能是"空闲/心跳连接"，不是 2000 并发生成 | 目标改为"≥500 空闲连接 + 32 并发生成 + 超出排队/503" |
| 2 | 多查询并行召回复用"批次 1 的执行器" | ❌ **会死锁**：管线本身已在执行器线程里，再向同一池提交任务，池满即自锁 | 改用**独立 4 线程小池**，或块数少时直接串行 |
| 3 | HNSW 迁移"drop 集合 + 从源文档重灌" | ❌ **会丢数据/成本高**：Milvus 支持原地换索引（release → drop_index → create_index → load），无需重灌 | 改为原地换索引；且当前仅 9 个块，**不作为本期必做项** |
| 4 | 聚合问答吞吐 "~4 QPS" | ⚠️ **高估**：取 min(执行器 32, 上游并发 16) / 8s = **2 QPS** | 目标改为 2 QPS（冷路径），缓存命中不计入 |
| 5 | 总工作量 7 人日 | ⚠️ **低估**：未含每批回归、压测、浏览器验证 | 调整为 11.5 人日 |
| 6 | 未覆盖：`AnalysisStore.save` 每请求全量重写 | ❌ **遗漏（高并发先炸点）**：`analysis_store.py:36-50` 每次问答把最多 1000 条记录整体 JSON dump；500 QPS 下写放大不可接受 | 新增到批次 1 |
| 7 | 未覆盖：审计写侧 | ⚠️ 查询侧持锁已修（`audit.py:127-130`），但**每请求 3 次同步 open/append/close + 全局锁** 仍在 | 批次 1 改批量 flush |
| 8 | 未覆盖：SQLite 单连接 + 全局锁 | ⚠️ 图存储/检查点在并发 Agent 下串行 | 批次 3 标注为已知上限，给出缓解 |
| 9 | 未覆盖：前端不处理 503 | ❌ 背压上线后前端只认 429，503 会显示成"服务不可用" | 批次 1 补前端处理 |
| 10 | 真流式（B4-3）作为可选 1 人日 | ❌ **与现有安全/校验语义冲突**：整段敏感词扫描要求先有全文；自检可能重生成，先发 token 会前后不一致 | **移出本计划**，另立专项 |

**复核方法**：把初版每条改动映射到具体文件与调用链，检查"是否引入嵌套等待 / 是否有界 / 失败是否可观测 / 是否与既有语义冲突"，再用实测数据反推容量数字。下表逐条给出修正后的依据。

### 1.1 实测（2026-10-19，docker 单副本）

| 路径 | 场景 | 吞吐 | P50 | P95 | 备注 |

### 1.2 决定并发上限的五件事

| # | 机制 | 现状 | 证据 | 影响 |
|---|---|---|---|---|
| 1 | AnyIO 线程池 | 默认 **40**，全端点共享 | `api/ask.py:86,137` 同步 `def` | 第 41 个在飞请求排队；SSE 每连接占 1 线程 |
| 2 | 管线本身同步 | LLM/Embedding/Rerank/Milvus 全同步 + `time.sleep` 退避 | `llm.py:155`、`embeddings.py:126` | 线程被整段占用，异步无法穿透 |
| 3 | 无闸门的线程创建 | Agent 每请求 1 线程；工具每次新建池 | `runner.py:285`、`tools.py:685` | 高并发 Agent 线程数线性增长 |
| 4 | 每请求同步落盘 | `AnalysisStore.save` 全量重写；审计 3 次 append | `analysis_store.py:36-50`、`audit.py:52-74` | 写放大随数据量增长，持锁即串行 |
| 5 | FLAT 全扫 | Milvus `index_type="FLAT"` | `milvus_store.py:71` | 10 万块 × 30 QPS 不可行（C 级估算） |

### 1.3 当前有效并发能力（结论）

| 维度 | 当前值 | 性质 |
|---|---:|---|
| 框架层吞吐（轻接口） | ~500 QPS | 实测，CPU 未饱和 |
| 最大在飞请求 | **40** | 硬上限（AnyIO 池） |
| 最大 SSE 连接 | 40 | 每连接 1 线程 |
| 并发生成数 | ≤40（受池限制） | 同左 |
| Agent 并发 | 无上限、不可控 | 风险型 |
| 单租户问答稳态 | 1 QPS（60/min） | 设计闸门，不是系统极限 |
| 入库 | 1 批串行 | 单 worker |
| 检索规模 | 万级块以内 | FLAT |

**一句话：当前瓶颈是线程模型（40）+ 无界线程创建 + 每请求同步落盘，而不是 CPU。**（A 级：代码 + 实测）

## 二、修正后的目标模型（单进程）

| 维度 | 当前 | 修订目标 | 推导 |
|---|---:|---:|---|
| 在飞问答（生成中） | ≤40 | **32** | 执行器固定 32；由上游配额与实测 P95 校准 |
| 排队请求 | 无界（隐藏在线程池） | **200 后 503 + Retry-After** | 有界队列，快速失败 |
| 空闲/心跳 SSE 连接 | 40 | **≥500** | 连接只占内存与 fd，不占线程 |
| 多租户聚合问答吞吐（冷，8s/req） | — | **2 QPS** | min(执行器 32, 上游并发 16) / 8s = 2 |
| 缓存命中吞吐 | — | **数百 QPS** | 6.5ms/req，受 GIL 与锁限制 |
| Agent 并发 | 无上限 | **16 在飞 + 排队 + 429** | 独立信号量 |
| 入库 | 1 批串行 | **解析 2 并行、索引 1 串行** | 索引写入受 `KnowledgeService._lock` |
| 每请求同步落盘 | 有 | **0 次（批量 flush）** | 写放大移出请求路径 |
| 过载行为 | 排队到死 | **503 快速失败** | 背压 |

**必须承认的硬上限**：

1. **GIL**：CPU 密集的解析、BM25、FAISS 与请求线程争抢；异步只解决 I/O 等待，不解决 CPU。解析必须留在后台池且限并发。
2. **同步上游 SDK**：不做全链路异步重写，就无法把"生成中的等待"变成可复用的空闲线程；本计划只把"连接等待"从线程里拿掉，不声称"2000 并发生成"。
3. **单进程**：不能用多 worker 绕过，否则六处进程内状态会分裂（限流/配额/缓存/会话/图谱/检查点）。

### 批次 1：线程模型 + 请求路径写放大（3.5 人日）

> 初版把"落盘写放大"漏了；实测 500 QPS 场景下它会先于线程池成为瓶颈，因此并入本批。

**B1-1 异步端点 + 有界执行器**（`api/ask.py`、新增 `services/pipeline_executor.py`）

- `/ask`、`/ask/stream`、`/resume` 改 `async def`；
- `PipelineExecutor`：`ThreadPoolExecutor(32)` + `asyncio.Queue(maxsize=200)`；队列满 → 503 + `Retry-After`；
- SSE：`async def` 生成器从 `asyncio.Queue` 取事件；worker 线程通过 `loop.call_soon_threadsafe(queue.put_nowait, ...)` 投递；**队列满时 worker 不阻塞**，置取消标志并停止（避免"客户端不读 → 线程卡死"）；
- 心跳 15s；`request.is_disconnected` → `registry.cancel(run_id)` + 设置管线取消标志；
- AnyIO 默认线程池显式调到 100（管理面/探针留余量）。

**B1-2 Agent 与工具复用同一执行器**（`runner.py`、`tools.py`）

- `spawn_thread` → 执行器（独立信号量 16）；超限 429；
- 工具调用复用执行器 + `future.result(timeout)`，删除每次新建池；
- `clear_cancel` 进 `finally`；deadline 早退置取消标志，工具/LLM 调用前检查。

**B1-3 请求路径去同步落盘**（`analysis_store.py`、`audit.py`、`pipeline.py`）

- `AnalysisStore`：内存追加 + 后台每 2s 或每 50 条批量 flush；`save` 不再在请求线程写文件；
- `AuditStore.append`：内存队列 + 后台批量写（保留"崩溃最多丢 N 条"的明确语义，N 可配置）；写失败计数而非逐条 warning；
- `MetricsStore`：每请求只累加计数，latency 采样（每 10 个请求留 1 个）避免 24h 列表无界。 <- 注意：这条是估算，需按实际 QPS 验证内存

**B1-4 前端 503 处理**（`frontend/src/lib/sse-client.ts`、`api-client.ts`）

- 429 与 503 都读 `Retry-After`，展示"服务繁忙，N 秒后重试"，不登出；
- 503 不触发全局错误页。

**验收**
- 500 条 SSE 连接保持 10 分钟：线程数 <120、RSS 平稳、断开 2s 内释放；
- 在飞 32 时第 33 个排队；队列 200 后 503；
- 500 QPS 轻接口下 `analysis_store` 不再有同步写（strace/日志可证）；
- pytest 全绿、smoke 双路径全过、浏览器验证通过。

**风险与回滚**：异步桥接改变事件投递时序 → 事件名/顺序不变；出问题 revert `api/ask.py` + 新增文件，其余模块无感。

### 批次 2：上游治理（2.5 人日）

**B2-1 隔离仓 + 熔断**（新增 `services/upstream.py`）

- `llm=16 / embedding=8 / rerank=4 / milvus=32 / ocr=2 / vl=2`；
- **约束：各信号量之和不得超过执行器线程数（32）**，否则线程全被"等信号量"占满。因此 llm+embedding+rerank+milvus 需要共享额度或按实测重设（建议：llm=12、embedding=4、rerank=2、milvus=8，其余按需）；
- 熔断：20 次窗口失败率 >50% → 打开 30s → 半开 3 次；打开期间返回结构化降级错误（不占线程）。

**B2-2 single-flight**（`cache.py`/`pipeline.py`）

- 同 key 并发：首个执行，其余等待复用；**等待带 deadline（如 30s）**，超时自行执行，避免等待者占满线程。

**B2-3 请求级缓存**（`pipeline.py`）

- `doc_id → 文档/ACL 判定/文件名`、`parent_id → 父块`；问题向量只算一次；
- 请求结束即弃，无跨请求状态。

**B2-4 观测补齐**（`core/metrics.py`）

- 新增 gauge：`inflight_requests`、`queue_depth`、`upstream_saturation{upstream}`、`upstream_circuit_open{upstream}`、`shed_total{reason}`；
- 这是批次 4 验收的前提（否则"有没有效果"只能靠感觉）。

**验收**：重排注入 5s → 向量检索 P95 恶化 <20%；10 个相同问题 → 上游 1 次；熔断打开时无 5xx（返回 503/降级信封）。

### 批次 3：计算与检索层（3 人日）

**B3-1 入库队列**（`services/ingest.py`）

- `queue.Queue(maxsize=200)` + `put_nowait`（**不能在 async 端点里阻塞 put**），满 → 503；
- worker 1 → 2（解析并行；索引写入已被 `KnowledgeService._lock` 串行化）；
- lifespan 收尾 `shutdown(timeout=30)`。

**B3-2 多查询并行召回**（`retrieval/hybrid.py`、`vector.py`）

- 使用**独立 4 线程小池**（不得复用管线执行器，避免嵌套死锁）；
- 改写后的查询批量 `embed_texts` 一次编码，替代逐条 `embed_query`；
- 并行度可配置，默认 4；失败单路仍走既有降级。

**B3-3 已知串行点标注与缓解**（不改架构）

- `SqliteGraphStore` 单连接 + 全局锁、`SqliteSaver` 单连接：在指标里暴露等待时间；Agent 并发 >16 时可能成为瓶颈；
- 缓解：图写入走后台队列（复用批次 1 执行器或专门单线程），读路径不受写锁影响。

**B3-4 HNSW（条件项，不排期）**

- 触发条件：单集合块数 >5 万且检索 P95 >100ms（当前 9 个块，做无收益）；
- 方案：Milvus `release_collection → drop_index → create_index(HNSW, COSINE)` → `load_collection`；**不 drop collection、不重灌**；
- 需先在测试集合验证召回率与延迟。

**验收**：20 文件入库 ≥2× 当前吞吐；6 条查询并行召回延迟下降 ≥50%；图/检查点锁等待指标可见。

### 批次 4：降级阶梯与固化（2 人日）

**B4-1 自适应并发**：自定义 `AdaptiveLimiter`（`asyncio.Semaphore` 不支持动态扩容，需自己实现 condition + permits）；AIMD：连续 50 成功 +1，超时 -30%，下限 1。

**B4-2 降级阶梯**（配置化，默认关）

| 水位 | 动作 |
|---|---|
| 上游 P95 > 阈值 | 关 HyDE/额外改写；CRAG 轮次 2→1 |
| 队列深度 > 阈值 | 拒低优先级（入库/图谱），交互保留 |
| 熔断打开 | 重排降级 RRF；生成降级模板/拒答 |

**B4-3 前端与文档**：503/降级提示；`README` 容量表；压测脚本固化。

**验收**：故障注入下 2s 内返回可读降级结果；`shed_total` 与队列深度能解释每一类拒绝。

### 移出本计划：真流式（TTFT）

原因：与两条既有语义直接冲突——

1. **输出侧安全**：`pipeline.py:820-831` 要求拿到完整答案再扫描；边生成边发会让敏感词跨 chunk 漏检，必须引入"holdback 窗口 + 增量扫描"，等于重做护栏；
2. **自检与重生成**：`pipeline.py:761-789` 可能整段重写答案；先发 token 再重写会造成"用户看到的内容和最终记录不一致"。

正确做法是先决策"自检是否允许重生成"与"增量扫描 holdback 长度"，再单独立项（预估 3~4 人日 + 评测）。本计划不承诺 TTFT 从 7.6s 降到 2.5s。

## 五、并发正确性检查清单（实施时必须逐条确认）

| 检查 | 说明 |
|---|---|
| 不得嵌套提交同一执行器 | 管线已在池内时，禁止再向同池提交（批次 3 用独立小池） |
| 信号量之和 ≤ 执行器线程数 | 否则线程被"等许可"占满，有效并行度下降 |
| 队列投递用 `put_nowait` | 消费者消失时 worker 不得阻塞 |
| 所有等待有 deadline | 队列、single-flight、信号量、Future 都不能无限等 |
| 锁顺序固定 | `KnowledgeService._lock` → `DocStore` → 向量库，不得反向 |
| 取消可传播 | `threading.Event` 在阶段边界检查；已发出的上游请求无法中断，文档写明 |
| 指标可解释拒绝 | 每一类 429/503 都有 `reason` 标签 |
| GIL 认知 | CPU 密集任务限并发（解析 2、OCR 2），不指望异步提速 |

| 信号量设置导致吞吐下降 | 中 | 按"和 ≤ 线程数"约束 + 压测校准 | 配置回退 |

| AnalysisStore 批量 flush 丢记录 | 低 | 同上；flush 失败计数告警 | 同上 |
| 图/检查点 SQLite 串行 | 中 | 指标暴露 + 写走后台 | 不改语义 |

## 七、明确不做

| 不做 | 原因 |
|---|---|
| 多副本 / Redis / MQ / Postgres | 用户约束：单体 |
| `--workers > 1` | 六处进程内状态分裂 |
| 全链路 async 重写（换异步 SDK） | 超出"架构不变"的边界；本计划只做桥接 |
| 真流式 | 与输出安全/自检语义冲突，另立专项 |
| 调大租户限流默认值 | 成本护栏，不是性能问题 |
| HNSW（当前） | 9 个块，零收益；设为语料 >5 万块的条件项 |
