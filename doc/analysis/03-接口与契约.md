## 〇、摘要

1. **端点由 13 个 router + `main.py` 内建探针组成（81 个端点），鉴权分三档**：`require_role("admin")`（router 级）、`get_principal`（router 级或端点级）、公开。router 注册顺序与 prefix 见 `backend/app/main.py:883-895`；逐端点清单见 §一。
2. **统一信封只覆盖非流式 JSON 端点**：`status/data/error/meta` 四字段定义在 `backend/app/core/envelope.py:121-135`（`ErrorBody` 121-123 / `Meta` 126-128 / `Envelope` 131-135）；SSE 端点、CSV 导出、图像资源、5 个运维探针**不走信封**（§三列出全部例外）。
3. **`warn` 三态实际只在 `/ask` 一处产生**：`warn_envelope` 的唯一生产调用点是 `backend/app/api/ask.py:140`，其余 80 余个端点只用 `ok_envelope` / `error_envelope`（§三）。
4. **错误码 47 个、6 个区段**：`backend/app/core/envelope.py:12-107`（1xxx / 2xxx / 3xxx / 31xx~38xx / **39xx 知识库** / 4xxx / 5xxx / 6xxx）；`6201 QUOTA_EXCEEDED` 已随配额下线移除，6xxx 段现只剩 `6101 RATE_LIMITED`。降级码集合 4401/4402/4501/4901/4902 定义在 `backend/app/core/envelope.py:98-107`，但 **`is_degraded_code` 在生产代码中零调用点**（仅测试 `backend/tests/integration/test_p0_fixes.py:68-70` 引用）——降级判定实际由 `backend/app/api/ask.py:122-133` 手工比对完成（§四、§八）。
5. **SSE 是跨端契约，不是后端内部实现**：前端在 `frontend/src/lib/sse-client.ts:81-92` 用白名单登记事件名，白名单外的事件在 `frontend/src/lib/sse-client.ts:155` **静默丢弃**（无报错、无日志）。后端新增事件必须同步前端白名单（§五）。
6. **后端已发出但前端白名单未登记的事件有 4 个**：`thought`、`verify`、`awaiting_human`、`hitl_resolved`——表现是"后端有发、前端没反应"，且无处可查（§五、§八）。`input_pii_detected` 已随敏感词功能下线移除。
7. **身份有两套来源**：开发档走 `X-User-Id`/`X-Tenant-Id`/`X-Roles` 头透传（`backend/app/services/security/auth.py:52-64`，**不验证任何凭证**），生产档走 `Authorization: Bearer`（`backend/app/services/security/auth.py:91-195`，自实现 HS256）。前端在 `frontend/src/lib/auth.ts:107-123` 按是否持有令牌二选一。
8. **前端严格区分"未设置"与"显式空串"**：`frontend/src/lib/auth.ts:51-58` 的 `readRaw` 返回 `null` 表示未设置、返回 `""` 表示显式设为空。空串是合法的"无角色"身份——用 `|| 默认值` 兜底会让人造不出越权断言场景（§六）。
9. **请求体上限没有全局设置**，只有三处端点级实现，超限一律 `FILE_TOO_LARGE`（2004）；超时分四层，各自有独立上限（§七）。

## 二、鉴权矩阵

### 2.1 三档鉴权与依赖落点

| 档位 | 依赖 | 失败语义 | 落点 |
|---|---|---|---|
| A. 公开 | 无 | — | 8 个端点，见 §2.3 |

### 2.4 两个 prefix 撞车

**（一）三个 `/knowledge` prefix**

| router | prefix | 注册位置 | 端点 |
|---|---|---|---|
| knowledge | `/knowledge` | `main.py:885` | 11 |
| ingest | `/knowledge` | `main.py:886` | 4 |

**（二）三个 `/admin` prefix**

| `api/admin.py:22` | router 级 `prefix="/admin"` +相对路径 | `main.py:889` | 9 |

## 三、统一信封

### 3.1 结构

`backend/app/core/envelope.py:121-135`（`ErrorBody` 121-123、`Meta` 126-128、`Envelope` 131-135）：

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `status` | `str` | 是 | 三态：`ok` / `warn` / `error` |
| `data` | `Any` | 否（默认 `null`） | 业务数据；`error` 信封下为 `null` |
| `error` | `{code:int, message:str}` \| `null` | 否 | 仅 `warn` / `error` 非空；`code=0` 表示"有告警但无固定码" |
| `meta` | `{trace_id:str, elapsed_ms:int}` | 是 | 追踪号与耗时；由 `Meta`（`core/envelope.py:126-128`）定义 |

三个构造器：`ok_envelope`（`core/envelope.py:138-139`）、`warn_envelope`（`:142-159`）、`error_envelope`（`:162-167`）。

### 3.2 三态语义

| 状态 | 构造器 | 语义 | 前端处置 | 生产调用点 |
|---|---|---|---|---|
| `ok` | `ok_envelope` | 完全成功 | 正常渲染 |全部非流式端点 |
| `warn` | `warn_envelope` | **部分成功 + 部分告警**：结果可用，但有降级事实需要让用户知道 | 正常渲染并附加提示 | **仅 `api/ask.py:140`**（经 `_envelope_for` / `_degraded_warning`，`:122-141`） |
| `error` | `error_envelope` | 失败 | 展示 `error.message` | 全局异常处理器（`main.py:717-768`） |

`warn` 的两条纪律（`core/envelope.py:149-153`）：①永远不用它表达失败；② `code` 传降级类错误码，为0 表示软提示。

**实际覆盖面**：`warn_envelope` 在生产代码中的唯一调用点是 `api/ask.py:140`。`/ask/stream`、`/quickask/ask`、`/ask/runs/*/resume` 三条 SSE 路径**不产 warn 信封**——降级信息只能靠 SSE 的 `confidence` / `crag_branch` 事件携带。这是一条**跨路径不一致**：同一份降级事实，聚合路径用 `warn` 表达、流式路径用事件字段表达。

### 3.3 `ApiError`

`backend/app/core/envelope.py:170-184`：

| 属性 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `code` | `ErrCode` | 必填 | 业务错误码；全局处理器据此选文案区段 |
| `message` | `str` | 必填 | 用户可读文案（**不直接回显上游原文**，见 `api/speech.py:133-140`） |
| `http_status` | `int` | `400` | HTTP 状态码；不是400 的必须显式传 |
| `retry_after` | `int \| None` | `None` | 限流时携带秒数；全局处理器写入 `Retry-After` 响应头（`main.py:723-724`） |

`ApiError` 是**业务失败**的唯一通道：抛 `ApiError` → `main.py:717-725` 的异常处理器 → 统一信封 + 对应 HTTP 状态码。

### 3.4 不走信封的端点（例外清单）

| 端点 | 响应形态 | 理由 |
|---|---|---|
| `POST /ask/stream`、`POST /quickask/ask`、`POST /ask/runs/{run_id}/resume` | SSE `text/event-stream` | 流式协议，`X-Trace-Id` 放在响应头 |
| `GET /assets/{name}` | 文件流 | 资源服务 |
| `GET /health`、`/livez`、`/readyz`、`/healthz`、`/metrics` | JSON / `text/plain` | 运维探针，不与前端契约耦合 |

### 6.2 身份头与令牌

| 头 | 开发档（`HeaderAuthProvider`） | 生产档（`JwtAuthProvider`） | 后端读取位置 |
|---|---|---|---|
| `Authorization: Bearer <token>` | 不使用 | **唯一凭证来源** | `dependencies.py:125-126` |

> 开发档的 `HeaderAuthProvider` **不验证任何凭证**（`services/security/auth.py:52-64`）：把请求头当成身份，因此 `auth_enabled=false` 的部署等同于"任何人都能声明自己是 admin"。生产档必须 `auth_enabled=true`。
> 生产档令牌是自实现 HS256（`services/security/auth.py:91-195`），**显式拒绝 `alg != HS256`**（`:160-165`）——防算法混淆攻击。

### 6.3 前端发送口径

`frontend/src/lib/auth.ts:107-123`：

| 场景 | 发送内容 |
|---|---|
| 持有令牌 | 只发 `Authorization: Bearer <token>`，**不发任何身份头** |
| 无令牌 + 构建期 dev | 发 `X-User-Id` / `X-Tenant-Id` / `X-Roles` |
| 无令牌 + 生产构建 | **一个身份头都不发**——发空身份头会让后端的头部透传档（若被误开）凭空造出一个"已认证但无角色"的主体，比不发更糟 |

`DEV_BYPASS` 是**构建期常量** `import.meta.env.DEV`（`frontend/src/lib/auth.ts:39`）：`npm run build` 产出的东西没有任何默认身份，必须真实登录；不存在"改个 localStorage 键就绕过登录"的路径。

### 6.4 "未设置"与"显式空串"的区分

`frontend/src/lib/auth.ts:51-58` 的 `readRaw()` 返回 `null` 表示**未设置**，返回 `""` 表示**显式设为空**；`currentPrincipal()`（`:74-88`）的 `pick` 用 `v === null ? fallback : v` 判定。

| 存储值 | 语义 | 后果 |
|---|---|---|
| `null`（键不存在） | 未设置 → 用开发默认身份 | 角色为 admin（仅 dev 构建） |
| `""`（键存在但为空串） | **显式声明"我没有任何角色"** | 合法身份，用于越权断言与降权验证 |

> 若用 `|| 默认值` 兜底，"显式空串"会被当成"未设置"，从而造不出非管理员身份——`frontend/src/lib/auth.ts:45-49` 的注释记录了这一约束。`rolesOf()`（`:126-131`）同样把空串解析为空数组，保持语义一致。

### 6.5 401 / 403 的前端处置

| 状态 | 前端行为 | 证据 |
|---|---|---|
| 401 | 触发全局登出回调（清会话 + 跳登录） | `frontend/src/lib/auth.ts:182-184`；`frontend/src/lib/api-client.ts:57-59`；SSE 路径 `frontend/src/lib/sse-client.ts:141` |
| 403 | **不登出**，只展示"无权限：当前身份无权访问该功能" | `frontend/src/lib/auth.ts:173-174`、`:197-200`；`frontend/src/lib/sse-client.ts:137-142` |

> 403 不跳转的原因：403 表示"已登录但无权"，跳转会掩盖真实原因，且会把用户踢出登录（`frontend/src/lib/auth.ts:173-174`）。

## 七、请求体上限与超时约定

### 7.1 请求体上限：无全局设置，三处端点级实现

应用层**没有**任何全局 body 大小限制（FastAPI/Starlette 未设相关中间件）。实际约束来自三处端点级实现 + 网关：

| # | 位置 | 覆盖端点 | 做法 | 失败码 |
|---|---|---|---|---|
| 1 | `api/upload_util.py:40-57` `stream_to_disk` | `POST /knowledge/upload`（`api/knowledge.py:73`）、`POST /knowledge/ingest`（`api/ingest.py:92`） | **边写边计数**，1MB 分块，超限立即中断并删除半成品——不把整文件读进内存 | 2004 `FILE_TOO_LARGE`（HTTP 400） |
| 2 | `services/quickask.py:193-197`、`:220-225` | `POST /quickask/upload` | 文件**整体读入内存后**校验字节数与解析段数 | 2004 `FILE_TOO_LARGE` |
| 3 | `api/speech.py:194-210` | `POST /speech/transcribe` | 两道检查：先按 multipart 解析出的 `file.size` 拒（避免"读进内存才发现超限"），再按实际读到的字节数拒 | 2004 `FILE_TOO_LARGE` |

> 三处口径不一致：① 流式落盘 vs 内存读全量；② 快问与语音把大小上限绑在**不同的配置项**上（快问取二者较小值，`services/quickask.py:163-165`）；③ HTTP 413（网关层拒绝）被映射为同一个2004（`main.py:744`），前端无法区分"应用层拒的"与"网关拒的"。
> 网关侧另有独立的上传大小限制（`deploy/nginx/nginx.conf` 与 `frontend/nginx.conf`），与本层并存——具体值见 README 关键数字表。

### 7.2 超时约定（四层，各自独立）

| 层 | 位置 | 语义 | 超限表现 |
|---|---|---|---|
| 管线在飞 / 排队 | `services/pipeline_executor.py:58`（同步 `acquire`）、`:88`（异步 `acquire_async`）、`:118`/`:128`（`run` / `run_async`） |申请执行槽位；排队已满**立即返回 False**（不阻塞） | 抛 `OverloadedError` → 503 + `Retry-After: 5`（`:221-230`） |
| SSE 心跳与产出 | `services/pipeline_executor.py:141-199` | 超过心跳间隔无事件则产心跳项；消费者慢于生产者时**停止生成**而非堵死线程 | 心跳 `: ping`；队列满 → 置 cancel 并断开 |
| Agent 工具单步 | `services/agent/tools.py:689-704` | 工具调用超时（配置项 `agent_tool_timeout_s`） | 返回 `ToolResult(error=...)`，标记该步失败，流程继续；已运行的线程仍会跑完（技术边界） |
| Agent 整体 deadline | `services/agent/budget.py:56-66` + `services/agent/runner.py:314-324` | 事件队列 `get(timeout=0.5)` 轮询；到期放弃等待 | 发 `fuse{reason:"budget_deadline"}`，转拒答降级作答 |

补充：single-flight 等待者复用结果的上限是 `_SF_WAIT_S`（`services/pipeline.py:1076`），超时后自行执行，避免等待者占满线程；LLM 上游超时由配置项 `llm_timeout_s` 控制（装配处 `main.py:445`）。各配置项的具体值见 README 关键数字表。
