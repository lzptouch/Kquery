## 〇、摘要

1. **入库有两条入口但只有一套内核**：同步 `POST /knowledge/upload`（单文件立等结果）与异步 `POST /knowledge/ingest`（多文件任务制），二者都汇入 `KnowledgeService` 的「解析 → 切块 → 索引」三段式（`backend/app/services/knowledge.py:356-427`）。
2. **解析路由是纯扩展名查表**，共 53 种扩展名映射到 8 个解析器；`.xls` / `.ppt` 不在白名单里，但给了专门的「请另存为 .xlsx」提示而不是笼统的「不支持」（`backend/app/services/parsers/router.py:27-42`）。
3. **四种切块策略共用一套产物契约** `(chunks, parents, chunker_name)`（`backend/app/services/chunkers/factory.py:24-28`）；`chunk_id` 一律是 `{doc_id}#{seq}`，**绝不用随机 UUID**——它是引用回溯、缓存命中与跨版本比对的基石（`backend/app/services/chunking.py:1-7`）。
4. **索引写入有两条硬纪律**：先算好新向量再清旧索引；向量条数必须严格等于块条数，否则**拒绝发布**（`backend/app/services/knowledge.py:375-390`）。没有第二条断言，「块与向量不一致」会表现为**检索静默漏召回**而不是报错。
5. **重新解析不删旧块**：旧块改名 `@v{旧版本}` 保留供历史答案溯源，只有超出保留份数才真删（`backend/app/services/knowledge.py:594-653`）。
6. **异步入库是 8 态文件 × 6 态任务的状态机**，失败按阶段重试（解析失败清缓存重解析，切块 / 索引失败复用解析产物），取消仅在可取消阶段生效（`backend/app/domain/schemas.py:89-107`、`backend/app/services/ingest.py:446-477`）。
7. **快问临时索引有四条不可让步的约束**：不入库、不 bump 版本、向量 + BM25 双写、缓存键带 `scope`（`backend/app/services/quickask.py:9-17`）。

## 一、同步上传与异步任务两条入口的对比

### 1.1 选择依据

| 维度 | 同步上传 `POST /knowledge/upload` | 异步任务 `POST /knowledge/ingest` |
|---|---|---|
| 端点 | `backend/app/api/knowledge.py:59-88` | `backend/app/api/ingest.py:49-153` |
| 文件数 | 1 | 1 ~ 20（`MAX_BATCH_FILES`，`backend/app/api/ingest.py:28`、`:64-65`） |
| 返回时机 | 解析 + 索引**全部完成**后返回最终状态 | 立即返回 `{task_id, total_files}`，后台执行 |
| 执行位置 | `run_in_threadpool` 调 `service.ingest_path`（`backend/app/api/knowledge.py:81-83`） | 单 worker 线程消费有界队列（`backend/app/services/ingest.py:232-240`） |
| 进度可见性 | 无（请求挂住直到完成） | 文件级 8 态 + 阶段进度 + 阶段耗时（`backend/app/domain/schemas.py:110-127`） |
| 重试 | 手动 `POST /knowledge/rebuild/{doc_id}` | `POST /knowledge/tasks/{id}/retry`，可指定单文件 |
| 取消 | 不支持 | `POST /knowledge/tasks/{id}/cancel`，仅可取消阶段生效 |
| 队列背压 | 无 | 队列满 → 503 + `Retry-After`，并回收已落盘文件（`backend/app/api/ingest.py:138-144`） |
| PII 硬拦截 | **无**（走 `ingest_path`，不经 `api/ingest.py` 的扫描） | **有**（`backend/app/api/ingest.py:113-137`） |
| 限流 | `Depends(enforce_rate_limit)` | `Depends(enforce_rate_limit)` |

### 1.2 两条入口的共同内核

```
validate → create_record → parse_document → apply_chunking → index_parsed → _run_post_index
```

- 同步路径：`ingest_path`（`backend/app/services/knowledge.py:497` 起）。
- 异步路径：`_process_file` 的四段推进（`backend/app/services/ingest.py:339-408`）。

两条路径都会在索引成功后触发**图谱 / 图像索引联动**（`_post_index` 钩子，组装于 `backend/app/main.py:529-561`）。

### 1.3 一处值得注意的差异

**PII 入口硬拦截只挂在异步入口上**（`backend/app/api/ingest.py:113-137`）。同步上传走 `service.ingest_path`，**不经过该扫描**。这是一个真实的口径差，已登记于第十一章缺口 #1。

## 三、各格式解析器

统一产物 `ParseResult{segments, tables, assets, outline, warnings}`（`backend/app/services/parsers/base.py`）。`segments` 是 `(source, text)` 片段列表，`source` 形如「第 3 页」「第 1 页·OCR」「第 2 页·表格 1」，是溯源标签的来源。

### 3.1 Markdown

`MarkdownParser`。产出大纲（标题层级），供预览页左侧结构树使用（`backend/app/services/knowledge.py:175-185`）。老数据没有持久化大纲时，对 `.md` / `.markdown` 现场重算兜底。

### 3.2 纯文本与 HTML

`PlainTextParser`（`backend/app/services/parsers/plaintext.py`）。三个刻意取舍：

1. **不引 `chardet`**：三级编码回退 `utf-8 → gbk → latin-1`（latin-1 永不失败）覆盖绝大多数场景，少一个依赖就少一处版本冲突与 CI 不稳定因素（`backend/app/services/parsers/plaintext.py:6-8`、`:41-42`）。
2. **HTML 去标签但不引解析库**：用标准库 `html.parser` 剥标签，`<script>` / `<style>` 的**内容**整段丢弃（不是只丢标签）——脚本内容混进索引会污染检索语义（`backend/app/services/parsers/plaintext.py:9-12`、`:47-50`）。
3. **代码文件只做纯文本入索引**，不做符号解析：代码块的价值在「能被搜到」，解析符号树的成本与收益不成比例（`backend/app/services/parsers/plaintext.py:13-14`）。

单文件最大解码字符数 `MAX_TEXT_CHARS = 2_000_000`，防止超大文本一次性进内存（`backend/app/services/parsers/plaintext.py:44-45`）。

### 3.3 PDF（含扫描版按页自动 OCR）

`PdfParser`（`backend/app/services/parsers/pdf.py`）。**按页混合策略**，每页独立判定：

| 页类型 | 判定 | 处理 | 代码位置 |
|---|---|---|---|
| 文字页 | 文本层字符数 ≥ `scan_min_chars` | 文本流抽取（`sort=True` 缓解双栏混杂）+ `find_tables` 几何表格识别 | `backend/app/services/parsers/pdf.py:69-77` |
| 扫描页 | 文本层缺失 / 极短 | 渲染位图 → VL OCR 整页识别 → 剥表格 → 正文与表格分开 | `backend/app/services/parsers/pdf.py:79-82`、`:110-151` |

关键参数（`backend/app/services/parsers/pdf.py:40-54`）：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `ocr_dpi` | 120 | 页面位图渲染 DPI |
| `ocr_max_pages` | 200 | 单文档 OCR 页数上限，超出的页**不入库**并写 warning |
| `scan_min_chars` | 30（`MIN_PAGE_CHARS`，`:31`） | 单页文字量低于该阈值视为疑似扫描页 |

其它纪律：

- PDF 加密 → 明确报错（`:63-64`）；打不开 → 报错（`:59-62`）。
- 整篇无文本且 OCR 不可用 → 明确报错，**不静默产出空索引**（`:98-102`）。
- OCR 输出中的 Markdown 表格块被剥离为独立 `TableRecord`（`modality=table`），与文字流表格享受同等的结构保护（`:147-151`、`:174-203`）。
- 页面位图进资源目录（`kind=page_image`），前端溯源时可回显原页图像（`:153-172`）。
- 大纲用**字号法**提取：span 字号显著大于正文中位数 → 标题，按字号梯队分级（最多 3 级）（`:207-236`）。

### 3.4 DOCX

`DocxParser`。解析段落 + 表格 + 图片。

### 3.5 XLSX（表格转 Markdown + 行列结构）

`SpreadsheetParser`。产出 `TableRecord{rows, cols, markdown}`（`backend/app/domain/schemas.py:146-155`）——**正文以 Markdown 进向量库，行列结构单独保留**（`:119`）。

### 3.6 PPTX

`PresentationParser`。

### 3.7 图像

`OcrParser`（`backend/app/services/parsers/ocr.py`）。见第九章的架构约束。产出一个 `MediaAsset{kind="image"}`，正文进 `segments`。

### 3.8 音频（云转写）

`AudioParser`（`backend/app/services/parsers/audio.py`）。

- 模型基线固定 `paraformer-v2`，注释明确「**禁止改成本地模型或其它厂商**」（`backend/app/services/parsers/audio.py:35`）。
- 平台调用走**百炼异步范式**：本地文件上传 → 提交异步转写任务 → 轮询任务 → 拉取结果。不用同步接口是因为单次转写的时长远长于一次 LLM 调用，同步 HTTP 会先撞超时墙（`backend/app/services/parsers/audio.py:6-7`）。
- **时间戳是功能不是装饰**：真实路径与 Mock 同构产出 `[起-止]` 分段，支撑「答案跳转到音视频对应位置」（`backend/app/services/parsers/audio.py:3-4`）。
- 长音频按平台时长上限切分后并行提交，切点优先落在静音段；并行度上限 `MAX_PARALLEL_CHUNKS = 4`，再高只会加剧平台限流（`backend/app/services/parsers/audio.py:14-15`、`:37`）。
- 三类平台失败分开对待：**限流** → 指数退避重试；**超时** → 退避重试，仍失败则明确报错（不返回半截答案）；**配额不足** → 立即失败（属运维事件，重试只会压窄限流窗口）（`backend/app/services/parsers/audio.py:9-12`）。
- 非 WAV（mp3 等）读不到 PCM 头：**整文件直传并跳过切分**，而不是静默产出空结果（`backend/app/services/parsers/audio.py:16`）。

## 四、四种切块策略

统一入口 `apply_chunk_policy`（`backend/app/services/chunkers/factory.py:31-85`），统一产物契约：

```python
@dataclass
class ChunkResult:
    chunks: list[Chunk] = field(default_factory=list)   # 全部入向量库的块
    parents: list[Chunk] = field(default_factory=list)  # 入 DocStore 的父块（父子分块）
    chunker: str = "recursive"
```

（`backend/app/services/chunkers/factory.py:24-28`）

### 4.1 recursive（默认）

分隔符优先级：**段落（空行）→ 行（换行）→ 中文句号 → 空格 → 字符兜底**（`backend/app/services/chunking.py:10`）。

- 按**字符**而非 token 计数：中文场景偏差小，且与用户可读长度直接对应（`backend/app/services/chunking.py:3-4`）。
- `chunk_id = {doc_id}#{seq}`，`seq` 从 1 起；**重建索引保持不变**——这是引用回溯、缓存命中、跨版本比对的基石，绝对不用随机 UUID（`backend/app/services/chunking.py:5-6`、`:98-108`）。
- 空块在入库前过滤；超短块（< `min_chars`）**保留但标记** `is_short=True`，检索展示端可识别（`backend/app/services/chunking.py:85-88`、`:106`）。

### 4.2 semantic

`SemanticChunker`（`backend/app/services/chunkers/semantic.py`）。

- 句子切分正则：`(?<=[。！？!?；;])|\n+`（`backend/app/services/chunkers/semantic.py:14`）。
- 相邻句子的**余弦距离** `1 − cos(v_i, v_{i+1})` 超过阈值即切；距离越小越像、越大越不同（`:1-5`、`:45-50`）。
- 上下限：`min_sentences` 避免单句成块（上下文断裂），`max_sentences` 防止永不切（buffer 膨胀）（`:3-4`）。
- 判定式：`(dist > threshold and over_min) or hit_max`（`:54-57`）。
- 默认参数：`threshold=0.4`、`min_sentences=2`、`max_sentences=12`（`backend/app/services/chunkers/factory.py:49-51`）。

### 4.3 parent_child

`ParentChildChunker`（`backend/app/services/chunkers/parent_child.py`）。

- **子块（200 字）入向量库**保证召回粒度；**父块（1200 字）入 DocStore**保证上下文完整。检索命中子块 → 按 `parent_id` 回查父块 → 完整父块喂给 LLM（`backend/app/services/chunkers/parent_child.py:1-4`）。
- 父块 id 形如 **`{doc_id}#P{n}`**（`backend/app/services/chunkers/parent_child.py:34`），`level=1` 标记为上层（`:44`）。
- 子块带 `parent_id`（指向父块）（`:53-60`）。
- 默认参数：父 1200 / 子 200 / 子重叠 40，父块重叠为父长的 1/10（`backend/app/services/chunkers/factory.py:59-61`、`backend/app/services/chunkers/parent_child.py:29`）。

### 4.4 raptor

`RaptorChunker`（`backend/app/services/chunkers/raptor.py`）。

- 流程：L0 原始块 → 聚类 → 每簇生成 L1 摘要 → 对 L1 再聚类 → ……直到顶层 ≤ `max_top_nodes`（`backend/app/services/chunkers/raptor.py:1-4`、`:64`）。
- **所有层级共同进入向量索引**：抽象问题命中高层摘要，细节问题命中低层叶子（`:4-5`）。
- 聚类用**轻量 k-means（numpy 实现，不引 sklearn）**，`seed=42`、最多 20 轮（`backend/app/services/chunkers/raptor.py:24-43`）。固定种子保证同一份文档每次构建出同样的树。
- 摘要块 id 形如 **`{doc_id}#L{level}-{cluster+1}`**（`backend/app/services/chunkers/raptor.py:82`），`level` 记录层级（`:91`）。
- 子节点的 `parent_id` 回指摘要块（层级 + 父块标识必须同时存在）（`:93-96`）。
- 成本显式承认：每层聚类 + LLM 摘要都是 token 开销，只在 ingestion 阶段跑一次，**检索路径零额外开销**；长文档才值得启用（`:6-7`）。
- 默认参数：`max_clusters=4`、`max_top_nodes=3`（`backend/app/services/chunkers/factory.py:78-79`、`backend/app/services/chunkers/raptor.py:64`）。

### 4.5 策略参数校验

`validate_chunk_policy(policy)`（`backend/app/services/chunkers/factory.py:88-112`），错误码 `CHUNK_POLICY_INVALID`（3601）。规则：

| 策略 | 校验 | 报错文案 |
|---|---|---|
| 通用 | 策略名 ∈ {recursive, semantic, parent_child, raptor} | 「未知的切块策略: X」 |
| semantic | `0.0 < threshold < 1.0` | 「semantic.threshold 必须在 (0, 1) 之间」 |
| semantic | `min_sentences ≥ 1` | 「semantic.min_sentences 必须 ≥ 1」 |
| semantic | `max_sentences > min_sentences` | 「semantic.max_sentences 必须大于 min_sentences」 |
| parent_child | `child_size < parent_size` | 「parent_child.child_size 必须小于 parent_size」 |
| parent_child | `child_size ≥ 50` | 「parent_child.child_size 不能小于 50」 |
| raptor | `max_clusters ≥ 2` | 「raptor.max_clusters 必须 ≥ 2」 |

校验在**两个入口**都调用：异步入库提交时（`backend/app/api/ingest.py:60-61`）与重新解析时（`backend/app/api/knowledge.py:284-287`）。

### 4.6 表格单独成块

表格段与文本段在切块前**分离**（`backend/app/services/knowledge.py:318-320`）：

```python

table_segments = [s for s in parsed.segments if TABLE_SOURCE_MARK in s[0]]
```

表格段**不交给切块器**，而是自己成为一块（`backend/app/services/knowledge.py:330-345`）：

| 字段 | 值 |
|---|---|
| `chunk_id` | `{doc_id}#{seq}`（接在正文块之后） |
| `content` | 表格的 Markdown |
| `chunker` | `"table"` |
| `modality` | `"table"` |

这样表格**不会被切块器拦腰切断**，同时与文字流表格、OCR 表格享受同等的结构保护。

## 五、索引写入纪律

`index_parsed`（`backend/app/services/knowledge.py:356-427`）是入库的**一致性临界区**，全程持锁（`:346`）。

### 5.1 纪律一：先算好新向量，再清旧索引

```python

    vectors = self._embeddings.embed_texts([c.content for c in chunks])
except Exception as exc:
    raise ApiError(ErrCode.INDEX_BUILD_FAILED, f"索引构建中断（Embedding 失败）: {exc}") from exc
…

    self._purge_chunks(record.doc_id)
self._store.add(chunks, vectors)
```

（`backend/app/services/knowledge.py:375-393`）

**顺序反过来会出事**：先 purge 后 embed 的顺序下，Embedding 失败 = 旧索引已删、文档从检索里消失（`backend/app/services/knowledge.py:376-377`）。

### 5.2 纪律二：向量条数必须等于块条数，否则拒绝发布

```python
if len(vectors) != len(chunks):
    raise ApiError(
        ErrCode.INDEX_BUILD_FAILED,
        f"索引发布中止：向量条数 {len(vectors)} 与块条数 {len(chunks)} 不一致",
    )
```

（`backend/app/services/knowledge.py:384-390`）

**没有这条断言，「块与向量不一致」会表现为检索静默漏召回，而不是报错**——这是最难排查的一类故障（`:355-356`）。

快问路径有**同样的一条断言**（`backend/app/services/knowledge.py:472-476`）。

### 5.3 纪律三：索引版本 bump → 旧缓存键自然失效

索引成功后 `self._bump_version()`（`backend/app/services/knowledge.py:415`）。全局数据版本进入语义缓存键的 `config_digest`（`backend/app/services/pipeline.py:252-264`），因此**任何入库 / 重建 / 重新解析都会让旧缓存条目自动失效**，无需手动清缓存。

### 5.4 三处写入与派生数据

| 写入 | 目标 | 代码位置 |
|---|---|---|
| 向量库 | `self._store.add(chunks, vectors)` + `save()` | `backend/app/services/knowledge.py:393-394` |
| BM25 | `self._bm25.add(chunks)` | `backend/app/services/knowledge.py:395-396` |
| DocStore | 父块 / 表格 / 资源 | `backend/app/services/knowledge.py:403-411` |

资源写入带**跨文档去重**：同一张图只入一次（`dedupe_by_hash=self._store.total > 0`，`backend/app/services/knowledge.py:401-405`）。

## 六、索引版本与生命周期操作

### 6.1 四个操作的实际效果

| 操作 | 端点 | **改了什么** | **删除了什么** | **留了什么** | 代码位置 |
|---|---|---|---|---|---|
| **重建** rebuild | `POST /knowledge/rebuild/{doc_id}` | 用**原内容原策略**重新解析并重建索引；`chunk_id` 稳定 | 旧块（先 purge 掉该文档的全部块） | 源文件、文档记录、大纲、ACL | `backend/app/services/knowledge.py:579-592` |
| **重新解析** reparse | `POST /knowledge/{doc_id}/reparse` | 用**新策略**生成新版本块集合，`record.version += 1`；旧块改名为 `@v{旧版本}` 下线保留 | 超出保留份数的历史版本块 | 旧版本块（改名保留）、源文件、文档记录 | `backend/app/services/knowledge.py:594-629` |
| **下架** offline | `POST /knowledge/{doc_id}/offline` | `chunk_count=0`、`status=offline` | 该文档的全部索引块（向量 + BM25 + DocStore） | **源文件**、文档记录、ACL、图谱贡献 | `backend/app/services/knowledge.py:655-663` |
| **删除** delete | `DELETE /knowledge/files/{doc_id}` | 从 `_docs` 移除 | 索引块、ACL 条目、图谱贡献、图像索引条目、资源文件、任务原件、源文件 | **无**（不可恢复） | `backend/app/services/knowledge.py:676-731` |

### 6.2 重新解析为什么不能物理删旧块

旧实现先物理删除旧块再重建，且 `chunk_id` 复用同一序号空间——结果**所有历史答案里的引用编号全部指向不存在的块**，溯源链在「重新解析」这个动作上静默断裂（`backend/app/services/knowledge.py:597-598`）。

现在的四步（`backend/app/services/knowledge.py:600-604`）：

1. 旧块的 `chunk_id` 加 `@v{旧版本}` 后缀落到「历史版本」区，**不删除**；
2. 新版本块的 `chunk_id` 带 `@v{新版本}`，与旧版本天然不冲突；
3. 检索侧按当前版本过滤，历史块不参与召回，**只服务溯源**；
4. 保留最近 `index_version_keep` 个版本，更早的才真删。

`_retire_version` 是这条纪律的落点（`backend/app/services/knowledge.py:631-653`）：改名 → 按保留份数删更早的 → bump 版本。改名后的块仍可在 `GET /knowledge/preview/{doc_id}/chunk/{chunk_id}` 中被直接查到（`:605`）。

### 6.3 预览只看当前版本

`chunks_of(doc_id)` 返回**当前版本**的块；历史版本块仍留在向量库里服务引用溯源，但不出现在预览 / 检索里——预览的语义是「现在被索引了什么」，混入历史块会让用户以为切块坏了（`backend/app/services/knowledge.py:187-198`）。存量数据没有版本标记（全为 0）时不过滤，避免升级后预览突然空白（`:172-173`）。

### 6.4 审计留痕

四个写操作全部调 `audit_admin`：`knowledge.upload`（`backend/app/api/knowledge.py:84-87`）、`knowledge.rebuild`（`:109`）、`knowledge.reparse`（`backend/app/api/knowledge.py:291`）、`knowledge.offline`（`:298`）、`knowledge.delete`（`:126`，注释明确「删除是不可逆动作，必须留痕」）。审计机制本身见 `08-安全与治理.md`。

```python
meta = self._store.get(doc_id)
if not meta:                          → 3004
if meta["user_id"] != principal.user_id or meta["tenant_id"] != principal.tenant_id:  → 3004
if bound_session and session_id is not None and bound_session != session_id:           → 3004
```

（`backend/app/services/quickask.py:287-303`）

| 情形 | 返回 |
|---|---|
| 已过期 / 不存在 | `QUICK_DOC_EXPIRED`（3004）+ 404 |
| 越权（他人文档） | `QUICK_DOC_EXPIRED`（3004）+ 404 |
| 不属于当前会话 | `QUICK_DOC_EXPIRED`（3004）+ 404 |
| 正常 | 元数据 |

**四种情形返回同一错误码**，避免通过错误码差异探测他人文档是否存在（`backend/app/services/quickask.py:281-282`）。

`session_id` 只在**文档绑定了会话**时才校验：未绑定（空串）的文档可以在任意会话使用——那正是「上传即问」的用法（`backend/app/services/quickask.py:284-285`）。

### 9.5 后台清扫

`sweep_expired(limit=50, budget_s=5.0)`（`backend/app/services/quickask.py:360-423`），启动时调用一次。

**为什么不能只靠 Redis 的 TTL**：TTL 到期后临时元数据就没了，再也拿不到那个 `doc_id`，对应的向量却还留在索引里——存储膨胀 + 检索噪声。启动清扫用**磁盘临时目录**兜住这类残留（`backend/app/services/quickask.py:363-366`）。

**必须限量**：清理一个文档要打两次 Milvus（query + delete）。不限量的话，几十个残留就能把启动拖成几分钟——容器在启动期就被判 unhealthy，重启策略还会把它打进 crash loop。因此同时限**个数**与**时间预算**，剩下的留给下次启动 / 后台线程（`backend/app/services/quickask.py:368-371`）。

清理两轮：① 登记信息已过期的僵尸条目（`:380-394`）；② 磁盘残留（`:396-415`）。

`KnowledgeService.delete(doc_id)`（`backend/app/services/knowledge.py:676-731`）。**派生副本按 best-effort 逐项清理：单项失败不中断整体删除**，失败的项写进 warning 日志（运维可据此做残留巡检）（`backend/app/services/knowledge.py:677-680`）。

## 十一、边界与已知缺口

> 本篇涉及的「有机制无度量」「有代码无调用点」「口径与实现不符」逐条登记。**确有缺口的共 7 处**。

| # | 缺口 | 证据 | 影响 | 当前处置 |
|---|---|---|---|---|
| 1 | **同步上传入口没有 PII 硬拦截**：`POST /knowledge/upload` 走 `service.ingest_path`，不经 `api/ingest.py` 的 PII 扫描 | `backend/app/api/knowledge.py:81-83` vs `backend/app/api/ingest.py:113-137` | 含身份证 / 银行卡的文档可经同步入口入库，绕开入口拦截；只剩输出侧掩码兜底 | 已登记；两条入口的 PII 口径不一致 |
| 2 | **BM25 全量重建模型**：任何一次索引增删改都会对全部块重新分词并重建打分模型 | `backend/app/services/retrieval/bm25.py:77-88`、`:90-109` | 文档量增大后，每次入库的 BM25 侧耗时随语料线性增长 | 无增量索引机制；未见耗时指标分解 |
| 3 | **RAPTOR 抽取上限写在 prompt 里，代码层无二次裁剪** | `backend/app/services/chunkers/raptor.py` 全文件未见裁剪；上限来自 `max_clusters` / `max_top_nodes` 参数 | 若 LLM 返回异常数量的簇，实际簇数由 k-means 决定而受参数约束；但摘要内容长度未裁剪 | 摘要输入按 `m.content[:500]` 截断（`backend/app/services/chunkers/raptor.py:78`），未记录截断留痕 |
| 4 | **表格单独成块后不再切分**，超长表格会成为超长块 | `backend/app/services/knowledge.py:330-345` | 一张宽表可能远超 `chunk_size`，直接撑爆上下文预算 | 上下文侧有硬截断兜底（`backend/app/services/context.py:126-153`） |
| 5 | **解析产物缓存只存在于内存**（`_parse_cache`） | `backend/app/services/ingest.py:73`、`:363-369` | 进程重启后重试会重新跑 OCR / ASR（分钟级成本） | 缓存命中才复用；已通过「解析失败清缓存」的规则明确其生命周期 |
| 6 | **`rebuild` 与 `reparse` 的端点不对称**：`rebuild` 走 `POST /knowledge/rebuild/{doc_id}`，`reparse` 走 `POST /knowledge/{doc_id}/reparse`，两者路径风格不同 | `backend/app/api/knowledge.py:105`、`:268` | 前端调用方容易混淆；`rebuild` 无参数（用原策略），`reparse` 必须带策略 | 无技术风险，仅是可读性 / 一致性 |
| 7 | **入库质量红线只标记不阻断**，且质量指标未纳入管理端看板 | `backend/app/services/ingest.py:318-335`、`backend/app/api/knowledge.py:318-337` | `quality_flags` 只在任务详情里返回，知识库 KPI 看板（`/knowledge/stats`）不含质量项 | 已按设计取舍落地；未见聚合统计 |

**逐项核实结论**：解析路由、四种切块策略、索引写入纪律、索引版本生命周期、异步入库状态机、解析预览、快问临时索引、删除级联清理八项**均有生产调用点且默认开启**；上述缺口全部属于「口径不一致」「有代价但无度量」「一致性取舍」，无「代码存在但生产路径无调用点」的情形。
