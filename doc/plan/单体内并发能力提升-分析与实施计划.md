## 零、复核结论（本次修订的原因）

初版计划方向正确，但有 3 处设计不成立、2 处数字高估、4 项关键遗漏。修订后总工作量从 7 人日调整为 **11.5 人日**。

| # | 初版内容 | 复核判定 | 修订 |
|---|---|---|---|
| 1 | "SSE 连接 40 → 2000" | ❌ **不成立**：管线是同步的，每条**正在生成**的流仍占 1 个工作线程；2000 只能是"空闲/心跳连接"，不是 2000 并发生成 | 目标改为"≥500 空闲连接 + 32 并发生成 + 超出排队/503" |
| 2 | 多查询并行召回复用"批次 1 的执行器" | ❌ **会死锁**：管线本身已在执行器线程里，再向同一池提交任务，池满即自锁 | 改用**独立 4 线程小池**，或块数少时直接串行 |
| 3 | HNSW 迁移"drop 集合 + 从源文档重灌" | ❌ **会丢数据/成本高**：Milvus 支持原地换索引（release → drop_index → create_index → load），无需重灌 | 改为原地换索引；且当前仅 9 个块，**不作为本期必做项** |
| 4 | 聚合问答吞吐 "~4 QPS" | ⚠️ **高估**：取 min(执行器 32, 上游并发 16) / 8s = **2 QPS** | 目标改为 2 QPS（冷路径），缓存命中不计入 |
| 5 | 总工作量 7 人日 | ⚠️ **低估**：未含每批回归、压测、浏览器验证 | 调整为 11.5 人日 |
| 6 | 未覆盖：`AnalysisStore.save` 每请求全量重写 | ❌ **遗漏（高并发先炸点）**：初版时 `analysis_store.py:36-50` 每次问答把最多 1000 条记录整体 JSON dump；500 QPS 下写放大不可接受 | 新增到批次 1（**已落地**：现为 `analysis_store.py:25-61` 内存追加 + 后台 flush） |
| 7 | 未覆盖：审计写侧 | ⚠️ 查询侧持锁已修，但**每请求 3 次同步 open/append/close + 全局锁** 仍在 | 批次 1 改批量 flush（**已落地**：现为 `backend/app/services/security/audit.py:41-49` 内存队列 + 后台 flush） |
| 8 | 未覆盖：SQLite 单连接 + 全局锁 | ⚠️ 图存储/检查点在并发 Agent 下串行 | 批次 3 标注为已知上限，给出缓解 |

## 二、修正后的目标模型（单进程）

| 维度 | 当前 | 修订目标 | 推导 |
|---|---:|---:|---|
| 在飞问答（生成中） | ≤40 | **32** ✅ | 执行器固定 32；由上游配额与实测 P95 校准（`services/pipeline_executor.py:40`） |
| 排队请求 | 无界（隐藏在线程池） | **200 后 503 + Retry-After** ✅ | 有界队列，快速失败（`services/pipeline_executor.py:160,221-230`） |
| 空闲/心跳 SSE 连接 | 40 | **≥500** ✅ | 连接只占内存与 fd，不占线程（`services/pipeline_executor.py:189-191`） |
| 多租户聚合问答吞吐（冷，8s/req） | — | **2 QPS** ⚠️ 未实测 | min(执行器 32, 上游并发 16) / 8s = 2 —— **推导值，无实测支撑**（见批次 0） |
| 缓存命中吞吐 | — | **数百 QPS** ⚠️ 未实测 | 6.5ms/req，受 GIL 与锁限制 —— **推导值** |
| Agent 并发 | 无上限 | **16 在飞 + 排队 + 429** ✅ | 独立信号量（`services/agent/runner.py:168`） |
| 入库 | 1 批串行 | **解析 2 并行、索引 1 串行** ✅ | 索引写入受 `KnowledgeService._lock`（`services/ingest.py:65`） |
| 每请求同步落盘 | 有 | **0 次（批量 flush）** ✅ | 写放大移出请求路径（`services/query/analysis_store.py:25-61`） |
| 过载行为 | 排队到死 | **503 快速失败** ✅ | 背压（`services/pipeline_executor.py:221-230`） |

**必须承认的硬上限**：

1. **GIL**：CPU 密集的解析、BM25、FAISS 与请求线程争抢；异步只解决 I/O 等待，不解决 CPU。解析必须留在后台池且限并发。
2. **同步上游 SDK**：不做全链路异步重写，就无法把"生成中的等待"变成可复用的空闲线程；本计划只把"连接等待"从线程里拿掉，不声称"2000 并发生成"。
3. **单进程**：不能用多 worker 绕过，否则六处进程内状态会分裂（限流/配额/缓存/会话/图谱/检查点）。

### 移出本计划：真流式（TTFT）

原因：与两条既有语义直接冲突——

1. **输出侧安全**：`backend/app/services/pipeline.py:930-941` 要求拿到完整答案再扫描（`scan(answer)` 后才决定 refuse/mask）；边生成边发会让敏感词跨 chunk 漏检，必须引入"holdback 窗口 + 增量扫描"，等于重做护栏；
2. **自检与重生成**：`backend/app/services/pipeline.py:866-899` 可能整段重写答案；先发 token 再重写会造成"用户看到的内容和最终记录不一致"。

> **2026-10-30 状态**：仍未实现，且**当前实现形态印证了本节的判断**——`backend/app/services/pipeline.py:1203,1252` 是把已完成的 `_final` 文本按 12 字符切片后 `yield "token"`，即「整段生成后切片重放」，TTFT = 全链路耗时（与 `doc/analysis/14-差距与演进.md` KQ-07 记录一致）。
> 目标态设计（holdback 窗口长度、增量扫描与重生成的一致性协议）见 `doc/design/05-并发提容与降级阶梯设计.md` §三。

正确做法是先决策"自检是否允许重生成"与"增量扫描 holdback 长度"，再单独立项（预估 3~4 人日 + 评测）。本计划不承诺 TTFT 从 7.6s 降到 2.5s。

## 五、并发正确性检查清单（实施时必须逐条确认）

| 检查 | 说明 |
|---|---|
| 不得嵌套提交同一执行器 | 管线已在池内时，禁止再向同池提交（批次 3 用独立小池） |
| 信号量之和 ≤ 执行器线程数 | 否则线程被"等许可"占满，有效并行度下降 |
| 队列投递用 `put_nowait` | 消费者消失时 worker 不得阻塞 |
| 所有等待有 deadline | 队列、single-flight、信号量、Future 都不能无限等 |
| 锁顺序固定 | `KnowledgeService._lock` → `DocStore` → 向量库，不得反向 |
| 取消可传播 | `threading.Event` 在阶段边界检查；已发出的上游请求无法中断，文档写明 |
| 指标可解释拒绝 | 每一类 429/503 都有 `reason` 标签 |
| GIL 认知 | CPU 密集任务限并发（解析 2、OCR 2），不指望异步提速 |
