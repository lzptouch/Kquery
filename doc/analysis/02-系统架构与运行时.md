## 〇、摘要

1. **五层装配 + 一个内核**：`main.py`（54 行，只建应用）→ `bootstrap.py`（应用外壳：中间件 / 异常处理器 / 路由注册）+ `assembly/`（9 个按域拆分的装配模块，装配顺序唯一真相源是 `assembly/lifespan.py`）→ `api/`（11 个 router）→ `services/`（业务）→ `core/`（横切设施）。依赖**只能向下**，`core/` 不 import `services/`。
2. **运行时只有一种进程形态**：单进程 + 线程池（问答执行器 32 线程 / Agent 池 16 许可）+ 共享存储（内存或 Redis）。
3. **启动顺序隐含强耦合**：`pipeline_executor` 依赖 `milvus_store.close()`；`agent` 依赖 `milvus_store` + `cache`；`long_term_memory` 依赖 `llm.embed`。改装配顺序前先读第二章的依赖链。
4. **关闭顺序是安全兜底**："先停执行器与任务管理器（等在飞任务）→ 再关存储连接"。漏掉会 temp dir 无法清理、WAL 不落盘。
5. **失败处理有两档**：**fail-fast**（配置自相矛盾 / 索引损坏 / Milvus 显式配置不可用）vs **降级**（Redis、checkpointer、OCR、OTel、rerank、工具超时）。
6. **最大装配缺陷已关闭**：`SharedState` 曾经被实例化两次（旧 `main.py:471` / `:877`），现在只在 `assembly/runtime.py:129` 建一次，「门面单实例」写进了模块 docstring。**当前最大的结构债已关闭**：`services/pipeline.py` 从 1753 行降到 **483 行**（`B0 X-27` 两步拆分：提示词/证据装配 → `generation/{prompt,evidence}`，编排与阶段 → `generation/{core,cache_stage,retrieve_stage,generate_stage,guard_stage,types}`），只保留类骨架 + 同名字薄委托。

## 二、启动装配（`assembly/lifespan.py:46-69`）

> `A-12` 之前这一整章的行号都在 `main.py` 里（`368-923`）。现在**装配顺序只有一个读法**：
> `lifespan()` 里 8 行函数调用，顺序即依赖链。新增装配步骤请加到那里，别再往 `main.py` 里塞。

### 2.1 导入期（import 时，进程启动最先发生）

| 顺序 | 做了什么 | 位置 | 为什么必须在这里 |
|---|---|---|---|
| 1 | 建应用外壳 + 读 `Settings`（环境变量 + `.env`） | `bootstrap.py:288-358`、`core/config.py` | 一切装配的入参 |
| 2 | 启动期配置校验（不过就 `RuntimeError`）+ 脱敏配置回显 + provider 提示 | `bootstrap.py:305-322` | 早失败好过运行期炸；`app.state.settings` 在此就位 |

| 4 | 建图存储（sqlite 或内存） | `assembly/agent.py:121-132` | 图谱能力可选，读取失败可降级为内存 |

### 2.2 lifespan 阶段（起服务前）

`lifespan()` 按固定顺序调 9 个装配函数（`assembly/lifespan.py:47-69`）：`prepare_process` → `build_metrics` → `build_models` → `build_runtime` → `build_storage` → `build_knowledge` → `build_pipeline` → `build_agent` → `install_hooks`。

| 阶段 | 模块 | 做什么 | 失败语义 |
|---|---|---|---|
| ① 进程参数 | `assembly/runtime.py:93-105`（`prepare_process`） | AnyIO 默认线程池 100、上游隔离仓与熔断 | **fail-fast**：许可和 > `pipeline_workers` |
| ② 指标 | `assembly/runtime.py:108-115`（`build_metrics`） | `PromMetrics` + `MetricsStore`（**必须最先**，其它层都要记数） | — |
| ③ 模型 | `assembly/models.py:37-140`（`build_models`） | **生成 / 向量 / 重排三条独立 provider 通道**（`resolved_provider` / `resolved_embedding_provider` / `resolved_rerank_provider`，装配层不做二次判断）+ 四档 LLM（`llm` / `fast_llm` / `agent_llm` / 降级链 `LLMRouter`，降级默认关）+ OCR | 降级：无凭据 → mock provider |
| ④ 运行时 | `assembly/runtime.py:118-209`（`build_runtime`） | `SharedState`（**唯一实例**）/ 配置存储 / 幂等 / 语义缓存 / 限流 / 执行器（`PipelineExecutor`+Agent 双池，`:177-192`）/ SSE 帧缓冲 / 灰度控制器 | 降级：Redis 不可用 → 内存实现 |
| ⑤ 存储 | `assembly/storage.py:31-94`（`build_storage`） | 索引别名 / 向量库（`load()` fail-fast）/ BM25 / 文档存储 / 解析路由 / 混合检索 | 索引损坏 → 拒绝启动 |
| ⑥ 知识 | `assembly/knowledge.py:34-87`（`build_knowledge`） | 知识服务 / 任务管理器 / 反馈存储 / 快问（+ 后台清扫线程） | 降级：Redis 不可用 → 内存临时态 |
| ⑦ 流水线 | `assembly/pipeline.py:28-83`（`build_pipeline`） | 查询预处理 / CRAG / 自检 / 问答编排 / 执行器接线 | — |
| ⑧ Agent | `assembly/agent.py:231-329`（`build_agent`） | 工具注册表 / 图谱 / 检查点 / 会话 / 运行器 / 长期记忆 / run pool / 工具池 | 降级：checkpointer 失败 → 无持久化 |
| ⑨ 钩子 | `assembly/hooks.py:64-79`（`install_hooks`） | 入库后置钩子等跨域回调 | — |
| 外围 | `bootstrap.py:302` | OTel（`setup_otel`） | 降级：OTel 不上报 |

**装配顺序的隐含约束（改顺序会炸）**

1. `pipeline_executor` 在 `build_runtime` 创建（`assembly/runtime.py:177-184`），关停顺序不再靠构造期回调，而由 `lifespan.shutdown()` 显式编排（先停执行器与 Agent 池、再关存储连接，`assembly/lifespan.py:72-95`）。
2. `agent` 同时需要向量库（`asm.store`）与缓存 → **必须在存储与运行时之后建**（`assembly/agent.py:231`，消费点 `:137`、`:172`）。
3. `long_term_memory` 需要 `llm.embed` → **必须在模型之后建**（`assembly/agent.py:304-310`）。
4. 缓存要 embedding 采样 → `build_models` 必须早于 `build_runtime`；这两条顺序已写成 `lifespan.py` 模块 docstring 的注释。
5. 快问清扫是 `daemon=True` 的后台线程（`assembly/knowledge.py` 内）——**不在关闭序列里**，进程退出时可能被硬杀。

## 三、请求生命周期

### 3.1 中间件链（实际执行顺序）

```
ServerErrorMiddleware
  → trace 中间件（生成 trace_id、计时、慢请求日志）
    → CORSMiddleware
      → ExceptionMiddleware
        → Router → 端点
```

### 3.2 端点内的固定四步

| 步 | 做什么 | 位置 |
|---|---|---|
| 1 | 取依赖（`Depends`）——路由**不直接碰** `app.state` | `dependencies.py` |
| 2 | 身份：**trace 中间件**已为每个请求写入恒定 `Principal(default, local)`（`bootstrap.py:221`）；端点再经 `get_principal()` 取用，该依赖不再解析任何凭证 | `bootstrap.py:221`；`dependencies.py:43` |

| 4 | 调 service → 包 envelope → 返回 | 各 `api/*.py` |

**写端点的额外约束**：`/ask` 的写类工具需要审批令牌（`services/tool_registry.py`）；入库端点在入队前做**大小 / 页数 / 扩展名**校验（服务层）——**配额已随治理面下线，不再有配额判定**。

## 五、失败处理策略

### 5.1 fail-fast（3 类：配错了就不该起）

| 类别 | 触发 | 行为 |
|---|---|---|
| 配置自相矛盾 | 必填项缺失 / provider 取值非法（`model_provider` 只允许 `auto\|dashscope\|deepseek\|minimax\|zhipu\|mock`）/ 显式 provider 无凭据 / `embedding_base_url` 与 `rerank_base_url` 非 http(s) / 各上游许可之和 > `pipeline_workers` / `vector_store` 非 `milvus\|faiss` / `top_k<=0` / `chunk_overlap >= chunk_size` / 非法 `chunk_policy` 预设 / `cache_backend=redis` 却无 `redis_url`（`core/config.py:963-1154` `validate_startup`，白名单校验在 `:978`） | `RuntimeError` → 进程退出 |
| 向量索引损坏 | 索引文件元数据/维度不一致 | `StorageCorruptedError` → 进程退出 |
| Milvus 显式配置不可用 | `vector_store=milvus` 但连不上 | 启动失败（不静默换内存） |

### 5.2 降级（9 类：能跑就降）

| 能力 | 降级为 | 可观测信号 |
|---|---|---|
| Redis | 进程内内存实现 | 启动 WARN「Redis 不可用…将降级为进程内实现」（`core/shared_state.py:198-199`）；`LocalStore._dead` 标记供探针展示 |
| 语义缓存 | Redis → 进程内（无「关闭」档） | `rag_cache_total{result}` 命中率变化（`core/metrics.py:40-42`） |
| rerank | 跳过重排（用融合序） | 响应 `reranked=false` + `stats.rerank_degraded=error/empty_result`，warn 信封（`services/retrieval/hybrid.py:245-272`） |
| embedding / LLM 无凭据 | mock provider | 启动日志「使用 MockLLM / MockEmbeddings / MockReranker」+ 生效配置摘要的 `resolved_provider=mock` 等字段（`services/llm.py:918-919`、`services/embeddings.py:421-422`、`services/retrieval/rerank.py:454-455`）；**不存在 `*_provider_up` 指标** |
| OCR | 纯文本提取（无文字则跳过） | 解析结果 `ocr_used=false` |
