## 〇、摘要

1. **Kquery 的系统性短板不在"缺机制"，而在"缺度量"**：混合检索、Agent 编排、ACL 下推、语义缓存、企业护栏一应俱全，但**没有检索金标集**（KQ-09），导致 recall@k / nDCG 无从测量，进而**ReAct 不敢默认开**（X-11）、**检索参数无法用数据调优**、**阈值无标定入口**——这是所有缺口中影响面最大的一个。
2. **复评旧缺陷清单（基线 `b40f053`）共 66 个主体条目**：已修 **17**、未修 **48**、已失效 **1**、计划项 **4**。已修的 17 条集中在**安全与正确性**（缓存三闸隔离、ACL 下推、版本过滤前置、租户断言、背压、流式真接），全部有回归测试锚点；未修的 48 条集中在**可观测性、前端工程、并发容量、Agent 链路深度**。
3. **3 条"已修但无专门回归测试"**（KQ-41、X-28.12、X-29.11）——已修的事实成立，但缺少防回退的用例，本身是缺口。
4. **已下线的报告中心与评测平台**以 `backend/tests/integration/test_removal_regression.py` 固化（11 条路径必须 404），本文只作留档，不复活。
5. **本次文档重构（2026-10-26）新发现 7 处代码内残留 / 部署不一致**（见 §五），与 B0 复评条目不重复计数。

> 判定口径与复评方法：本文所有行号以 git `2eaaec0` 为准；三态判定（已修 / 未修 / 已失效）与抽查口径见 `doc/plan/_B0-缺口复评清单.md` §六。**未修条目必须给出 `文件:行号` 或测试锚点，不允许"据说/可能"。**

## 一、判定口径

什么算"缺口"——四种形态，一条都不能含糊：

| 形态 | 定义 | 本文示例 |
|---|---|---|
| 有机制无度量 | 实现了能力，但没有任何数据能证明其有效 | KQ-09（检索无金标集） |
| 有代码无调用点 | 代码存在、测试通过，但生产路径没有调用方 | X-28.1（`BackgroundQueue`）、X-28.15（长期记忆 Redis 后端） |
| 有契约无实现 | 接口/注释/Schema 声明了，实际没兑现 | KQ-19（`top_k` 声明但忽略）、X-29.x（注释与实现矛盾） |
| 口径与实现不符 | 指标 / 日志 / 预算的计量方式与实际链路对不上 | X-16（指标桶 vs 业务超时）、X-15（日志字段空） |

**三态**：已修（能指到修复点 + 回归测试锚点）/ 未修（能给当前可复现路径）/ 已失效（前提不成立）。
